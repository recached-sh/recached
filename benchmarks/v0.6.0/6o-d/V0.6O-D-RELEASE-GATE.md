## The seventeen questions

| # | Question | Answer |
|---|---|---|
| 1 | Was MSET reader atomicity reproduced deterministically? | **Yes.** A test-only hook stops MSET after its first key. MGET answered `[new, old]` and sequential reads produced non-linearizable histories, in 10/10 runs at the store level and over TCP, on `69f0d1c` |
| 2 | What was the exact incorrect execution history? | `[0..5] MSET a b c := new` · `[1..2] GET a → new` · `[3..4] GET b → old (the hash it was)`. GET a completed before GET b began, so no sequential order explains it. MGET gave `[new, old, old]` |
| 3 | Which synchronization design was selected? | **Versioned write-order stripes** (no new lock hierarchy). Each existing stripe gains `seq`, for every write, and `multi`, for writes visible in several steps; only the holder writes either. Single-key reads check `multi` before and after reading and wait for a multi-step write. Multi-key reads validate `seq` and fall back to the stripes' locks in ascending order after 4 attempts |
| 4 | Does MGET now observe a consistent MSET result? | **Yes**: owned, borrowed and inside EXEC; deterministic tests and a load test with 8 keys × 6 threads. MGET also evaluates expiry at one time |
| 5 | Are single-key reads linearizable with concurrent MSET? | **Yes.** Once any read has seen part of an MSET, later reads of its other keys wait for it. One-key multi-step writes (`MSET k 1 k 2`, `RENAME k k`, emptying pops, OOM rollbacks) are never seen between steps. In the reviewer's stress probe, 0 violations in ≈ 60M reads |
| 6 | How much did GET/MGET performance change? | **GET P=1: 1.000** (1 and 3 workers). **GET P=16: −2.7% / −2.6%** (1 / 3 workers; +57..69 user cycles). **MGET: +1.1% (P=1), +1.8%/+4.1% (P=16).** Mixed contention: −1.2% GET, −2.2% MGET, −2.8% MSET |

## Correctness issues that remain (none introduced by this phase)

| Item | Severity | Status |
|---|---|---|
| A read-only `MULTI`/`EXEC` is not isolated from concurrent writes. `MULTI GET a GET b EXEC` racing MSET answered a ≠ b 645 / 108,842 (unordered) and 3,727 / 108,500 (ordered) | **High, pre-existing**, documented ("writer-isolated, not reader-isolated") | Recorded follow-up. Fix: EXEC takes the replication-order stripes of its queued reads' keys too. Needs its own design review |
| WATCH misses a lazily expired key: Redis aborts EXEC, Recached commits | Medium, pre-existing, confirmed against Redis 7.2.5 | Recorded |
| WATCH notification payload charged against the 8 MiB budget: a large watched value disconnects instead of aborting EXEC | Medium, pre-existing (6O-C) | Recorded, unchanged |
| FLUSHDB and restore visible part-done to readers | Low–Medium, pre-existing, documented | Recorded. Deliberately unmarked, so readers do not block for a whole restore |
| Multi-victim eviction removes victims one at a time | Low, pre-existing, capped stores only, documented | Recorded |
| KEYS and DBSIZE are not snapshots | Low, pre-existing, documented | Recorded |
| The decoder silently drops non-bulk elements of LPUSH/SADD/HSET/… requests (`filter_map`); Redis rejects the protocol | Low, pre-existing | Recorded. The store now refuses the empty writes this could build |
| A large multi-key read under writes holds back writers on its stripes (nearly all for ≥ a few hundred keys) | Medium, **new, accepted**, documented | Bounded by one read's duration. Per-key versions are a follow-up |

## Decisions requested from the maintainer

1. **Confirm the atomicity trade-off.** #164 and #165 were merged before the native numbers were in.
   - Costs: GET −2.7% at P=16 (still 1.05× Redis); −1 to −3% under mixed reader/multi-key-writer contention; a large MGET under writes briefly holds back writers.
   - Alternative: a narrower guarantee, cross-key only, without one-key multi-step coverage. That would not remove the P=16 cost, which comes from the single-key read check itself.
2. **MSET-A**: approve the reviewed one-lookup design (`../6o-c/V0.6O-C-MSET-DESIGN.md`) on top of the fix, or defer. Its compatibility with the fix is checked in `V0.6O-D-MSET-A.md`.
3. **MSET-B**: approve after MSET-A is accepted, or defer.
4. **Transaction read isolation** (High, pre-existing): authorize a design for EXEC taking its read keys' stripes.

## Recommended next milestone

1. If approved, **MSET-A, then MSET-B**, each with its own review and a ~30 s-cell validation against `rc-fix` (sha256 `6c12deb9…`).
2. **EXEC read isolation**: a small design and fix, independent of MSET.
3. Then, as decisions: **Phase 6P** (memory and set/list layout: SADD, memory per key), the AOF P=1 work, Option A, and finally the release-candidate soak.

**STOP.** Phase 6O-D ends here. MSET-A, MSET-B, 6P, Option A, the AOF redesign and the release are not started.
