# v0.6.0 Phase 6O-D: performance

## 1. Builds and method

| Label | Source | Binary sha256 | Stage |
|---|---|---|---|
| `base` | `dev` `69f0d1c`: the 6O-C final code | `a0ff616f…24597`, byte-identical to 6O-C's measured `rc-final` | Baseline |
| `fix` | `1965943`: the atomicity fix, code-identical to #165's `2f71f6e` | `6c12deb9…f0eb1` | Atomicity fix |
| MSET-A, MSET-B | not built | — | **NOT IMPLEMENTED — APPROVAL PENDING** |

- **Builds.** Release builds, `--locked`, rustc 1.98.0, one target directory per label (`build.sh`).
- **Host.** Native Fedora 45 (kernel 7.3.4), Intel i5-9400F, governor `performance` on all 6 CPUs. Server on CPU 0 (1 worker) or CPUs 0–2 (3 workers); redis-benchmark 7.2.5 on CPUs 3–5.
- **Workload.** 100,000-key space, 32-byte values, a fresh server per cell populated by its own command (GET and MGET by 300,000 SETs). No persistence, unless marked AOF.
- **Comparators.** Redis 7.2.5 (`d6dd5400…`) is the comparator. Valkey 9.1.0 (`89061886…`) was not run in this phase's cells, since the primary comparison is against Redis.
- **Kit.** The 6O-C kit (`run-6od.sh` = `run-6oc.sh` plus an `mget` test: MGET of 10 × `key:__rand_int__`). Cells were ~30 s (P=1: 6M requests; MSET/MGET ×0.5). Repetitions were interleaved, alternating order (`ALTERNATE=1`): 5 for the primary gate, 3 elsewhere.
- **Data.** Raw data with SHA256SUMS: `fedora-i5-9400f-20261123-d1/`. Driver: `d1.sh`, `mixed.sh`.
- **Caveat.** The desktop session (VS Code) stayed up, as in 6O-C. Each cell waited for load < 1.0 and settled I/O; per-repetition pressure is in each `summary.md`.

## 2. The atomicity fix: read-side cost (GET/MGET)

Paired fix/base ratios are per repetition (interleaved neighbours); medians in bold.

| Cell | base ops/s | fix ops/s | fix / base | per repetition | user cycles/op base → fix |
|---|---:|---:|---:|---|---:|
| GET c50 P=1, 1 worker | 191,994 | 191,969 | **1.000** | 1.016 0.984 0.992 0.992 1.000 | 4,289 → 4,392 (+103) |
| MGET×10 c50 P=1, 1 worker | 131,857 | 133,321 | **1.011** | 1.022 1.000 0.989 1.000 1.011 | 13,041 → 12,880 (−161) |
| GET c50 P=16, 1 worker | 1,408,371 | 1,369,788 | **0.973** | 0.973 0.986 0.973 | 1,607 → 1,664 (+57) |
| MGET×10 c50 P=16, 1 worker | 344,732 | 350,779 | **1.018** | 1.000 1.017 1.018 | 9,712 → 9,594 (−118) |
| GET c50 P=1, 3 workers | 359,957 | 359,957 | **1.000** | 1.000 0.990 1.020 | 6,940 → 7,177 |
| MGET×10 c50 P=1, 3 workers | 312,989 | 313,016 | **1.000** | 1.000 1.000 1.000 | 15,838 → 15,949 |
| GET c50 P=16, 3 workers | 3,783,580 | 3,684,017 | **0.974** | 0.974 0.987 0.961 | 1,812 → 1,881 (+69) |
| MGET×10 c50 P=16, 3 workers | 874,863 | 910,421 | **1.041** | 1.032 1.008 1.041 | 11,525 → 11,085 |

- **GET at P=1** is unchanged at 1 and 3 workers. The extra ≈ 100 user cycles of the read protocol (stripe hash, two loads of `multi`, the retry closure) disappear under the per-request network cost.
- **GET at P=16** loses **2.6–2.7%**, in every repetition, at 1 and 3 workers: ≈ 57–69 user cycles per op once the network cost is amortized. Recached GET P=16 stays **1.05×** Redis at 1 worker (1,369,788 vs 1,298,297). This is the measurable price of single-key atomicity. It is not hidden; the release gate presents it for review.
- **MGET** is as fast or faster: +1.1% (P=1), +1.8% and +4.1% (P=16). The single clock read per MGET more than pays for the validation loads.
- **p99** is unchanged within the histogram's resolution: GET P=16 0.639 → 0.655 ms, 1 worker; MGET P=16 2.527 → 2.527 ms. **RSS** is unchanged (+0.2–0.5 MiB; the stripes went from 2 to 16 KiB). There were no errors.

## 5. Mixed contention: GET + MGET + MSET at once, 3 workers (3 repetitions)

Three redis-benchmark processes ran at once against one server on CPUs 0–2: GET with 20 clients, MGET ×10 with 15 and MSET ×10 with 15. Each had its own generator CPU, and a 300,000-SET populate came first (`mixed.sh`).

| Median | base | fix | fix / base |
|---|---:|---:|---:|
| GET ops/s | 128,971 | 127,375 | 0.988 |
| MGET ops/s | 108,617 | 106,176 | 0.978 |
| MSET ops/s | 110,162 | 107,057 | 0.972 |
| GET / MGET / MSET p99 ms | 0.215 / 0.255 / 0.255 | 0.223 / 0.263 / 0.263 | +1 histogram step |
| Server CPU s (whole run) | 52.24 | 53.33 | +2.1% |

Under real contention between readers and multi-key writers of the same keyspace, the fix costs **1.2–2.8% throughput**:
- readers now wait for in-progress MSETs of their stripes;
- MGETs validate, and occasionally retry or lock.

That cost is the atomicity being enforced, not overhead on the uncontended path, which §2 shows is free at P=1.

## 7. In-process adversarial numbers (from the independent review, indicative)

These were measured by the reviewer in-process on a loaded host. They are reported because a native benchmark cannot construct them.

| Workload | Effect of the fix |
|---|---|
| 3 SET threads + 1 thread doing MGET of 2,000 keys | SET −50..−54%. The MGET covers ~all 256 stripes, writes always overlap it, and it falls back to locking them for its own duration. Accepted and documented: the exclusion MGET's atomicity needs |
| 3 GET threads on one hot key + 1 thread looping MSET of that key | GET −73..−78%, MSET ×4. Readers of a key must wait for a multi-key write of it in progress. Inherent; a narrower mark window is a follow-up |
| GET only / GET under SET / MGET8 under SET | −3..−8% / ≈ −6% / ≈ −2% (in-process, noisy) |

## 8. Verdict

- **The atomicity fix is cheap where it is uncontended.**
  - GET and MGET at P=1 are unchanged, and MGET is faster at every depth.
  - SET, LPUSH, MSET and AOF writes are within ±1%, inside the spread.
  - RSS is unchanged.
- **Measurable costs:**
  - GET at P=16: −2.7%, still 1.05× Redis;
  - mixed reader/multi-key-writer contention: −1.2 to −2.8%;
  - two adversarial in-process cases (§7) where atomicity itself forces waiting.

  None is a silent regression; the release gate presents them for review.
- **MSET ×10 is 0.819×**, unchanged; D4 is not met. Closing that gap was MSET-A/B's purpose, and they await approval.
