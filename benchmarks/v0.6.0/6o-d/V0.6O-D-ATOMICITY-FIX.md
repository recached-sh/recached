## 1. What changed

All of it is in `core-engine/src/store.rs`, apart from tests, docs and a test-only hook.

### Stripes

`write_order: Arc<[Stripe]>`, with 256 stripes of 64 bytes each, one cache line per stripe:

```rust
#[repr(align(64))]
struct Stripe { lock: Mutex<()>, seq: AtomicU64, multi: AtomicU64 }
```

- `seq`: `ACTIVE` while any write holds the stripe; the version advances on every release.
- `multi`: `MULTI_ACTIVE` while a write **visible in several steps** holds it; the epoch advances on such a release.

### Writers

`order_keys(keys, several_steps)`:
- takes every stripe in ascending order, as before;
- then marks them all, still before the first mutation:
  - `ACTIVE` on `seq`;
  - for a write naming several keys, or one the caller says is multi-step, `MULTI_ACTIVE` on `multi`.
- `StripeHold::drop` advances `multi` (if marked), then `seq`, then releases the lock, on unwinding too.
- Only the holder writes either word: a load and a Release store, never a read-modify-write.

`run_write_gated` treats a write as multi-step when any of these holds:
- its scope names more than one key before deduplication (`MSET k 1 k 2`, `RENAME k k`, `SMOVE s s`, every multi-key write);
- `leaves_steps_visible(cmd)`: the writes that may empty a collection, which the path then removes (LPOP, RPOP, LREM, LTRIM, SREM, SPOP, HDEL, ZREM, ZPOPMIN, ZPOPMAX, ZADD);
- it took a rollback copy. The mark is added before `exec`.

The probed single-key path, the reserved path and the sweeper mark `ACTIVE` only. `order_all` (FLUSHDB, restore) marks nothing.

### Readers

- **`read_one_at`**, for every single-key read:
  1. Load `multi`. If it is marked, wait: spin read-only (64 tries), then lock and release.
  2. Read.
  3. Accept if `multi` is unchanged.
  4. Otherwise retry; after 4 attempts, read holding the lock.
- **`read_many`**, for MGET, EXISTS k…, SINTER, SUNION and SDIFF:
  1. Take the distinct stripes, sorted once.
  2. Sum their `seq` words, waiting briefly while any is `ACTIVE` (no spin above 16 stripes).
  3. Read.
  4. Accept if the sum is unchanged. A read across more than 16 stripes that a write overlapped stops trying after one attempt.
  5. After 4 attempts, take the stripes' locks in ascending order and read.
- **`read_scope`** is an exhaustive classification of `Command` into one key, several keys, or unkeyed (connection-level and whole-keyspace commands).
- **`execute_read_inner(&Command)`** now holds the 44 read-only arms of `execute_inner`, moved verbatim apart from borrows. A read can therefore be re-run without cloning its command. This removed the clone `execute_reporting_ref` made for every read.
- **Entry points:**
  - `execute` / `execute_reporting`: owned;
  - `execute_reporting_ref` and its capped variant: by reference;
  - `execute_ref_into`: borrowed GET, HGET and MGET, which truncate their reply buffer on a retry.

### Expiry and refused writes

- MGET evaluates every key at one `now` (Redis 7's per-command time).
- `HINCRBYFLOAT` refuses an infinite increment before the hash exists, with `ERR value is NaN or Infinity`, as Redis 7.2.5 does.
- `push`, `sadd` and `hset` with nothing to add refuse instead of creating an empty key.

### Test hook

`store::write_pause`, under `cfg(test)` or the `test-hooks` feature, which only the server's dev-dependency enables. It is scoped to one store. It stops:
- a write after mutating a chosen key: in MSET, DEL, RENAME, and after a general write's `exec`;
- a reader after its validation load, after its read, or after an MGET's or EXISTS's first key.

## 2. Changed locking behaviour

| | Before | After |
|---|---|---|
| Single-key read | DashMap shard read guard only | + 2 loads of `multi`. While a multi-step write of its stripe is in progress, it waits for it: spin, then lock and release. It holds the lock across its read only after 4 refused attempts |
| Multi-key read | One shard guard per key, in turn | + 2 loads of `seq` per distinct stripe. Under persistent overlap, it takes its stripes' locks in ascending order for its own duration |
| Single-key write | Stripe lock | + 2 stores to `seq` |
| Multi-step write | Stripe locks | + 2 stores to each of `seq` and `multi` per stripe. Readers of its keys now wait for it |
| Large multi-key read under writes | Never blocked a writer | Can hold back writers on every stripe it covers (nearly all for ≥ a few hundred keys) for one read. Documented in the concurrency model |
| Lock order | gate → stripes ↑ → shard → index | Unchanged. Readers take stripes (ascending) before any shard guard, never the gate, and hold nothing else then |
| Memory | 256 × 8 B of mutexes | 256 × 64 B = 16 KiB per store |

No server-side lock changed. EXEC still takes the replication-order stripes of its write and watched keys only, so its queued reads stay unisolated, a recorded follow-up.

## 3. Read-side performance

Native, Fedora, i5-9400F, against `rc-base`. See `V0.6O-D-PERFORMANCE.md` §2 for the full tables.

| Cell | fix / base (median, per-rep) | user cycles/op |
|---|---|---:|
| GET P=1, 1 worker | **1.000** (1.016 0.984 0.992 0.992 1.000) | +103 |
| GET P=16, 1 worker | **0.973** (0.973 0.986 0.973) | +57 |
| GET P=1, 3 workers | **1.000** | +237 (3 workers) |
| GET P=16, 3 workers | **0.974** (0.974 0.987 0.961) | +69 |
| MGET×10 P=1, 1 worker | **1.011** | −161 |
| MGET×10 P=16, 1 / 3 workers | **1.018 / 1.041** | −118 / −440 |
| Mixed GET+MGET+MSET, 3 workers | GET 0.988, MGET 0.978, MSET 0.972 | server CPU +2.1% |
| SET / LPUSH / MSET P=1 (writes) | 0.992 / 0.992 / 0.991 | +110 / +179 / +235 |

GET loses 2.6–2.7% only when pipelining removes the network cost (P=16). It is still 1.05× Redis there. MGET gains everywhere, from evaluating expiry at one time. Contended mixed workloads pay 1–3% for the waiting that atomicity requires. There are no p99 or RSS changes beyond one histogram step. The large-read and hot-key cases the reviewer measured in-process are in `V0.6O-D-PERFORMANCE.md` §7.
