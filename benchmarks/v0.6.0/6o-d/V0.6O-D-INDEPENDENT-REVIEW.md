# v0.6.0 Phase 6O-D: independent review

## How the review was run

- **Who reviewed.** One reviewer agent reviewed the atomicity fix (PR 2, #165). It did not write any of the code and worked read-only on a detached worktree at each reviewed commit.
- **What it was given.** The diff, the surrounding code, the requirements (Redis semantics, the brief's invariants and the atomicity-reviewer focus list), and permission to run targeted tests and its own probes and benchmarks from scratch copies. It was not given the author's correctness argument.
- **What it was asked to do.** Construct adverse schedules and name wrong implementations that would pass the tests.
- **How follow-ups were handled.** Follow-up commits went back to the same reviewer.
- **Measurement caveat.** Benchmarks quoted from the review are in-process and were measured on a loaded host (load average 4–7). They are indicative; the native numbers are in `V0.6O-D-PERFORMANCE.md`.

MSET-A and MSET-B were not implemented (approval pending), so they had no implementation review. The MSET-A design review is 6O-C's (`../6o-c/V0.6O-C-MSET-DESIGN.md` §13).

## Round 1 (`51aa372`)

Confirmed correct:
- `read_many` validation: monotonic words, and the post-read load catches any write the read observed;
- single-key "new then old" across keys, wherever there is a happens-before chain;
- every read entry point is covered, and `read_scope` is exhaustive and correct;
- the lock order (gate → stripes ascending → shard → index), with no recursion and no deadlock;
- panics, cancellation, the borrowed MGET's reply on retry, MGET's single `now`, and duplicate-key last-wins;
- release builds contain no hooks.

## Round 2 (`48880bb`): APPROVE WITH CHANGES

Confirmed:
- #3, #4 and #5a/b are correct;
- validation and the lock fallback are correct, and there is no deadlock;
- the store-scoped hooks work.

**Refuted my claim** that marking each stripe just before its own key's mutation ("lazy marking") would still be correct. The schedule:
1. `GET a` loads its stripe (clean).
2. The writer marks *a*'s stripe and writes *a*.
3. `GET a` reads new and replies.
4. `GET b`, sent afterwards, loads *b*'s stripe, which is not yet marked, and reads old.

The protocol keeps eager marking.

| # | Sev | Finding | Resolution |
|---|---|---|---|
| R2-1 | Medium | Marking protects only readers that load the word *after* the mark. A read that loaded first and read during a one-key multi-step write still saw its in-between state. Stress probe: RENAME k k → nil 3,848 / 17.3M; MSET k a k z → "a" 450 / 8.8M; OOM rollback 97 / 2.05M; an emptied hash 82 / 17.3M | **Fixed:** a separate `multi` word that single-key reads validate after reading, with bounded retries and then the lock. The read-only arms moved into `execute_read_inner(&Command)`, so retries need no clone. The borrowed GET/HGET truncate on retry |
| R2-2 | Medium, pre-existing | `HINCRBYFLOAT missing f inf` created an empty hash, erred, then removed it (TYPE saw it 11.9M / 22.8M). Redis refuses up front | **Fixed:** refused before creating, with Redis 7.2.5's `ERR value is NaN or Infinity` (checked against Redis) |
| R2-3 | Low, pre-existing | `LPUSH k <nil>` decodes to `LPush(k, [])`, which created an empty list | **Fixed in the store** (push, sadd and hset refuse empty input). The decoder's silent drop of non-bulk arguments is **recorded** (a protocol-handling change) |
| R2-4 | Medium (accepted) | After round 1, MGET×2000 under 3 SET threads: SET −34% | **Accepted with conditions, both met:** the cost is documented; the spin is skipped above 16 stripes |
| R2-5 | Low–Medium (perf) | Hot key with a looping MSET of it: GET −70% | Read-only spin added. Inherent (see R3-2) |
| R2-6 | Nit | GET −6%, GET under SET −9%, MGET8 under SET −6% (in-process, loaded host) | — |

Confirmed:

- there is no deadlock.
