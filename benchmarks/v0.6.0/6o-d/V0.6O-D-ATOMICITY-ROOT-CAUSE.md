# v0.6.0 Phase 6O-D0: MSET reader atomicity, root cause

| | |
|---|---|
| Base | `dev` `69f0d1c814c24c0f3f75a789ec93752b060187e3` (#157–#163 merged) |

| Verdict | **Reproduced, deterministically.** A concurrent reader can see part of an MSET: one MGET answers some keys new and others old, and two sequential single-key reads can see a state that never existed. 10/10 runs fail at the store level, and the same failures occur over TCP |

## 1. The guarantee being broken

In Redis, `MSET` is atomic: "MSET is atomic, so all given keys are set at once. It is not possible for clients to see that some of the keys were updated while others are unchanged" (Redis command reference). Redis executes commands one at a time, so every reader sees an MSET either not at all or entirely. `MGET` is atomic in the same way, and a sequence of completed reads is linearizable with it.

Recached runs commands concurrently on several workers. It must therefore produce only histories that some one-at-a-time execution could have produced.

**Recached documented this deviation.** Since 2026-10-10, `docs/server/commands.md` ("Concurrency model") has stated that "readers do not join the writer barriers. Commands such as `MSET` and `SMOVE` update their keys one at a time". The same deviation is stated in `docs/guide/how-it-works.md` and `use-cases.md`, and in the RENAME, RENAMENX and SMOVE command rows. So it was a known limitation, not an unknown bug. This milestone treats it as a defect against the Redis guarantee, as the brief does, and the fix updates those documents.

## 2. Call graph

### Writes

Every keyed write reaches the store through `KeyValueStore::run_write` → `run_write_gated` (`core-engine/src/store.rs:4193`). There are two ways in:
- the owned entry `execute_reporting` (l. 4054), used by AOF replay, replica apply and library callers;
- the by-reference entry `execute_reporting_ref` (l. 4087), used by the server's write paths.

The server chooses between:
- `try_execute_unordered` (`server-native/src/propagation.rs:512`): no AOF, replica, watcher, push receiver or capacity limit. It takes no replication-order stripe, only a pass through the `UnorderedGate`;
- the ordered path (`execute_ordered_write`): `ReplHub::lock_write` takes the replication-order stripes of the command's keys (`replication.rs:756`), and the gate stays open.

Inside the store, `run_write_gated` takes the store's own **write-order stripes**. These are 256 `std::sync::Mutex<()>` (`write_order`, l. 2684), chosen by a multiplicative hash (`write_order_stripe`, l. 2698):
- a one-key, probe-eligible write on an uncapped store goes to `run_probed_write` (l. 4438), which holds one stripe;
- every other keyed write sorts and dedups its keys and takes `order_keys` (l. 3006), all its stripes in ascending order. It then reads the before-states, runs `exec`, reads the after-states and updates the index and memory counter, and releases the stripes;
- `MSET`'s `exec` is `mset` (l. 5105), which writes the pairs **one at a time**. Each pair takes a shard write guard (`write_slot`), replaces or inserts, and releases that guard before the next pair.

The other users of the stripes are:
- the expiry sweeper (`remove_expired_candidates`, l. 3633), one key at a time;
- the capped reservation path (`try_reserved_write`, l. 4520);
- `FLUSHDB` and restore, which take all 256 (`order_all`, l. 3023).

### Reads

| Read | Path | Takes a write-order stripe? |
|---|---|---|
| TCP `GET`, `HGET`, `MGET` (the borrowed path, every read) | `try_execute_borrowed` (`propagation.rs:567`) → `execute_ref_into` (l. 4855) → `read_str` (l. 4811), one per key | **No.** One DashMap shard read guard per key, in turn |
| Every other read (`EXISTS`, `TYPE`, `TTL`, `STRLEN`, `SINTER`…), owned MGET/GET (EXEC queue, WebSocket, library) | `execute_and_record` (`clients.rs:363`) → `execute` → `execute_reporting`: `MutationScope::ReadOnly` → `execute_inner` (l. 4059) | **No** |
| By-reference reads | `execute_reporting_ref`: `ReadOnly` → `execute_inner(cmd.clone())` (l. 4089) | **No** |

**No read takes a write-order stripe, and none checks for a write in progress.** The stripes order writers against writers only. The doc comment of `try_execute_unordered` makes the same assumption: it says the store's stripes and shard locks keep a write "atomic and per-key ordered". That holds for one key, but not for MSET's keys taken together.

## 3. The exact interleaving

```text
initial: a = old, b = old

T1  MSET a new b new
      run_write_gated: order_keys(a, b)          stripes of a and b held
      mset pair 1: write_slot(a) … guard released   a = new
                                                    ← T1 is here (preempted, or stopped by the test hook)
T2  MGET a b
      read_str(a): shard read guard → "new"
      read_str(b): shard read guard → "old"
    → [new, old]                                  ← a state that never existed
T1    mset pair 2: write_slot(b)                    b = new
      after-states, index, memory; stripes released
```

Single-key reads give the same failure in sequence (the recorded history, `[invoke..respond]` ticks of one clock):

```text
[ 0.. 5] MSET a b c  writes a=new b=new c=new
[ 1.. 2] GET a      observed a=new
[ 3.. 4] GET b      observed b=old (the hash it was)
```

`GET a` finished (tick 2) before `GET b` began (tick 3). Since `GET a` saw new, the MSET must take effect before it. Since `GET b` saw old, it must take effect after `GET b`. These two constraints contradict each other, so no sequential order explains the history, and it is **not linearizable**.

This is not a demand that separate reads share one snapshot. The checker accepts "old, old", "new, new" and "old, new" in sequence. It also accepts "new, old" when the two reads overlap. It refuses only this combination.

In production the window is the time between MSET's first and last pair, normally a few hundred nanoseconds. It becomes arbitrarily long if the worker thread is preempted mid-MSET, which happens when the host has more runnable threads than CPUs. A load test over TCP (2 MSET writers and 2 MGET readers, 4 workers, 8 s, 108,842 MGETs) observed no mix: the window is too small to hit by chance. The deterministic hook hits it every time.

## 4. Deterministic reproduction

Test-only hook `core_engine::store::write_pause`, compiled under `cfg(test)` or the new `test-hooks` feature. The server enables that feature as a dev-dependency only, so release builds do not contain it. The hook stops the first write that mutates an armed key, right after that mutation. At that point the write holds its stripes and no shard guard. A test thread then reads, and the hook counts readers that wait. No sleeps: every wait is a condition with a 20 s bound.

| Test | Level | Result on `69f0d1c` |
|---|---|---|
| `an_mget_never_sees_part_of_an_mset` | store, owned MGET | **FAIL**: `[new, old, old]`, answered while the MSET was stopped |
| `a_borrowed_mget_never_sees_part_of_an_mset` | store, `execute_ref_into` (the server's MGET) | **FAIL**: `*2 new old` |
| `sequential_single_key_reads_are_linearizable_with_an_mset` | store: `GET a`, then each of GET, MGET, TYPE, STRLEN, GETRANGE, HLEN of `b` (a hash the MSET replaces) and GET, EXISTS, TYPE, TTL, PTTL of `c` (absent, created by the MSET) | **FAIL: 11 of 11 histories not linearizable** |
| `a_tcp_mget_never_sees_part_of_an_mset` | server, two TCP connections, unordered MSET, borrowed MGET | **FAIL**: `[new, old]` |
| `tcp_gets_after_seeing_an_mset_key_see_the_rest` | server: `GET a` → new, then `GET b` (sent after that reply) → old | **FAIL** |
| `the_checker_accepts_and_refuses_what_it_should` | checker self-test | pass |
| `the_reads_agree_with_the_model_without_a_concurrent_write` | control: the same reads without a stopped write | pass |

All 5 reproductions failed in 10 of 10 runs (`raw/d0-reproduction/`). The three store-level ones are committed `#[ignore]`d on this branch, so `dev` CI stays green, and 6O-D1 removes the `ignore`. The two TCP ones (`server-native/src/tests/mset_atomicity.rs`) arrive with the fix in 6O-D1. CI's Load & Chaos job runs the server's ignored tests, so an ignored failing test cannot land before the fix. Their output on `69f0d1c` is `raw/d0-reproduction/base-69f0d1c-tcp.txt`.

The linearizability check (`atomicity_tests::linearization`) is an exhaustive search with memoization over orders that respect real time. It is used on the few-operation histories these tests record and is checked by its own unit test.

## 5. Affected command paths (audit)

| Path | Affected? | Notes |
|---|---|---|
| MGET (borrowed and owned) | **Yes** | Reproduced |
| GET, and every single-key read (EXISTS, TYPE, TTL/PTTL, STRLEN, GETRANGE, HLEN, …) | **Yes**, in sequence | Reproduced for 11 read forms. Each read is atomic for its own key; the defect is across keys, over time |
| Multi-key reads EXISTS k1 k2, SINTER/SUNION/SDIFF | **Yes** | The same reads-in-turn structure as MGET (`execute_inner`) |
| Other multi-key **writes**: DEL k1 k2, RENAME, RENAMENX, COPY, SMOVE, the *STORE family | **Yes**, same root cause | They use the same generic path. RENAME removes the source and then inserts the destination, so a reader can see both absent. Fixed by the same mechanism, since that lives at the stripe hold |
| MULTI/EXEC: a queued MGET | Yes, as MGET | |
| MULTI/EXEC: several queued reads (`GET a`, `GET b`) racing an MSET | **Yes, and a separate, wider defect**: §6.1 | |
| QSUB initial state, SAVE/snapshot, replica full-sync cut, expiry tick | **No** | These use `lock_all_writes`, which closes and drains the unordered gate and takes every replication-order stripe. A write in flight finishes first, and a new one waits, on either path |
| `FLUSHDB`, restore (`order_all`) | Yes, pre-existing | `data.clear()` runs shard by shard. A reader can see one key gone and another still there. Not MSET; recorded (§6.4) |
| Lazy expiration | Partly | Reads mask expired entries. MGET reads the clock once **per key**, so keys sharing a deadline can answer live and expired in one MGET. Redis 7 uses one time snapshot per command |
| Reads during eviction | Yes, capped stores only, pre-existing | `remove_victim` (l. 3909) takes no stripe. A write that evicts several keys removes them one at a time (6O-C, recorded) |
| KEYS, SCAN, DBSIZE | Not snapshots, pre-existing | Whole-keyspace walks without a barrier. SCAN gives no snapshot in Redis either; KEYS and DBSIZE do. Recorded |

## 6. Related findings

### 6.1 A read-only EXEC is not isolated from concurrent writes (new, pre-existing, High)

EXEC takes `lock_commands_and_keys(queue, watched)` (`connection.rs`). `lock_stripes` skips queued commands that are not writes (`replication.rs:771`), so a queue of reads takes **no stripe for the keys it reads**. Closing the unordered gate does not stop writers either: a write that finds the gate closed takes the ordered path under its own keys' stripes and runs. So a whole MSET can land between two GETs of one transaction:

```text
MULTI / GET a / GET b / EXEC   racing   MSET a g b g (2 writers)
```

| Mode (debug build, 4 workers, 8 s) | EXECs | EXEC answered a ≠ b | Plain MGET a ≠ b |
|---|---:|---:|---:|
| No watcher (writes unordered) | 108,842 | **645** | 0 |
| A WATCH elsewhere (writes ordered) | 108,500 | **3,727** | 0 |

(`tools/exec_read_isolation.py`, `raw/d0-audit/exec-read-isolation-base.txt`.) Redis runs EXEC as one step, so it would never answer a ≠ b here. The same happens with two plain SETs, so this is about transaction isolation, not MSET atomicity. The MSET fix does not change it: a whole MSET still fits between the two GETs.

The narrow fix would be for EXEC to also take the replication-order stripes of the keys its queued reads name. That changes EXEC's locking, so per brief §7 it is **recorded as its own follow-up**, not combined with this milestone.

### 6.2 WATCH and lazy expiry (6O-C follow-up #5): confirmed, Medium

`SET wk v PX 150` → `WATCH wk` → wait 400 ms → `MULTI` → `SET other 1` → `EXEC`:

| | EXEC |
|---|---|
| Redis 7.2.5 | `*-1` (aborted) |
| Recached `69f0d1c` | `*1 +OK` (committed) |

The control (no expiry) commits on both (`raw/d0-audit/watch-lazy-expiry-redis-vs-base.txt`). A client that relies on WATCH to detect a lock or lease expiring commits anyway. This is a compatibility defect for optimistic-locking patterns built on expiring keys. Medium; pre-existing (recorded in 6O-C), not a regression of this phase. Recorded.

### 6.3 WATCH notification payload accounting (6O-C #3): unchanged, Medium

The code is unchanged since 6O-C: a watch on a value over 8 MiB disconnects instead of aborting EXEC. Still recorded as a separate issue.

### 6.4 Whole-keyspace writes and eviction

FLUSHDB and restore (§5) and multi-victim eviction leak partial states the same way. They are pre-existing and outside MSET. Recorded; the design (`V0.6O-D-ATOMICITY-DESIGN.md` §5) states exactly what it does and does not cover.

## 7. Smallest safe fix candidates

The root cause is one fact: **the write-order stripes exclude only writers, and readers neither take them nor detect a write in progress.** Every candidate below makes the readers aware of the stripes held by multi-key writes:

1. **Readers take the stripes** (brief Option A): each read locks its keys' stripes, a multi-key read all of them in ascending order. This is simple and obviously correct. But every GET would do an atomic read-modify-write on a stripe shared with writers, and hot-key readers on several workers would serialize on it.
2. **Versioned stripes with reader validation** (Option B): each stripe gets a sequence word that a writer marks while it holds the stripe. Single-key reads wait only while a multi-key write holds their stripe. Multi-key reads validate the words around the read, retry, and after a bound fall back to (1). Readers write nothing shared.
3. **A smaller boundary** (Option C): MSET publishing all its pairs under one lock, or a store-wide multi-key-write counter. There is no lock covering several DashMap shards, and a global counter would be a single cache line bounced by every MSET and read by every GET.

The comparison, the selected design and its proof are in `V0.6O-D-ATOMICITY-DESIGN.md`.
