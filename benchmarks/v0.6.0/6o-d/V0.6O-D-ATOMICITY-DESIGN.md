# v0.6.0 Phase 6O-D1: MSET reader atomicity, design

| | |
|---|---|
| Root cause | `V0.6O-D-ATOMICITY-ROOT-CAUSE.md`: write-order stripes exclude writers only. Readers neither take them nor see a write in progress |
| Selected | **Versioned write-order stripes.** Each stripe gets a sequence word that only its holder writes. Single-key reads wait only behind a *multi-key* write. Multi-key reads are validated, and fall back to the existing stripe locks after 4 attempts |
| Change | `core-engine/src/store.rs` only: `Stripe`, `StripeHold`, `order_keys`, `read_one_at`/`read_one`, `read_many`, `execute_read`/`execute_read_ref`, `read_scope`. No server, protocol, AOF, replication or default change |
| New lock hierarchy | **None.** Readers use the existing stripe mutexes, in the existing ascending order, only on their slow path |

## 1. Requirements

From brief §3.3, restated for what readers observe:
- **R1 (multi-key read):** every key of one MGET, EXISTS k…, SINTER/SUNION/SDIFF is read at one instant. In particular, no part of one multi-key write.
- **R2 (single-key reads in sequence):** if a read sees a key written by a multi-key write *W*, every read that *starts after it completes* sees all of *W*. Together with R1, every history of completed operations is linearizable. Separate reads are not required to share a snapshot.
- **R3:** writer-versus-writer ordering, accounting, capacity, TTL, AOF and replication stay exactly as they were. Nothing changes on the write side except two plain stores per stripe held.
- **R4:** no deadlock or lock-order inversion, no starvation, safe under cancellation and panics.

## 2. Alternatives

| | A. Readers take the stripes | B. Versioned stripes, validated readers (**selected**) | C. A smaller boundary |
|---|---|---|---|
| Mechanism | Each read locks its keys' stripes (shared, or as a mutex); a multi-key read takes them in ascending order | Each stripe gets a sequence word written only by its holder. A single-key read waits (takes the lock) only while a multi-key write holds its stripe. A multi-key read validates the words around the read, and after 4 tries takes the locks | (a) MSET publishes all pairs under one lock; (b) a store-wide "multi-key write in progress" counter that every read checks |
| GET cost | An atomic RMW on acquire and on release, on a line every writer of that stripe also RMWs. With `RwLock`, readers still RMW the reader count | **One load** of a word in the stripe's cache line; nothing written | (b) one load of a single global line |
| Hot-key reads, many workers | Serialize (mutex), or bounce the reader-count line (`RwLock`) | No reader writes shared state. The line moves only when a writer writes it, as today | (b) every MSET writes the global line twice, and every GET on every worker reads it: one global bouncing line |
| MGET ×n | n RMW pairs, sorted | 2n loads, no sort, no allocation | (b) one load |
| Readers vs writers | A GET blocks SET/MSET of its stripe (and vice versa) | A GET waits only behind an in-progress *multi-key* write of its stripe. An MGET falls back to locking only under contention | (a) is impossible: DashMap has no lock spanning shards, and a global lock serializes every MSET |
| Correctness argument | Trivial (mutual exclusion) | The seqlock argument (§3), with the existing locks as the fallback | (a) n/a; (b) correct but costly |
| New synchronization | None (more users of the stripes) | One word per existing stripe; no new lock | (b) one global atomic |

**Why not A.** It is the simplest to prove, but it puts a read-modify-write on a writer-shared line into every GET. It also makes every GET contend with every SET of its stripe, a workload Recached has optimized since 6G (spin-then-block stripes, the probed write). The brief asks that a substantial GET regression not be accepted silently. A costs that on every read to fix an observation that needs only multi-key writes to be visible to readers.

**Why not C.** (a) cannot be built on a sharded map without a global lock. (b) is a global contention point by construction.

**Why B is not "a custom lock-free protocol".** It is the standard sequence-lock pattern, with three properties that keep it small:
- the existing mutex already serializes the word's writers, so the word needs no read-modify-write;
- the protected data stays under its DashMap shard guards, so the word only *detects* overlap and never stands in for the data's own synchronization;
- the fallback is the existing lock, taken in the existing order, so progress does not depend on validation succeeding.

## 3. The protocol and its correctness

### Words and writers

`Stripe { lock: Mutex<()>, seq: AtomicU64, multi: AtomicU64 }`, one 64-byte cache line per stripe:
- **`seq`**: `version·4 | ACTIVE`, for every write. Multi-key reads validate it.
- **`multi`**: `epoch·2 | MULTI_ACTIVE`, only for writes **visible in more than one step**. Single-key reads validate it.

"Visible in several steps" covers:
- a write naming more than one key *before* deduplication: MSET, DEL k1 k2, RENAME, COPY, SMOVE, the STORE family, and also `MSET k 1 k 2` and `RENAME k k`;
- a write that may empty a collection which the general path then removes: LPOP/RPOP/LREM/LTRIM/SREM/SPOP/HDEL/ZREM/ZPOPMIN/ZPOPMAX/ZADD;
- a capped write for which a rollback copy was taken.

The writer side:
- `order_keys(keys, several_steps)` takes every stripe in ascending order, then marks them all, still before the first mutation: `seq |= ACTIVE`, and `multi |= MULTI_ACTIVE` for multi-step writes. `run_write_gated` adds the multi-step mark when it takes a rollback copy, before `exec`.
- `drop(StripeHold)` does `multi ← multi + 1` if marked (flag cleared, epoch advanced), then `seq ← (seq | 3) + 1`, then releases the lock. `Drop` runs on unwinding too.
- Only the holder writes either word, so each update is a load and a store, never a read-modify-write.
- Every store is `Release` and every load `Acquire`. These are plain moves on x86-64.
- Both words are monotonic.
- `order_all` (FLUSHDB, restore) is **not marked** (§5).

### Single-key read (`read_one_at`)

```text
repeat up to 4 times:
    m₁ = multi.load
    if m₁ has MULTI_ACTIVE: wait (spin on `multi`, read-only; then lock + unlock); m₁ = reload; if still set, retry
    r = read()
    if multi.load == m₁: return r          // no multi-step write held the stripe in between
read() holding the lock                      // no multi-step write can start
```

**R2 proof (one key, and across keys).**
- **f saw part of a multi-step write.** Suppose `read()` observed a mutation by a multi-step write *W*. *W* marked `multi` before that mutation and published it through the shard guard that `read()` then took. So *W*'s mark happens-before the second load, which therefore returns the mark, or a later value: *W*'s release, or a later holder's mark (a Release store made after taking the lock *W* released). Each of those differs from m₁, so the read is refused and repeated. An accepted read saw no step of a multi-step write in progress. In particular it never saw a one-key write between its steps.
- **m₁ was a release.** If m₁ is *W*'s release (or later), the Acquire load synchronizes with it, so `read()` sees all of *W*.
- **Across keys.** Let *X* be a read that saw *W*'s write of *a* and completed, and *Y* a read of *W*'s key *b* that starts afterwards. *W* marked *b*'s stripe before writing *a*, so *Y*'s first load finds the mark, or *W*'s release, and either waits or sees *b* new.
- **Eager marking.** All of a write's stripes are marked before its first mutation. Marking each stripe just before its own key's mutation is **not** correct: a reviewer gave the schedule where `GET a` = new completes before `b`'s stripe is marked, so `GET b` = old.
- **Single-key writes** touch only `seq`, so a GET costs two loads of an L1-hot word and is never retried because of them. They need no wait: one mutation under one shard guard is atomic.
- **No clone on retry.** Retries re-run the read without cloning the command, because the read-only arms of `execute_inner` live in `execute_read_inner(&Command)`. The borrowed GET and HGET truncate their reply buffer on each attempt.

### Multi-key read (`read_many`)

```text
stripes = the keys' distinct stripes, ascending
repeat up to 4 times:
    (s₁, busy) = Σ seq.load over stripes; spin up to 64 times while busy (not above 16 stripes)
    if not busy:
        r = read all keys (one `now` for expiry)
        if Σ seq.load == s₁: return r
        if more than 16 stripes: break            // a large read overlapped once will be again
lock the stripes in order; return read all keys
```

**R1 proof.**
1. The words are monotonic, so equal sums mean equal words. A sum of up to *n* words cannot wrap: versions grow by 4 per write.
2. With no flag set at the first load and no word changed by the second, **no writer held any of these stripes at any time between the two loads**. A writer that took one in between would have changed its word. A writer that held one before the first load and released it in between would have advanced it.
3. Every mutation of a key happens with that key's stripe held. That holds for every keyed write, the expiry sweeper and the reserved path; the exceptions are in §5.
4. So no key the read read changed between its first load and its second. All of them held their values at every instant of that interval: one snapshot.
5. Memory ordering:
   - If the read observed a mutation, it took that key's shard guard after the writer released it. So the writer's flag store happens-before the read's second load, which then cannot see the old word.
   - If the first load saw a writer's release, the Acquire load synchronizes with it, so the read sees that writer's mutations.
   - The loads need nothing stronger: on x86-64 they are plain `mov`s.
6. The locked fallback is plain mutual exclusion against every writer of those stripes.

Single-key writes matter here too. "MGET a b; SET a 1; SET b 1", with the two SETs sequential and landing between MGET's reads of *a* and *b*, would otherwise answer (old, new), which is not linearizable. Their version bump makes validation see it. Duplicate keys are fine: a word counted twice is still monotonic. A retried borrowed MGET truncates its reply buffer and starts over.

### Every read goes through it

- **Owned**, `execute`/`execute_reporting`: every `MutationScope::ReadOnly` command goes to `execute_read`, by `read_scope`:
  - one-key reads (moved in, no clone) → `read_one_at`;
  - MGET, EXISTS, SINTER/SUNION/SDIFF with more than one key → `read_many` by reference;
  - connection-level and whole-keyspace commands run as before.
- **By-reference**, `execute_reporting_ref` and the capped variant: `execute_read_ref`.
- **Borrowed**, `execute_ref_into`, which the server uses for every TCP GET/HGET/MGET: the same `read_one`/`read_many`.
- `read_scope` is an **exhaustive** match over `Command`, so a new command has to be classified.

The server's reads all reach one of these three: EXEC-queued reads, WebSocket and the sync router go through `execute_and_record` → `execute`. QSUB's initial state, snapshots and replica cuts run under `lock_all_writes`, which already excluded every writer.

## 4. Lock order, deadlock, starvation, cancellation

| Lock | Writers | Readers |
|---|---|---|
| Capacity gate | before stripes | **never** |
| Write-order stripes | all of a write's, ascending, before any shard guard | slow path only: a single-key read takes and releases one to wait, or holds it for one read after 4 refused attempts; a multi-key read takes all of its own, ascending, deduplicated. Always **before any shard guard** |
| DashMap shard guard | one at a time, released before the next | one at a time, inside the read |
| Index shard lock | after the shard guard | never |

- **No inversion.** Readers take stripes before shard guards, in the writers' order, and hold no other lock when they do.
- **No recursion.** A thread holding a stripe is inside a store write: `run_write_gated`, `run_probed_write`, `try_reserved_write` or the sweeper. None of them reaches `execute`/`execute_read*`: `exec` calls `execute_inner` and the primitives directly. The only public entry point that recurses is `execute` → `execute_reporting`, and it holds nothing at that point.
- **Starvation.**
  - A single-key read retries at most 4 times, then reads holding its stripe's lock.
  - A multi-key read retries at most 4 times, then waits on the locks like a writer. `lock_stripe`'s spin-then-block is as fair as for writers.
  - A writer can be delayed by a reader's slow path for one read's duration, as by any other writer of its stripes.
- **Cancellation.** All waiting is synchronous, inside one `poll`. A Tokio task cannot be cancelled mid-wait, and the guards drop on return. A client that disconnects while its read waits has its read complete; the reply write then fails. Covered by `a_reader_disconnecting_while_it_waits_releases_everything`.
- **Panics.** `StripeHold::drop` clears the flags during unwinding, and the mutex's poisoning is recovered as everywhere else in the store.
- **Blocking a worker.** A reader blocks a Tokio worker exactly where a writer already does: on a stripe, for the rest of one multi-key write. That is hundreds of nanoseconds, or longer for a large MSET or DEL.

## 5. Not covered, and why

| | Status | Reason |
|---|---|---|
| FLUSHDB, restore (`order_all`) | **Unmarked**, as before | Marking them would block every reader on every worker for a whole restore. On a replica in full sync that can be seconds. Recorded as a follow-up with its own design |
| Multi-victim eviction (`remove_victim` takes no stripe) | Unchanged, pre-existing (6O-C) | Capped stores only. An MGET may see one victim gone before another. Values it does see are never mixed between writes (`eviction_racing_msets_and_mgets_never_mixes_generations`) |
| KEYS, SCAN, DBSIZE | Unchanged | Whole-keyspace walks. SCAN is not a snapshot in Redis either; KEYS and DBSIZE are recorded |
| Read-only EXEC isolation (root cause §6.1) | **Unchanged, separate defect** | A whole write can land between two queued reads. It needs EXEC to take its read keys' replication-order stripes. That is a separate follow-up, because it changes EXEC's locking |

## 6. Expiry

Reads mask expired entries, as before. MGET now evaluates every key at **one** `now`, as Redis 7 does with its per-command time snapshot. Keys sharing a deadline are therefore all live or all expired in one answer (`one_mget_sees_keys_sharing_a_deadline_together`). This also removes n − 1 clock reads per MGET ×n. Single-key reads are unchanged. The sweeper removes under each key's stripe, as a single-key write.

## 7. Cost model (measured in `V0.6O-D-ATOMICITY-FIX.md` and `V0.6O-D-PERFORMANCE.md`)

| Operation | Added |
|---|---|
| Single-key write | 2 plain stores to `seq`, on the line its mutex CAS already owns |
| Multi-step write | + 2 plain stores to `multi` per stripe |
| GET (no multi-step write in progress) | 1 multiplicative stripe hash + 2 loads of `multi` (L1-hot) |
| MGET ×n | n stripe hashes, a sort of n stripe indices, 2 loads per distinct stripe; minus n − 1 clock reads |
| A read during a multi-step write of its stripe | waits for that write (spin, then lock) |
| A large multi-key read under writes | takes its stripes' locks for its own duration; ≥ a few hundred keys can hold back nearly every writer |
| Memory | 64 B per stripe: 16 KiB per store (was 2 KiB of mutexes) |

## 8. Revisions after independent review

The design above is the one reviewed and approved in three rounds (`V0.6O-D-INDEPENDENT-REVIEW.md`). It differs from the first implementation as follows:
- **One-key multi-step writes are covered.** `MSET k 1 k 2`, `RENAME k k`, collection-emptying writes and rollbacks are marked. Single-key reads validate a separate `multi` word after reading. Marking alone left a load-then-read window that a stress probe hit about 1 in 5,000 RENAMEs.
- **No reader holds a lock across its read** except in the final fallback. Marks are set after all stripes are held. The flag stores are `Release`.
- **`read_many`** deduplicates stripes once and waits briefly for a write in progress; a large read falls back after one overlapped attempt.
- **Writes that created an empty collection and then removed it** are refused before creating it: `HINCRBYFLOAT k f inf`, and library calls of LPUSH/RPUSH/SADD/HSET with nothing to add.
