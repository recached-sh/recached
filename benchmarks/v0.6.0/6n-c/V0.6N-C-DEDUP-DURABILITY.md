# v0.6.0 Phase 6N-C: DEDUP acknowledgement and recovery guarantees

**Scope:** what a DEDUP client may conclude from each answer, on every transport and in every role, after 6N-C PRs 0a, 0b and 0d. This applies to both `RECACHED_AOF_FANOUT` modes.
**Fixes:** O1 and RV-9 (PR 0a, #128); RV-6 and NEW-4 (PR 0b, #132); RV-7, RV-14 and the full-resync table install (PR 0d, #130); the replica-local refusal (integration review L1, #133).

## The rule

> **No DEDUP outcome becomes readable before its frame has reached the AOF stage the configured policy requires of an acknowledged write.**

A DEDUP outcome is any of these:
- a mark, which makes a replay answer `+DUP`;
- a remembered permanent refusal, which makes a replay answer the same error;
- a no-op mark, for a write that changed nothing.

"Readable" means visible to any of these:
- a replay on any connection, over TCP or WebSocket, including the WebSocket early-replay path that runs without `dedup_order`;
- a full-sync DEDUP table sent to a replica;
- a checkpoint's DEDUP sidecar.

| Policy | Stage required before the outcome is readable |
|---|---|
| AOF disabled | None. Snapshot-only contract: a crash loses everything since the last checkpoint, marks included. |
| `no` | `write(2)` of the frame |
| `everysec` | `write(2)` of the frame. Durable within about 1 s. |
| `always` | `write(2)` and `fdatasync` of the frame. If either fails, the process stops (exit 74) before any waiter resumes. |

Under `everysec` and `no`, a failed append is non-fatal, as for every write: persistence latches unhealthy and later writes are refused with `MISCONF`. The outcome stays in memory and is answered, which is the documented contract (6N-B decision D2).

## How each path meets it

| Path | Before 6N-C | After |
|---|---|---|
| TCP DEDUP write, AOF on, no replication | Frame queued and the mark committed before `write(2)`: the deferred gate path. A replay elsewhere could get `+DUP` early (O1). | DEDUP writes never defer (`may_defer && dedup.is_none()`). The mark is committed after the inline append returns. |
| TCP or WS DEDUP write with replication, watcher or route | Inline: correct. | Unchanged. In `coalesced` mode the append is shared, but the writer still waits for its own batch before committing. |
| Permanent refusal on the write path | Remembered, then logged (RV-9). | Logged, then remembered. |
| WS refusal of a command that never ran (admin or out-of-scope key) | The refused command's stripes: all of them for FLUSHDB, one per key for a keyed command (RV-6). | `dedup_order`, then the identity's single stripe. Logged, then remembered. Paced at 32 refusals/s per connection. |
| WS early replay (strict, token in force) | Read marks without `dedup_order`, so it could see an O1 mark or an RV-9 refusal early. | Can only see outcomes committed after their stage (all of the above). |
| Replica: replicated DEDUP envelope | Mark committed before the replica's own AOF append (RV-14). | Appended (`on_write_identified`), then the mark is committed, under the write's stripes. |
| Replica: mark-only or refusal record | No stripe, no `still_following` check; remembered or committed before being logged (RV-7). | The client id's stripe and `still_following`; logged, then committed or remembered. |
| Replica: full resync | Data replaced under the barrier, the DEDUP table installed after it. | Both under the same barrier. |
| Replica: WS client's refused DEDUP write (scope or admin) | Recorded as a permanent refusal in the replica's own AOF and table, and fanned out to its sub-replicas, with no `still_following` check | Not recorded on a replica: its DEDUP state follows its primary's. Checked under the identity stripe, so it cannot race a promotion. The `NOSCOPE` answer is unchanged and remembered nowhere, which is safe for in-order replay (the SDK outbox). |

## What a client may conclude

| Answer to `DEDUP c n <write>` | Meaning |
|---|---|
| The write's own reply | Applied, and the write and its mark are at the policy's stage. A crash and restart replay both; a retry answers `+DUP`. |
| `+DUP` | Applied earlier. That application and its mark are at the policy's stage, on this node. |
| A permanent error, first time or on replay | Refused for good. Once remembered, the refusal is at the policy's stage and survives a checkpoint, in the sidecar or the AOF after the truncate, never in between. |
| A transient error (`TRYAGAIN`, `MISCONF`, `NOSCOPE … send SYNC TOKEN`, …) | Not recorded. Retry. |
| No answer (reset, close, timeout) | Unknown. Retry with the same `(c, n)`: the server applies it at most once. |

## Crash and retry

| Situation | Result after restart and retry with the same `(c, n)` |
|---|---|
| `always`, the original's batch fails while a replay waits | Neither connection is answered; the process exits 74. The retry gets the write's reply or `+DUP`, and the write is applied exactly once. Tested in `aof_fail_stop::a_dedup_replay_during_a_failing_always_batch_is_never_answered` (`fsync:eio`, `fail:eio`) and `a_dedup_retry_after_a_fail_stop_is_applied_exactly_once`. |
| Crash after a reply under `everysec` | Within the `everysec` window the write and its mark are lost together: since 0.5 one AOF frame holds both. The retry then applies it once. |
| Refusal recorded while a checkpoint runs | The refusal waits for the checkpoint's stripes and lands after it, in the AOF. Tested in `ws_refusal_barrier::a_refusal_never_lands_inside_a_checkpoint_window` and `a_checkpoint_waits_for_a_refusal_and_keeps_it` (restart from the sidecar). |
| Replica promoted while a record is pending | The record is refused, which ends the link. A retry on the new primary runs if the record never applied: the asynchronous-replication window. Tested in `replication::dedup_order_tests`. |
| Sub-replica attached while a record arrives | The record lands in the cut's table or the stream after it, never in neither. Tested in `dedup_order_tests::a_record_racing_a_sub_replica_cut_reaches_the_sub_replica` and `ws_refusal_barrier::a_refusal_racing_a_replica_cut_reaches_the_replica`. |

## Limits that remain (documented, not changed)

- **Reads are not gated (6N-B D5/O2).** A plain `GET` can read a write before its AOF stage. Only DEDUP answers and QSUB's `qstate` (PR 0c) are gated. Redis behaves differently under `always`.
- **`dedup_order` is one process-wide mutex.** Every DEDUP write and every recorded refusal holds it across its own AOF append, so TCP DEDUP writes are serialized server-wide. Under `always` that caps them at about 1 / fsync latency. This predates 6N-C: WS DEDUP writes and replicated primaries already held it inline. PR 0a extends it to TCP DEDUP without replication. Per-connection pacing bounds the refusal stream from one socket, but not from many. The planned structural fix is seq gating (6N-B PR 4, Option A), which is not authorized.
- **Asynchronous replication.** A `+DUP` or reply from a primary says nothing about a replica that has not received the frame yet. A promotion inside that window can re-run a retry. This is unchanged.
- **Chained replicas.** A chained replica's full resync does not propagate the replaced keyspace to its existing sub-replicas or to its own AOF. This predates 6N-C, is outside DEDUP ordering, and is recorded as a follow-up.
