## Decision: PERFORMANCE INVESTIGATION REQUIRED

Why not each of the other outcomes:
- **Not OPTION D SUFFICIENT.** Both M1 thresholds fail.
- **Not OPTION A JUSTIFIED.** The result contradicts the expected bottleneck. Option D was meant to fix "one `write(2)` per command", and it did so at P=1. At P=16 it made things **worse**, for a reason the counters identify: the coalescer judged ≈1,000,000 of 1,000,000 yields "gained", while batches held 1.2 frames, so its back-off never engaged. Option A shares that "lead later, let others join" premise. Its estimated 7–8 µs/op would take P=1 only to about 0.75–0.86× standalone, against 0.73× measured for D. Its gain over a fixed D is unproven.
- **Not CORRECTNESS BLOCKED.** No confirmed data-integrity, durability, ordering or security regression remains.

### Recommended next milestone (needs maintainer approval)

1. **Fix and re-measure the coalesced path.** Small and contained.
   - Judge a yield a gain only when *another writer's frame joined the batch*, not when the batch was merely performed by someone else.
   - Do not yield while every stripe is held.
   - Consider yielding only when other appenders are ready.
   - Re-run M1 cells P=1 and P=16 with the same kit, on the same host.
2. **Profile the replicated path.**
   - Instructions per op and the scheduler cost per yield are unmeasured, because the host has no `perf`. Installing `perf` on the Fedora host needs your authorization (`sudo dnf install perf`).
   - Even a perfectly coalesced replicated P=1 primary used 8.2 µs/op against 6.0 standalone. Where the remaining 2.2 µs/op go (the replication `fan_out` copy, the stream lock, the yield itself) decides whether Option A could help.
3. **Only then decide on Option A**, on the 6N-B rule (continue only if D, fixed, stays below 0.85×), with the profile as evidence.

**Option A was not implemented and must not be started without your approval.**
