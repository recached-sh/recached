# v0.6.0 Phase 6N-C3: Gate M1, targeted Linux performance

## Verdict

**M1 = FAIL.** A material performance gap remains:

| Measure (M1 reads only the coalesced cells) | P=1 | P=16 | Threshold |
|---|---:|---:|---:|
| Coalesced ÷ standalone (both runs with replication off vs on; see the table below) | **0.733** | **0.250** | ≥ 0.85 |

The reading of that verdict is **PERFORMANCE INVESTIGATION REQUIRED**, not "Option A justified".
- **P=1:** Option D works as designed, but is not enough. The replicated primary goes from 0.46× to 0.73× standalone.
- **P=16:** `coalesced` is **slower than `inline`**. Throughput is 0.69× inline, and p99 is 8.9 ms against 4.9 ms. That contradicts the bottleneck 6N-B assumed.
- **The cause is identifiable:** the coalescer counts nearly every yield as a gain, even when batches average 1.2 commands, so it never backs off.
- **Option A's case is weak on current numbers.** 6N-B's estimate for it (7–8 µs/op) would only take P=1 to about 0.75–0.86×.

So the [release gate](V0.6N-C-RELEASE-GATE.md) recommends investigating and fixing the coalescer first. It does not recommend starting Option A. **The default stays `inline`.**

## Why P=1 improved and P=16 regressed

The AOF counters of each run (raw `aof_before`/`aof_after` in `results.txt`) show the mechanism:

| `coalesced` cell | Yields judged "gained" | Yields judged "missed" | Frames per batch |
|---|---:|---:|---:|
| P=1, 1 worker (per run) | ≈ 1,000,190 | 1–2 | 4.7 |
| P=16, 1 worker (per run) | ≈ 1,000,130 | 2–4 | 1.2 |

How a yield is judged:
- The `Coalescer` judges a yield a gain when `done.is_complete() || strong_count(done) > holders`.
- At P=16 a connection's 16 pipelined commands run one after another. Each queues a frame, yields, and very often finds that another writer has *already performed its batch*, with only one or two frames in it.
- That counts as a gain, so the back-off (2 misses → skip 32) never engages, and every one of the million commands pays a scheduler round trip.
- The yields also interleave the 50 connections' pipelines, which delays each pipeline's last reply. That explains p99 going from 4.9 to 8.9 ms.
- Net cost: +2.1 µs/op of CPU against `inline`, for 0.18 fewer `write(2)`s per command.

At P=1, the 50 connections each have exactly one command ready. The yield lets the others queue into the open batch: 4.7 frames per batch and 0.21 writes per command. That is the gain Option D was designed for.

This explanation is consistent with every counter. It has **not** been confirmed with a profile (no `perf`), and no fix has been tried. That is the investigation the release gate recommends.

## Replica lag and convergence

- Every replicated run converged, and its 300-key sample matched on primary and replica:
  - 18 Recached runs (inline and coalesced, in all three replicated cells);
  - 6 Redis runs;
  - 6 Valkey runs.
- `coalesced` *lowered* replica lag: P=1 p99 0.46 ms against 0.94 ms inline, and P=16 p99 0.50 against 3.64.
- It *raised* the 4-worker p99 lag tail (3.26 against 2.83 ms) while improving its p50.
