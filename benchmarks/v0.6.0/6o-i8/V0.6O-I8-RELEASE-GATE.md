## 4. The replica-with-AOF operating limit

There is **no sharp sustainable rate** on this host; the data give failure counts by rate. On this host (6 CPUs, a 7,200 rpm HDD, btrfs with `zstd`, `tcp_rmem` maximum 32 MiB, a 100,000-key keyspace of 32-byte values), a replica with its own AOF `everysec`, in every build alike:

- on an **established link**, never disconnected at 1,380 and 1,610 tx/s of 100-`SET` transactions (138,000–161,000 replicated writes/s; 11 and 7 minutes per build); at 1,840 tx/s, over five 30-minute soaks (H one, I two, P two), one disconnect in about 135 established-link minutes (P's rerun, after a 2.72 s disk stall), and one in H's 600 s `r5` run before its first forced resync (+105 s);
- on a **young link**: P's first soak lost its first links in a chain of 5 full syncs within 150 s of the load's start (not repeated in its rerun); after a **resynchronization under load** (24 forced), the new link failed again in 5 cases within 31 s of its install, at 1,380 tx/s as well as 1,840 (H 2, I 1, P 2 of 8), and held after the next full sync; the longest chain observed anywhere was 5 full syncs in 150 s;
- fails increasingly from 2,070 tx/s.

The cause is the replica's design, unchanged since 6O-H (itself unreleased, so this ships in v0.6.0): its link reader runs in the applier's task, so a stall in its AOF `write(2)` (the disk's `fdatasync`) stops it from reading its link, and the primary's byte budget disconnects it when the stall outlasts the buffering between the nodes, which is small on a young link (a small TCP receive buffer) and depends on the host's `tcp_rmem` (32 MiB here; the kernel's 6 MiB default was not tested). A link can also fail **during its own install** when the snapshot's checkpoint outlasts what the 64 MiB read-ahead holds (one case: a 6.5 s install at 1,840 tx/s); install time grows with the dataset, which was 100,000 small keys in every run, so for large datasets under sustained writes this limit is **not bounded by these measurements** (§5).

6O-I does not change the stall, the buffering or the install; its replica costs 2.6× less CPU per transaction and recovers faster in overload. On tmpfs, 6O-I's replicas streamed at the primary's maximum for about 92 s without a resync (until the host's tmpfs quota) where 6O-H's, at a slightly higher accepted rate, took 21 full syncs.

**Operational guidance:** put a replica's AOF on storage with short `fdatasync` tails, or run it without an AOF; size `tcp_rmem` generously; expect a replica that resynchronizes under heavy write load to need several full syncs, more with a large dataset. **Until D10 is fixed:** a replica's AOF is truncated only by a full sync (it never autosaves), so size a replica's disk and memory for that or run it without an AOF; and on every node, since replay reads the whole AOF, provide RAM of at least the dataset plus the AOF written over one save interval (write rate × record size × interval, 900 s by default; about 12.6 GB at this cell's 14 MB/s) plus headroom, using the file's logical size on compressing filesystems (btrfs `zstd` compressed this AOF about 7×).

## 7. Next development milestone (recommended; nothing started)

1. **Release-risk fixes for persistence on replicas (D10)**, as a design first: a replica checkpoints on a schedule (replicated writes count toward autosave; D10a); AOF replay streams the file instead of reading it whole (D10b); full-sync retries back off and AOF write errors are rate-limited (D10c, review C F10). All are pre-existing production behaviour, so each needs a design, an independent review and the maintainer's approval before any code. Measure them in the `r4`/`r6` cell (a 30-minute 1,840 tx/s soak whose replica checkpoints and restarts from its own files within bounded memory) and with a 1–2 GB dataset under sustained writes (review D F1: the install-time failure). Run every restart check inside a memory limit (`systemd-run --user -p MemoryMax=…`): `r6`'s OOM also killed desktop-session helpers and aborted its campaign.
2. **The remaining v0.6.0 release gates** (Q22): standalone AOF P=1 ≥ 0.90× Redis, `MSET`×10 P=1 ≥ 0.90×, memory per key ≤ 1.5× Redis, replicated M1 P=16 ≥ 0.85×, the release-candidate soak, and the SSD rerun of the stall cases.
3. **Optional, on approval only:** PR 3 (D8); the young-link causal test; the CI flake's test-only hardening (a deadline instead of an iteration budget, `V0.6O-I8-CORRECTNESS-VALIDATION.md` §4).

Not in this phase and not started: PR 3, any production change, MSET-A/B, Phase 6P, Option A, the v0.6.0 tag or release.
