# v0.6.0 Phase 6O-I8: why 6O-I resynchronized more under overload (Investigation 2)

| | |
|---|---|
| Cell | the 6O-I campaign C replica cell: primary 1 worker (CPU 0), no AOF; one replica, 1 worker (CPU 1), its own AOF `everysec` on the HDD; 100-`SET` transactions over 100,000 keys, 20 connections; here **paced** at fixed offered rates (`V0.6O-I8-BENCHMARK-METHODOLOGY.md` §3.2) |
| Evidence | `raw/r1/` (8 rates × H, I, P, 90 s), `raw/r2/` (refinement, 3 reps × 120 s), `raw/r3/` (no replica AOF, replica files on tmpfs, diag builds); per-run event timelines (`tools/timeline_i8.py`) and cycle tables (`tools/cycles_i8.py`) |

## 1. Answer

| Question | Answer |
|---|---|
| What triggers each reconnection? | always the primary's **byte budget** for the replica's queue (`RECACHED_REPL_BUFFER_BYTES`, 8 MiB charged): every disconnect in `r1`–`r5` (361 in `r1`–`r3` alone) logged `Replica byte queue full`; the frame cap (`channel full`) never fired |
| Why is every resync a full sync? | at the disconnect the replica is already behind by what sat in the primary's queue and in both sockets (up to tens of MB on this host); it then notices the end of its link only after applying what it had already read, and waits 2 s before reconnecting. By then the primary has streamed far more than its 16 MiB backlog holds (≈ 250,000 frames: 0.5 s at 5,000 tx/s). 0 partial resyncs in 361 disconnects (`r1`–`r3`); rule 2 (no resume inside a group) never applies, since a capable replica's resume point is always a group boundary |
| Why did 6O-I take more full syncs than 6O-H under overload? | **each of its cycles is shorter, not its capacity lower.** An overloaded replica cycles: stream until the queue overflows, notice, wait 2 s, install, repeat. P survives each install as long as H or longer (0.8–1.1 s against 0.6–0.8 s), but H takes 1.3–4.5 s to *notice* the end (it applies its read-ahead one frame and one AOF `write(2)` at a time), against 0.3–1.3 s for P. Shorter cycles fit more of them into a window |
| Why was 6O-I "still syncing at the end" where 6O-H had caught up? | a snapshot of where in its cycle each run ended. Measured properly (after the load, until lag 0), every run of every build converged exactly (expected keyspace, replica digest, restart from the replica's own AOF where checked): below the failure region by streaming, within 0.25 s; in 13 of the 15 overloaded `r1` runs through a full sync that completed after the load |
| Is any buffering unbounded? | no: the primary's queue is bounded by bytes and frames (unchanged), the replica's read-ahead by 64 MiB of chunks, its group buffer by 64 MiB (D1); replica RSS (`r1`, peak): 29–41 MiB below saturation, up to 150 MiB in overload, **the same in every build** (H 147, I 150, P 148 MiB at 7,820 tx/s): the read-ahead and its chunk queue (128 MiB per link at most, by design) fill while a snapshot installs; primary RSS 60–88 MiB |
| A qualitatively new failure? | none found: no divergence in any run; no resume inside a group and no partial resync at all; no apply or protocol error in any replica log (a partial group application is not observable by these benchmarks, which check final state: that guarantee rests on the code and 6O-I's atomicity tests). Below the failure region, failures come as short chains on young links (the longest: 4 new links in a row, then held), not as a loop (`V0.6O-I8-REPLICA-SUSTAINABLE-THROUGHPUT.md` §3) |

## 2. The overload cycle (`r1`, one rep per rate)

From both servers' logs (`tools/cycles_i8.py`, `raw/r1/cycles.md`): for every disconnect during the measured window, the time since the replica's last install during the load (survival), the time until it saw the link end (notice), the reconnect wait, and the install (snapshot transfer, load and checkpoint). Medians per run; each overloaded run has 11–19 disconnects:

| offered | build | disconnects in the window | survival s | notice s | wait s | install s |
|---|---|---|---|---|---|---|
| 3,680 | H / I / P | 17 / 12 / 18 | 0.70 / 1.15 / 1.14 | 1.33 / 0.38 / 0.29 | 2.0 | 0.76 / 0.69 / 0.62 |
| 5,060 | H / I / P | 16 / 19 / 17 | 0.65 / 1.03 / 0.93 | 1.90 / 0.60 / 1.32 | 2.0 | 0.67 / 0.78 / 0.81 |
| 6,440 | H / I / P | 13 / 19 / 19 | 0.61 / 1.29 / 0.82 | 3.71 / 0.84 / 0.89 | 2.0 | 0.82 / 0.83 / 0.82 |
| 7,820 | H / I / P | 11 / 17 / 18 | 0.76 / 1.08 / 1.08 | 4.45 / 1.91 / 1.26 | 2.0 | 0.84 / 0.79 / 0.79 |

At 2,300 tx/s each run has only 1–2 disconnects, too few for medians (`raw/r1/cycles.md`).

- **Survival** after an install is what capacity means here; in these four overloaded rates, one run each, I's and P's are longer than H's.
- **Notice** is the time to apply the backlog already read. H's replica writes one AOF record per frame (one `write(2)` each: 2.5–3.1 µs per write, 24–54% of its time in `write(2)`); I and P write one per group. H's replica costs about 2.6–3× more CPU per transaction below saturation, so it takes longer to reach the end of what it holds.
- The 2 s reconnect wait and the install (0.6–0.8 s) are the same in every build.
- **In overload, 6O-I's replica blocks longer per AOF write** (its write is a whole group): its longest `write(2)` accumulation per second reached 3.71 s (I) and 3.22 s (P) against 1.68 s (H) at 3,680–7,820 tx/s (3.75, 3.50 and 1.32 s at 9,200 tx/s, a rate not valid for replica capacity; `raw/r2/stalls.md`). Its survival per cycle was nevertheless the same or longer (review D F12).

So the count of full syncs per minute in overload is a *rate of cycles*, and the replica that works through its read-ahead faster cycles faster. 6O-I's campaign C saw 5–6 full syncs in 20 s against 4: the same effect. These are single runs per rate: the direction (I and P survive as long or longer, and notice sooner) holds at every overloaded rate, the sizes are indicative.

## 3. Below the failure region

`V0.6O-I8-REPLICA-SUSTAINABLE-THROUGHPUT.md` §3: no disconnect in any build at 1,380–1,840 tx/s (`r1`, `r2`; the soak `r4` and the forced resynchronizations of `r5` are reported there).

## 4. What triggers a cycle

`V0.6O-I8-REPLICA-SUSTAINABLE-THROUGHPUT.md` §4: the replica's single task, which both applies and reads its link, blocks in an AOF `write(2)` for 0.35–1.5 s at a time; a stall longer than the buffering between the nodes (the primary's 8 MiB queue plus the socket buffers: 1–2 s at these rates on this host, whose `tcp_rmem` maximum is 32 MiB) lets the primary's byte budget fill, and the primary disconnects the replica. The same mechanism starts every cycle of §2; in overload the replica, behind from its last install, meets the next stall sooner.

## 5. Initial and unwanted synchronizations

Each run's replica attaches before the prefill with one full sync (24 in `r1`, one per run); the counts above exclude it (`full syncs (after prefill)`). Four syncs in `r1` ended during the snapshot transfer (`primary closed the link during a full synchronization`) and were retried.
