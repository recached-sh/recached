## What the measurements say

1. **The 6N-C hypothesis was right but incomplete.** The gain signal was wrong. The bigger defect, though, was that a resumed writer led batches that were not its own. Fixing only the signal would have traded the P=16 regression for a P=1 one: P=1 fell to 76.9k, against 89.9k before (see [the ablation](V0.6N-C4-ROOT-CAUSE.md#ablation-on-native-linux)).
2. **On the replicated path, AOF `write(2)` cost is now at parity with standalone** (0.52–0.68 against 0.32–0.74 µs/op).
3. **P=1 is limited by replication, not by the AOF.** A replicated primary with **no AOF at all** reaches only 98.8k ops/s, which is 0.815× M1's standalone. With a replica attached, the coalesced AOF adds only about 0.13 µs/op. **No AOF design can lift P=1 to 0.85.**
4. **P=16 is limited by the per-command AOF wait on the replicated path.** Each write waits for its own batch, about one scheduling round, before it fans out. The connection gate waits once per pipeline. That costs +0.71 µs/op with no replica and about +1.75 µs/op with one. Replication alone at P=16 reaches 465k, roughly standalone's level, so this is the gap an AOF-side design could close.
5. **4 workers:** coalescing gains 22% in throughput, but its p99 is worse than inline. The counters point at review F1 (219k busy leads per run) and F2 (18k back-offs per run at 2.4 frames per batch).

## Option A

The brief's conditions for recommending Option A (watermark-gated fan-out, 6N-B):

| # | Condition | Assessment |
|---|---|---|
| 1 | The corrected Option D still leaves a significant gap on the production path | **Yes:** 0.805 at P=1 and 0.460 at P=16 |
| 2 | Profiling identifies costs that Option A can realistically eliminate | **At P=16 only.** Option A stages effects in the batch, and the performer releases them. That removes the per-command wait before fan-out (bottleneck #2), so it is the only identified design that targets it. **At P=1, no:** the gap is per-replica fan-out (bottleneck #1, about 1.1 µs/op), which Option A does not touch. |
| 3 | The projected gain justifies the ordering and synchronization complexity | **Unproven.** The P=16 ceiling for an AOF-side design is roughly replication without AOF: 465k, about 1.0× standalone. Option A's own overhead, and how it interacts with the replica sender, are not measured. Even a perfect P=16 would leave M1 failing at P=1. |
| 4 | The original design's independent-review conditions still apply | Yes. Nothing in 6N-C4 touched the code that 6N-B's conditions cover (R3-1 and the rest). |
| 5 | The maintainer explicitly approves implementation | **Not given** |

**Recommendation: do not start Option A next.** The brief's rule is: "If profiling shows that most remaining CPU time is in replication fan-out … identify the narrower optimization first". That rule applies here, because:
- the P=1 limit is replication fan-out;
- it affects every replicated configuration, `inline` included, and replication without AOF;
- it can be addressed without new ordering machinery.

Option A should be reconsidered for the P=16 per-command wait once that work and a `perf` profile exist. It would then need an explicit decision on whether the M1 P=1 threshold is reachable at all with one replica attached.

## Recommended next milestone (needs maintainer approval)

1. **Authorize `perf` on the Fedora host** (`sudo dnf install perf`, and `kernel.perf_event_paranoid ≤ 1` for kernel samples). Without it, the internal split of the replica cost stays a hypothesis.
2. **Replication fan-out cost (narrow, P=1).** Profile `rc-repl-noaof` and `rc-coalesced`, then remove per-write overhead, measured: the frame copy in `on_write_logged`, per-write backlog and channel work, and sender wake-ups. Target: `rc-repl-noaof` P=1 toward standalone.
3. **Coalescer follow-ups (small).** Do not yield when a leader is already performing (F1). Observe once per batch (F2). Re-measure the 4-worker p99. Optionally apply the same skipped lead and exact gain to the connection gate (F4), after re-validating the standalone path.
4. **Then revisit Option A** for P=16, with the profile as evidence and the 6N-B review conditions.

**Not recommended:**
- adopting `coalesced` as the default: M1 is not met, and the 4-worker p99 regresses;
- a production deployment of `coalesced` without the one sustained run of that exact candidate and topology that the brief requires.

No soak was run in this phase. None was needed for an opt-in mode that is not proposed for adoption.
