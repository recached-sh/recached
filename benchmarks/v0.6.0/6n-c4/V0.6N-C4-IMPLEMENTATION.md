# v0.6.0 Phase 6N-C4A: the coalescer correction

**Merged:** PR #136 into `dev` as `625f88a`, from these commits:
- `41403f2`: the change;
- `5276571`: configuration docs;
- `3ce871a`: review follow-up tests and docs.

**Scope:** `RECACHED_AOF_FANOUT=coalesced` only. The default is still **`inline`** and is unchanged. The connection gate (the deferred, standalone path) keeps its behaviour.

**Not implemented:** Option A, watermarks, staged effects, and any change to replication fan-out.

Why the change was needed is in [the root cause](V0.6N-C4-ROOT-CAUSE.md).

## The change

`AofWriter::append_coalesced` (`server-native/src/persistence.rs`):

```text
                          6N-C                                    6N-C4
queue_only(frame)                                    queue_only(frame); position = batch.frames
if should_yield():                                   if should_yield():
    holders = strong_count(done)                         guard = LeadOnDrop
    guard = LeadOnDrop                                   yield_now().await
    yield_now().await                                    guard.disarm()
    guard.disarm()                                       observe(gained = done.frames() > position)
    observe(gained = done.is_complete()              if done.is_complete():
              || strong_count(done) > holders)           found_written += 1      -- do not lead
lead()                                               else:
gate_wait(done).await                                    lead()
                                                     gate_wait(done).await
```

1. **Gain is batch growth.** `AofDone` gains `frames: AtomicU64`. `AofBatch::push_frame` mirrors the batch's frame count into it. It runs under the queue lock, which is already held, as one relaxed store.
   - A coalesced append records the count right after pushing its frame. That count is its position: 1 if it opened the batch.
   - A yield is a gain only if the count is higher when the append resumes, meaning some other frame joined *this* batch after this one.
   - "Another writer completed the batch" and "the completion gained a holder" no longer count.
   - The count is final once the batch is taken, because only the queue's back batch can be joined.
2. **No lead for a batch already written.** A writer that resumes to find its own batch complete does not call `lead()`. Leading then would write only the batch opened since, which holds other writers' frames, before those writers could be joined.
   - The new `fanout_found_written` counter records the skip. It counts completion, whether the batch succeeded or failed.
3. **Separate counters.** `Coalescer` carries a `CoalescePath` (`Gate` or `Fanout`), which only chooses where its observations are counted:

| INFO field | Path | Meaning |
|---|---|---|
| `recached_aof_coalesce_gained` / `_missed` | gate | As before for the gate. **Since #134 (unreleased) it had also included the fan-out path's yields; now it is the gate's alone.** |
| `recached_aof_coalesce_backoffs` | gate | New: back-offs triggered |
| `recached_aof_fanout_coalesce_gained` / `_missed` | fan-out | New: a yield after which another frame joined the writer's batch, or not |
| `recached_aof_fanout_coalesce_backoffs` | fan-out | New: back-offs triggered |
| `recached_aof_fanout_found_written` | fan-out | New: appends that found their batch already completed and did not lead |

Comparing with 6N-C raw data: its `rc-coalesced` rows reported the fan-out yields in `coalesce_gained`/`_missed`. The 6N-C4 runs report them in `fanout_coalesce_*` (review F3).

### What did not change

- **The back-off policy.** It is still `COALESCE_MISSES = 2` misses in a row, then lead at once for `COALESCE_BACKOFF = 32` appends, then probe again. With an honest gain signal the existing policy behaves as designed, so there was no evidence to retune it:
  - one client: 20 probes per 340 appends (Test D);
  - writers that cannot overlap: about 6% of appends yield (Test C, serialized variant);
  - M1 P=16 with both fixes: about 5 back-offs per million commands, because batches really fill.

  The constants became `pub(crate)` so that tests can name them.
- **`RECACHED_AOF_COALESCE=off`.** It still disables both coalescers, which makes `append_coalesced` equivalent to `append`.
- **The connection gate.** Its yield, its gain test and its `lead()` after the yield are unchanged, as the brief requires. Review F4 notes that it has the same two weaknesses; that is left to a later milestone.
- **Write ordering and durability.** The writer still holds its write-order stripes across the yield, still returns only after `gate_wait` on its own batch, and only then fans out. `always` fail-stop, everysec non-fatal failure and torn-write cut-back are untouched.

## Why skipping the lead cannot strand a frame

Every producer of a queued frame leads it, unless that producer's own batch has already completed:

| Producer | Leads |
|---|---|
| `enqueue` (`append`, `flush`, truncation) | at once |
| `append_coalesced` | after its yield; on drop, if cancelled during the yield (`LeadOnDrop`); at once if it did not yield |
| a deferred append (connection gate) | when its connection settles, or on `Drop` |
| `AofTail::settled` (QSUB) | at once |

Batches complete in queue order. A writer whose batch is complete therefore owes nothing to later batches, and each later batch has writers of its own that will lead it.

`lead()` returns early only when the queue is empty or another performer holds `busy`. The inline performer re-locks after releasing `busy`, and `drain_blocking` releases `busy` only after it has seen the queue empty under the lock. A frame queued while someone else is performing is therefore swept by that performer.

The independent review tried to break this and could not (question 3 in [the review](V0.6N-C4-INDEPENDENT-REVIEW.md)).

## Ineffective-yield avoidance: what was and was not done

| Case named in the brief | Handling |
|---|---|
| Single active writer | The back-off: 2 misses, then 32 leads at once (Test D) |
| Repeated ineffective yields | Now detected, because a one-frame batch is a miss (Test A) |
| A writer holding every write-order stripe (EXEC, FLUSHDB, capped-store evicting writes), or a key contended by pipelines in lock step | Its yields are misses, and the back-off holds them to about 6% of appends (Test C, serialized variant). The "holds every stripe" context is **not** passed down to `on_write_logged`, which would need a new argument through the whole write path. It is accepted as a bounded cost: at most one futile yield per probe. |
| A busy performer (another worker's inline leader, or `always` on the blocking pool) | **Not handled; review F1, accepted.** The yield is credited with joins that would have happened anyway. Cost: one scheduler pass per append, next to a `write(2)` or `fdatasync` already in progress. It does not occur in the 1-worker `everysec` M1 cells, where `lead_busy` was 0. |
| A ready-appenders hint | Not added. Nothing measured showed it would add value. |

## Cost on the default path

`push_frame` makes one extra relaxed store, under a lock it already holds, to a cache line that `Arc::clone` of the same `AofDone` already touches. `AofDone` grows by 8 bytes per batch. `INFO persistence` gains 5 lines. The `inline` mode's M1 numbers are in [M1](V0.6N-C4-M1-PERFORMANCE.md).
