# v0.6.0 Phase 6N-C4C: Gate M1 revalidation

## Verdict

**M1 = PARTIAL. The regression is fixed, but throughput is below the threshold.**

| M1 ratio (corrected `coalesced` ÷ standalone, medians of 3) | P=1 | P=16 | Threshold |
|---|---:|---:|---:|
| 6N-C (`0b48332`) | 0.733 | 0.250 ‡ | ≥ 0.85 |
| **6N-C4 (`625f88a`)** | **0.805** | **0.460** | ≥ 0.85 |

‡ An upper bound: in 6N-C the P=16 references hit a 2-second-run artifact (see [the generator ceiling](#the-p16-generator-ceiling)).

- **The P=16 regression is gone.** `coalesced` is now **1.14× `inline`** at P=16 (it was 0.69×), and its CPU/op is 23% *below* inline.
- **The P=1 gain is kept and grown.** `coalesced` is **1.68× `inline`** (it was 1.58×), with p99 16% lower.
- **Both 0.85 thresholds still fail.** P=1 is close (0.805). P=16 is far (0.460). [Profiling](V0.6N-C4-CPU-PROFILING.md) puts the P=1 gap on per-replica fan-out, which no AOF change can remove. The P=16 gap is the per-command AOF wait on the replicated path.
- **The tail is not uniformly better.** p99 at P=16 is **+8.6%** against inline (4.98 against 4.58 ms), while p50 is −15.5%. With 4 workers, throughput is +22% but **p99 is +79%** (1.89 against 1.06 ms).
- Correctness held: every replicated run converged and its 300-key sample matched, with no errors.

**Recommendation:** keep `RECACHED_AOF_FANOUT=inline` as the default. `coalesced` is a sound opt-in, but it does not meet M1 and has a 4-worker p99 regression. Option A is discussed in the [release gate](V0.6N-C4-RELEASE-GATE.md#option-a).

## The P=16 generator ceiling

In 6N-C, standalone Recached, Redis and Valkey all reported 499,500 ops/s at P=16, which is 1,000,000 requests in 2.002 s.

| Check | Result |
|---|---|
| Run length | P=16 cells now take 20–53 s instead of 2 s |
| Server-limited or generator-limited? | `redis-benchmark` used **0.16–0.29 cores** of its 3 at P=16, measured by `time` around it, so it is not CPU-bound. The servers now differ: standalone Recached 470k, Redis 412k, Valkey 429k (earlier: 499.5k each). |
| Independent wall clock | Requests ÷ wall time agrees with `redis-benchmark`'s figure within 0.1% in every cell |
| More generator threads | A probe with `--threads 3` was no faster (434k against 493k for standalone), so `--threads 2` was kept for comparability. Data: [`fedora-i5-9400f-20261119-ceiling/`](fedora-i5-9400f-20261119-ceiling/). |
| Server CPU | Standalone used 1.63 µs/op × 470k ≈ 0.77 of its core, and coalesced 3.65 × 216k ≈ 0.79: the closed loop of 50 × 16 requests keeps the server near, not at, its core's limit. |

The 499.5k reading was an artifact of a 2-second run, not a hard generator cap. The P=16 references are now trustworthy as server-limited closed-loop measurements.

One caveat: standalone and Redis P=16 varied across repetitions (standalone 388k–500k, Redis 354k–444k). Medians are used. For M1, the P=16 ratio lies between 0.43 and 0.56 over the whole standalone range, so it fails either way.

### Batching counters (`coalesced` cells, medians per run)

| Cell | Yields per command | Real gains | Misses (≈ one per batch) | Back-offs | Found batch already written, per command |
|---|---:|---:|---:|---:|---:|
| P=1, 1 worker (1M commands) | 1.000 | 93.1% | 6.9% | 3 | 0.931 |
| P=16, 1 worker (10M commands) | 1.000 | 96.3% | 3.7% | 41 | 0.963 |
| P=1, 4 workers (1M commands) | 0.629 | 85.9% | 14.1% | 18,241 | 0.551 |

How to read these:
- **Ineffective yields** (misses) are about one per batch: the last writer to join, which nothing followed. In 6N-C, nearly all yields were recorded as gains while batches held 1.2 frames, so the yields were mostly wasted.
- **One worker:** back-off is almost never needed, because yields now form batches.
- **Four workers:** with about 2.4 frames per batch and misses counted across writers, the back-off engages often (review F2). Busy leaders are frequent too (219k per run, review F1). Together they explain the lower batching and the p99 tail.

## Acceptance against the brief

| Criterion | Result |
|---|---|
| P=1 coalesced ≥ 0.85× standalone | **FAIL** (0.805) |
| P=16 coalesced ≥ 0.85× standalone | **FAIL** (0.460; 0.43–0.56 over the reference's range) |
| P=1 improvement preserved | **PASS**: 1.68× inline, +9.7% against 6N-C |
| No material P=16 throughput regression against inline | **PASS**: +14.1% |
| No material p99 regression against inline | **P=1 PASS** (−15.8%). **P=16 marginal** (+8.6%, +0.39 ms, while p50 is −15.5%). **4 workers FAIL** (+78.9%). |
| Replica convergence | **PASS**: 18/18 Recached replicated runs, plus Redis and Valkey |
| Durability and ordering | **PASS**: see [correctness tests](V0.6N-C4-CORRECTNESS-TESTS.md) |
| Bounded queues and scheduler overhead | **PASS**: about one yield per command, ≤ 0.001 context switches/op on 1 worker, nothing left queued in the tests |

**Outcome: M1 PARTIAL.** The regression is fixed and P=16 improves substantially, but both 85% thresholds fail. A p99 regression remains with 4 workers. The [profiling](V0.6N-C4-CPU-PROFILING.md) shows that the P=1 gap is not in the AOF.
