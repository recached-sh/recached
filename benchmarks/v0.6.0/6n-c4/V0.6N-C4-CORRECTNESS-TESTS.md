# v0.6.0 Phase 6N-C4: correctness tests and mutations

All of these are in `server-native/src/tests/coalesced_fanout.rs` (PR #136, `dev` `625f88a`). Unless noted otherwise, each test drives `append_coalesced` futures by hand with `poll!`, so each interleaving is exact rather than left to the scheduler.

## Required tests (brief §4)

| Brief | Test | What it shows |
|---|---|---|
| **A** False-positive gain | `a_batch_another_writer_wrote_with_nothing_joined_is_a_miss` | Writer A queues and yields. A `tail().settled()`, which adds no frame, writes A's batch. A resumes, finds its batch written and does not lead. The batch stays at one frame, and the yield is a **miss**. After `COALESCE_MISSES` (2) such yields the path backs off once, and the next append completes on its first poll, with no yield. The gate's counters stay at 0. **It fails with the 6N-C heuristic (mutation M1).** |
| **B** Genuine gain | `frames_that_join_a_batch_are_gains_and_share_one_write` | Ten writers queue into one open batch before any resumes. There is one `write(2)`. | **C** Pipelines | `pipelined_writers_share_writes_and_count_only_real_gains` (one-worker runtime, 50 × 16) | Independent pipelines get ≥ 8 frames per write; 6N-C got about 1.2. | **C** (review F5) | `pipelined_writers_on_four_workers_strand_nothing` (four-worker runtime, 32 × 16, under `no`, `everysec` and `always`) | The same order, once-only, no-early-return and nothing-queued checks, with leaders on several threads, tasks migrating across yields, and blocking-pool drains |
| **D** Single writer | `a_single_coalesced_writer_backs_off` (one-worker runtime) | 340 appends with no other traffic: exactly 20 probes, 10 back-offs, 0 gains, 340 writes. Every write completes. |
| **E** Cancellation | `a_writer_cancelled_mid_yield_strands_nothing` (6N-C, unchanged) | Polled once and dropped during the yield, under every policy: the frame is still written, with no other traffic |
| **E** (new path) | `skipping_the_lead_strands_nothing_when_the_next_writer_is_cancelled` (all policies) | A's batch is written by someone else. C opens the next batch and yields. A resumes, finds its batch written, and does **not** write C's batch (checked under `no`/`everysec`). C is then cancelled, and its guard writes its batch. ### What the 6N-C4 runs found while building these tests

Test F, written first with the hot-key write at the same pipeline step in every client, made only about 2 frames per write on the real path. The cause was lock-step contention, not a defect. Each holder of the hot key's stripe yields with nothing able to join it, because every other client is waiting for that stripe. Those yields are now correctly misses, and they back off. Staggering the hot-key writes models a more realistic mix, and the test keeps the ≥ 2 frames per write bound. The serialized variant of Test C covers the worst case directly.
