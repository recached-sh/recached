# v0.6.0 Phase 6O-G1: two-phase `EXEC`

PR 2, `feat/v0.6o-g-two-phase-exec`. Design: Option E revision 5, milestones 2–4. Code: `server-native/src/transaction.rs` (new), `server_state.rs` (`on_transaction_logged`), `persistence.rs` (`append_frames`, `append_coalesced_frames`, `append_client_writes`), `connection.rs` (the TCP and WebSocket `EXEC` call sites).

"G2" in the brief's section 4 is this runtime split, not the separately gated 6O-G2 transaction framing, which was not started.

## The four stages

| Stage | What runs | Held |
|---|---|---|
| 0. Acquire and validate (unchanged, 6O-E) | Close and drain the unordered gate; `lock_transaction` (server stripes of every read, written and watched key; all of them on a capped store); the transaction instant `now`; overflow, WATCH and expired-WATCH checks; READONLY on a replica; MISCONF; WebSocket scope re-check | gate, server stripes |
| 1. Apply, synchronous | `KeyValueStore::apply_transaction(queue, now, …)`. Per queued write (`apply_queued_write`): the claimable-members check, the store call, the deadline read-back (only when frames are built here), the frame (`broadcast_for_at`, when anything observed writes as phase 1 began), the removal kind (`DEL`/`UNLINK`, or a `*STORE` that left its destination absent, read in scope), eviction's forgetting of claims, the ephemeral reconciliation. Reads run as before. `PUBLISH` is answered in phase 2 | + capacity gate (capped) and store stripes from the first queued write to the last |
| 2. Effects, asynchronous, command order | Frames still missing are built (pure: command, reply, instant, deadline). AOF: the transaction's frames, each command's eviction `DEL`s after it, appended as **one batch**. Replication: each frame in order. Then per command: WATCH/QSUB notifications (coalesced, `V0.6O-G-NOTIFICATION-CORRECTNESS.md`), its WebSocket push, its evictions' notifications and pushes (origin 0), `PUBLISH` delivery with its reply | gate, server stripes |
| 3. Release and reply (unchanged) | Unregister watches, drop the guards, write the reply (still gated on durability) | — |

One implementation serves both transports: the TCP and WebSocket `EXEC` arms both call `run_transaction_queue`.

## Synchronous/asynchronous boundary

- Phase 1 runs inside a synchronous closure. Neither the closure nor anything it calls can `await`: there is no await to hold a `std::sync` guard across. Review B confirmed that the spawned connection future still compiles as `Send`, and that no ephemeral mutex nests with a store stripe.
- The store hold (stripes, marks, capacity gate) is dropped inside `apply_transaction` at the last queued write. Phase 2 holds only the server stripes and the closed gate, which 6O-E already held across the same effects.
- A stalled `fdatasync` in phase 2 therefore holds back writers of the transaction's keys and all-write barriers, exactly as before 6O-G, and **no reader**.
- Phase 1 is CPU work. Its length is the queue's, not the disk's: measured as the stall in `V0.6O-G-PERFORMANCE.md`.

## Ordering

| Stream | Before 6O-G | Now |
|---|---|---|
| AOF | per command: frame, its eviction DELs | the same bytes in the same order, as one batch (`push_frames` inside one queue-lock hold, so the coalescer cannot split it) |
| Replication | per command, after its AOF append | each frame in the same order, after the batch |
| WATCH/QSUB | per command | per key, at its last effective write (below) |
| WebSocket pushes | per command | per command, same frames |
| Eviction DELs | after their command | after their command (AOF, replication, push, notification) |
| `PUBLISH` | at its position | at its position, between the effects of the writes around it |
| Ephemeral state | per command, after effects | per command, in phase 1, in the same relative order (eviction forget, then reconciliation) |

Review B's probes, now tests in `transaction_streams_6og.rs`, check the AOF bytes, the replication stream, the eviction placement, the pushes and `PUBLISH` against running the same commands one by one, for both fan-out modes, `always` and `no`, with and without a watcher, on a capped store that evicts.

## AOF behaviour and its limits

- **Format unchanged.** No `MULTI`/`EXEC` or BEGIN/COMMIT records: the bytes are the frames the commands produced before.
- **Policies unchanged.** `always`: the batch is written and `fdatasync`ed before anyone resumes; a failure is the existing fail-stop (exit 74). `everysec`/`no`: a failure latches persistence unhealthy.
- **No early acknowledgment.**
  - A TCP connection that gates its socket on the AOF defers the batch's wait to its reply (`append_client_writes`); it never sends a reply before the batch is written.
  - With a WebSocket client routed, a watcher present or replication on, the wait happens in phase 2 instead.
  - Test `no_exec_reply_precedes_its_aof_write`: all 301 frames are in the file when the reply arrives, over TCP deferred, TCP with a watcher, and WebSocket, inline and coalesced.
- **DEDUP is unaffected.** A DEDUP envelope queued in `MULTI` is refused by the store at `EXEC`, so it produces no frame.
- **Not crash atomicity.** One batch makes a torn transaction less likely, never impossible:
  - a process crash between the batch's `write(2)` calls, or one before the batch was written at all, loses a suffix;
  - under `everysec`/`no` a power loss can persist an arbitrary part of the page cache;
  - replay applies whatever prefix is present.

  Durable transaction atomicity needs the separately gated framing (§ follow-ups in `V0.6O-G-RELEASE-GATE.md`).

## Read-only and degenerate transactions

- A read-only `EXEC` takes no store stripe and no scope. It skips the WATCH fence (`watched_after_write`) and builds no frames (review B-4).
- A `PUBLISH`-only `EXEC` delivers in phase 2.
- The replica READONLY refusal and the MISCONF refusal are unchanged.

## Memory

- **Per write:** phase 1 keeps one record (indices, the frame when built, evicted keys) and one reply. No value is copied for notifications (N1). Test `many_appends_to_a_large_value_copy_it_once`: 1,000 `APPEND`s to a 1 MiB value with a full-value live query allocate less than two values more than with no subscriber.
- **Large transactions (review B-3, accepted and documented).** Until the batch is appended, the transaction's frames are held together. The AOF batch copies them into one buffer, and replication copies each frame. Peak memory for a large `EXEC` is therefore about three times its frames. Before, one frame lived at a time. The queue is capped at 10,000 commands, not by bytes. A byte cap on the queue is listed as a follow-up and was not introduced: it would change what clients can queue, which needs a maintainer decision.

## Deviations from the design

| Design | Implementation | Why |
|---|---|---|
| Frame captured in phase 1 | Built in phase 1 only when something observed writes as phase 1 began. Otherwise built in phase 2 if a consumer registered meanwhile | Keeps a plain cache's `EXEC` free of per-write allocations. `broadcast_for_at` is pure, and in a transaction the deadline fallback equals the store's deadline, since both use the transaction's instant |
| "`PUBLISH` moves to phase 2" | Done; its reply is filled in there | — |
