# v0.6.0 Phase 6O-G: release gate

**Verdict: PASS WITH CONDITIONS.** `MULTI`/`EXEC` writes are now atomic to ordinary readers on the primary, under the reviewed two-phase design: no synchronous lock is held across asynchronous I/O, and every earlier guarantee is kept. Two kinds of condition remain:
- **performance trade-offs** that are inherent or measured-and-explained, and need the maintainer's explicit acceptance (§3);
- the **durability and replica atomicity limits**, which are separately scoped (6O-G2 framing, not authorized).

No gate is BLOCKED.

## 5. Durability and replica atomicity: what remains

- **Crash atomicity:** not provided. The transaction's frames go to the AOF as one batch, so a process crash leaves all or none of a batch only if the write itself was not torn; a power loss under `everysec`/`no` can persist a non-prefix. Replay has no incomplete-block detection.
- **Replica atomicity:** not provided. Replicas apply the frames one by one; their readers can see part of a transaction.
- **Visibility before durability:** as before and as Redis: readers on the primary can see a transaction before it is durable; the client's reply is still durability-gated.

These need 6O-G2 framing (separate approval).

## 6. Follow-up design coordination

How the implemented runtime boundary meets the two future protocol workstreams. Nothing here is implemented.

### Transaction framing (6O-G2)

| Need (brief §16) | What 6O-G1 provides | What framing must add |
|---|---|---|
| AOF transaction grouping | Phase 2 appends exactly one batch per `EXEC`, in command order, each command's eviction `DEL`s after it, inside one queue-lock hold (`push_frames`) that the coalescer cannot split | Wrap the batch in a group record (`MULTI`/`EXEC` markers or one composite record) at that same point. The batch boundary already exists, so the change is the encoding, not the runtime |
| Detection of incomplete tails | — | Replay discards a trailing group without its end marker; `everysec`/`no` power-loss non-prefix remains |
| Replica grouping and atomic application | Frames reach replication after the batch, in the same order; the replica already applies through the store | Send the group as a unit behind `caps=txn`; the replica applies it with the same `apply_transaction` (its own stripes and marks), so replica readers get the same guarantee |
| Partial-resync boundaries, backlog trimming, forwarding | `reset_stream` after a divergent panic; sub-replica reset on full resync | Resume offsets, trimming and sub-replica forwarding must respect group boundaries (design R10) |
| Mixed versions | — | Without `caps=txn`, send frames ungrouped as today |

### Expiry Option E (logged expirations, `caps=expirylog`)

| Point | Ordering rule this milestone fixes |
|---|---|
| Sweeper `DEL`s vs a transaction | The sweeper takes the all-write barrier, which waits for any `EXEC` in progress. Its `DEL` records therefore land wholly before or wholly after a transaction's batch, never inside it. Framing can wrap the batch without special-casing the sweeper |
| A queued write that observes an expired key (E1) | It runs inside the transaction at the transaction's instant (`at_instant`). Its observed-expired `DEL` must go **inside the group**, immediately before that command's frame (the design's "with the frames of that queued command"), built in phase 1 or 2 like the command's own frame |
| Eviction `DEL`s | Already inside the batch, after the evicting command; framing keeps them in the group |
| Capability negotiation | `caps=txn` and `caps=expirylog` are independent; a replica may hold either. Rule: an `expirylog` `DEL` inside a group is applied as part of the group; without `caps=txn` the frames flow ungrouped in the same order |
| Format markers | Both need an AOF compatibility marker; they should share one versioned header decision rather than two independent markers |

## 7. Engineering assessment (brief §17)

1. **Is external transaction partial visibility fixed?** Yes, on the primary, for every read that goes through the store's stripe marks (GET, MGET, EXISTS, TYPE, STRLEN, borrowed reads, TCP and WebSocket). `KEYS`/`SCAN`/`DBSIZE` are the documented exception.
2. **Does the original F1 reproduction pass?** Yes: 10/10 failures on `25948a1`, a permanent ungated passing test now.
3. **How does `apply_transaction` establish atomic visibility?** Before the first queued write it takes (capacity gate if capped, then) every stripe its writes touch in ascending order, marks them `SEQ_ACTIVE | SEQ_MULTI` once all are held, runs every queued command at one instant inside a thread-local scope, and releases right after the last write: the writes become visible together.
4. **Which store stripes are marked?** The union of `mutation_scope` over the queued writes; all 256 for a whole-keyspace write (`FLUSHDB`) and for a capped store (with #180: only when the queue might evict).
5. **How are in-scope reads handled without deadlock?** A read inside the scope never waits for or locks a stripe: on the slow path (mark seen or validation failed) it reads directly. Sound because the server's phase 0 excludes every other writer of the transaction's keys.
6. **Are ordinary GET/MGET fast paths unchanged?** Yes: the scope check is only on the slow path; GET 1.000, MGET within noise.
7. **Does TCP EXEC match WebSocket EXEC?** Yes: one shared `run_transaction_queue`; parity tests.
8. **Are queued writes applied at one transaction clock?** Yes: `at_instant(now)` for every command (6O-E), now inside one hold.
9. **How are AOF frames handled?** Built per command (in phase 1 when anything observes writes, else in phase 2), appended in phase 2 as one batch in command order with each command's eviction `DEL`s after it; replies remain durability-gated.
10. **Are effects correctly ordered?** Yes: AOF batch, then replication in the same order, then per command its notifications, WebSocket push, eviction effects and `PUBLISH`; byte-for-byte tests.
11. **Can WATCH detect every effective write?** Yes: one notification per key at its last effective write, invalidating by the OR over its writes (a removal after a set counts as a set); 11 cases, mutants killed.
12. **Do delta clients converge?** Yes: a key written once keeps its delta; written more than once gets its full value; 14 convergence cases.
13. **Is notification memory bounded?** Yes: no per-write copy; at most one lazy value read per key per transaction; per-subscriber queues keep their existing bounds (natively: an 8 MiB value is still dropped by the 8 MiB queue bound, as before).
14. **How are panics contained?** `catch_unwind` per queued command inside the held scope; the queue stops; the repair runs under its own `catch_unwind`.
15. **What happens if a mutation is partially applied?** Metadata rebuilt from the keyspace (in place when possible); the prefix is replied to, logged, replicated and notified; the failing command errors, the rest are not run; persistence fails closed (`MISCONF` until `SAVE`).
16. **Can replicas safely recover after an incomplete mutation?** Yes: the run id rotates and the backlog is cleared under `EXEC`'s guards, so every replica, and recursively every sub-replica, takes a full synchronization of the actual keyspace; WebSocket sync clients are closed to resynchronise.
17. **Measured transaction throughput changes?** Small 1-worker `EXEC`s 0.93–0.97 on the release binary (read-only 0.94–0.97, at parity with aligned builds; set-set 0.956–0.962, code); heavier queues 0.97–1.01; 3-worker wide20 0.90–0.91; capped with room 0.88–0.91 (`dev`) / 0.985–0.991 (#180); at the cap 0.82–0.90; AOF and replica cells 0.94–1.02; 10,000-command transactions 1.05.
18. **Worst-case capped-store stall?** The apply time of the largest queue holding every stripe: ≈ 16 ms for 10,000 SETs on an evicting store (tx p50 15.4 ms; reader max 15.8 ms, below base's 16.8 ms); at 1,000 commands the reader max rose 2.9 → 4.3 ms. FLUSHDB of 100,000 keys: 11 ms. Observers lengthen the span (≈ 10 ms for 10,000 SETs uncapped with a replica). A single large collection command is bounded by its data, not its count, and was not measured.
19. **How much store-stripe contention?** 20-key transactions: −9–10% transaction throughput on 3 workers, readers unaffected. 100 keys: readers 0.80; 1,000+ keys: readers 0.47, reader p99 up to 20×; 99% (90% at 10,000) of those reader waits are stripe sharing rather than true key conflicts. Three concurrent large transactions: readers 0.10–0.15. Closed-loop p99 understates the exposure (D5).
20. **Are both AOF fan-out modes passing?** Yes: server suite under `inline` and `coalesced`; stream equality tests for both; native everysec cells in both (0.988, 0.970).
21. **Durability and replica atomicity limitations?** No crash atomicity (no AOF framing, no tail detection), no replica atomicity (frames applied one by one), visibility before durability as before; panics outside phase 1 not contained (P-1); C-6.
22. **What must happen before the v0.6.0 release?** The decisions D1–D5; a rerun of the AOF everysec stall cells off this rotational disk (the open maximum, G4); then the remaining v0.6.0 gates (§8): the expiry decision (Option E), MSET×10 and AOF P=1 performance gates, memory per key, M1 at P=16, and the release-candidate soak. Framing (6O-G2) only if crash/replica transaction atomicity is to be a v0.6.0 claim.
