## The small-transaction residual, explained

Small read-only and two-write transactions lost 3–5% natively. In process they cost the same as base. The brief requires such regressions to be explained, so three measurements were taken:

| Measurement | get-get | set-set |
|---|---|---|
| In process, store level (`exec_cost_6og`, ns/EXEC, median of 6) | 703 → 717 | 981 → 986 |
| In process, whole TCP connection (`exec_cost_conn_6og`, median of 9) | 3,066 → 3,073 | 3,250 → 3,354 |
| Native, release binaries (campaign 2): server CPU per transaction | +4.7% | +6.5% |
| Native, profiling builds (symbols and frame pointers, 3 alternating reps × 15 s, CPU 0): user instructions per transaction | 17,151 → 17,385 (+1.4%) | 17,896 → 18,623 (+4.1%) |
| Same: user cycles per transaction, throughput | 13,302 → 12,988; 112k → 113k tx/s | 14,714 → 14,692; 107k → 106k tx/s |

The sampled profiles (`raw/perf/c2-prof`, 134,900 samples per label and mode) put the extra work in `transaction::run_transaction_queue`: 3,463 samples against 1,465 in base's `connection::run_transaction_queue`. That is +1.5% of server user cycles for get-get, ≈ 330 cycles or about 80 ns per `EXEC`. By source line (`tools/prof_lines.py`):

| Where | get-get samples | What |
|---|---:|---|
| Function entry and return (`transaction.rs:284`, `:483`) | ≈ 1,100 | The larger async future: queue, replies, applied writes and the result move through its state |
| Observer checks (`watch.rs:648–649`, `sync_router.rs:664`, `server_state.rs:485` ×2) | ≈ 600 | Four shared atomic loads deciding whether phase 1 builds frames and whether phase 2 runs. They touch cache lines a read-only `EXEC` did not touch before, which accounts for the +24 L1D misses per transaction |
| Store bookkeeping (`store.rs:3461–3485`) | ≈ 400 | The `mutation_scope` scan for the span, per-command `catch_unwind` and `at_instant` |

For set-set the same three appear, plus the transaction hold (`order_keys` +133 cycles, `StripeHold` drops +142) and an allocation per writing `EXEC` (the `writes` vector grows from empty, `grow_one` +72).

On the profiling builds, total cycles and throughput are equal across the three reps, so the remaining 2–3% of the release-build gap was not attributable to code. Campaign 3 tested the layout explanation on the release sources (§campaign 3): the instruction delta is the same (+1.4% / +4.3%), the read-only gap disappears when both labels are rebuilt with 32-byte branch alignment, and the set-set gap does not.

**Avoidable part (estimated ≤ 1.5% of server CPU on small `EXEC`s), not implemented in this phase:**
- skip the four observer loads for a queue with no writes and no `PUBLISH`;
- pre-size `writes`;
- answer a read-only queue without entering the phase-2 future.

These are a follow-up PR if the maintainer wants them. They do not touch the reviewed atomicity boundary.

## Capped stores (`raw/perf/c2-capped`)

Labels: `base`, `g1` (= `dev`), `gcap` (= `dev` + #180). The "room" cells (`RECACHED_MAX_KEYS=200000`) never evict. The "at cap" cells (`90000`, on the 100,000-key set) sit at the key cap: 74,000–1.13 million evictions per cell, recorded. About 6% of writes evict (109,000 of 1.88 million in the 1-worker set-set cell); the others overwrite an existing key.

|---|---:|---:|---:|---:|---:|

| room, 3w set-set + 8 MGET readers | 19,315 | 0.891 | **0.991** | 0.980 / 0.999 | 1.035 / 1.003 |
| room, 3w wide20 + 8 readers | 15,308 | 0.912 | **0.985** | 0.885 / 0.987 | 1.137 / 1.021 |
| at cap, 1w set-set, 4 writers | 34,698 | 0.840 | 0.824 | — | — |
| at cap, 3w set-set + 8 readers | 19,097 | 0.896 | 0.885 | 0.978 / 0.973 | 1.040 / 1.046 |
| at cap, 3w wide20 + 8 readers | 12,901 | 0.901 | 0.894 | **0.782 / 0.783** | **1.426 / 1.430** |

- **With room**, #180 removes the capped cost. It is a design deviation awaiting sign-off (`V0.6O-G-ATOMICITY-IMPLEMENTATION.md`).
- **At the cap**, every writing transaction holds every stripe and the capacity gate for its whole apply, with or without #180. Writers lose 10–18% (1 worker: +21–23% server CPU per transaction, about 6 µs, consistent with taking, marking and releasing 256 stripes). Outside readers on 3 workers lose 22% beside wide transactions, and their p99 rises 43%. Base evicted 4–16% more keys only because it ran more writes.
- **Most of that is not inherent** (review D2-3). #180's fit check counts every `SET` as creating a key (`creating_key_count`), so at the key cap no writing queue fits. Yet about 90% of the keys exist: ≈ 81% of the set-set queues and ≈ 35% of the 10-command queues only overwrite, could not evict, and would hold only their own stripes under an exact count. Outside readers almost never read a key the transaction writes (P ≤ 2×10⁻⁴), so their loss here is stripe sharing, not a real conflict. Only a transaction that may actually evict needs every stripe: an eviction victim can be any key.
- **Two options** would move most at-cap cells toward the "room" ratios. Each is a further deviation like #180, and neither is implemented:
  1. Count new keys exactly under the exclusive gate: a key that is present, expired or not, is not created.
  2. Evict the queue's worst-case new keys before the span, under the gate, then hold only the queue's stripes.

  They are offered with decision D1 (`V0.6O-G-RELEASE-GATE.md`).

What this shows:
- **The worst stall is the apply time.** In these cells: 10,000 SETs apply in about 7 ms uncapped and about 16 ms at the cap, and FLUSHDB of 100,000 keys takes about 11 ms. Reader and writer maxima stay at or below base everywhere except FLUSHDB and TX_N=1,000 at the cap (4.3 ms). Base already stalled readers for as long, behind the same work on its worker threads.
- **The apply time is bounded by the queue's work, not its command count** (review D2-4). A single command on a large collection (`DEL` of a big set, `SUNIONSTORE`) applies for as long as its data takes, and with an observer (AOF, replica, watcher) phase 1 also builds the frames inside the span. Campaign 3 measures the observer cases and 3 concurrent large-transaction clients (§campaign 3). A large single collection command, and snapshots or the sweeper running during a stall, were not measured.
- **FLUSHDB** (review D2-7): readers must wait for an atomic flush, but most of the 11 ms is dropping 100,000 entries with every stripe marked. A standalone FLUSHDB does not hold readers that way. Swapping the maps under the hold and dropping the old ones after release would cut this stall to the swap. It is not implemented; it is listed as mitigation 4 below.
- **What changes is how often readers wait.** A reader whose key's stripe is held during the apply waits for the whole apply. A looping large transaction then halves outside reader throughput on 3 workers and multiplies reader p99 by up to 20× (37× for MGET×10 readers, which touch 10 stripes).
- **The closed-loop reader p99 understates exposure** (review D2-5). At TX_N ≥ 1,000, reader throughput 0.47 means readers spend about half of wall time blocked. A fixed-rate client would see p95 ≈ 4.4 ms and p99 ≈ the span (≈ 5–7 ms), against the closed-loop 1.6 ms. This is the reviewer's estimate; open-loop readers were not run. Decision D5 should read it this way.
- **A waiting reader blocks its worker thread** (review D2-6): readers wait in a `std::sync::Mutex` on the Tokio worker. While they wait, server CPU falls (2.03 → 1.53 CPUs at TX_N=1,000 and 10,000; 2.13 → 1.36 at the cap), so part of the throughput loss is parked workers rather than the stripe sharing itself. The split was not measured (it needs contention counters in a bench build). Before 6O-G, readers waited only for server stripes, asynchronously.
- **The transaction itself is faster** (tx p50 0.94–0.95 at 10,000): it no longer interleaves with readers.
- **1 worker: no change.** The apply was already exclusive there.
- **AOF `always`** (this host's rotational disk: about 100 ms per transaction, stands in for slow-fsync simulation): readers are unaffected (p99 47 → 47 µs) because phase 2's `fdatasync` holds no store stripe. Transaction and writer tails are dominated by the disk; the ratios over 3 reps (0.9–2.0) are noise at 9 tx/s.
- Nothing deadlocked or leaked a mark: 436 cells, every server alive, every reader and writer finished. The core tests check the marks.
- No new limit was introduced, and the 10,000-command queue limit is unchanged.

### Store-stripe contention, quantified

Readers and transactions draw keys uniformly from the same 100,000. During a transaction's apply, a reader waits if its key's stripe is held, so how often it waits depends on how many stripes the queue covers, and true conflicts are rare:

| Transaction keys | Stripes held (of 256) | P(reader's key is written) | P(reader's stripe held) | Waits that are stripe sharing |
|---:|---:|---:|---:|---:|
| 2 | 2 | 0.002% | 0.8% | 99.7% |
| 20 | 19 | 0.02% | 7.5% | 99.7% |
| 100 | 82 | 0.1% | 32% | 99.7% |
| 1,000 | 251 | 1% | 98% | 99% |
| 10,000 | 256 | 10% | 100% | 90% |

Measured effects:
- 20-key transactions (3w wide20): outside readers 1.03, p99 1.00, because a 7.5% stripe chance during a span of a few µs is negligible. Transactions and writers lose 9–10% to each other's stripes (0.897–0.914; writers 0.93).
- 100+ keys: reader throughput 0.80 at 100, 0.47 at 1,000 or more.

A larger stripe table would reduce the sharing for queues of up to a few hundred keys. It cannot help at 1,000 or more (4,096 stripes would still be 22% covered at 1,000 and 91% at 10,000). 6O-F measured that a larger table seriously penalises capped stores. **No stripe-count change is recommended from this milestone.** The default stays 256.

### Bounded mitigations, if the maintainer finds the large-transaction reader cost unacceptable

None of these is implemented. Each needs a design decision.

1. **Mark per key, not per stripe, for queues above a threshold.** Readers of unrelated keys never wait. Costs a key set lookup on the reader slow path. This is the only option that removes the false sharing at 1,000+ keys.
2. **A per-transaction write budget** (a byte or command cap on the queue). It bounds the apply time but changes what clients can queue: a compatibility decision. The brief forbids introducing it silently.
3. **Yielding reader waits** (park the task, not the worker). The tail is the same, but other connections on that worker keep running. On 3 workers that recovers part of the throughput loss (the parked-worker share, D2-6), not the p99.
4. **FLUSHDB: swap, then drop after release** (D2-7). This cuts the FLUSHDB stall from about 11 ms to the swap. It is an implementation change inside the reviewed boundary.

- **Read-only small `EXEC`s:** the change adds 1.4% user instructions per transaction and 6–8% more L1D misses (the observer loads, §residual). With aligned layout, throughput is at parity. The rest of the release build's 3–6% gap is front-end stalls in this binary's code layout (IPC 0.90–0.94×). It is real for the binary as built, which is what ships. But it is not a cost of the work the change does, and an unrelated code change can move it either way.
- **Two-write small `EXEC`s:** the 4% gap survives the layout change (0.961 in both builds). It matches the +4.3% instructions and 1.21–1.26× branch misses: a code cost (the transaction hold and the `writes` vector, §residual). The avoidable items above address part of it.

## Memory

| Measure | base | `gcap` |
|---|---|---|
| Peak RSS, uncapped tx cells | 24–61 MB | `gcap`/base 0.97–1.03 (median 1.002) |
| Peak RSS, TX_N=10,000 cells | 33–39 MB | +11–19% (34 → 39, 38 → 46 MB) |
| 10,000 APPENDs to one key in EXEC, TCP watcher + WebSocket QSUB, 8 MiB value (`g-mem.py`, 3 reps) | growth 0 | growth 0 |
| Same, 4 MiB value | growth 5.8–18.6 MB | growth 0–25.5 MB |

- **The TX_N=10,000 growth** is +4.6 MB (+13%) uncapped and +7.4 MB (+18%) at the cap. Current RSS at the end of the cell is also higher, so the allocator keeps some of it. It comes from the transaction's working set (review D2-10):
  - the queue is kept until `EXEC` ends, where base dropped each command as it ran;
  - the applied-writes vector grows by doubling from empty;
  - at the cap, an eviction `DEL` frame is built for every victim even when nothing observes it.

  That is about 500 bytes per command, an estimate from peak RSS, not an allocator measurement. It is bounded by the 10,000-command queue limit. The last two items are avoidable (pre-size the vector; build victim frames only when observed), in the same follow-up as the small-`EXEC` items.
- **8 MiB value:** the WebSocket subscriber is dropped in both builds. A full value of 8 MiB plus the appends exceeds the 8 MiB per-subscriber notification queue bound (`NOTIFICATION_QUEUE_BYTES`) — the existing bound working.
- **4 MiB value:**
  - base sends a full value per `APPEND`, so the subscriber's queue overflows at once ("notification queue overflowed");
  - `gcap` sends one coalesced full value per key per transaction, which was delivered (8,398,771 bytes received in one rep). The subscriber was then closed by the existing sync-mailbox lag rule ("lagged, missed mutations; closing so the client resynchronises"), because an unscoped sync client receives one push per queued command, 10,000 per `EXEC`.
  - Both builds end in the existing resync contract. Peak growth depends on how many 4 MiB copies were in flight when the client was cut off.
- **The coalescing bound** itself (at most one full value per key per transaction) is asserted in process by `transaction_atomicity_6og` (`request_path::bytes_allocated_in`).

## Limitations

- **Closed-loop readers** (review D M-5): a reader that waits issues no requests while it waits, so its p99 under-reports how often a fixed-rate client would see a stall. The reader-throughput ratio is the better signal of exposure.
- **Not measured:**
  - snapshots and the expiry sweeper running during a stall (the core tests cover their correctness);
  - Tokio worker utilization and queue depth (server CPU per cell is recorded instead);
  - cancellation: a synchronous apply cannot be cancelled, and the brief's concern, blocking across asynchronous I/O, does not arise (phase 1 has no await).
- **Slow fsync** is this host's rotational disk (AOF `always`), not a simulated delay.
- **`foreign_cpus`** is all busy CPU (including irq and softirq time) minus the server's, generator's and replica's on-CPU time. It therefore carries the kernel's network work and scales with throughput, and no cell was rejected on it (review D2-8). It serves as a paired check between labels, not as an absolute detector.
- 30-second cells were preferred by the brief; cells ran 20 s with 5 interleaved repetitions (3 for stalls), and every ratio is given with its range.
