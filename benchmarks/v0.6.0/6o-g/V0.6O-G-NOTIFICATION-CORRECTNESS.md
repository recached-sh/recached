# v0.6.0 Phase 6O-G3: notifications and synchronized clients

Code: `server-native/src/transaction.rs` (`NotificationPlan`, `distinct_keys`), `server-native/src/watch.rs` (`KeyChange::removed_after_set`), `server-native/src/propagation.rs` (`notify_flushdb_after`).

## Why coalescing is needed

In phase 2 every queued write has already been applied, and a notification reads its key's value lazily (`KeyChange::current`). Announcing each write separately, as before 6O-G, would send each one with the final value, or with the last write's delta. Revision 1 of the design did that, and review R2 showed it corrupts delta clients: `SET k a; APPEND k b` announced as `keydelta(append b)` gives `old + b`. Copying each value in phase 1 (revision 2) was unbounded (N1). Revision 5, implemented here, copies nothing.

## The rules

1. **Effective writes only (Q1).** A write counts exactly when it produced a frame (`broadcast_for_at` returned `Some`), today's notification condition. A failed `SET … NX`, a refused `RENAME` and a WRONGTYPE error do not count. A `*STORE` always produces a frame. An empty one onto an existing destination deletes it, a real change.
2. **The removal kind is fixed in phase 1.** `DEL`/`UNLINK` remove their keys. A `*STORE` removes its destination when the destination is absent after the command, checked with an in-scope read at the command. Eviction victims and `FLUSHDB` are removals by definition.
3. **Last write per key.** The plan walks the transaction's writes in order and records, per key, how many effective writes it had, the last one (command position, and whether as an eviction victim), and whether any of them **set** it:
   - every key a command names counts: each key of `MSET`, both of `RENAME`/`SMOVE`/`COPY`, a `*STORE`'s destination, each key once even if named twice;
   - an eviction victim counts at the command that evicted it, after that command's own keys;
   - an effective `FLUSHDB` ends every earlier key's run: they are announced by the flush (its per-watched-key removals and one sentinel per live-query pattern), and nothing earlier is notified. Keys written after the flush start afresh.
4. **One notification per key, at its last effective write.**

| Effective writes of the key | Last write | Announced as |
|---|---|---|
| 1 | a set | as before: the value read lazily, or the command's delta to `CLIENT DELTA ON` clients |
| 1 | a removal | a removal (nil) |
| ≥ 2 | a set | its **full value** (`keychange`), never a delta |
| ≥ 2 | a removal, after a set | a removal that **invalidates a WATCH** like the set did (`removed_after_set`) |
| ≥ 2 | a removal, no set | a removal |

5. **WATCH invalidation is the OR over the key's writes (P1).** A WATCH notification invalidates when the key was live at `WATCH` or the change is not a removal. A removal that ends a run containing a set counts as not a removal for that rule, so a watcher of an absent key is invalidated by `SET k a; DEL k`, as in Redis. Review round 4 of the design showed the OR reproduces the per-command semantics exactly; review B re-checked it against the code.
6. **The value read in phase 2** belongs right after the key's last write. No later queued write touches the key, by construction. Outside writers of it are excluded by the server stripes. The expiry sweeper takes the all-write barrier, which waits for `EXEC`. The value is read on the wall clock, as before (N5).
7. **Registration while `EXEC` runs (N4).** A watcher registering concurrently is handled by 6O-E's handshake: phase 2 calls `watched_after_write` once, after every write of the transaction. A registration either is seen there or reads the post-transaction state. At worst a watcher is over-notified, which is a spurious abort and safe.
8. **WebSocket pushes** carry each command's own frame, so they stay per command and in order. A connection that watches or live-queries every key of a push still gets the notification, not the push (`forwards_push`, unchanged).

## Cost

- The plan is built only when a watcher or live query exists.
- It is linear in the keys the transaction names: `distinct_keys` uses a set for commands of more than 8 keys. A pairwise check made one wide `DEL` take minutes (review B-1).
- No value is copied per write. A key written N times costs one lazy read, and only if a subscriber takes full values.

Mutants (`raw/mutation/`): notifying every write (S07), the last write's delta instead of the full value (S08), dropping the OR (S09), and counting non-effective writes (S09b) are all killed.

## Multi-tenant isolation, subscription authorization, overflow

None of these paths changed. The plan only decides **which** `KeyChange` each existing delivery path (`fan_out`, `deliver_to`, `notify_flushdb_after`) carries. Scope checks, per-connection budgets and overflow disconnects apply as before. Their suites (`multitenant`, `security_v06_regressions`, `watch_overflow_exec`, `sync_routing`, `sync_reliability`) pass on the final tree (`V0.6O-G-CORRECTNESS-TESTS.md`).
