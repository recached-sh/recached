# v0.6.0 Phase 6O-G1: the store transaction boundary (`apply_transaction`)

PR 1, `feat/v0.6o-g-store-transaction`. Design: `6o-f/V0.6O-F-TRANSACTION-ATOMICITY-DESIGN.md`, Option E revision 5, milestone 1. Code: `core-engine/src/store.rs` (search `apply_transaction`, `TX_SCOPE`, `TransactionHold`, `repair_after_panic`), tests `core-engine/src/store/transaction_tests.rs`, hooks `core-engine/src/store/write_pause.rs`.

## The API

```rust
pub fn apply_transaction<'q>(&self, queue: &'q [Command], now: u64,
                             each: impl FnMut(usize, &'q Command)) -> TransactionApplied
pub struct TransactionApplied { pub panicked: Option<usize>, pub diverged: bool, pub repaired: bool }
```

`each(i, cmd)` runs queued command `i` and whatever synchronous work the caller attaches to it (the server's reply, frame, deadline read-back and ephemeral bookkeeping), in queue order, every one inside `at_instant(now)`.

## How atomic visibility is established

1. **The stripe set** is computed inside core-engine from `mutation_scope`, the same classification every queued write's own `run_write` uses: the union of the writes' keys' stripes, or **every** stripe when the queue holds a whole-keyspace write (`FLUSHDB`) or the store enforces caps (an eviction may remove any key). There is no second, server-side classifier (R3).
2. **Before the first queued write** the thread takes, in this order: the capacity gate exclusively (capped stores only, R5), then the set's stripes in ascending order. Once all are held it marks each `SEQ_ACTIVE | SEQ_MULTI` — exactly how one MSET marks its keys in 6O-D.
3. **The write span** runs with a thread-local scope set. **After the last queued write** the hold drops: the scope is cleared first, then each stripe's marks are cleared and its version advanced, then the gate is released. That release is the instant the transaction becomes visible, all at once.
4. Reads before the first write and after the last run as ordinary reads; a read-only queue takes and marks nothing.

Readers see all or none by 6O-D's argument:
- a single-key reader of a marked stripe waits (`read_one_at`: spin, then the stripe lock the transaction holds to its end);
- a multi-key reader finds a stripe busy and retries, then locks (`read_many`);
- once any written key's new value is visible, every written stripe is released (new) or still marked (the reader waits), so one client's sequence of reads cannot see new-then-old.

The deadlock argument is the design's §4 #16: gate → stripes (ascending), all taken before the first write and nothing taken afterwards; inside the scope nothing waits on or takes a stripe or the gate.

## The thread-local scope

| | |
|---|---|
| Storage | `TX_SCOPE` (`ScopeState { store, capped, held: [u64; 4] }`) plus a one-word copy `TX_SCOPE_STORE` for the hot check |
| Lifetime | set by `hold_transaction`, restored by `TransactionHold::drop` on every exit path, unwinding included; synchronous only, so it cannot cross an `.await` or reach another task; per store (a second store on the same thread is unaffected) |
| `order_keys` / `order_all` | take nothing inside the scope. `assert!` (also in release builds, on the in-scope branch only) that every key is in the held set, or that all stripes are held for a whole-keyspace write: a violation becomes a contained panic, not a silent race (review A4) |
| `run_write_gated` | enforcement is the scope's decision; the gate is not taken again |
| `try_reserved_write` | refuses inside the scope (it would take the gate shared under the exclusive hold, N3) |
| `execute_reporting_ref_within_capacity` | decided under the scope's held gate |
| Eviction tick, capped expiry sweep | `assert!` not inside a scope: a panic instead of a self-deadlock |
| `read_one_at`, `read_many` | inside the scope never wait for or lock a stripe. The check sits only on the slow path — after a mark is seen or a validation failed — so an ordinary read pays nothing (N6) |

Why the read bypass is sound: the server's phase 0 (`lock_transaction` and the closed unordered gate) excludes every writer of every key the transaction reads or writes. The only mutations in flight belong to outside writers of unrelated keys, so an in-scope read of a key on a marked stripe reads a value only this thread changes. Locking an unheld stripe from inside the span would be an out-of-order acquisition, and is never done.

## The read fast path

`GET` and `MGET` are unchanged when no transaction is applying: the scope is consulted only where a reader would otherwise wait or retry. The write path gained one thread-local word read (`order_keys` and `run_write_gated`). Measured in `V0.6O-G-PERFORMANCE.md`.

## Panic containment (store side)

- `each(i)` runs under `catch_unwind` **inside** the hold, so nothing is released while it unwinds (R3, N2, P3). On a panic the queue stops: commands after it do not run.
- If the panicking command was a write (`diverged`, conservatively set even if it changed nothing yet), the store's metadata is rebuilt from the keyspace and collections it left empty are removed (`repair_after_panic`, P2):
  - **in place**, before anything is released, when every other stripe can be taken without waiting (`try_lock`, which cannot deadlock) — always for a capped store or a whole-keyspace queue, which hold them all already;
  - otherwise (another holder has one, rare) after releasing, by taking all stripes in order. Readers may see the part-applied command in between; the caller already treats the store as diverged.
- The repair is itself under `catch_unwind` (review C-4): a second panic, from the same corrupt value, reports `repaired: false` instead of unwinding out of `EXEC` before the server fails closed.

What the server does with `TransactionApplied` is in `V0.6O-G-PANIC-AND-RECOVERY.md`.

## Test hooks (test builds and the `test-hooks` feature only)

- `write_pause::after_transaction_write_of(store, key, readers_of)`: stops a transaction synchronously inside its span, after its queued write naming `key`, with its stripes held and marked; counts readers that wait (R11). The server's asynchronous `exec_pause` cannot stop inside a synchronous span.
- `transaction_fault::panic_during_mutation_of(key)`: a panic in the store call after the mutation, before its accounting (general and probed write paths).
- `transaction_fault::observe_repair(store, f)`: runs `f` inside the repair, to check what is held there.

## Deviations from the design

| Design | Implementation | Why |
|---|---|---|
| Rebuild "*k*'s touched keys" metadata | Rebuild all metadata from the keyspace | The size estimate is a store-wide counter adjusted by deltas; a part-applied command's delta is unknown, so only a full rebuild makes it exact. O(keys), on a bug-only path |
| "A `debug_assert!` in `order_keys`/`order_all`" | `assert!` on the in-scope branch | Review A4: in release a scope miss would be a silent unordered write; an assertion is a contained panic. It costs nothing outside a scope |
| Repair "before release" | In place when the rest of the stripes are free; else release, then rebuild | Taking the rest while holding some would be out of order (review A1) |
| "Every stripe for a capped store" (R7, §4) | Draft #180 only: every stripe unless the whole queue provably fits without eviction | Capped writing `EXEC` at 0.85–0.88× with every reader blocked per transaction; **needs maintainer sign-off**, not on `dev` |

## Performance follow-ups after PR 3

The first native campaign (`V0.6O-G-PERFORMANCE.md`) found writing `EXEC` at 0.91× and capped-store writing `EXEC` at 0.85× of `25948a1`. Two follow-ups:

| PR | State | Change | Design status |
|---|---|---|---|
| #179 `perf/v0.6o-g-exec-overhead` (`ce770d6`) | **merged** (`3601543`) | `hold_transaction` visits only the set bits of the held set, not all 256 stripes. Phase 2 is skipped entirely when nothing observes writes (no AOF or replication, no watcher or live query, no routed WebSocket, no eviction, no `PUBLISH`) | Within revision 5 (an implementation detail of stages 1–2) |
| #180 `perf/v0.6o-g-capped-fit` (`8a75116`) | **draft, not merged: awaits maintainer sign-off** | On a capped store, `hold_transaction` takes the capacity gate exclusively as before and, under it, `queue_fits_without_eviction` checks that the whole queue certainly fits (summed `growth_bound` of its writes keeps memory at or below the eviction threshold; over-counted creating keys stay within the key cap; no write is unbounded or whole-keyspace). A fitting queue holds and marks only its own stripes, as on an uncapped store; otherwise every stripe, as before | **Deviation** from revision 5 (§4 "Eviction: every stripe is held", R7). Proof obligations checked by review D (code reading and a 20,000-seed randomized probe); review D's D-1 to D-4 fixed in the same commit |

What #180 means for this report while it is a draft: on `dev`, a capped store's transaction holds every stripe (the table above at step 2 describes `dev`). With #180, the panic repair's contended fallback becomes reachable on a capped store; it keeps the capacity gate across `order_all` and the rebuild (D-1), so no eviction can race the rebuild. Tests: `capped_fit_tests.rs` (review D's probes: fitting queues never evict, refuse or touch other keys; the sum is checked, not each write; a contended repair keeps the gate).
