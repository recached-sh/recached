# v0.6.0 Phase 6O-G4: panic containment and convergence

PR 3, `fix/v0.6o-g-transaction-effects`, plus the store containment of PR 1. Design: Option E revision 5, "A panic inside phase 1 is contained per command" (R3, N2, P2, P3, Q2). No change outside the reviewed design was needed (review C: "Every fix stays inside the reviewed design. No change to the recovery protocol is needed").

## What can be left behind

A queued command panics, which is a server bug: the client-supplied-number overflow checks are the reachable ones, since release builds keep `overflow-checks = true`. `catch_unwind` cannot undo a mutation interrupted part-way: a `RENAME` between removing the source and writing the destination, an `MSET` after some pairs. And a mutation that completed may have no frame yet. Either way, the AOF and the replicas no longer describe the primary's keyspace.

## What happens

| Step | Where | Behaviour |
|---|---|---|
| Contain | store, `apply_transaction` | All of a queued command's phase-1 work runs under `catch_unwind` **inside** the held scope: the store call, claimable check, frame, reconciliation and eviction bookkeeping. Nothing is released while unwinding. The queue stops: later commands do not run |
| Repair | store, `repair_after_panic` | For a write (`diverged`): remove emptied collections and rebuild size, key count and the TTL and eviction indexes from the keyspace. In place, with every stripe held and the queue's marks kept, when the other stripes are free (always on a capped store). Otherwise right after releasing. The repair has its own `catch_unwind`: a second panic reports `repaired: false` and still fails closed (review C-4) |
| Reply | server | Commands before it: their replies. It: `ERR internal error executing the command; writes are disabled until SAVE succeeds` (for a read: without the second clause, N-1). The rest: `ERR command not executed: an earlier command of the transaction failed`. The connection keeps working |
| Effects of the prefix | server, phase 2 | Logged, replicated and notified like any `EXEC`'s. The reply stays durability-gated |
| Fail closed | `fail_closed` | Persistence latched unhealthy (`record_internal_failure`): client writes get `MISCONF` until `SAVE`. `SAVE` snapshots the actual keyspace under the all-write barrier, truncates the AOF and clears the latch. Error log with the command name and whether the metadata was rebuilt; metrics `recached_transaction_panics_total{command}` and `recached_persistence_errors_total{operation="transaction_panic"}` |
| Replicas | `converge` → `ReplHub::reset_stream` | A new replication run id, an emptied backlog, and every replica link closed, with `EXEC`'s guards still held, so no replica can attach in between. A reconnecting replica names the old run id and is sent a **full** synchronization of the keyspace as it is. Closing alone is not enough: a replica would resume partially with the old id (Q2). Clearing the backlog alone is not enough either: a replica fully caught up resumes with zero frames (review C N-2) |
| Sub-replicas | replica's `sync_from_primary` | A replica that takes a full synchronization resets its **own** stream the same way, under its barrier, so its sub-replicas follow in full, recursively. Before 6O-G a sub-replica resumed partially from the replica's backlog onto the replaced keyspace and kept keys the primary had deleted meanwhile (pre-existing, found by design review Q2, fixed here, test `a_replicas_full_resync_makes_its_sub_replicas_resync_in_full`) |
| WebSocket sync clients | `resynchronise_clients` | Every sync connection closed with the sync-gap code (4001), so each rebuilds its copy. Called right after the guards are released and **before** the reply is written, so a client that does not read, or has gone, cannot delay it (C-1, C-2). The connection that ran `EXEC` still sends its reply first, because the gap closes a connection at its next poll |
| Watchers, live queries | `converge` | The command's keys announced as their full values; for `FLUSHDB`, every watched key |
| Ephemeral maps | `ServerState` | A poisoned mutex is recovered, and its poison cleared, at every access. They used to stop tracking for good, and `SAVE` panicked on them (C-3) |

A release build never keeps accepting writes with unlogged state. After an injected panic, even one that hits the repair too, `SET` answers `MISCONF` (test `a_panic_in_the_repair_still_fails_closed`).

## Known limits

- **C-6:** the failing command's own effect on connection-scoped ownership is lost with the unwind. An `ESET` that panicked after its mutation leaves its key unclaimed: it is not removed when the owner disconnects. Its eviction victims' claims are not forgotten, so a later disconnect deletes an absent key. The keyspace itself stays consistent with what the primary serves. Documented in `fail_closed`.
- **Restart without `SAVE`:** the AOF lacks the part-applied command, so a restart reproduces the state before it, plus the applied prefix. That is the AOF's state and the copy that is durable. `MISCONF` keeps new writes from building on the difference.
- **Out of scope (P-1, pre-existing):** a panic in a non-transactional write or in phase 2 is not contained: no `MISCONF`, no reset. It was today's exposure before 6O-G and is recorded as a follow-up.
