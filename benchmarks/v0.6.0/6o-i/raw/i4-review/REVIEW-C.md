# Review C: Phase 6O-I PR 4 (atomic apply of transaction groups on capable replicas)

- Branch `feat/v0.6o-i-replica-atomic-apply`, PR 4 commit `6c4b89f` (on top of the PR 2 + PR 3 merges).
- Reviewer: independent (review C). I did not write this code.
- Scope: `apply_repl_group`, `parse_replicated`, `push_replicated`, the `apply_repl_frame` refactor, `tests/replica_atomicity_6oi.rs`. PR 3's `GroupAssembler`, both apply loops in `sync_from_primary`, and `fan_out_group` were read as context.

## Verdict: **APPROVED WITH CHANGES**

The atomicity core is sound. The replica takes the order stripes for every member, checks `still_following`, and runs one `apply_transaction` hold. That gives atomic publication, the same lock order as `EXEC`, correct expiry handling, and a contained panic. Nothing is logged or relayed before the apply succeeds.

The effects phase has a regression: **H1 must be fixed, with a test, before merge.** PR 4 announces WATCH/QSUB changes per member, but only after the whole group has applied. A delta subscriber of the replica ends up with a wrong value. PR 3's per-frame path did not have this bug, and the primary avoids it with `NotificationPlan`. I reproduced H1 with a failing test, and the same test passes on the PR 3 apply path. **M1 should be fixed in this PR**: a failed group leaves an applied prefix that nothing downstream ever learns of, if the node is promoted before its full sync. The H1 fix diff should be re-reviewed. The rest can be handled at the author's discretion.

## What I verified

1. **Atomic publication.** `apply_repl_group` parses and checks every member (DEDUP records and mark-only frames are refused) before anything is locked or applied. It then takes `lock_commands` for all members, runs `still_following`, and makes one `apply_transaction` call, so the members get one marked hold of their store stripes from the first write to the last. The reader rules (single-key readers wait; multi-key readers validate or wait) are 6O-G's own. I ran the PR's tests: 7/7 pass on 6c4b89f, and the full `recached-server` test binary passes (839 passed, 11 ignored) with the PR 4 path active. With the PR 3 per-member path swapped in, `readers_of_a_replica_wait_for_the_whole_group`, `a_replica_reader_never_sees_part_of_an_exec` (hundreds of part-applied MGETs, 3/3 runs), the AOF test, the relay test and the panic test all fail. The new tests therefore do test the new boundary. Ran the 6O-I, 6O-H and replication suites 5 times: no flakes. `KEYS`, `SCAN` and `DBSIZE` keep the documented 6O-G exception.
2. **Mutation scope and lock order.** The order stripes come from `ordering_key_refs` over write members. `FLUSHDB` (and anything without keys) takes every stripe. Expiry and eviction `DEL`s are ordinary members, so their keys are included. The store hold comes from `mutation_scope`. The replica store is a follower (`set_follower(true)` in `main.rs` and the test nodes), so `enforces_caps()` is false: no capacity gate, only the members' key stripes. Lock order: unordered gate, then order stripes (async), then store stripes (sync, never held across an `.await`), then AOF/stream/watch locks after the store hold is released. This is the same order as `EXEC` (`lock_transaction`, then `apply_transaction`). Promotion (`lock_all_writes`), checkpoints (`save_lock`, then the barrier), the full-sync install, QSUB snapshots and a sub-replica attach (the all-write barrier) all take the gate and then every stripe, so none of them can interleave with a held group, and none takes an order stripe while holding a store stripe. `still_following` runs after the stripes are taken, so a promotion either completes first (the group is refused, nothing applied, error kind `Other`, and the loop exits) or waits for the whole group and its effects.
3. **Expiry.** With `upstream_expirylog`, the whole `apply_transaction` (including `hold_transaction` and any `repair_after_panic`) runs inside `without_expiry`. DEL members are applied in place. `at_instant(clock_ms())` still fixes the clock for access times and relative deadlines. Without the flag, every member runs at one frozen instant. `upstream_expirylog` is set only under the full-sync barrier, and a partial resume requires the same `expirylog`/`txn` mode (`ReplResume`). Not tested without `expirylog1` (L1c).
4. **Cancellation.** See L3. At `lock_commands().await` nothing has been applied. After the apply, the effects are not cancellation-safe, but no production caller can drop the future. `fan_out_group`/`publish` is synchronous: it holds the stream lock once and assigns consecutive offsets, so it cannot be cut part-way.
5. **Panic.** `apply_transaction` catches the panic and stops. It repairs metadata for a write member. `record_internal_failure("replica_transaction")` runs only if `state.aof.is_some()`. The error is `InvalidData`, so `run_repl_client` clears the resume point and the next link is a full sync. That full sync's checkpoint sets `persistence_healthy` back to true (`checkpoint_locked_with`), and its install calls `reset_stream()` and `invalidate_all()`. The gap before that is M1.
6. **Failure.** After the first `Value::Error`, the closure skips the remaining members, and the error takes the same path as a panic. This is the same behaviour as the single-frame path's `InvalidData`.
7. **Readers while a group applies.** Readers of the group's keys block for the synchronous apply span only. The order stripes, held across the AOF `fsync`, block writers and barriers, never readers. See N2 for the cost.
8. **Downstream effects.** The AOF takes the group as one group (`append_transaction`/coalesced, `may_defer = false`), then `fan_out_group`, then per-member notifications and pushes, all under the order stripes. Nothing is relayed before the apply succeeds, and on failure nothing is logged or relayed. I found no double or lost relay apart from L3's unreachable cancellation. The AOF and relay frames are the push-normalized bytes, as in the single-frame path. DEDUP: a group with a DEDUP record is refused, which is correct because `on_transaction_logged` never wraps members and 6O-G refuses DEDUP inside `MULTI`. Ephemeral reconciliation is not needed: replicated writes never create claims, and the single-frame path does not reconcile either. The WATCH registry is notified per member after the whole group, and that is H1.
9. **`apply_repl_frame` refactor.** `push_replicated` is a verbatim move, including the per-key multi-key `DEL` from B-5, and is called with the normalized bytes as before. No behaviour change. The visibility changes in `replica_expirylog_6oh.rs` (`pub(super)`) are test-only.

## What I could not verify

- **M1** is reasoned, not run (it needs a three-node chain with a promotion in the window).
- **The borrowed TCP read path on a replica during a held group.** No harness exposes a replica's TCP listener in these tests. I rely on 6O-G's primary-side coverage of the same store code.
- **Groups with `txn1` and without `expirylog1`.** Reviewed by reading only.
- **Performance and the reader-stall cost.** Not measured; this is deferred to PR 6.
- **Clippy.** I did not run clippy on the branch. My copy carried a test-only toggle.
