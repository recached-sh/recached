## 2. Maintainer decisions

| # | Decision | Recommendation |
|---|---|---|
| D1 | The replica's group bound: 64 MiB charged and 524,288 frames; a full sync above it | accept: groups above 16 MiB already need a full sync with the default queue and backlog |
| D2 | A 6O-H build replays 6O-I `txn` files legacy (expiry evaluated), including the file a 6O-I `SAVE` leaves before a downgrade, until its own first checkpoint | accept: 6O-H is unreleased; the bit is what keeps a crash followed by a direct downgrade from losing acknowledged writes on re-upgrade |
| D3 | An abandoned group (another server appended after it) replays one by one | accept |
| D4 | A record holding a nested record refuses the start (any file) | accept: corruption refused, not applied; no release writes one (corpus) |
| D5 | Every tail cut is copied, best effort, to `<aof>.cut-<offset>-<ms>`; never removed by the server | accept |
| D6 | The measured framing cost (`V0.6O-I-PERFORMANCE.md`): grouped transactions under AOF two-write `everysec` transactions at 0.934× (HDD; 0.973× tmpfs; 0.893× coalesced), CPU +3.2–3.8%, +114 B and 2 records each, recovery +23%; replica readers wait for a group's application (3 workers: p99 0.71 / 2.98 ms and throughput −20% / −31% beside 1,000- / 10,000-write transactions; about 14 ms at most with default limits, estimated). Two extreme cells, both unexplained: 10,000-write transactions with 4 outside writers on 3 workers (0.925×, outside writers −23%, CPU +5.8%), and a replica with its own AOF under overload (one or two more full syncs per 20 s, not back in sync at the end of a run); replica memory +2.7–4.6 MiB primary RSS with a replica at the default backlog (+38 MiB at 256 MiB), replica unchanged; +22–45 MiB, unexplained, in the 10,000-write replicated cell | accept the AOF, recovery and reader costs: they are the price of the atomicity this phase adds, and the same trade-off 6O-G made on the primary. Do not accept the two extreme cells until they are measured and explained before v0.6.0: the 10,000-write cell over at least 120 s with i, to see whether the RSS plateaus and to separate the stream-lock hold; and a replica with AOF below saturation, to find its sustainable rate against base |
| D7 | Merge #200 | merge: review E approved it at `976574a`. It halves the framing's CPU cost (two-write `everysec`: +8.7% → +3.8% CPU, 0.91× → 0.934×) and brings the primary's RSS with a replica from +12–13 to +3–5 MiB. `785f042` adds only a test |

## 3. Final engineering assessment (brief §18)

| # | Question | Answer |
|---|---|---|
| 1 | Which AOF framing format was selected? | `TXN-BEGIN n` / `TXN-COMMIT n`: 6O-H control records (`RECACHED-CHECKPOINT <id>`) of the ignorable kinds `0x81`/`0x82`, payload the member count, around the 6O-G batch, unchanged; only in files whose `FORMAT` carries the must-understand `txn` bit (16) |
| 2 | Why is it compatible with 6O-H? | the same control-record family, kinds in 6O-H's ignorable range, a must-understand bit with 6O-H's meaning; `FORMAT` only at a file's head; arrays/pushes authorship kept; 6O-H replays a `txn` file legacy and appends pushes, which is exactly what makes a dangling group detectable |
| 3 | Can older binaries replay the files? | yes, all six tested (v0.4.0–6O-H): complete groups replay, markers are no-ops; an incomplete tail's prefix is applied (per-frame recovery, not crash atomicity) |
| 4 | Downgrade and re-upgrade? | `SAVE` first (unchanged procedure) truncates the groups away; re-upgrade needs no step. Without `SAVE`, after a crash, the re-upgrade replays an abandoned group one by one and loses nothing (v0.4.0 after a torn member: refused, never misapplied) |
| 5 | Can an incomplete transaction survive replay as a partial write? | no: an open group at the tail is discarded and cut; one another server appended after is replayed as that server did (the only case where it applies one by one, after a binary switch without `SAVE`) |
| 6 | Corrupt records vs torn tails? | only an open group or torn record at the very end, followed by nothing but this format's arrays, is a tail; anything followed by complete records is history: refused if malformed. A corrupted length mid-file is indistinguishable from a tail (pre-existing); every cut is now copied and logged |
| 7 | Are all fsync policies preserved? | yes: no change to `AofSync`, the batch `fdatasync` or the fail-stop; atomic recovery is not durability (crash-recovery report §3) |
| 8 | Are checkpoints transaction-consistent? | yes: a checkpoint holds the all-write barrier, which excludes `EXEC`'s phase 2 and a replica's group apply; a group is queued in one lock hold; `FORMAT(expirylog, txn)` goes in the truncation's batch |
| 9 | Which replication capability? | `txn1`, negotiated like `dedup1`/`expirylog1`: a 24-byte header at offset 0 before each group's first frame, only to replicas that accepted it |
| 10 | Do old replicas remain compatible? | yes: 6O-H, 6O-G, 6O-F and v0.5.2 replicas of a 6O-I primary link and converge (real processes); they apply frame by frame as before |
| 11 | Are capable replicas atomic to outside readers? | yes, through `KeyValueStore::apply_transaction` (the primary's boundary): readers block on a paused group; 0 part-applied reads in-process and across processes; `KEYS`/`SCAN`/`DBSIZE` keep 6O-G's exception |
| 12 | Are expiry DELs included correctly? | yes: they are group members in the primary's per-command order, applied timelessly with `expirylog1` |
| 13 | Are replication offsets group-aware? | yes: one offset per frame as before; a group's offsets are consecutive (one `fetch_add`); the resume point and ACKs advance only at group boundaries |
| 14 | Can partial resync begin inside a group? | no for a capable replica (rule 2; review D's worked example); a legacy replica may, as before |
| 15 | Backlog boundaries? | trimming unchanged (by bytes); a group's tail left at the front is never replayed as a fragment (rule 2, or the first frame missing → full sync) |
| 16 | Do sub-replicas converge after upstream recovery? | yes: a middle replica relays only what it applied, as one group; its full sync, its restart, or a failed group resets its stream so sub-replicas full-sync |
| 17 | Disconnect mid-transaction? | the buffered members are dropped; nothing applied or acknowledged; the replica resumes before the group (partial if retained, else full) |
| 18 | Promotion? | waits for a group being applied (all-write barrier); a partly received group is dropped; the promoted node's stream and its sub-replicas' capabilities continue |
| 19 | How are transaction buffers bounded? | replica: one group per link, 64 MiB charged (len + 128 per frame) and 524,288 frames, checked from the header; AOF replay: none (pass 1 holds a few integers); primary: unchanged |
| 20 | CPU, latency and RSS costs? | see D6 and `V0.6O-I-PERFORMANCE.md` §1. With #200: ordinary commands, non-grouped transactions and replication alone unchanged (CPU 0.98–1.02×); grouped `everysec` transactions CPU +2–4% and 0.934× throughput for two writes on this HDD (the excess is `write(2)`/`fdatasync` time); `always` unchanged; recovery +23% on grouped files; replica CPU +11% (2 writes) to −11% (100 writes); replica reader p99 = the group's apply time (≈0.35 µs per member); RSS +3–5 MiB with a replica |
| 21 | Are 6O-G and 6O-H guarantees preserved? | yes: their test suites pass unchanged (but for pinned ids/strings); primary atomicity, two-phase `EXEC`, panic convergence, logged expirations, timeless replay, `expirylog1` |
| 22 | Which limitations remain? | §4, and the performance limits in `V0.6O-I-PERFORMANCE.md` §9 |
| 23 | What remains before v0.6.0? | §5, and the maintainer decisions D1–D7 |

## 5. What remains before v0.6.0

- **Performance milestones:** MSET-A, MSET-B, Phase 6P, standalone AOF P=1, replicated M1 P=16, the remaining Redis targets.
