### 2.2 Attribution

For the large groups the extra server CPU per transaction is proportional to the members: +62 ns per member at 100 writes (98.2 → 104.4 µs), +48 ns at 1,000 (917 → 965 µs), +58 ns at 10,000 (8,970 → 9,548 µs). Much of it is the one-record check each member gets in every build (review A L6; §2.4 measures how much, with the check compiled out), which parsed every length with a window search and `str::parse`: four lengths per `SET` frame. For a 2-`SET` transaction (+0.6–0.7 µs) the rest is the two marker frames formatted per `EXEC` (two `u64`-to-decimal conversions, four allocations) and the `write(2)` of 114 more bytes. The ordinary write path does neither, which is why every non-grouped cell is flat.

## 6. Recovery time

`tools/replay_time.py` writes each workload's file with each binary (AOF `everysec`, the server on CPU 0), stops the server with SIGKILL, and then times restarts on copies of the file from spawn to the first `PONG`. The three workloads are 1,000,000 `SET`s (no transactions); `exec2`, 250,000 two-`SET` transactions; and `tail`, `exec2`'s file with an open group appended (a `TXN-BEGIN 2` and one member), which is the discard-and-cut path.

The first two runs ran each binary's restarts back to back (`raw/i5-perf/replay/replay-1.txt` and `replay-2-reversed.txt`, the second in the opposite order). Their times moved by up to 50% between runs, and the ordering decided the sign. The third run interleaves the restarts, alternating the order every rep for 11 reps, and its ratios are paired (`replay-3-interleaved.txt`):

## 7. Reader stalls

Review E H3: a capable replica now applies a group under `KeyValueStore::apply_transaction`, which holds the stripes of every key in the group, so readers of those stripes wait for the whole group. 6O-H applied the same writes frame by frame, so readers waited for one write at a time but could see a part-applied group. `tools/bench/i-stall2.sh` measures what that costs readers. The primary commits `TX_N`-write transactions (`txbench setn`, 2 clients, 25 s; TX_N = 1, which is never grouped, then 100, 1,000 and 10,000). Meanwhile `redis-benchmark GET` (c10 P1, 600,000 requests over the 100,000 prefilled keys) reads the replica, which runs 1 or 3 workers. ## 9. Limits of these measurements

- One host, an HDD, 6 CPUs; foreign load of up to about one CPU in some cells (recorded). Cells are interleaved and rotated, and the conclusions rest on effects larger than the paired per-rep spread, or on CPU per transaction, which foreign load moves less than throughput.
- `always` cells are fsync-bound on this disk: they show that framing adds no fsync, not its CPU cost.
- The 1,000- and 10,000-write cells have few transactions per run (12,000 and 1,200), so their throughput ratios are noisy; their CPU per transaction is the stable signal.
- In campaign 1 and the remeasure, the driver's AOF bytes read 57 (the `FORMAT` record only): the driver measured the file after a SIGTERM, whose shutdown save truncates it. From §2.4 on, the driver reads the server's own AOF counters before it stops the server; §3 measured the file on the running server.
- Two idle servers, left by a campaign run that stopped early, were alive (idle, holding about 60 MiB) during §4, §6's first two runs and §7; they were found and stopped before §5 and §6's interleaved run. The driver now stops its children on exit. Later attempts at B were also lost to port collisions, first with those servers and then with the kernel's ephemeral port range; only complete campaigns are reported.
- The replica-with-AOF cell (§5.2) is overloaded in both builds, so its full-sync counts depend on when in the 20 s the overflows happen; 3 reps.
- Not measured: ordinary `SET` at P=16; a replica's catch-up rate; groups near or above the 64 MiB bound (the design's ~450 MiB per link worst case remains an estimate); the stream-lock hold time per group; the 10,000-write cell with i and over 120 s; an SSD.
