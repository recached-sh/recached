## 1. What must hold

Three boundaries, one property each:

| Boundary | Property | Today |
|---|---|---|
| Primary runtime | A reader never sees part of an `EXEC` (6O-G) | holds |
| AOF recovery | Replay never applies part of an `EXEC`: all of its records or none | **fails**: 34 of 68 cut points inside an `EXEC`'s records replay a prefix (`raw/i0-baseline/`) |
| A capable replica | A reader of the replica never sees part of an `EXEC`, and replication offsets never resume inside one | **fails**: a replica reader saw 274 part-applied `MGET`s over 3 transactions |

Not changed: the 6O-G transaction engine, `fsync` policies, the 10,000-command queue limit, the replica read-ahead limits, the 256 stripes, the client protocol. **Atomic recovery is not durability**: framing decides *which* records replay together, never *whether* an acknowledged write survives a power loss (§3.7).

A transaction here is what 6O-G's phase 2 hands the AOF and replication as one unit: per queued write, in queue order, its observed-expiry `DEL`, its frame, its eviction `DEL`s (`V0.6O-H-TRANSACTION-INTEGRATION.md` §2).

## 2. The AOF encoding

### 2.1 The records

Both control records use the 6O-H family, `RECACHED-CHECKPOINT <id>` with `id = 0xEC00 << 48 | kind << 40 | layout << 32 | payload` (layout 1):

| Record | Kind | Payload | Id (n = 2) | Bytes |
|---|---|---|---|---|
| `FORMAT` | 1 | features: bit 0 `expirylog` (ignorable), **bit 16 `txn` (must-understand)** | `17005593296757653505` (`0xec00010100010001`) | 57 |
| `TXN-BEGIN` | `0x81` (ignorable range) | the group's member count `n`, `2 ≤ n ≤ u32::MAX` | `17005734034245943298` | 57 |
| `TXN-COMMIT` | `0x82` (ignorable range) | the same `n` | `17005735133757571074` | 57 |

A group is `TXN-BEGIN n`, then exactly `n` member records, then `TXN-COMMIT n`, all RESP2 arrays, all in one AOF batch.

### 2.2 What is grouped

| `EXEC` produced | Written |
|---|---|
| no record (read-only, `PUBLISH`-only, every write a no-op that found nothing expired) | nothing, as today |
| exactly one record (one effective write; or one observed-expiry `DEL` alone) | that record, ungrouped: a single record is already replayed whole or not at all (a torn record is cut, §3.5) |
| two or more records | a group around the 6O-G batch, **unchanged**: no record regenerated, reordered or re-encoded beyond 6O-H's authorship byte |

An `EXEC` whose writes produce no command frame but do produce an expiry `DEL` follows the same count rule: one `DEL` is ungrouped; a `DEL` plus anything else is grouped.

A transaction stopped by a panic (6O-G4) groups the records of its applied prefix, which is what its phase 2 logs today. The keyspace then holds the part-applied command too, which has no record; `MISCONF` until `SAVE` is unchanged (`V0.6O-G-PANIC-AND-RECOVERY.md`).

Single writes that emit several records outside `EXEC` (`[DEL][frame]`, a capped write's `[frame][eviction DEL…]`, the sweeper's chunks) are **not** grouped: they are not transactions, and their torn prefixes are already defined as harmless (6O-H design §6). This is unchanged.

### 2.3 Where groups are written: only in a `txn` file

The writer's file modes gain one bit. Groups are written **only** into a file that begins with `FORMAT` carrying the `txn` feature:

| Mode | Begins with | Records written as | Groups |
|---|---|---|---|
| `Empty` | — | — | — |
| `Timeless { txn: true }` | `FORMAT(expirylog, txn)` | arrays | **yes** |
| `Timeless { txn: false }` | `FORMAT(expirylog)` (a 6O-H file, upgraded) | arrays | no, until the next checkpoint |
| `Legacy` | anything else | pushes | no, until the next checkpoint |

A 6O-I node writes `FORMAT(expirylog, txn)` wherever 6O-H wrote `FORMAT(expirylog)`: a primary's new or emptied file at startup, every checkpoint's truncation batch, a replica's full-sync checkpoint when the stream is `expirylog`. The rule mirrors 6O-H's: **a file never gains a guarantee part-way**; an upgraded file keeps its mode until its first checkpoint (autosave, 900 s by default, or `SAVE`).

### 2.4 Why the `txn` bit is must-understand: authorship

The recovery algorithm (§3) must tell **its own torn tail** from **an older server's records appended after a dangling group** (a crash, then a different binary started directly on the file). Both look like `TXN-BEGIN n`, some members, and no `TXN-COMMIT`. Content cannot separate them; authorship can:

- Every record in a `txn` file is written by 6O-I as an array (`*N`).
- Every other server appends **pushes** (`>N`) into a `txn` file: released servers always write pushes (T4/T5c on v0.4.0–v0.5.2, `410235b`, `f9a364d`); the 6O-H build (`6068337`) does not understand bit 16, so it treats the file as legacy and writes pushes too (T5b/T5c). Without the bit it would have continued the file in arrays (6O-H design §2.2 rule 3), indistinguishable from group members.

So in a `txn` file, **a push inside an open group is proof that another server took over the file**, and **an incomplete group made only of arrays is this format's own torn tail**.

The cost of must-understand: a 6O-H build replays a `txn` file with expiry evaluated (legacy) instead of timelessly (T5b). 6O-H is unreleased; no released binary was ever able to replay timelessly, so released downgrades are unaffected (§5).

The record kinds stay **ignorable** (`0x80`–`0xFF`): a reader that does not know them (6O-H, in a non-`txn` file; every older release, everywhere) treats them as no-ops, which is the 6O-H definition ("a writer may omit them; records written without them stay valid"). They never end a timeless part.

### 2.5 Alternatives

| Alternative | Verdict |
|---|---|
| **A1: ignorable kinds, no feature bit** | Rejected. 6O-H (`6068337`) continues a timeless file in arrays (T5, 6O-H rule 3), so after a crash and a direct start of 6O-H, its appended arrays look like the dangling group's members: a later 6O-I would discard acknowledged writes (if fewer than `n` were appended) or refuse to start. The bit costs 6O-H only its timeless replay of such files |
| **A2: non-ignorable kinds** | Rejected. 6O-H ends the timeless part at the first unknown non-ignorable control record, i.e. at the first transaction: worse than A1 for 6O-H, no better for detection |
| A3: `TXN-BEGIN` with a byte length instead of a count | Rejected. Does not separate a torn tail from appended records either (both can be shorter than the length); the count is what the replication header and the member check need |
| A4: a sequence id in `TXN-BEGIN`/`TXN-COMMIT` | Rejected. A group is contiguous by construction (one queue-lock hold, §3.5), so matching ids add nothing a member count does not; the 32-bit payload holds one of the two |
| A5: a checksum (CRC32C of the members) in `TXN-COMMIT` | Rejected for revision 1. Crash atomicity needs truncation detection, which structure and count give. No other AOF record has an integrity check; a checksum on groups alone would invite a claim the file cannot make for its other records. Per-record integrity is a separate must-understand feature for a later milestone |
| A6: tagging each member (a prefix byte, a wrapper) | Rejected: changes the 6O-G frames, which the brief forbids, and old binaries refuse unknown record names (6O-H A5) |
| **B: one composite record** | Rejected. Every binary refuses to start on it (`ERR unknown command`, T8); a 10,000-command record exceeds `MAX_ARRAY_ELEMENTS` (1,000,000) with wide commands; it must be parsed whole in memory; a torn composite and a torn member are the same case anyway |
| **C: `MULTI`/`EXEC` records** | Rejected. Every binary refuses to start (`ERR EXEC without MULTI`, T7). Replaying them would also run the client transaction machinery (WATCH, queue limits, `EXECABORT`) inside recovery |
| A sidecar index | Not atomic with the AOF (6O-H §2.5) |

## 3. Recovery

### 3.1 Pass 1: classify every group

Pass 1 already reads the whole file (the checkpoint, the DEDUP marks, the timeless end). In a file whose first record is `FORMAT` with the `txn` bit, it also runs this state machine. In any other file, `TXN-*` records are ignorable unknown controls, as for 6O-H.

| State | Record at offset `o` | Result |
|---|---|---|
| Outside | `TXN-BEGIN n`, `n ≥ 2` | Inside(`begin = o`, `n`, `seen = 0`) |
| Outside | `TXN-BEGIN n`, `n < 2`; or `TXN-COMMIT` | **corrupt** |
| Outside | anything else | as 6O-H |
| Inside | an **array** command record, not a DEDUP record | `seen += 1`; `seen > n` → **corrupt** |
| Inside | `TXN-COMMIT m`, `m = n = seen` | complete; Outside |
| Inside | `TXN-COMMIT` otherwise; `TXN-BEGIN` (nested); an array checkpoint marker, `FORMAT` or other control record; a DEDUP record | **corrupt** |
| Inside | **any push** | **abandoned** (another server appended after the dangling group, §2.4); Outside; the push is then handled as 6O-H handles a push (it ends the timeless part) |
| Inside | a torn record, or the end of the file | **incomplete tail**: `discard_from = begin` |
| any | a group marker after the timeless part ended | **corrupt** (no conforming writer puts one there, §2.3) |

The state is a few integers: no buffering (pass 1 already holds the file in memory, as it always has).

### 3.2 What each outcome does

| Outcome | Replay | File |
|---|---|---|
| complete group | its members are applied, in order, in the file's mode | unchanged |
| **incomplete tail** | **none of it is applied** | cut back to `begin`, then `fsync`: the next session appends after the last complete record, never after a dangling `TXN-BEGIN`. A warning names the offset and how many members were found |
| abandoned group | its members are applied one by one, as the server that took over the file applied them (it served that state, and its later records were written against it); a warning says transaction atomicity was lost to a binary switch without `SAVE` | unchanged |
| corrupt | the server **refuses to start** (`InvalidData`, "AOF corrupted at offset …: <reason>"), as for any record that does not parse | unchanged |

Corrupt includes "a malformed group followed by valid-looking records": a stray or mismatched `TXN-COMMIT`, a count overrun, a nested `TXN-BEGIN`. Only the **tail** is ever discarded, and only when everything from its `TXN-BEGIN` to the end of the file is arrays (and at most one torn record). That is the line between a torn tail and history: a torn tail is the last thing this format's writer was writing; anything followed by complete records it did not write is history, and history is never silently dropped.

### 3.3 Pass 2

Pass 2 applies records from the replay start to `discard_from` (or the end), skipping every marker as today. Nothing runs concurrently with startup replay, so applying a complete group's members in order **is** atomic recovery: the recovered keyspace holds all of the group or (incomplete tail) none of it. No rollback is needed, since pass 1 decided before anything was applied. An error while applying a member (a record that fails) refuses the start, as today.

### 3.4 The snapshot and the replay start

The snapshot's checkpoint marker is never inside a group: a checkpoint holds the all-write barrier (`save_lock` and every replication-order stripe), `EXEC` holds its stripes through phase 2, and a group is queued in one queue-lock hold. A replay start inside a group is therefore corrupt. Groups before the replay start are in the snapshot and are only classified (an incomplete group cannot precede the snapshot's marker: it would not be the tail).

### 3.5 The writer never leaves a group open

| Event | Rule |
|---|---|
| Queueing | `TXN-BEGIN`, the members and `TXN-COMMIT` are pushed onto one batch under one queue-lock hold, so no other append can land among them (as 6O-G's batch) |
| A `write(2)` fails part-way (`cut_back`) | Today it keeps the whole frames that landed. It now keeps only whole frames **outside** an open group: the cut goes back to the `TXN-BEGIN` of a group whose `TXN-COMMIT` did not land. A cut that fails is retried before the next write (`torn_at`), unchanged; an unknown position still stops all appends until a truncation |
| Startup | the incomplete tail is cut off before the first append (§3.2) |
| Checkpoint | `FORMAT(expirylog, txn)` in the truncation's batch, under the same lock hold (6O-H R2-7b), unchanged otherwise |

### 3.6 Crash points

Every row was built from 6O-G's batch shape (`[BEGIN][DEL?][frame][evict…]…[COMMIT]`); the tests in PR 2 cut the file at every byte of a group.

| Crash or fault | File after restart | Replay |
|---|---|---|
| before `TXN-BEGIN` reaches the file | no group | none of it; the reply was not sent (6O-G gates replies on the batch) |
| `TXN-BEGIN` torn, or whole | incomplete tail | none; cut back to `begin` |
| after the first member, between members, before or during `TXN-COMMIT` | incomplete tail | none; cut back |
| right after `TXN-COMMIT` | complete group | all |
| `write(2)` fails (any policy) | the cut keeps only complete groups | none of the failed group; `always`: fail-stop (exit 74) before any reply, as today; `everysec`/`no`: persistence latched unhealthy, as today |
| `fdatasync` fails (`always`) | whatever the page cache held | fail-stop before any reply; on restart a complete group replays, an incomplete one does not |
| power loss, `everysec`/`no` | any prefix of the page cache | complete groups replay; an incomplete tail does not; zero-filled or garbage blocks inside the file are a parse error and refuse the start, as today |
| a member corrupted so it does not parse | — | refused, as today |
| a member corrupted so it parses as a different command | — | not detected (no checksum, §2.5), as for any record today |
| `*` flipped to `>` in a member | abandoned group, then a stray `TXN-COMMIT` | refused (corrupt) |

### 3.7 `fsync` policies: atomic recovery is not durability

| Policy | What framing adds | What it does not change |
|---|---|---|
| `always` | a group that `fsync` covered replays whole; one that it did not replays not at all | `fdatasync` per batch before the reply; fail-stop on any write or sync failure |
| `everysec` | an incomplete group is never replayed | up to about a second of acknowledged transactions can be lost on power loss; a lost transaction is lost whole |
| `no` | the same | the kernel decides when data reaches the disk |

## 4. Checkpoints and snapshots

Unchanged in mechanism (6O-H §4.3). The snapshot is taken under the all-write barrier, which no `EXEC` holds stripes across, so **it never contains part of a transaction**; its checkpoint id and the AOF truncation describe that same instant. The new file begins `FORMAT(expirylog, txn)` (57 bytes, as before). Every crash window of 6O-H §4.3 keeps its outcome, with "torn `FORMAT`" now including the `txn` bit.

### 5.1 Other servers reading a 6O-I file (real binaries, `raw/i1-compat/`)

| T1 complete group: starts, replays all, markers are no-ops | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| T2 incomplete tail group | **prefix applied** | prefix | prefix | prefix | prefix | prefix |
| T2b same with a torn member | prefix; torn tail left (0.4 limit) | prefix; torn record cut | same | same | same | same |
| T3 `SAVE`, write, `SIGKILL`, restart | ✓, group markers gone | ✓ | ✓ | ✓ | ✓ | ✓ |
| T4 appends after a dangling group | push | push | push | push | push | push |
| T5 `FORMAT(expirylog)` replay | legacy | legacy | legacy | legacy | legacy | **timeless** |
| T5b `FORMAT(expirylog, txn)` replay | legacy | legacy | legacy | legacy | legacy | **legacy** (must-understand) |
| T5c appends to a `txn` file as | push | push | push | push | push | **push** |
| T6 replay start: the snapshot's marker, not a group's | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| T7 option C `MULTI`/`EXEC` | refuses to start | refuses | refuses | refuses | refuses | refuses |
| T8 option B composite | refuses | refuses | refuses | refuses | refuses | refuses |
| T9 malformed group markers | no-ops | no-ops | no-ops | no-ops | no-ops | no-ops |

**Replaying frames one by one is not transaction crash atomicity.** Every older binary replays a complete group correctly, but applies the prefix of an incomplete one (T2): an older server gives the same recovery a file without framing gives.

### 5.2 6O-I reading other files

| File | Replay | Writes |
|---|---|---|
| no `FORMAT` (any release's) | legacy, as today | pushes, no groups, until the first checkpoint |
| `FORMAT(expirylog)` (6O-H) | timeless, as today; `TXN-*` records would be ignorable no-ops | arrays, no groups, until the first checkpoint |
| `FORMAT(expirylog, txn)` | timeless, groups as §3 | arrays, groups |
| a `txn` file with an unknown must-understand bit (a later server's) | legacy, as 6O-H rules; no groups recognized | pushes |

### 5.3 Downgrade and re-upgrade

| Path | Result |
|---|---|
| **Documented downgrade: `SAVE`, stop, start the older binary** | `SAVE` truncates every group away (T3); the older binary sees `FORMAT` and its own records only. Unchanged procedure |
| Downgrade, the older binary writes and crashes, re-upgrade | The file is the older binary's: legacy (or, for 6O-H, `FORMAT(expirylog)`), no groups. 6O-I replays it by its rules and writes no groups until its first checkpoint. **No re-upgrade step** |
| A 6O-I crash, then an older binary started directly on the file (outside the procedure) | The older binary applies the incomplete group's prefix (T2) and appends pushes (T4). On re-upgrade the group is **abandoned** (§3.2): replayed as the older binary did, with a warning. Transaction crash atomicity for that one group was lost when the older binary recovered it; nothing later is lost |
| The same with a 6O-H build | The same: 6O-H replays the `txn` file legacy and appends pushes (T5b/T5c) |
| Remedy for a refused start (corrupt group) | Start the binary that wrote the records after it and `SAVE`, or restore from the snapshot; as for any corrupt AOF today |

The re-upgrade evidence on the 6O-I binary (T4's files replayed by 6O-I: abandoned, not discarded) is PR 2's.

## 6. Replication: `caps=txn1`

### 6.1 Negotiation

As `dedup1` and `expirylog1` (6O-H design §8): the primary advertises `<run-id>;caps=dedup1,expirylog1,txn1`; a replica that understands it answers `accept=…,txn1`. Never inferred from a version. The run-id string grows by 5 bytes (28 of the 82 left after a 40-character run id). Older replicas split the list on `,` and look for their own tokens (6O-H review C verified 6O-F/6O-G/0.5 against a fake primary; PR 3 repeats it for `txn1`).

`txn1` is a **framing** capability, independent of `expirylog1`, which describes the stream's content. Every 6O-I node advertises `txn1` (a replica relays whatever groups it applies, §6.4):

| `expirylog1` | `txn1` | Behaviour |
|---|---|---|
| no | no | today's legacy stream |
| yes | no | logged expirations; frames ungrouped, applied one by one (6O-H) |
| no | yes | groups applied atomically, with expiry evaluated at one instant for the whole group (a 6O-I replica relaying for a pre-6O-H primary; a test hook for real groups) |
| yes | yes | groups applied atomically and timelessly |

### 6.2 The wire: one header per group, capable peers only

The frame format is unchanged (`offset u64 LE`, `len u32 LE`, `bytes`). Offsets start at 1, so **offset 0** never names a data frame. A primary sends, **only on a link whose replica accepted `txn1`**, a header right before a group's first frame:

```
offset = 0            u64 LE
len    = 24           u32 LE
payload:  version u8 = 1 | kind u8 = 1 (GROUP) | reserved u16 = 0
          count  u32 LE   (≥ 2)
          first  u64 LE   (the offset of the group's first frame)
          bytes  u64 LE   (the sum of the group's frame lengths)
```

The `count` frames follow with offsets `first … first + count − 1`, each an ordinary frame. Nothing marks the end: the group is complete when its last frame has arrived. Nothing else changes on the wire: no `FORMAT`, no `TXN-*` AOF record, and every frame is still a push (6O-H R2-1). A partial synchronization's `count` field counts data frames only; headers precede group starts among them. A legacy link carries no header.

A WebSocket or TCP client never sees a header: it exists only on the replication socket, after the authenticated handshake.

### 6.3 The primary

| Step | Rule |
|---|---|
| Offsets | `EXEC`'s phase 2 replicates a group with `fan_out_group`: one hold of the stream lock assigns its frames **consecutive offsets** and backlogs them (today each frame takes the lock separately, so another connection's frame could get an offset between them) |
| Backlog | each backlogged frame of a group carries its group's extent (`first`, `count`, `bytes`: 24 bytes per frame). Trimming is unchanged: by bytes, from the front |
| Live frames | per replica, as today (each frame charged and `try_send`; a full queue disconnects). A replica disconnected part-way through a group discards it (§6.4) |
| Sender | for a `txn1` replica, writes the header before a frame whose offset is its group's `first` |

### 6.4 The capable replica

```
Idle ──header(count, first, bytes)──▶ Assembling(group)
  ▲                                      │ frame (offset = next): buffer; sum lengths
  │                                      │ last frame: validate, apply (below)
  └──────────── applied, offset := first + count − 1 ◀──┘
Idle ──frame (offset = next)──▶ apply alone, as today
```

Validation, each failure a protocol error (`InvalidData`: the link ends, the resume point is cleared, the next connection is a **full** synchronization):
- the header's `len`, version, kind, reserved field; `count ≥ 2`; `first` = last committed offset + 1;
- a header while assembling (nested); a frame whose offset is not the next; a header on a link that did not negotiate `txn1` (today's "offset gap");
- `bytes`, charged as `bytes + 128 × count`, above the replica's group bound (§8); the frames' summed length differing from `bytes`;
- a member that is a DEDUP record (an `EXEC` never carries one: 6O-G refuses DEDUP inside `MULTI`).

Applying a complete group (the 6O-G boundary, reused):
1. Parse every member as today (normalize `*`, clamp a pre-6O-F deadline, refuse trailing bytes).
2. Take the replication-order stripes of all of them (`lock_commands`), then check the node still follows (`still_following`, which promotion's barrier excludes).
3. `KeyValueStore::apply_transaction(&commands, now, |_, cmd| execute_reporting_ref(cmd))`, inside `without_expiry` when the stream is `expirylog`. The store's mutation scope, stripe marks, in-scope reads and panic containment are 6O-G's own: no second locking implementation. A replica's store is a follower, so it holds only its keys' stripes (`enforces_caps` is false) and evicts nothing.
4. Effects, as on the primary and in member order: this node's AOF takes the group (a group in its own `txn` file), its sub-replicas get it through `fan_out_group`, then WATCH/QSUB notifications and sync pushes per member, as `apply_repl_frame` does per frame today.
5. The resume offset becomes `first + count − 1`; the acknowledgement follows the existing rule (when nothing more is buffered).

| Failure | Behaviour |
|---|---|
| link ends mid-group (EOF, reset, primary restart, queue-full disconnect) | the buffered members are dropped; nothing was applied or acknowledged; the resume offset is still `first − 1`; the next connection resumes there (partial if retained, else full) |
| malformed or oversized group | protocol error → full synchronization |
| promotion while assembling | the members are dropped with the link (`still_following` fails, or the link closes); the node is at its last committed boundary |
| shutdown while assembling | the same; nothing was applied |
| a member fails on the replica (it diverged), or panics | `apply_transaction` contains a panic and repairs metadata (6O-G4); the replica latches persistence unhealthy (`MISCONF` if promoted before a `SAVE` or the full sync's checkpoint) and ends the link with a protocol error → full synchronization, which also resets its sub-replicas (6O-G). **Readers can see the part-applied group until that full sync installs**: the store cannot undo a member that ran. This is an error path only (a replicated write that fails means the replica had already diverged), as on the primary in 6O-G4 |

Readers of a replica then see a group as readers of a primary see an `EXEC`: `GET`, `MGET`, `EXISTS`, `TYPE`, `STRLEN` and the borrowed TCP/WebSocket reads wait for or validate across the marked stripes. **`KEYS`, `SCAN` and `DBSIZE` keep their documented 6O-G exception.** Sync (WebSocket) clients of the replica receive one push per member, as clients of the primary do.

### 6.5 Expiry inside a group

The group's members are the primary's batch, so observed-expiry `DEL`s sit before the frame that observed them and eviction `DEL`s after the frame that caused them. With `expirylog1` the whole group applies inside `without_expiry`: no entry expires by the replica's clock while the group applies, absolute deadlines are applied as sent, and the replica runs no sweeper (6O-H). Without it, the group applies at one frozen instant (`apply_transaction`'s `at_instant`), so every member sees the same clock.

## 7. Offsets and resynchronization

### 7.1 Definitions (replica side)

| Term | Meaning |
|---|---|
| last received | the highest offset read from the link (may be inside a group) |
| last applied | the highest offset applied to the store: always a committed boundary, since a group applies whole |
| last committed boundary | `ReplResume::offset`: advanced only after a frame or a whole group is applied **and** its effects are queued |
| last acknowledged | what the replica last wrote to the primary: ≤ last committed boundary, never inside a group |
| resume point | the last committed boundary, sent in the next handshake |

Primary side: the **backlog retention boundary** is the oldest retained offset; a partial synchronization from `r` needs every offset `r + 1 …` current retained (unchanged).

### 7.2 Rules

1. A capable replica resumes and acknowledges only at committed boundaries (by construction, §6.4).
2. **The primary refuses a mid-group resume from a `txn1` replica.** If the first missing frame `r + 1` is a group member whose `first ≤ r`, it answers with a **full** synchronization (and counts it). A correct capable replica never asks for this; the check covers a replica that applied the stream before it negotiated `txn1`, and a bug.
3. A legacy replica may resume anywhere, as today: it never had group atomicity.
4. The full-sync boundary (the offset read under the all-write barrier in `handle_replica`) is never inside a group: the barrier excludes `EXEC`'s phase 2 and a replica's group apply, and `fan_out_group` assigns a group's offsets in one lock hold.

### 7.3 Backlog trimming

Trimming stays byte-based and may leave a group's tail at the front of the backlog. That is safe:
- a capable replica's resume point is `first − 1` or earlier (frame `first` is gone: full sync) or at/after the group's end (it never needs the fragment);
- a request for an offset inside the group is refused by rule 2.

**Worked example (required by review D).** Group G = offsets 101–103. A capable replica applied up to 100, received 101 and 102, and the link dropped. Its resume point is 100. The backlog was trimmed to begin at 102.
- It asks for 100: offset 101 is not retained → full synchronization.
- A buggy replica asks for 101: frame 102 is retained but belongs to G with `first = 101 ≤ 101` → rule 2 → full synchronization. Without rule 2 it would receive 102–103 alone and apply them as a fragment.
PR 5 carries both as deterministic tests.

### 7.4 Chains, promotion, restart

- **A → B → C.** B applies A's group atomically, **then** relays it with `fan_out_group` to C (as a group if C accepted `txn1`); B never forwards what it has not applied. If B's link to A drops mid-group, nothing of the group exists on B, so nothing reaches C.
- **B takes a full sync** (from A): B resets its own stream (6O-G: new run id, sub-replicas resync in full), unchanged.
- **B restarts**: its in-memory resume point is gone, so it full-syncs; it resets its stream on that full sync, so C resyncs in full. Unchanged.
- **B is promoted**: its stream, run id, backlog and each sub-replica's negotiated capabilities continue; a partially assembled group from A is dropped. Unchanged otherwise (6O-H's expiry rules apply).

## 8. Memory

| Where | Extra memory | Bound |
|---|---|---|
| AOF replay | none: pass 1 keeps a few integers; the file is already read whole (pre-existing) | — |
| AOF writer | two 57-byte records per grouped `EXEC`, in the batch 6O-G already builds | — |
| Primary backlog | 24 bytes of group extent per frame of a group | the backlog's own byte bound (frames' bytes), unchanged |
| Primary per-replica queue | none | unchanged (8 MiB default) |
| **Replica group buffer** | the frames of **one** group per link, from its header to its last frame, plus their parsed commands at apply time | **`REPL_GROUP_MAX_BYTES` = `MAX_REPL_FRAME_BYTES` (512 MiB)**, charged as `Σ (len + 128)` (the per-frame charge the primary's queue uses). Checked against the header before anything is buffered and again per frame |
| Replica read-ahead | none | unchanged: 64 MiB during install + 64 MiB while streaming |

The group bound reuses the largest payload a replication link already accepts (a snapshot or a single frame); it adds no client-visible limit. A transaction whose frames exceed it cannot be applied atomically by a replica: the replica refuses the group and takes a **full** synchronization instead, which carries the transaction's effects atomically (the snapshot is taken under the barrier). On a primary such a transaction already holds about three times its frames (6O-G review B-3), so 512 MiB of frames means at least 1.5 GiB there. Worst case per link: 128 MiB read-ahead + 512 MiB charged group + its parsed commands (about the same again). **Decision D1** asks the maintainer to accept this bound or choose a smaller one (64 MiB, the read-ahead's, would force a full sync for any transaction above 64 MiB of frames).

## 9. Security

| Threat | Why it cannot happen |
|---|---|
| A client forges `TXN-BEGIN`/`TXN-COMMIT` | `RECACHED-CHECKPOINT` is not a command (6O-H §7); every AOF record comes from `broadcast_for_at` or the server's own control frames |
| A client makes the server group, or ungroup, its writes | grouping is decided by the server from 6O-G's batch; no client input reaches it |
| A client sees a group header | headers exist only on the replication socket, after its password/TLS handshake |
| A primary (or an on-path attacker without TLS) sends malformed groups | every field is validated (§6.4); any failure ends the link and forces a full sync; memory is bounded before buffering |
| Resource exhaustion through a huge declared group | refused from the header alone (§8) |
| A crafted AOF | a malformed group refuses the start, as a malformed record does today; a forged incomplete tail can only make the replay drop that tail, which a truncated file does today |
