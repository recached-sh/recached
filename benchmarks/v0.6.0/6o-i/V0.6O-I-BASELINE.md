## 1. The two defects, reproduced

Both tests assert the property 6O-I provides; on `6068337` both fail (`raw/i0-baseline/repro-6068337.txt`, test source `raw/i0-baseline/transaction_framing_6oi.rs.txt`). They are carried into PR 2 and PR 4 as regression tests.

### 1.1 Problem A: a cut AOF replays part of an `EXEC`

`an_exec_cut_anywhere_in_its_records_replays_all_or_nothing`: a primary with an `always` AOF runs `SET acct:a old; SET acct:b old`, then `MULTI; SET acct:a new; SET acct:b new; EXEC`. The file is then cut at **every byte** of the transaction's records, and a node is booted on each cut.

| Cut | Result on `6068337` |
|---|---|
| inside the first `SET`'s record | torn record cut; neither applied |
| after the first `SET`, anywhere in the second | **`acct:a = new`, `acct:b = old`** |
| after both | both applied |

**34 of 68 cut points replay part of the transaction** (first: offset 159). Nothing in the file says the two records belong together.

### 1.2 Problem B: a replica reader sees part of an `EXEC`

`a_replica_reader_never_sees_part_of_an_exec`: a primary and a replica over the real replication handshake. The replica sleeps 100 ms after applying each frame (`test_apply_delay_us`, a replica slower than its link). A thread reads `MGET acct:a acct:b` from the replica's store while the primary commits three `MULTI; SET acct:a n; SET acct:b n; EXEC`.

**The reader saw 274 part-applied states**, e.g. `["1", "0"]`. The primary applies the transaction atomically (6O-G); the replica applies its frames one by one, each under its own stripes.

## 2. How the baseline frames a transaction

Verified against the code, not assumed:

| Piece | Behaviour at `6068337` |
|---|---|
| `KeyValueStore::apply_transaction` (`core-engine/src/store.rs`) | one hold of the union of the queue's write stripes (all of them on an enforcing capped store), marked `SEQ_MULTI`, released after the last write; panics contained, metadata repaired. Takes `&[Command]` up front: the mutation scope is computed before the first write. A follower store (`enforces_caps` is false) holds only its keys' stripes |
| `run_transaction_queue` (`server-native/src/transaction.rs`) | phase 2 builds, per queued write, `[expiry DEL][frame][eviction DEL…]`, hands them to `on_transaction_logged` |
| `on_transaction_logged` (`server_state.rs`) | AOF: one batch via `append_frames` / `append_coalesced_frames` / `append_client_writes` (`push_frames` under one queue-lock hold). Replication: **one `fan_out` per frame**, each taking the stream lock separately, so another writer's frame can take an offset between two of the transaction's |
| `AofBatch::push_frame` | 6O-H authorship: arrays in a timeless file, pushes otherwise |
| `cut_back` / `whole_frames_len` | a failed `write(2)` keeps every whole frame that landed (a transaction's prefix included) |
| `replay_aof_format` | pass 1: checkpoint, DEDUP marks, timeless end; pass 2: every record from the replay start; a torn tail is cut at the torn record |
| `FORMAT` control records | `RECACHED-CHECKPOINT <0xEC00…>`; kind 1 = `FORMAT` (bit 0 `expirylog`), kinds `0x80`–`0xFF` ignorable, others end the timeless part; must-understand features 16–31, none understood |
| `without_expiry` | thread-local; the replay and a capable replica apply inside it |
| Replica apply (`apply_repl_frame`) | per frame: `lock_commands` of that frame, `still_following`, `execute_reporting_ref` (inside `without_expiry` with `expirylog1`), `on_write` (AOF, then `fan_out` to sub-replicas), notifications, pushes |
| `ReplHub` | one offset per frame (from 1); backlog trimmed by bytes from the front; `resume_frames` needs every missing offset retained; `reset_stream` on a part-applied panic or a replica's full sync |
| Offsets and ACKs | the replica's `ReplResume::offset` advances per applied frame; it acknowledges the cumulative offset when its read queue is drained |
| Full and partial sync | the boundary is read under the all-write barrier; partial sync writes backlog frames directly to the socket; the replica checks every offset is the next |
| Read-ahead (6O-H #190) | 64 MiB while a full sync installs, 64 MiB queue of chunks while streaming: at most 128 MiB per link |
| DEDUP | refused inside `MULTI` at `EXEC` (6O-G); never in a transaction's frames |
| Ephemeral writes | phase 1 reconciliation; not affected by framing |

## 3. Thresholds kept

The v0.6.0 release thresholds and the 6O-G/6O-H accepted trade-offs are unchanged: the 10,000-command queue limit, no byte cap on transactions, large-transaction reader blocking (6O-G), `KEYS`/`SCAN`/`DBSIZE` outside the stripe boundary, the replica read-ahead limits, the 256 stripes, every `fsync` policy.

## 4. Performance baseline

The native performance baseline (`6068337` against the 6O-I build, interleaved, pinned) is taken in PR 6 with the binaries side by side, as in 6O-G/6O-H; this binary's hash is recorded above.
