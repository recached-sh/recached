# v0.6.0 Phase 6O-E3: large values and WATCH

| | |
|---|---|
| Branch | `fix/v0.6o-e-watch-overflow-payload` (on top of PR 3) |
| Verdict | **Fixed, within the existing notification design.** A TCP watcher's invalidation is now a per-connection flag, not a queued copy of the value. No new queue and no event-distribution change, so the stop-for-design clause (brief §5.5) did not apply |
| Severity before | Medium, pre-existing (6O-C #3). The client was disconnected instead of getting an aborted EXEC. Since #157 it could not commit |
| #157 | Preserved: EXEC still checks the overflow channel under its guards and disconnects without committing, for any connection that has one |

## 1. Before

A TCP `WATCH` registered a `WatchSubscriber`, the same type that serves WebSocket keychange pushes and live queries. Every change to the key built a `WatchNotif` carrying the key's **whole current value** and queued it. The connection was charged:
- the value's size against its 8 MiB notification budget;
- one slot of its 256-item queue.

A TCP client is never sent these notifications. The connection only turned their arrival into `watch_dirty`.

So a TCP connection was disconnected (`recached_notification_overflows_total`), not answered with an aborted EXEC, whenever either of these happened before EXEC:
- a watched key changed to a value over 8 MiB;
- a watched key changed more than 256 times (or changes accumulated past 8 MiB).

#157 made sure such a connection could not commit. It could not stay connected either.

## 2. After

`WatchSubscriber` carries two new fields:
- **`invalidated: Arc<AtomicBool>`**, shared by all of one connection's registrations;
- **`pushes: bool`**: false for a TCP WATCH (`cas_watch_channel`), true for every WebSocket watcher and live query (`notification_channel`, unchanged).

`notify(change)`:
1. Decides whether the change invalidates (6O-E2: everything except the removal of a key that was not live at WATCH). If it does, it sets `invalidated` (Release) **before anything else**.
2. With `pushes == false`, it returns there. Nothing is built, charged or queued, so nothing can overflow. The registration stays while the connection's receiver lives, and is dropped once the receiver is gone. That mirrors what a failed `try_send` used to do (test `registrations_of_gone_connections_are_released`).
3. Otherwise it continues as before: the delta or full value is charged against the budget and queued. Overflow still disconnects, because a WebSocket watcher or live query needs the payload.

EXEC (TCP and WebSocket), under its guards: `watch_dirty |= watch_subscriber.invalidated()`, next to the existing queue drain and the 6O-E2 expiry check.

The flag is cleared only where the watches were just unregistered (EXEC, DISCARD, UNWATCH of everything; 15 sites). Unregistering takes the registry lock that every notification holds, so no notification of an old watch can set the flag after the clear.

The TCP connection no longer polls a `watch_rx` arm in its `select!` (nothing arrives there). WATCH no longer arms the overflow arm either; SUBSCRIBE and PSUBSCRIBE still do.

## 3. Why no conflict can be missed

- **Ordering.** A write to a watched key notifies while it holds the key's replication-order stripe. EXEC reads the flag while holding the stripes of every watched key (`lock_transaction`). So either the write's notification is complete, with the flag already set, before EXEC holds the stripe, or the write starts after EXEC releases it.
- **Delivery.** The flag is set before any fallible step (budget, `try_send`), so nothing between the change and EXEC can lose it.
- **Bounds.** The flag is one bit per connection. The registry holds at most `max_watches_per_conn` registrations per connection, as before. A TCP watcher now holds **no** notification memory; before, a TCP watcher could hold up to 8 MiB.

## 4. What is unchanged

- **WebSocket watchers:** still pushed every change, with the payload and delta selection, the 256-item and 8 MiB limits, and overflow disconnecting. Their EXEC also reads the flag, so an overflow that drops a push still cannot let it commit. #157's channel check stays too.
- **Live queries (QSUB), pub/sub, WebSocket sync fan-out, replication:** untouched code paths. A live query registration has `pushes == true` and `live_at_watch == true`.
- **Subscription authorization:** unchanged. WATCH scope checks happen before registration.

## 5. Behaviour change, deliberately

`WATCH k`, a change to `k`, then `UNWATCH` and a transaction, all in one batch. The transaction now **commits**: nothing is watched at EXEC, and Redis's `UNWATCH` clears `CLIENT_DIRTY_CAS`. Before, the change overflowed and the connection was disconnected. The #157 test for this case was renamed and now asserts the commit (`watch_unwatch_in_one_batch_then_exec_commits_as_in_redis`). The 6O-B test that WATCH's overflow arming still disconnected in that batch now asserts that the connection stays (`a_large_change_within_one_watch_batch_keeps_the_connection`). Its subject, an overflow signalled within one batch, no longer arises for WATCH. SUBSCRIBE arming is still covered by the neighbouring tests.

### #157's tests, updated (`watch_overflow_exec.rs`)

Each one still asserts "no committed EXEC and the transaction's write not applied". The TCP cases now also assert that EXEC answered nil and the connection stayed open:
- one batch (9);
- an overflow from another writer, 8 rounds;
- several keys;
- the in-flight write while EXEC waits, deterministic;
- earlier replies of the batch.

The WebSocket cases are unchanged and pass: overflow before EXEC, pipelined messages after an overflow, and the two-tenant case (13). `concurrent_check_and_set_with_overflowing_values_loses_no_update` passes unchanged: no increment lost.

## 7. Costs

- **TCP WATCH:** a change costs a flag store, instead of building the value (one store read), measuring it, and an `Arc` and a channel send per notification. It is cheaper for writers of watched keys.
- **EXEC:** one atomic load.
- **WebSocket:** one atomic store per notification.
