## 1. What changed

### core-engine (`core-engine/src/store.rs`)

- **`ReadScope::Keyspace`.** `KEYS`, `SCAN` and `DBSIZE` move out of `Unkeyed`. The read protocol treats `Keyspace` like `Unkeyed`, so there is no behaviour change outside transactions.
- **`pub fn read_keys(&Command) -> ReadKeys`.** It exposes the exhaustive `read_scope` to the server. Its variants are `None`, `One`, `Many` and `Keyspace`.
- **`pub fn at_instant(now, f)` and `pub fn clock_ms()`.**
  - `now_ms()` reads a thread-local override first and the system clock otherwise.
  - The override covers only the synchronous `f`. It nests, and it is restored on return and on unwind.
  - It is per thread, so another task or thread never sees it (unit tests).

### server

- **`ReplHub::lock_transaction(queue, watched)`** (`replication.rs`) replaces `lock_commands_and_keys` at both EXEC sites.
  - It closes and drains the unordered gate, then takes, in ascending order, the stripes from `transaction_stripes`.
  - `transaction_stripes` builds a 256-bit set from, for every queued command, `ordering_key_refs` (write keys plus `*STORE`/COPY sources) and `read_keys`, then adds the watched keys.
  - It returns "every stripe" for `FLUSHDB`, `KEYS`, `SCAN` and `DBSIZE`, or once the set covers all 256.
  - A capped store still takes `lock_all_writes`.
- **`run_transaction_queue`** (`connection.rs`) is the one loop shared by the TCP and WebSocket EXEC.
  - Every queued read runs inside `at_instant(now, …)`.
  - Every queued write runs through `execute_locked_write_at(cmd, now, …)`. Its store call, its claimable-member check and its deadline readback for propagation run at the same instant.
  - The fallback deadline counts from `now`.
- **The instant `now`** is read once the guards are held, before the overflow and WATCH checks.
- **The guards are released** once the queue has run and the watches are unregistered, before the reply is serialised and written. This applies on both transports, for commit and abort. Every queued write has reached its AOF stage by then, as on the ordinary write path, where the guards also drop before the reply is flushed.

## 4. Locking behaviour, before and after

| | Before (`1f9232f`) | After |
|---|---|---|
| Read-only EXEC | Gate closed; **no stripe** | Gate closed; its read keys' stripes, ascending |
| Mixed EXEC | Gate closed; write keys + watched keys | + read keys |
| EXEC with KEYS/SCAN/DBSIZE | Gate closed; no stripe | Every stripe |
| Guards held while | the queue runs **and the reply is written** | the queue runs; released before the reply |
| Clock | Read per command, per key | One instant for the whole transaction |
| Ordinary commands | — | One thread-local load per clock read (`now_ms`) |

No change to the lock order, the AOF format, replication, DEDUP, defaults or the protocol.

## 5. Remaining, recorded

- **F1:** a transaction's writes are visible part-way to outside readers. High, pre-existing, documented, out of this brief.
- **Queued writes' WATCH and push fan-out** (`notify_write`) read the store on the wall clock. That code is asynchronous, so it cannot run inside `at_instant`. A key with a TTL shorter than the transaction's remaining duration can be pushed as nil to WebSocket peers, and a peer then applies the expiry early. Low.
- **Reviewer findings outside this change** (pre-existing):
  - AOF replay of `SET … KEEPTTL` onto an expired entry resurrects a persistent key (an INCR of an expiring counter replays as a persistent key);
  - Recached expires at `now >= deadline`, Redis at `now > deadline`;
  - on a capped store, a queued write can evict a key that a later queued command reads; Redis evicts once, before EXEC.

  All three are recorded in the release gate.
