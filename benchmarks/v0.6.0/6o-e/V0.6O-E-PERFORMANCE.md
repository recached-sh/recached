## 1. Ordinary commands: no regression

The only change outside transactions is one thread-local load per clock read (`now_ms`). Ordered writes also gain a SeqCst fence before checking for watchers.

## 2. Transactions

`txbench` sends each transaction as one pipelined write (`MULTI`, the queued commands, `EXEC`) and reads every reply. Values are 32 B, over 100,000 populated keys.

Notation in the tables below:
- **Clients and writers.** `cN` is N transaction clients; `+4w` adds 4 connections running `MSET` of 2 keys from the same key set.
- **Key sets.** `unrelated` is uniform over the 100,000 keys; `overlap` is 16 keys; `same` is 2 keys.
- **Ratios.** Medians of 3 interleaved reps against base; per-rep ratios are in `raw/bench/results-tx/summary.md`.

| 1 | GET, GET | c50 | 0.949 | **0.942** | 117,066 | 5.87 → 6.30 | 13,469 → 16,730 | 466 → 492 |
| 3 | GET, GET | c50 | 0.921 | **0.908** | 247,544 | 6.99 → 7.67 | 13,827 → 16,869 | 617 → 392 |
| 1 | MGET×10, GET | c50 | 0.879 | **0.874** | 78,878 | 8.77 → 10.30 | 26,853 → 35,712 | 632 → 717 |
| 3 | MGET×10, GET | c50 | 0.914 | **0.901** | 187,704 | 10.10 → 11.94 | 26,968 → 37,059 | 415 → 753 |
| 1 | EXISTS, GET | c50 | 0.936 | **0.958** | 114,648 | 6.14 → 6.56 | 14,270 → 17,534 | 477 → 496 |
| 3 | EXISTS, GET | c50 | 0.951 | **0.954** | 244,440 | 7.20 → 7.77 | 14,532 → 17,663 | 621 → 367 |

**What the cost is.** It is the isolation itself:
- one asynchronous stripe lock and release per distinct key (2 keys: +3,100 instructions per transaction; 11 keys: +8,900);
- the stripe set built from both classifications;
- one thread-local clock override per queued command.

The rest of the transaction path is unchanged: the gate already closed for every EXEC before 6O-E. Read-only transactions lose 3–13% of throughput, most with the MGET of 10 keys. Most of the per-key cost is the `tokio::sync::Mutex` acquire and release on stripes that are uncontended here.

### Mixed

| Workers | Transaction | Clients | e1 / base | fix / base | fix tx/s | user instr/tx base → fix | abort % base → fix |
|---|---|---|---:|---:|---:|---:|---:|
| 1 | GET, SET | c50 | 0.946 | **0.945** | 104,766 | 15,035 → 17,609 | — |
| 1 | MGET×10, MSET×10 | c50 | 0.899 | **0.898** | 51,594 | 57,706 → 65,322 | — |
| 1 | WATCH k, GET k / MULTI SET k EXEC | c50 | 0.987 | **0.974** | 56,367 | 25,602 → 27,577 | 1.09 → 3.02 |

**Abort rates.** They come from real conflicts in the workload, not from Recached: the generator's clients' key sequences collide.
- With one client, base and fix both abort 0 times.
- Redis 7.2.5 aborts 2.4–4.4% on the same generator and settings.
- Recached's rate rises with E2/E3 because more of each transaction's window counts. The CAS check now uses the transaction's instant, and a change counts even if its notification would not have been queued. That is still within Redis's range.

### Contention (3 workers, 50 transaction clients, 4 MSET writers)

| Key set | e1 / base | fix / base | writer MSET/s base → fix | p99 µs base → fix |
|---|---:|---:|---:|---:|
| `same` (2 keys) | 0.631 | **0.619** | 20,470 → 12,006 | 582 → 489 |
| `overlap` (16 keys) | 0.983 | **0.964** | 21,241 → 13,842 | 561 → 584 |
| `unrelated` (100,000 keys) | 0.847 | **0.822** | 16,196 → 10,642 | 639 → 786 |

- **`same`.** The base number is the defect's: transactions and writers on the same two keys ran concurrently, so transactions could return mixed states. Serialising them is what isolation means, and Redis serialises every command. This −38% is a correctness cost, accepted explicitly.
- **`unrelated`.** This is the trade-off to watch. Transactions on unrelated keys now hold back writers that hash to the same replication-order stripe. There are 256 stripes; 50 concurrent transactions of 2 keys hold up to 100 of them, so a 2-key writer often finds one taken. Writers lose 34% and transactions 18% (the per-rep spread is wide: 0.962, 0.817, 0.822). It is not a global lock: each wait lasts one transaction (its queued commands only, since the guards are released before the reply). But it is false sharing at stripe granularity.
- **Follow-up (not done here).** More stripes or per-key ordering would reduce it. More stripes make every all-write barrier (snapshot, sweeper, QSUB, replica cut) take proportionally more locks. That is a separate measurement and decision.

## 3. Gate E5 assessment

| Requirement | Result |
|---|---|
| No unexplained large regression in ordinary GET/MGET | **Met.** GET 1.000 at P=1 and 0.987 at P=16; MGET 1.000–1.021 |
| Transaction contention costs measured | **Met.** §2: −3 to −13% read-only uncontended, −38% hot keys (inherent), −18% unrelated keys with writers (stripe false sharing) |
| p99 changes measured | **Met.** Unchanged for commands. Transactions moved both ways: from −36% (GET+GET, 3 workers, 617 → 392 µs) to +81% (MGET×10+GET, 3 workers, 415 → 753 µs) |
| No unbounded memory | **Met.** RSS unchanged; TCP WATCH now holds no notification memory |
| No unnecessary global serialisation | **Met**, with the stripe-granularity trade-off recorded. Only KEYS/SCAN/DBSIZE/FLUSHDB inside a transaction take every stripe, as Redis runs them alone |

**Verdict: ACCEPTABLE.** The material cost is in transactions, and it is the cost of the isolation the release requires; it is stated here, not hidden.
