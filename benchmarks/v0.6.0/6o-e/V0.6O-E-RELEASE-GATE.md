## The fifteen questions

| # | Question | Answer |
|---|---|---|
| 1 | Was read-only EXEC isolation reproduced and fixed? | **Yes.** Five deterministic reproductions failed 10/10 on `1f9232f`, and the load test found 6 and 48 illegal EXECs per ~144k (Redis 0). All pass on the fix, and Test D checks linearizability under load |
| 2 | Which key scopes does EXEC now lock or validate? | Every key any queued command reads (`core_engine::store::read_keys`, exhaustive) or writes (`ordering_key_refs`, with `*STORE` and COPY sources), plus the watched keys. Every stripe for KEYS, SCAN, DBSIZE and FLUSHDB, or once the keys cover all 256. Capped stores: the all-write barrier, unchanged. An oracle test checks this against `sync_scopes::command_scope` for every catalog command |
| 3 | Are unordered writes correctly excluded throughout EXEC? | **Yes.** EXEC closes and drains the gate before taking stripes and holds it until its last command. A write that arrives meanwhile takes the ordered path and waits on its stripe. Proof obligations O1–O7 (design report); confirmed by the reviewer and by the gate-skipping mutant (killed) |
| 4 | Were any deadlocks or starvation cases found? | **No** deadlock: the lock order is unchanged, the stripes are deduplicated, and store stripes are synchronous-only. A descending-order mutant deadlocks and is killed. **One starvation-like defect was found and fixed**: EXEC held its guards while writing its reply, so a client that never read stalled writers of its keys (review round 1, High) |
| 5 | Are mixed read/write transactions correct? | **Yes**: they see their own writes and nobody else's (Test C), and the MULTI-of-SETs writer in Test D. Their writes are still visible part-way to readers outside the transaction: **F1**, below |
| 6 | Does WATCH now abort after lazy expiry? | **Yes**, as Redis 7.2.5 does: checked at EXEC, at the transaction's instant, for keys live at WATCH |
| 7 | Does large-value WATCH invalidation behave correctly? | **Yes.** A 9 MiB change, or 600 changes, aborts a TCP watcher's EXEC with nil. The connection stays and nothing is charged. A WebSocket watcher is pushed the change and, past its budget, disconnected as before; its EXEC can never commit |
| 8 | Is WATCH notification memory bounded? | **Yes.** A TCP watcher holds one flag per connection and its registrations (≤ `max_watches_per_conn`). WebSocket watchers keep the 256-item and 8 MiB bounds |
| 9 | Are subscriptions and WebSocket updates unaffected? | **Yes.** Pushes, deltas, QSUB, pub/sub and scope checks are unchanged; their tests pass. A WebSocket DEL keychange carries the same nil payload |
| 10 | Were AOF, replication and DEDUP guarantees preserved? | **Yes.** No change to frames, ordering or acknowledgement. The reply release keeps the AOF gate. Both fan-out modes pass |
| 11 | What performance changes did transaction isolation introduce? | Read-only EXEC uncontended: −3% (1 client) to −13% (MGET×10, 50 clients), +3,100 to +8,900 instructions per transaction. Hot keys: −38%, inherent. Unrelated keys with concurrent writers: −18%, writers −34%, from 256-stripe false sharing. Ordinary commands: none beyond GET P=16 −1.3% |
| 12 | Did the independent reviews approve the changes? | **Yes.** E1: 2 rounds (High, Medium and test gaps fixed). E2/E3: 3 rounds ending in APPROVE (a High and two Mediums fixed). `V0.6O-E-INDEPENDENT-REVIEW.md` |
| 13 | Are any High-severity correctness findings still open? | **One, outside this milestone: F1.** Readers outside a transaction can see its writes part-way: an `MGET` between two queued SETs answered `[new, old]`. Pre-existing, documented, the same class 6O-D fixed for MSET. Not in the 6O-E brief. It needs a design that holds the store's multi-step marks across the transaction's asynchronous persistence steps |
| 14 | What Redis compatibility differences remain? | F1. Queued writes' WebSocket pushes read the store on the wall clock (Low). ZADD NX/XX no-ops on a watched key abort where Redis commits (pre-existing, safe side). Expiry at exactly the deadline (`>=` vs Redis's `>`; nit). A capped store can evict between queued commands (Redis evicts once, before EXEC). AOF replay of an expiring counter can resurrect it (pre-existing; the frozen clock widens a replica-side window). KEYS/DBSIZE are not snapshots outside MULTI. UNWATCH with keys is a Recached extension |
| 15 | What is the recommended next milestone? | See below |

| Item | Severity | Status |

## Decisions requested from the maintainer

1. **F1.** Authorize a design for transaction atomicity to outside readers, or accept it as a documented v0.6.0 deviation.
2. **The transaction performance trade-off.**
   - Uncontended read-only EXEC: −3 to −13%.
   - Unrelated-key transactions against concurrent writers: −18%, writers −34%.
   - Accept it, or authorize a stripe-count or per-key ordering study.
3. **The AOF/replica counter-resurrection bug** (Medium, pre-existing): schedule it.
4. The MSET-A and MSET-B approvals still stand from 6O-D.

## Recommended next milestone

1. **F1 design** if v0.6.0 must give Redis's transaction atomicity. It is the last release-blocking correctness gap in the transaction area.
2. **The expiring-counter replay fix**: small, release-bound, a durability correctness issue.
3. Then, as decided: MSET-A and MSET-B (MSET ×10 is still 0.829×), Phase 6P (memory, SADD), the AOF P=1 work, Option A, and finally the release-candidate soak.

**STOP.** Phase 6O-E ends here. MSET-A, MSET-B, 6P, Option A, the AOF redesign and the release are not started.
