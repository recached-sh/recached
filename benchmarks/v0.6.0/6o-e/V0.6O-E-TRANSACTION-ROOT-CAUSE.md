# v0.6.0 Phase 6O-E0: transaction isolation, root cause

| | |
|---|---|
| Base | `dev` `1f9232f` (#164–#166 merged, CI 13/13 green) |
| Branch | `investigate/v0.6o-e-exec-isolation` |
| Verdict | **Reproduced, deterministically.** A transaction's queued commands are not isolated from other connections' writes, and they do not share one clock. 5 deterministic reproductions fail in 10 of 10 runs. The load test reproduces too |
| Severity | **High, pre-existing, release-blocking for v0.6.0** (gate E1). No data is lost and no final state is wrong. A transaction returns a combination of values that no single instant ever had |

Line references are to `1f9232f`.

## 1. The guarantee being broken

Redis runs `EXEC` as one step. No other client's command runs between two of a transaction's queued commands. Redis 7 also fixes the clock for the whole transaction: every queued command sees the time at which `EXEC` began. Verified on Redis 7.2.5:

```text
SET a v PX 100
MULTI · GET a · DEBUG SLEEP 0.2 · GET a · PTTL a · EXISTS a · EXEC
→ v · OK · v · 97 · 1          (and GET a after EXEC → nil)
```

Recached documents the deviation (`docs/server/commands.md`, "Concurrency model": "the reads a transaction queues are not isolated from other connections' writes: another command can land between two of them"). This phase treats it as a defect against the Redis guarantee, as the brief does.

## 2. The exact invalid history

```text
initial a = old, b = old

T1  MULTI · GET a · GET b · EXEC
      EXEC: lock_commands_and_keys(queue = [GET a, GET b], watched = ∅)
            closes the unordered gate; takes NO stripe (no queued write)
      GET a → old
                                           ← T1 is here
T2  MSET a new b new
      try_execute_unordered: gate closed → ordered path
      lock_write: stripes of a and b (free) → runs → OK
T1    GET b → new
    → EXEC answers [old, new]               ← no instant had a = old, b = new
```

The same happens with two separate SETs (`SET a new`, then `SET b new`): `[old, new]` is illegal because `b` became new only after `a` had. It also happens with the clock and no writer at all (`SET a v PX 150`, `MULTI GET a GET a PTTL a EXISTS a EXEC`, deadline passing after the first read): Recached answers `[v, nil, -2, 0]`, Redis `[v, v, >0, 1]`.

## 3. Call graph

### EXEC (TCP `connection.rs:794–930`, WebSocket `connection.rs:1968–2105`)

1. Refusals first: `EXECABORT` after a queuing error, `READONLY` on a replica with a queued write, `MISCONF` when persistence is unhealthy. WebSocket also re-checks scopes.
2. Guards:
   - capped store: `lock_all_writes()`, the gate closed and drained plus all 256 stripes;
   - otherwise: `lock_commands_and_keys(&queue, watched)` (`replication.rs:744`), which closes the gate (`UnorderedGate::close`, l. 287) and calls `lock_stripes` (l. 756).
3. `lock_stripes` collects stripes from `ordering_key_refs` (`propagation.rs:167`) **of queued writes only**: `if !is_write_command(command) { continue; }` (l. 771). It adds the watched keys, sorts, dedups, and locks in ascending order. A queued write with no key list (`FLUSHDB`) takes every stripe.
4. Under the guards: the overflow check (`overflow_rx.try_recv()`, l. 875), the WATCH check (drain `watch_rx`), then each queued command in order:
   - `PUBLISH` through the pub/sub hub;
   - writes through `execute_locked_write` (store write, then AOF, replication, WATCH and push fan-out, under the guards);
   - **reads through `execute_and_record(&store, qcmd)`** (l. 917), the store's read protocol (6O-D) with no server-side guard.
5. The guards drop when the arm ends: the gate reopens and the stripes are released.

### Writers, and what each takes

| Writer | Path | Takes |
|---|---|---|
| Client write, nothing observing order | `try_execute_unordered` (`propagation.rs:512`) / borrowed `try_execute_borrowed` (l. 567) → `enter_unordered` (l. 539) | An `UnorderedPass` through the open gate; no stripe |
| Client write, gate closed or a consumer present | `execute_ordered_write` (l. 366) → `lock_write` (`replication.rs:718`) | Its keys' stripes; the gate stays open |
| Capped store write that may evict | `lock_all_writes` (`propagation.rs:431`) | Gate closed and drained + every stripe |
| ESET/EADD | `lock_commands` | Gate closed + its stripes |
| Replica applying the primary's stream | `apply_repl_frame` → `lock_commands(&[cmd])` (`replication.rs:2268`, `2342`) | Gate closed + its stripes |
| Active expiry | `sweep_expired_tick` under `lock_all_writes` (`main.rs:974`) | Gate closed and drained + every stripe |
| Ephemeral release on disconnect | `lock_commands` / `lock_all_writes` (`propagation.rs:807`) | Gate closed + stripes |
| Snapshot load, replica full sync, restore | `lock_all_writes` (`replication.rs:1367`, `2026`; `server_state.rs:459`, `860`) | Everything |
| DEDUP outcome records | `lock_identity` (client-id stripe) | One stripe of a client id, not a key |
| Lazy expiry | none: reads mask expired entries and remove nothing | — |
| Eviction | inside a capped write, which holds every stripe | — |

## 4. Answers to the investigation questions

1. **Which writers take replication-order stripes?** Every ordered client write, every capped write, ESET/EADD, every replicated write, the sweeper, ephemeral release, and every whole-keyspace barrier (table above).
2. **Which use the unordered path?** A client write on an uncapped primary with no AOF, no replication stream or backlog, no push receiver, no WATCH or live query and no ephemeral claim, excluding DEDUP and ESET/EADD. The borrowed hot path uses the same gate.
3. **What happens to an unordered write already executing when EXEC closes the gate?** It runs to completion. `close()` increments `closed`, then waits until every in-flight slot reads 0.
4. **Does the gate closure wait for in-flight writes?** Yes. The handshake is Dekker-style, all `SeqCst`: a writer increments its slot and then reads `closed`; a closer increments `closed` and then reads the slots. One of them sees the other. A pass is held only across synchronous code, so the wait is bounded by one command.
5. **Are writes arriving after the closure guaranteed to use the ordered path?** Yes. `try_enter` returns `None` while `closed != 0`, and the write then runs `execute_ordered_write`'s ordered branch, which takes its keys' stripes through `lock_write`.
6. **Which stripes must EXEC hold for its whole sequence?** Those of every key any queued command reads or writes, plus the watched keys. Today it holds only the queued writes' keys (with their `*STORE` sources and COPY source) and the watched keys. **The queued reads' keys are missing.** That is the defect: with the gate closed, a write to a read key goes ordered, finds its stripe free, and runs.
7. **How are WATCH and write scopes combined?** As one sorted, deduplicated stripe list (`extra_keys`), taken before the dirty check. Watched keys are therefore already protected: a write naming a watched key waits for the EXEC. The test `a_watched_transaction_is_isolated_while_it_runs` passes on `dev` for that reason.
8. **Can expiration, eviction or replica application bypass the boundary?**
   - Active expiry: no, it takes every stripe.
   - Eviction: no, a write that may evict takes every stripe, and EXEC on a capped store takes every stripe too.
   - Replica application: no, `lock_commands` closes the gate and takes its keys' stripes.
   - **Lazy expiry: yes.** No lock is involved: a read decides "expired" from `now_ms()`, which every queued command reads afresh (`store.rs:30`, 111 call sites). A key whose deadline falls between two queued commands is live to the first and gone to the second. **Locks alone cannot fix this. The transaction needs one clock.**
   - **Whole-keyspace reads** (`KEYS`, `SCAN`, `DBSIZE`): `read_scope` classifies them `Unkeyed` (`store.rs:7554`), so they name no key at all. Inside EXEC they need every stripe.

## 5. Deterministic reproduction

Two test-only hooks, compiled only under `cfg(test)`:
- **`propagation::exec_pause`** stops an EXEC right after a queued command that names an armed key. The transaction still holds every guard it took. The hook waits on a semaphore that the test closes. Keys are unique per test, so parallel tests do not stop each other's transactions.
- **`ReplHub::stripe_waits`** counts takers that found their stripe held, per hub. A test then sees a writer **waiting** behind the transaction instead of inferring it from a timeout.

There are no sleeps, except one test that has to let a 150 ms PX deadline pass. Every other wait is a condition bounded at 20 s.

| Test (`server-native/src/tests/exec_isolation.rs`) | What it does | `1f9232f` |
|---|---|---|
| `two_queued_reads_never_straddle_an_unordered_mset` | Test A: `MULTI GET a GET b EXEC` stopped after `GET a`; another connection's `MSET a new b new`; nothing observing order | **FAIL**: `[old, new]`; the MSET answered while EXEC was stopped |
| `two_queued_reads_never_straddle_an_ordered_mset` | Test A with an unrelated WATCH held, so writes are ordered | **FAIL**: `[old, new]` |
| `two_queued_reads_see_a_state_two_sets_passed_through` | Test B: `SET a new`, then `SET b new`. Legal: `(old,old)`, `(new,old)`, `(new,new)` | **FAIL**: `(old, new)` |
| `a_mixed_transaction_sees_its_own_writes_and_no_one_elses` | Test C: `GET a · SET b mine · GET b · GET c`, with `MSET a new c new` | **FAIL**: `GET c` saw `new` |
| `every_queued_command_sees_the_clock_at_one_instant` | `SET a v PX 150`; `GET a · GET a · PTTL a · EXISTS a`; the deadline passes after the first read | **FAIL**: `[v, nil, -2, 0]` |

The 5 reproductions fail in **10 of 10 runs** (`raw/e0-reproduction/base-1f9232f-10runs.txt`). CI runs ignored server tests too (coverage and Load & Chaos use `--include-ignored`), so `#[ignore]` would not keep `dev` green. Instead each reproduction returns at once unless `RECACHED_REPRODUCE_6OE=1` is set, and the fix removes the gate. To reproduce: `RECACHED_REPRODUCE_6OE=1 cargo test -p recached exec_isolation`.

## 6. Why the obvious fix is only half of it

Adding the read keys to `lock_stripes` closes the writer gap, for these reasons:
- The gate is already closed by every EXEC, and its closure drains in-flight unordered writes (§4.3–4.4). So once EXEC holds the gate, no unordered write is running and none can start.
- Every other writer takes the stripes of the keys it writes (§3). So once EXEC also holds its read keys' stripes, no write to a key it reads can commit until it finishes.

It does not fix the clock. The boundary therefore has three parts:
1. **The gate**, closed and drained, as now.
2. **The stripes of every key the transaction reads or writes, plus its watched keys**, in ascending order as now. A whole-keyspace read takes every stripe.
3. **One clock instant**, taken once the guards are held, for every queued command's store execution.
