# v0.6.0 Phase 6O-E1: transaction isolation, design

| | |
|---|---|
| Base | `dev` `1f9232f` |
| Root cause | `V0.6O-E-TRANSACTION-ROOT-CAUSE.md` |
| Selected | **Option A, extended**: EXEC's existing guards also cover every key its queued commands read, and every queued command runs at one clock instant |
| Not selected | Option B (a store-level transaction boundary), Option C (a new combined barrier): not needed, since A covers every writer (§4), and B cannot be held across EXEC's awaits |

## 1. What has to hold

From EXEC's first queued command to its last, two conditions hold:
- **No other write commits to any key the transaction reads, writes or watches.**
- **Every queued command evaluates expiry at the same instant**, the one at which the transaction's guards were complete.

Given both, the transaction's answers are those of a one-step execution at that instant (§5).

## 2. Options

### Option A: extend EXEC's stripe coverage (selected)

EXEC already closes and drains the unordered gate and takes, in ascending order, the stripes of its queued writes (`ordering_key_refs`, with `*STORE` sources and COPY's source) and its watched keys. Option A adds the **keys of its queued reads** to that same sorted list. A whole-keyspace read (`KEYS`, `SCAN`, `DBSIZE`) takes every stripe, as a queued `FLUSHDB` already does.

- Lock order unchanged: gate → stripes ascending → (store) stripes → shard → index.
- Same execution path, same WATCH check, same persistence barriers.
- A read-only transaction still appends nothing to the AOF or the replication stream.

### Option B: a store-level read boundary (rejected)

The idea is to hold the store's own write-order stripes (6O-D's `StripeHold`) for the whole transaction. Rejected:
- **Not holdable across awaits.** Those locks are `std::sync::Mutex`, and EXEC awaits inside the transaction (AOF append, `fsync` under `always`, replication fan-out, WATCH notification). A guard held across them would block a worker thread for an `fsync`. `MutexGuard` is not `Send`, so the connection future would stop compiling.
- **Recursive.** Every queued write re-enters the store, which takes the same stripes. Holding them would mean a re-entrant protocol or a "held by this transaction" bypass in `run_write_gated`: a new transaction engine, which the brief excludes.
- **Not needed** for isolation from writers (§4).

It would be the only way to also give F1 (outside readers seeing a transaction's writes part-way). That is out of scope and needs its own design.

### Option C: a minimal combined barrier (not needed)

The question was whether some writer bypasses the replication-order stripes. §4 shows none does once the gate is closed, and the only lock-free effect, lazy expiry, is handled by the clock (§3.3). No new barrier is added.

## 3. The change

### 3.1 Classification: `core_engine::store::read_keys`

`read_scope` (6O-D) is the store's **exhaustive** classification of read-only commands: every `Command` variant is listed, with no wildcard. It now distinguishes:

| `ReadScope` | Commands | Read-side protocol (unchanged) | Transaction scope |
|---|---|---|---|
| `One(key)` | GET, STRLEN, GETRANGE, GETEX (no option), TTL, PTTL, EXPIRETIME, PEXPIRETIME, TYPE, MEMORY USAGE, HGET, HSTRLEN, HGETALL, HKEYS, HVALS, HLEN, HEXISTS, HMGET, HSCAN, LRANGE, LLEN, LINDEX, SMEMBERS, SCARD, SISMEMBER, SMISMEMBER, SRANDMEMBER, SSCAN, ZRANGE, ZREVRANGE, ZRANGEBYSCORE, ZREVRANGEBYSCORE, ZSCORE, ZMSCORE, ZRANK, ZREVRANK, ZCARD, ZCOUNT, ZSCAN, JGET | `read_one` | its key |
| `Many(keys)` | MGET, EXISTS, SINTER, SUNION, SDIFF | `read_many` | every key |
| **`Keyspace`** (new; was `Unkeyed`) | KEYS, SCAN, DBSIZE | none, as before | **every stripe** |
| `Unkeyed` | connection-level commands (PING, ECHO, INFO, CONFIG, CLIENT, …), PUBLISH, DEDUP envelopes, and the writes, which never reach the read path | none | nothing |

A public `read_keys(&Command) -> ReadKeys` exposes it to the server. Because `read_scope` stays exhaustive, a new command does not compile until it is classified.

### 3.2 `ReplHub::lock_transaction(queue, watched)`

This replaces `lock_commands_and_keys` at both EXEC sites (TCP and WebSocket). For every queued command, **whatever `is_write_command` says**, it takes the union of:
- `ordering_key_refs(cmd)`: the write keys, `*STORE` sources and COPY source. `None` (FLUSHDB) means every stripe;
- `read_keys(cmd)`: the read keys. `Keyspace` means every stripe;
- the watched keys.

Taking the union, rather than one or the other by `is_write_command`, means a command classified differently by the server and the store still has its keys covered.

The gate is closed and drained first, the stripes are sorted and deduplicated, and they are taken in ascending order. On a capped store EXEC still takes `lock_all_writes`, unchanged. `lock_stripes` and every other caller are unchanged.

**Oracle test.** `sync_scopes::command_scope` is a second, independently written and exhaustive classification of every command's keys (the strict-mode scope check). The test parses one sample of every command verb and checks that the transaction's stripes cover every key `command_scope` names, or are all stripes.

### 3.3 One clock per transaction

`core_engine::store::at_instant(now_ms, f)` runs `f` with the store's clock (`now_ms()`) reading `now_ms`. It is a thread-local override with a drop guard: it restores the previous value on return and on unwind, and it nests. `now_ms()` checks the override first, which costs one thread-local load per call.

EXEC reads the clock once its guards are held. It then runs every queued command's synchronous store call inside `at_instant`:
- reads through `execute_and_record`;
- writes through a variant of `execute_locked_write` that takes the instant down to its one synchronous `execute_and_record_ref`.

The override never spans an `await`. Each store call is synchronous, so no other task can run on that thread while the override is set, and the transaction itself may move between workers between commands. Writes inside the transaction compute relative deadlines (`SET k v PX n`) from the same instant, as Redis does.

### 3.4 The EXEC loop

The TCP and WebSocket loops run identical queued-command code. They now share `run_transaction_queue(queue, now, …)`, so the clock, the hook and future changes cannot diverge between the transports. Command order is preserved.

## 4. Why every conflicting writer is excluded (proof obligations)

**O1. Every writer is in one of four classes.** See the root cause's table. Each one either:
- (a) runs inside an `UnorderedPass`, with no stripe;
- (b) holds the stripes of every key it writes (and, for `*STORE`/COPY, the keys it reads) across its store mutation;
- (c) holds every stripe;
- (d) writes no key (a DEDUP outcome record, under a client-id stripe).

No other path mutates the keyspace while the server runs. Lazy expiry mutates nothing: reads mask expired entries.

**O2. Class (a) is excluded.** EXEC calls `UnorderedGate::close()` before taking any stripe and holds `GateClosed` until its last command has finished. `close()` returns only once every in-flight count reads 0, so no pass taken before the closure is still running. Under the `SeqCst` store-buffer handshake, a `try_enter` that follows the closure in the total order reads `closed != 0` and fails, so no pass is taken during the transaction. The writer then takes the ordered path, which is class (b).

**O3. Classes (b) and (c) are excluded on the transaction's keys.** EXEC holds the stripes of every key in its scope (O4) from before its first command until after its last. A class (b) writer of such a key needs one of those stripes, and a class (c) writer needs all of them, so neither can commit inside the transaction. A writer already holding a stripe when EXEC asks for it finishes first, because EXEC waits for the stripe.

**O4. The scope covers every key a queued command reads or writes.** The coverage comes from three facts:
- `read_scope` is exhaustive for reads;
- `ordering_key_refs` covers writes and their sources;
- both are taken for every command, and the oracle test checks coverage against `command_scope`.

Whole-keyspace commands take every stripe.

**O5. Class (d) does not matter.** It changes no key a command can read.

**O6. The clock.** Every queued command evaluates expiry at the instant `t` taken after the guards. A key's liveness at `t` is fixed, so expiry cannot split the transaction either.

**O7. Keys outside the scope are not read.** By O4, nothing the transaction returns depends on them, so writes to them may run concurrently without breaking the result. This is what keeps unrelated writers concurrent.

Therefore the transaction's replies equal those of running its commands one after another at instant `t`, with no other command in between: a one-step execution, linearizable at `t`.

**Deadlock and starvation.**
- EXEC acquires in the existing global order: gate, then stripes ascending. Every other taker uses the same order or a prefix of it, and a gate closer waits only for synchronous unordered writes, which hold nothing.
- No stripe is taken twice: the list is deduplicated, and the queued writes run through `execute_locked_write`, which takes none.
- The store's stripes are taken only inside synchronous store calls, never across a server-side wait, so they cannot close a cycle with the replication-order stripes.
- `tokio::sync::Mutex` is fair (FIFO), so an EXEC is not starved by a stream of writers, nor a writer by a stream of transactions.

**Cancellation.** If the connection future is dropped while EXEC waits for a stripe, `lock().await` is cancel-safe: the guards already taken drop, and so does `GateClosed`, which reopens the gate. The clock override is scoped to synchronous calls and cannot leak.

## 5. Invariants (brief §3.2)

| # | Invariant | How it holds |
|---|---|---|
| 1 | Read-only EXEC observes one state | §4 |
| 2 | Mixed EXEC keeps its atomicity | Its write keys were already in scope; the reads join them |
| 3 | No conflicting write between queued reads | O2, O3 |
| 4 | Unrelated writes continue | O7; only the scope's stripes are taken. A whole-keyspace read takes all, as Redis would |
| 5 | WATCH checks correct | Watched keys stay in scope; the check still runs under the guards |
| 6 | No lock-order inversion | Same order |
| 7 | No recursive acquisition | Deduplicated; writes take none inside |
| 8 | No nested-execution deadlock | Store stripes are synchronous-only |
| 9 | No starvation | FIFO mutexes; the gate wait is bounded by one synchronous command |
| 10 | No early acknowledgment | The reply is still sent after the guards drop, after every command's persistence step |
| 11 | No AOF entries for read-only transactions | Reads are not logged; unchanged |
| 12 | Cancellation and cleanup | RAII guards; tested (Test F) |
| 13 | Tenant isolation | Strict-mode EXEC re-checks scopes before locking, as before. Locking adds no read path |

## 6. Performance risk

| Cost | Who pays | Expected |
|---|---|---|
| One stripe lock per distinct read key | Transactions only | Tens of ns per stripe, uncontended |
| Writers of a transaction's read keys wait for it | Contended transactions | Inherent: Redis runs the whole transaction alone |
| A whole-keyspace read inside EXEC takes all 256 stripes | Rare | Bounded by one transaction |
| `now_ms()` checks a thread-local | **Every command** | About 1 ns per clock read. Measured in `V0.6O-E-PERFORMANCE.md` |
| The gate closes for every EXEC | Unchanged | — |

Plain GET, MGET, SET and MSET outside transactions gain only the thread-local check.
