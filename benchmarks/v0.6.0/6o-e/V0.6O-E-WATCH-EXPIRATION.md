## 1. What Redis does

Redis 7.2 keeps one flag per watched key: `expired`. It is set at `WATCH` when the key is present but logically expired.

| Event after `WATCH` | Key live at WATCH | Key absent or already expired at WATCH |
|---|---|---|
| A command modifies the key (SET, DEL of a present key, EXPIRE, PERSIST…) | abort | abort |
| The key expires, and nothing touches it (lazy) | **abort** (`isWatchedKeyExpired` at EXEC) | — |
| The key is deleted by expiry (lazy on access, or active) | abort | **no change** (`touchWatchedKey`: "Already expired key is deleted, so logically no change") |
| `FLUSHDB` | abort | **no change** (`touchAllWatchedKeysInDb` dirties only keys that existed) |
| `DEL` of the absent key | — | **no change** (nothing was deleted, so nothing is signalled) |
| A no-op write (`SETNX` on an existing key, `PERSIST` without a TTL, `HDEL` of a missing field) | no change | no change |

Every row was checked against Redis 7.2.5 by `tools/watch_expiry_diff.py` (31 cases) and by the CI differential (22 cases, §4).

## 2. What Recached did (`1f9232f`)

WATCH registers a subscriber per key. Every write, sweeper removal and `FLUSHDB` notifies the key's subscribers, and **any** notification dirtied the transaction. Two consequences:
- **Lazy expiry was invisible.** A key that expires without being touched produces no notification, so EXEC committed. Redis aborts.
- **Removals of absent keys dirtied.** `DEL k` of an absent key and `FLUSHDB` both notify every watcher of `k`, so EXEC aborted. So did the sweeper removing a key that was already expired at `WATCH`. Redis commits in all three cases.

No-op writes were already right: they are not notified (`broadcast_for` filters them).

Differential on `1f9232f` (`raw/e0-reproduction/watch-expiry-diff-dev-1f9232f-run1.md` and `-run2.md`; the second run adds the six no-op cases. Two runs, because the sweeper's timing moves some cases): the divergences were `live_then_expires`, `live_then_expires_then_read`, `two_keys_one_expires`, `expires_between_multi_and_exec`, `absent_deleted`, `absent_flushdb`, `expired_before_watch_then_swept` and `watch_cycles`. On the CI differential, 8 of 22 cases differed (`raw/e0-reproduction/redis-diff-watch-on-66e6293.txt`).

## 3. The fix

Recached now keeps the same flag as Redis, with the opposite sense: **live at WATCH**. It uses the transaction instant 6O-E1 introduced. No timer and no per-key background work are involved.

1. **At `WATCH`** (TCP and WebSocket), each newly watched key's liveness is read and stored in its registration: `WatchSubscriber::watching(live)`. The read happens under the watch registry's lock, before the registration is published. A writer notifies under that lock too, so a write is either seen by the read or notifies the new registration afterwards. On TCP the unordered gate is also closed, as before, so no unordered write is in flight. Re-watching a key keeps its first registration, as in Redis.
2. **At notification**, `WatchNotif::invalidates` is false only when two things hold: the registration was not live at WATCH, and the change is a **removal**. A removal is `KeyChange::removed`, as announced by `DEL`, `UNLINK`, `FLUSHDB`, expiry, eviction, and a replica resync that drops the key. Which changes count as removals is decided by the command, never by reading the store, so every write that sets the key invalidates, whatever its TTL. Live-query registrations always count as live and are unaffected. A WebSocket watcher is still pushed every change; only the dirtying follows the rule.
   - *Review round 1 (High):* the first version decided by reading the key when the notification was delivered. That read happens after the write's AOF stage, and for a queued write outside the transaction's instant. A key created with a short TTL, or with a `PXAT` already past, had expired by then, so a watcher of the absent key missed its creation and committed. Redis aborts. The reviewer's probes committed 20/20 under `appendfsync always` and 9/200 without AOF.
3. **At `EXEC`**, under the guards, which include every watched key's stripe, and at the transaction's instant `now`, `watched_key_expired` checks each of the connection's live-at-WATCH registrations. If any key is no longer live at `now`, the transaction aborts. That is `isWatchedKeyExpired`. It takes one registry lock and one `EXISTS` per watched key, only for transactions that watch something. The watch count per connection is capped (`max_watches_per_conn`).

### Why the distinctions in brief §4.3 hold

| Case | Outcome | Why |
|---|---|---|
| Key already absent at WATCH, stays absent | commit | Not live at WATCH. No notification, or only removals |
| Key expires after WATCH | abort | Live at WATCH, not live at `now` (step 3) |
| Key deleted explicitly | abort if it was live; commit if it was absent | Step 2 (`DEL`/`UNLINK` announce removals) |
| Key recreated | abort | The write leaves the key present (step 2) |
| TTL changed (`PEXPIRE`, `PERSIST` on a TTL) | abort | A write to a live key |
| Value changed | abort | — |
| Key expired and then recreated | abort | The write leaves it present |
| UNWATCH, then expiry | commit | The registration is gone |
| WATCH cleared by EXEC or DISCARD | the next transaction is clean | Registrations dropped, as before |

**Concurrent expiry and EXEC.** EXEC judges every watched key at the instant it takes once its guards are held, which is also the instant its queued commands run at. A key that expires after that instant does not abort it, and the queued commands still see it (test `expiry_during_exec_is_judged_at_the_transactions_instant`). This is Redis's behaviour, where EXEC runs at its command-time snapshot. The sweeper takes every stripe, so it cannot remove a watched key while EXEC holds that key's stripe.

## 5. Costs

- **WATCH:** one `EXISTS` per newly watched key, under the registry lock.
- **EXEC with watched keys:** one registry lock and one `EXISTS` per watched key.
- **Writes:** nothing; the decision needs no store read. A replica's full resync checks each watched key's liveness once.

No path without WATCH changes.
