## 1. Current resource limits (on `2807434`)

Read from `server-native/src/replication.rs` and `main.rs`.

| Resource | Bound | Where |
|---|---|---|
| Frames queued per replica | `RECACHED_REPL_BUFFER`, default **4096**. This is the tokio `mpsc` channel's capacity. | `handle_replica`: `mpsc::channel(repl_channel_capacity)` |
| Bytes queued per replica | `RECACHED_REPL_BUFFER_BYTES`, default **8 MiB**. Each frame is charged its **payload length only**. | `fan_out`: `pending_bytes.fetch_update(checked_add, ≤ max_queue_bytes)` |
| What a queued frame really holds | A `QueuedReplFrame` (32 B) in a 32-slot tokio block (about 33 B per slot), the frame's `Arc<Vec<u8>>` (40 B, a 48 B jemalloc class), and the payload allocation. The `Arc` and payload are shared with the backlog until the backlog trims them. | `QueuedReplFrame`, `ReplFrame` |
| Backlog | `RECACHED_REPL_BACKLOG_BYTES`, default **16 MiB**, primary-wide, payload length only | `fan_out` trims from the front |
| Channel memory | Allocated on demand, block by block. Capacity reserves nothing. | tokio `mpsc` |
| Socket buffers | The sender's `BufWriter`: **64 KiB** per replica, outside the charge (frames written into it have left the channel). The kernel send buffer (`tcp_wmem` autotuning) is also outside it. | `REPL_SEND_BUFFER_BYTES` |
| Replicas | Every replica connection takes a permit from the listener semaphore shared with the client ports (`RECACHED_MAX_CONNECTIONS`). A queue exists only after authentication and a valid handshake. | `run_repl_server` |

**How a charge is acquired and released.** `fan_out` reserves the frame's length with `fetch_update`, refusing a sum that overflows or passes the budget. It then `try_send`s. A frame leaves the queue when the sender's `recv`/`try_recv` returns it. Its `QueuedReplFrame` is dropped after `write_repl_frame` has copied it into the `BufWriter`, and `Drop` subtracts exactly the charge. A failed `try_send` (`Full` or `Closed`) hands the `QueuedReplFrame` back inside the error, and dropping that releases the reservation. **A failed enqueue therefore cannot leave the accounting inconsistent** (PR 2 now tests this). A dropped receiver (an aborted sender) drops every queued frame, so their charges are released.

**When a replica is disconnected.** `fan_out` drops it from the registry when the reservation fails (`queue_bytes`) or the channel is full (`queue_items`), and silently when the channel is closed. Its sender then drains what was queued, flushes, and ends; the replica reconnects and resynchronizes.

**Oversized frames.** A frame larger than the byte budget fails the reservation, so a single 9 MiB write disconnects every replica at the default budget. Each replica then resumes from the backlog, which writes the frame directly, not through the queue. This is correct but costly. It is pre-existing and unchanged.

**The interaction between the two bounds.** The frame count binds first for any frame under 8 MiB / 4096 = 2 KiB. Typical replicated commands are 30–100 bytes, so a full channel holds 120–400 KB: 1.5–5% of the byte budget. In the reproduction below it held **27,654 bytes: 0.33%**. Despite its documentation ("Maximum pending frames per replica"), `RECACHED_REPL_BUFFER` bounds frames **not yet drained by the sender**, not frames behind the primary. Frames in the `BufWriter` and the kernel buffers are not counted. The code comment "When a replica falls this many writes behind the primary it is disconnected" is inexact for the same reason.

## 2. Reproduction

`pipelined_rounds_at_default_capacity_with_acks` (the 6N-C5 `#[ignore]` measurement), unchanged workload. One worker; 40 writers × 128 frames per poll, all resuming together, 8 rounds; a scripted replica that acknowledges every burst as `run_repl_client` does. Debug build of `2807434`.

| Run | Result |
|---|---|
| 10 runs | **10/10 disconnected**, every run at exactly **10,112** frames received (79 polls of 128) |
| Same, acknowledgements off (scratch `c6_trace_r1`, `C6_NOACK=1`) | **Disconnected at the same frame, 10,112**. Acknowledgements are not the trigger. |

A scratch trace recorded every writer poll, sender drain and flush, and the overflow. ## 3. Mechanism

The sender is an ordinary tokio task. Three facts about tokio 1.54's multi-thread scheduler (`runtime/scheduler/multi_thread/worker.rs`, `scheduler/defer.rs`) explain the trace.

1. **A wake from inside a running task goes to the worker's LIFO slot.** A writer's `try_send` wakes an idle sender, so the sender runs right after that writer's poll. That is the `S drain depth=128` after each writer.
2. **A task that is already notified cannot be moved.** Waking a task already in the run queue does nothing, so a writer's `try_send` cannot bring forward a sender that is queued.
3. **Every 61 polls a worker runs maintenance (`park_yield`).** It polls the I/O driver, then `defer.wake()` wakes everything that `yield_now`ed since the last park, popping the defer list **from the back**. Each wake takes the LIFO slot and pushes its previous occupant to the **back** of the run queue, behind every task already there.

The sender's held flush (6N-C5's `RoundEnd`) is a `yield_now` deferral, armed when it drains after a flush. When a maintenance park falls **mid-round**, it fires that deferral. The sender is pushed behind the writers of the round not yet run (W33…W2 above) and is now notified, so their `try_send`s do nothing. Thirty-two of them queue 4096 frames, and the thirty-third overflows the channel at its first frame.

At an *idle* park (the end of a round, run queue empty) the same pop order leaves the sender near the front, because its latest deferral is near the end of the list. Only a mid-round maintenance park strands it behind a whole round. That explains why the failure is deterministic for a given workload shape and phase.

An acknowledgement does the same through the I/O driver. Readiness found at the maintenance park wakes the sender into the LIFO slot, and the next deferred wake pushes it to the back. That was the pre-6N-C5 path (8 of 10 runs in 6N-C5's measurement). 6N-C5's held flush made it every run. **Both are the same mechanism: any wake the sender receives while its worker parks between polls can queue it behind every ready writer.**

### A second, independent cause: one poll

Even a perfectly scheduled sender (in the LIFO slot after every writer) cannot drain *during* a writer's poll. A connection's poll parses every complete command in each read: `TCP_READ_BUFFER_BYTES` = 16 KiB per read, up to tokio's coop budget of 128 reads per poll. With commands of about 30 bytes, one poll of **one connection** can queue tens of thousands of frames, many more than 4096, while using a fraction of the byte budget. PR 2's `one_poll_of_more_than_4096_frames_fits_the_default_queue` demonstrates it deterministically: 6000 frames in one poll overran the old cap at frame 4097.

## 4. Which cause?

| Candidate | Finding |
|---|---|
| Scheduler ordering | **Yes.** A park-time wake (the held flush's deferral, or acknowledgement readiness) queues the sender behind the round's remaining writers, and their wakes cannot move it. |
| Channel capacity | **Yes.** The frame count binds with 0.33% of the byte budget used. One round, or one poll, of small frames exceeds it. |
| Sender starvation | Bounded: one round at most. The sender runs once the writers ahead of it have polled once each, never later. |
| Burst admission | No admission control exists on the primary's write path, by design: the primary never waits on a replica. |
| Byte-budget exhaustion | **No.** 27.6 KB of 8 MiB. |
| Genuine replica slowness | **No.** The replica's socket was never full, and the outcome is identical without acknowledgements. |

**Root cause:** the replica channel must absorb whatever the writers ahead of a queued sender produce, which is up to a whole scheduling round, and one connection's poll can exceed 4096 small frames on its own. A fixed 4096-frame cap is smaller than that while bounding far less memory than the byte budget allows. No change to the sender's wakes alone can fix this ([design](V0.6N-C6-BACKPRESSURE-DESIGN.md#option-a--scheduling)).
