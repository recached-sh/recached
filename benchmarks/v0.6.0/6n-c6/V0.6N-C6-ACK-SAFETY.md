# v0.6.0 Phase 6N-C6C: cancellation-safe replica acknowledgement read

**Branch:** `fix/v0.6n-c6-replica-ack-read` (PR 3), commits `77a4c42` (the fix) and `20b4e24` (the review's test fixes). It is independent of the queue change.

**Origin:** 6N-C5 review F4 (Low, pre-existing).

**Verdict:** **Fixed.** The wire format is unchanged and there is no protocol change.

## The defect

| Question | Finding, from the source |
|---|---|
| Wire format | After the synchronization, and after each burst it has applied, the replica writes the cumulative offset it has applied: **8 bytes, little-endian** (`run_repl_client`). Nothing else travels in that direction once the stream starts. |
| Fixed size? | Yes, always 8 bytes. |
| Partial reads possible? | Yes. TCP and TLS deliver byte streams, and an acknowledgement can arrive split, or in the same read as part of the next. |
| Which branch cancels the read | The sender's `select!` has three branches: `rx.recv()` (a frame), `round_end` (the held flush, 6N-C5) and `rd.read_exact(&mut ack_buf)`. When either of the other two wins while `read_exact` holds part of an acknowledgement, the `read_exact` future is dropped. The bytes it consumed are gone, and the next `read_exact` starts at index 0. |
| Effect | Every later acknowledgement is read across a boundary. In the reproduction the primary held `100 << 40` for an acknowledgement of 100, so it reported a lag of 0 from then on. |
| What reads the acknowledged offset | **Only the lag metric:** `ReplicaHandle::acked` is read by `max_lag_frames`, which feeds `INFO` `recached_replication_lag_frames` and the `recached_replication_lag_frames` gauge. I checked the whole crate: there is no `WAIT`, and failover, promotion and backlog trimming do not read it. The independent reviewer confirmed this. |
| Severity | Low. The replica's data is unaffected. An operator or external tooling reading lag could be misled, for example seeing "caught up" when the replica is not. |

## The fix

```rust
res = rd.read(acks.spare()) => match res {
    Ok(0) | Err(_) => break,                       // as before: the stream ends
    Ok(n) => if let Some(applied) = acks.take(n) {
        acked.fetch_max(applied, Ordering::Relaxed); // as before: monotonic
    },
}
```

- **`read` instead of `read_exact`.** tokio's `read` is cancel-safe: one `poll_read` either returns data or returns Pending having consumed nothing. This holds through `tokio::io::split`'s `ReadHalf`, `TcpStream`, and tokio-rustls's server stream, which keeps undelivered plaintext in its own buffer. In `select!`, a read that returned Ready is always the winner, so its data is never discarded.
- **`AckReader`**, a 64-byte buffer that outlives the `select!` iterations:
  - `spare()` is where the next read goes. At most 7 bytes are ever kept, so it always has at least 57 free bytes and is never empty, which rules out a spurious `Ok(0)`.
  - `take(n)` accounts the bytes, returns the highest complete acknowledgement, and moves a trailing partial one to the front.
- **Option rejected: a dedicated ACK reader task.** Its task and synchronization costs are not justified for an 8-byte cumulative counter, and the brief asked for the minimal persistent buffer.
- **EOF and errors** end the stream, as `read_exact`'s error did before. The old comment claimed "the stream continues either way", which was wrong, and it is corrected. A replica that predates acknowledgements never writes, so the branch never completes for it.
- **Wire compatibility:** unchanged in both directions. A 0.5 replica and a 0.6 replica both write 8-byte offsets.

## Remaining limitations

- A replica can acknowledge more than it was sent (`u64::MAX`), which makes its own lag read 0. This is pre-existing, cannot panic, and affects only that replica's metric.
- `INFO`'s lag is the furthest-behind replica's `sent − acked`. It is reported at most one burst late, by design (the replica acknowledges once per burst).
