# v0.6.0 Phase 6N-C6: replica queue and backpressure design

| | |
|---|---|
| Problem | A healthy replica is disconnected when the writers ahead of its queued sender produce more frames than its channel holds. See the [root cause](V0.6N-C6-ROOT-CAUSE.md). |
| Constraint | Every option that fixes it at the shipped configuration changes either the `RECACHED_REPL_BUFFER` default or its meaning. The brief requires maintainer approval for that. |
| **Decision** | **Option B, approved by the maintainer on 2026-11-20.** The queue is sized by bytes, each frame is charged its payload plus 128 bytes, and the frame cap is derived from the byte budget unless `RECACHED_REPL_BUFFER` is set. |
| Not chosen | A (scheduling) cannot fix it alone, and its writer-side variant changes the primary's write semantics. C (raise the default) is arbitrary and still frame-bound. D (catch up from the backlog) is an architectural change. |

## Requirements

1. A **healthy** replica, one that keeps up with the sustained write rate, is not disconnected by a bounded burst that fits the queue's **memory** budget.
2. A replica that **cannot** keep up is still disconnected once its queue reaches a fixed bound, and the primary never waits on it.
3. Memory **and** the number of queued items both have stated upper bounds.
4. Ordering, the backlog, resynchronization, DEDUP, promotion and AOF-before-fan-out are unchanged.

## Option A — scheduling

Make the sender drain before a round can fill its channel.

| Variant | Finding |
|---|---|
| A1. Earlier sender wake-ups: a high-water notification, re-arming the round-end wait, bounded `yield_now` in the sender | **Cannot work.** The overflow happens while the sender is already *notified* and queued behind the writers (root cause §3, fact 2). A wake to a notified task is a no-op, and tokio has no priority or "move to front" API. 6N-C5 tried a high-water `Notify` and re-arming; both still overflowed 10/10. Any yield in the sender only adds park-time wakes, which are the cause. |
| A1'. Remove the held flush (`RoundEnd`) | Removes one park-time wake, but not the acknowledgement's (8/10 before 6N-C5), and gives up 6N-C5's +13%/+35%. **Rejected.** |
| A2. Writer-side yield at a high-water mark: a replicated write yields its task while any replica's channel is above, say, half capacity | **Fixes the harness.** The yielding writers go to the defer list, which runs only after the run queue, sender included, so the sender drains before they resume. Measured with the reproduction (3 runs each, all 40,960 frames delivered; raw: [`investigation/a2-*.txt`](investigation/)): high-water 1024 → peak 1052, 82 yields; 2048 → peak 2068, 42 yields; 3072 → peak 3084, 13 yields. The peak is the high-water mark plus one frame per task ahead of the sender. **Rejected**, because it changes what the primary promises. While a replica lags, every client write yields: a stalled replica throttles all clients until it is dropped, and a replica sustaining half the primary's rate throttles them indefinitely. That is synchronous replication backpressure, against the documented "overflow disconnects only the lagging replica without blocking primary writes". It needs a yield point in every write path (RESP pipelines mid-poll, WebSocket, `EXEC`, the coalesced AOF). It still allows the high-water mark plus one frame per ready task, which is unbounded in connections. |
| A3. A dedicated sender thread per replica | Not scheduled behind writers. But every `try_send` becomes a cross-thread wake (futex), which undoes 6N-C5's batching, and it adds a thread per replica. Too large a redesign for a P0 fix. **Rejected.** |

**Conclusion:** within tokio's scheduling model, a task-based consumer can always be queued behind every ready producer. One connection's poll can also exceed the cap with perfect scheduling. The queue must hold that much. The question is only how its bound is expressed.

## Option B — size the queue by bytes (selected)

| Element | Design |
|---|---|
| Charge per frame | `repl_queue_charge(len) = len.saturating_add(REPL_QUEUE_FRAME_OVERHEAD)`, with `REPL_QUEUE_FRAME_OVERHEAD = 128`. It saturates: a charge that cannot be represented exceeds every budget and is refused, never wrapped. |
| Byte budget | `RECACHED_REPL_BUFFER_BYTES`, **unchanged default 8 MiB**, now charging payload plus overhead. Reservation and release are unchanged: `fetch_update` with `checked_add` and `≤ budget`, then `Drop`. |
| Frame cap | `repl_channel_capacity(explicit, bytes)`. An **explicit `RECACHED_REPL_BUFFER` is kept exactly** as a strict cap. Unset, the cap is `bytes / 128`, clamped to `[1, 1,048,576]`: **65,536** at the default budget. |
| Independent item bound | The channel capacity bounds items regardless of bytes. With a derived cap, every frame charges at least 128 bytes, so the budget is reached first: `items ≤ budget / 128`. Zero-length frames reach both limits together, at 65,536. |
| Why 128 | A queued frame holds a `QueuedReplFrame` in a channel slot (about 33 B), the `Arc<Vec<u8>>` (48 B class) and the payload's allocator rounding (under 16 B for payloads under 128 B): about 97 B. 128 covers it with a margin. |
| Observability | `INFO replication`: `recached_replication_send_queue_bytes_peak`, `_queue_disconnects`, `_syncs_partial`, `_syncs_full`. The Prometheus counters `recached_replication_disconnects_total{reason}` and `recached_replication_syncs_total{type}` remain. |
| Startup log | `Replication buffers: … per-replica queue=<bytes> bytes / <frames> frames (derived from the byte budget \| RECACHED_REPL_BUFFER)` |

### Exact memory bounds, per replica

| Quantity | Before (4096 frames, payload-only charge) | After (default) |
|---|---|---|
| Items queued | ≤ 4096 | ≤ 65,536, and ≤ budget / 128 |
| Charged bytes | Σ payload ≤ 8 MiB | Σ (payload + 128) ≤ **8 MiB** |
| Queue metadata (slot + `Arc`) | ≤ 4096 × ~81 B ≈ 0.32 MiB, **uncharged** | inside the 8 MiB charge |
| Payload allocator rounding | uncharged | uncharged (≤ 15 B under 128 B; jemalloc classes above, at most about ¼ of the size) |
| Worst-case heap held by the queue | ≈ 8 MiB + 0.32 MiB metadata + rounding | ≈ **8 MiB** + rounding above 128 B |
| Outside the queue | 64 KiB `BufWriter` + kernel socket buffers | unchanged |

Worst cases: before, it is 8 MiB of 2 KiB frames plus metadata; after, 8 MiB of any mix. A queue of tiny frames, which today stops at about 0.4 MiB, can now grow to 8 MiB before the replica is dropped. That is the intended trade: memory the byte budget always allowed, now usable by small frames.

**Payload capacity.** The charge counts `len`, not the `Vec`'s capacity. Frames built by `resp.to_vec()` have exact capacity. DEDUP envelopes and records are built by appending, so their allocation can reach about twice their length. That was true before and is unchanged, and the backlog's accounting has the same property. It is recorded as a follow-up, not changed here.

**Many replicas:** N × the per-replica bound, plus the shared 16 MiB backlog. N is bounded by the listener's connection permits (`RECACHED_MAX_CONNECTIONS`), and a queue exists only after authentication and a valid handshake. This is unchanged.

### Effect on healthy and slow replicas

| | Before | After |
|---|---|---|
| A round of 40 × 128 small frames (the reproduction) | disconnected 10/10 | kept 30/30 ([correctness](V0.6N-C6-CORRECTNESS-TESTS.md)) |
| One poll of 6000 frames | disconnected at frame 4097 | kept |
| A stalled replica, 50-byte frames, 300k writes/s | dropped after about 4096 queued frames (≈ 14 ms) plus kernel buffers | dropped after about 47k queued frames (8 MiB / 178 B, ≈ 157 ms) plus kernel buffers |
| A stalled replica, frames ≥ 2 KiB | dropped at the byte budget | dropped at the byte budget, 128 B per frame sooner |
| A replica slower than the sustained rate | dropped when its queue fills | dropped when its queue fills, at the same rate of fall-behind; later only by the extra frames the budget admits |

The primary never waits: `fan_out` still only `try_send`s.

### Comparison

| | A2 writer yield | **B bytes (selected)** | C raise to 16,384 | D backlog catch-up |
|---|---|---|---|---|
| Fixes the reproduction | yes (harness) | **yes** | yes | yes |
| Fixes one 6000-frame poll | only with a per-command yield | **yes** | yes | yes |
| Rounds up to | the high-water mark + ready tasks | **the byte budget** | 16,384 frames | the backlog |
| Code change | every write path | **charge function, capacity derivation, `main.rs`** | one constant | sender reads from the backlog when its channel overflows; a new sender state |
| Memory bound | unchanged | **≈ 8 MiB per replica, metadata included** | 8 MiB + ~1.3 MiB metadata | unchanged (the backlog) |
| Healthy replica | kept, but every client is throttled while it lags | **kept within the budget** | kept up to 16,384 frames | kept within the backlog |
| Slow replica | throttles the primary until it is dropped | **dropped at the budget** | dropped at 16,384 frames | dropped when it leaves the backlog |
| Scheduling | adds yields to hot paths | **none** | none | none |
| Throughput / latency cost | a check per write, and yields under lag | **none expected** (one saturating add) | none | backlog reads under the stream lock |
| Configuration | unchanged | **default frame cap derived; byte charge adds 128 B**; an explicit cap is still strict | new default | disconnect threshold becomes the backlog |
| Security / abuse | none new | **none new**: per-replica bytes unchanged, and an authenticated replica can hold no more memory than before | +1.3 MiB metadata per replica | none new |
| Rollback | revert | **`RECACHED_REPL_BUFFER=4096`**, or revert | set it back | revert |

**Why B.** It is the smallest change that removes the cause: the frame count is no longer the binding limit, and the byte budget, which the documentation already calls "the primary memory bound", now really bounds memory. It needs no scheduling change and no change to any write path, wire format or replication state machine. An operator who set `RECACHED_REPL_BUFFER` keeps exactly that cap.

**What changes for operators** (approved; documented in `configuration.md`, `operations.md`, `protocol.md`, `upgrading-0.6.md` and the CHANGELOG):
- With `RECACHED_REPL_BUFFER` unset, the frame cap is 65,536, not 4096.
- `RECACHED_REPL_BUFFER_BYTES` now charges 128 B per frame. A workload of 1 KiB frames fits about 11% fewer frames in the same budget.
- A stalled replica is dropped when its queue reaches 8 MiB charged rather than 4096 frames, so it holds more memory until then (≤ 8 MiB, as large frames already could).

### Found in review and fixed in PR 2

**Review M1, Medium (pre-existing).** `fan_out` unregistered a replica whose queue was full, but its sender kept draining the queue into a socket that the peer might never read. It held up to the whole budget, out of every gauge, until TCP gave up. With bytes as the binding limit that is 8 MiB rather than about 0.5 MB, so PR 2 now closes such a replica's connection at once (`Registered`). See [implementation](V0.6N-C6-IMPLEMENTATION.md) and [review](V0.6N-C6-INDEPENDENT-REVIEW.md).

## Rollback

- Operational, with no code change: set `RECACHED_REPL_BUFFER=4096`. This restores the old frame cap; the overhead charge stays, which is slightly stricter than before.
- Code: revert the PR 2 merge. Neither the charge, the derived cap nor the INFO fields touch any persistent or wire format.

## Recorded, not changed

- **Payload capacity is not charged** (see above). DEDUP envelopes can hold up to about twice their length. Follow-up: build them with exact capacity, or charge `capacity()`.
- **A single frame larger than the byte budget** disconnects every replica, which then resume from the backlog. This is pre-existing and correct.
- **An explicit `RECACHED_REPL_BUFFER` above tokio's permit limit** (`usize::MAX >> 3`) panics the replica's task at the handshake. This is pre-existing; a derived cap cannot reach it.
