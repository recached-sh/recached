## Host conditions: noisier than 6N-C5's run

The desktop session had 6.9 of 8 GB swap in use. Disk IO pressure (`/proc/pressure/io`) stayed at 4–14% "some" through the runs ([`host-pressure.txt`](fedora-i5-9400f-20261120-main/host-pressure.txt)). The kit's idle check was therefore raised to load ≤ 4.0, from 1.0; the load was IO wait, not CPU.

On this HDD, AOF `fsync`s then stalled for up to 1–3 s. **Max latency** in AOF cells measures those stalls and is not used. The stalls also cut closed-loop throughput: a 1 s stall in a 10 s run costs about 10%. The metrics used are **CPU per operation**, p50–p99, and throughput **across repetitions in both orders**.

**The first attempt aborted.** In `c6/rc-coalesced-P64` rep 2, the lag probe's own `SET` to the primary got no reply within its 3 s socket timeout. That was a 3.0 s fsync stall; the benchmark's max latency in the same run was 3000.3 ms. The probe then printed a traceback, `summarize` failed on it, and `set -e` ended the run. The probe now records `<n> pstall`, reconnects and continues. The aborted run's environment and that cell are kept in [`fedora-i5-9400f-20261120-aborted-probe/`](fedora-i5-9400f-20261120-aborted-probe/).

## Order effect, and how it was controlled

In the main run each pair ran `base`, then `c6`. The second binary of a pair runs while the disk is still writing back, and deleting, the first one's AOF (about 450 MB at P=64). In every AOF cell `c6` had the larger stalls and lower throughput, while CPU per operation was identical. So the stall-affected cells were run again **with `c6` first** ([`fedora-i5-9400f-20261120-reversed/`](fedora-i5-9400f-20261120-reversed/)):

| Cell | rps, base first (base / c6) | rps, c6 first (c6 / base) | Pooled medians, 6 + 6 runs | CPU µs/op, pooled (base / c6) |
|---|---|---|---|---|
| `rc-inline-P1` | 64,499 / 60,591 | 56,325 / 55,534 | **1.014×** | 12.57 / 12.75 (1.015×) |
| `rc-coalesced-P1` | 105,252 / 92,997 | 102,554 / 99,980 | **1.026×** | 6.81 / 6.78 (0.995×) |
| `rc-coalesced-P16` | 285,559 / 279,572 | 261,308 / 263,026 | **0.986×** | 2.87 / 2.86 (0.997×) |
| `rc-coalesced-P64` | 324,791 / 304,952 | 300,381 / 307,295 | **0.950×** | 2.61 / 2.60 (0.994×) |

Reversing the order reverses the inline P=1 and coalesced P=1 gaps, and shrinks P=16's to −0.7%. Coalesced P=64 stays below in both orders (−6% and then −2.2%) at identical CPU per operation. Its spread is large: in the second run the ranges are 285–315k against 296–320k. The same pipeline depth **without AOF**, which has no fsync, is unchanged: P=64 is 596,659 against 596,588 (1.000×), and P=128 is 614,515 against 605,254 (0.985×, ranges 605–614k for both). The P=64 AOF difference is within the HDD's fsync noise. A quieter host would settle it (follow-up).

- **Against the 6N-C5 reference:** `base` coalesced P=1 is 105,252 rps at 6.73 µs/op (6N-C5: 105,252 at 6.83). P=16 is 285,559 at 2.82 µs/op (6N-C5: 287,637 at 2.89). Despite the noise, the baseline reproduces 6N-C5's numbers, and `c6`'s CPU per operation matches it everywhere.
- **Frames per flush** (replication socket segments) are equal: 21.3 / 21.4 at coalesced P=1 and 30.1 / 30.1 at P=16. 6N-C5's sender batching is untouched.
- **Replica lag:** sub-millisecond to low-millisecond in both binaries. Differences are within the run-to-run spread, and above 6N-C5's 0.5 ms p99 on both, because of the host.
- **Convergence and samples:** `ok` in all 54 runs. RSS: primary 59–69 MiB, replica 25–29 MiB, in both.
- **Disconnects and resyncs:** none in any cell. `c6` reports `queue_disconnects:0` and a single synchronization (the initial full one). `base` logged no queue-full warning.

## The bounded burst, end to end

With 50 clients, no cell of the matrix overruns 4096 frames. At P=64 the deepest queue is exactly one round, 50 × 64 = 3200; at P=128 the benchmark's clients do not all become ready together (peaks 2,249–3,012). The burst cell therefore uses **100 clients × P=64, 6400 frames a round**, with no AOF so fsync stalls do not shape the rounds. One replica, 10M SETs, 3 repetitions ([`fedora-i5-9400f-20261120-burst/`](fedora-i5-9400f-20261120-burst/)):

| | base | c6 |
|---|---|---|
| **Healthy replica disconnected** | **5, 4, 3 times** ("channel full") | **0, 0, 0** |
| Synchronizations during the run | 5, 4, 3 **full** resyncs (the replica's offset had left the backlog by the time it reconnected) | none beyond the initial one |
| Queue peak | 4096 frames (the cap) | **6400 frames, 1,299,200 bytes charged** (15% of the 8 MiB budget) |
| Throughput | 596–624k rps | 571–588k rps |
| p99 / max latency | 27.9–28.7 ms / 59–66 ms | **12.3–12.6 ms / 14–17 ms** |
| CPU µs/op | 1.53–1.59 | 1.63–1.67 |
| Primary RSS peak | 85–86 MB (snapshots for the resyncs) | 66–71 MB |
| Replica converged, samples | ok | ok |

`c6`'s throughput and CPU per operation here are not a regression to set against `base`: `base`'s replica spent much of each run disconnected or loading a snapshot, so that primary was replicating less. `c6` replicated every write continuously, with lower and steadier latency.

## Slow replica, bounded (stopped for 2 s)

One replica is `SIGSTOP`ped 3 s into a 6M-SET P=16 coalesced run, then resumed after 2 s ([`fedora-i5-9400f-20261120-slow/`](fedora-i5-9400f-20261120-slow/)).

| | base | c6 |
|---|---|---|
| Dropped | once per run, by frames (queue peak 4096) | once per run, **by bytes** (`queue_disconnects` 1) |
| Primary kept serving | yes: 263–300k rps over the run (stall-noisy) | yes: 261–304k rps |
| Primary RSS peak | 79.5–80.1 MB | 74.8–78.4 MB: **not higher**, because the unregistered replica's connection is closed at once (review M1) |
| Recovery | a full resync (2 s of writes is more than the 16 MiB backlog) | a full resync (`syncs_full` 2) |
| Converged, samples | ok, ok | ok, ok |

`send_queue_bytes_peak` reads only 16 KB in this cell. It is sampled when the sender wakes, and a sender blocked on a full socket does not wake. The queue's real charge is still bounded at 8 MiB, which the tests check directly.

## Two replicas

Two replicas, both reading, through a 6M-SET P=16 coalesced run, 3 repetitions ([`fedora-i5-9400f-20261120-two/`](fedora-i5-9400f-20261120-two/)):
- **No disconnects** and one synchronization per replica, in both binaries.
- Both replicas converged in every run, and every key sample matched.
- CPU per run: 19.5–19.7 s for `base` and 19.6–19.8 s for `c6`.
- Throughput was 237–261k against 224–245k with `c6` always second in its pair, the same order effect as above.

## Acceptance (brief §9)

| Criterion | Result |
|---|---|
| Eliminate the avoidable bounded-burst disconnect | **Yes.** `base` disconnects 3–5 times per run at 100 × 64; `c6` never does. |
| Maintain bounded memory | **Yes.** Queue ≤ 8 MiB charged by construction (tests). Primary RSS is equal in the matrix and lower in the burst and slow cells. |
| Preserve healthy replica convergence | **Yes.** Every run converged with matching samples. |
| No meaningful P=1 or P=16 throughput regression | **Yes.** Pooled over both orders: inline P=1 1.014×, coalesced P=1 1.026×, coalesced P=16 0.986×, with CPU per operation within ±1.5%. Coalesced P=64 is 0.950× but within fsync noise; replication at P=64 without AOF is 1.000×. |
| No material p99 regression | **Yes.** p99 is within run-to-run ranges in every cell; in the burst cell `c6` p99 is less than half of `base`'s. |
| Replica lag in a documented range | Sub-millisecond p50 and 1–5 ms p99 in both binaries, the same as each other on this host |

**What was not run:** the full historical matrix, Redis and Valkey (no change in scope), and a soak. All were excluded by the brief.
