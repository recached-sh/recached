# v0.6.0 Phase 6O-A: correctness tests

PR 2 changes how write frames are *produced*. Every guarantee below depends on the produced bytes being the same as before, and on nothing around the encoder moving. Both are tested.

## New tests (`server-native/src/tests/frame_encoding_6oa.rs`, `request_path.rs`)

| Test | What it holds |
|---|---|
| `resp_push_matches_the_original_encoder` | The new `resp_push` equals the original `format!` encoder, kept verbatim in the test, and its capacity equals its length, for every case below. **Part lengths:** 0, 1, 2 and each side of every power of ten up to 100,001. **Part counts:** 0–2, 9–11, 99–101, 999–1,001. **Parts:** empty, CRLF/RESP-marker bytes (`\r\n`, `$-1\r\n`, `>3\r\n`), and a 1 MiB value |
| `frames_match_the_baseline_build` | Every frame a fixed 113-command script propagates is byte-identical to `fixtures/broadcast-6oa-baseline.bin`, generated on **unmodified `a697f54`**. The script covers every `broadcast_for_at` arm reachable without randomness: SET (all expiry forms, NX/XX/GET), SETNX/SETEX/PSETEX/APPEND/GETSET, the counters at `i64` extremes, EXPIRE/PEXPIRE/EXPIREAT/PEXPIREAT/PERSIST, MSET, GETDEL, GETEX (all forms), RENAME/RENAMENX/COPY, HSET/HDEL/HINCRBY/HINCRBYFLOAT/HSETNX, list, set and sorted-set writes, JSET/JMERGE, RLSET, ESET/EADD, DEL/UNLINK, DEDUP, FLUSHDB. It also covers values at every length-digit boundary up to 100,000, binary values, a tenant-prefixed key, and MSET/HSET past ten parts. Then come 8 frames through the stored-deadline (`exact_deadline`) branches, and the DEDUP envelope (`dedup_wrap`), mark, refusal and checkpoint records. Regenerating the fixture fails the run, so it can never pass silently |
| `the_fixture_script_builds_frames` | Exactly 15 named commands build no frame, each on purpose: failed conditions, missing keys or fields, an overflow, a type error, and the DEDUP-wrapped writes. A broken arm cannot hide behind a `-` |
| `hand_written_frames` | SET, INCR at `i64::MIN` and at 0, HSET with an empty and a CRLF value, MSET with an empty value: literal bytes |
| `a_frame_is_one_allocation_of_its_exact_size` | `resp_push` allocates once, at exactly the frame's length. One allocation for the frames of SET and INCR; two for HSET and MSET (the frame plus the borrowed-parts list). The baseline makes 8 |
| `aof_logged_writes_stay_within_their_allocation_budget` | The real connection loop with the AOF on: SET ≤ 5, INCR ≤ 4, HSET ≤ 7 allocations per command. The baseline makes 11.05, 11.95 and 20.05 |

**On the baseline**, the parity, fixture and hand-written tests pass, which is the point of them. The two allocation tests fail ("resp_push allocated 8 times", "SET … 11.06 allocations per command, budget 5"), so they detect the old behaviour.

The independent reviewer regenerated the fixture from base code on their own and got a byte-identical file. They also ran three throwaway differential tests against the old encoder, all passing:
- 3,000 random part lists;
- about 40,000 `i64` counter values (every power-of-ten boundary, both signs, `i64::MIN`, `i64::MIN + 1`, `i64::MAX`);
- HSET and MSET with up to 500 pairs.
