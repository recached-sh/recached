# v0.6.0 Phase 6O-A2: optimization design

The input is the [CPU profile](V0.6O-A-CPU-PROFILE.md). Frame construction is 1,921 of the 5,863 user cycles the AOF adds to a SET at P=1, and 29% of all user cycles at P=16. It has no ordering, durability or scheduling role: what it produces is fixed byte for byte, and only how it is produced may change.

## Where the cycles go in the frame build (a697f54)

```rust
pub(crate) fn resp_push(parts: &[&[u8]]) -> Vec<u8> {
    let mut out = format!(">{}\r\n", parts.len()).into_bytes();        // String alloc, fmt
    for part in parts {
        out.extend_from_slice(format!("${}\r\n", part.len()).as_bytes()); // String alloc + free, fmt
        out.extend_from_slice(part);                                       // realloc as it grows
        out.extend_from_slice(b"\r\n");
    }
    out
}
```

A SET with a 13-byte key and a 32-byte value makes **8 allocator calls** in total (measured by `frame_encoding_6oa::a_frame_is_one_allocation_of_its_exact_size` on the baseline). By construction, they are:
- the header `String`;
- a temporary `String` per part;
- the `realloc`s of the `Vec` doubling from the header's 4 bytes toward the frame's 75.

Each part goes through `core::fmt`. The samples agree: in the frame build, 967 cycles/op are allocator and 754 are `fmt`.

Some arms add more on top:

| Arm | Extra work |
|---|---|
| `HSET` | Copies the key, every field and every value into a `Vec<Vec<u8>>` (2 + 2n allocations), then collects a `Vec<&[u8]>` |
| `MSET` | The same: every key and value cloned |
| `INCR`/`DECR`/`INCRBY`/`DECRBY` | `n.to_string()`, 1 allocation |

## Candidates

| | Approach | Expected effect | Risk | Chosen |
|---|---|---|---|---|
| A | **Encode into one buffer of the exact size**, lengths formatted on the stack | 8 → 1 allocator call per frame; no `fmt` | Low: one function, 58 call sites unchanged; byte parity checked against the old encoder and a baseline fixture | **Yes** |
| A′ | Write an integer formatter for it | — | — | **No**. `core_engine::resp` already has an allocation-free one (`format_i64`, used by the reply encoder) and the matching `write_bulk`. Reused; one `write_push_header` added beside `write_array_header` |
| B1 | **HSET/MSET: borrow the parts** instead of copying them | HSET 1 field: −3 allocations and copies; MSET 4 pairs: −9 | Low: same parts, same order | **Yes** |
| B2 | Counters: format the new value on the stack | −1 allocation | Low | **Yes** |
| B3 | Pass the frame by ownership into the AOF batch | The batch copies the frame into its shared `Vec` either way (that is the batching), so ownership saves nothing on the standalone path. The replicated path's `to_vec` is ≤ 81 cycles (6N-C5) and outside this phase's standalone scope | — | **No** |
| C | Reuse a frame buffer across writes (thread-local or per-connection) | Would save the one remaining allocation | Medium: the frame is moved into a WebSocket push and the replica stream when those exist; a reused buffer would need a copy there, or a lifetime change across `apply_write_effects` | **No**: A already removes 7 of 8 |
| C′ | Upper-bound capacity (20 digits per header) instead of exact | One fewer pass over the parts | Over-allocates ≈ 60 bytes per SET frame (75 → ~135, the next jemalloc size class) | **No**: exact, with checked arithmetic, is cheap (`ilog10`) and keeps frames tight in the replication backlog (6N-C6 follow-up #1) |
| D | Lazy `now_unix_ms` per write | ≈ 100–200 cycles | Touches every arm that takes `now_ms` | No (small; recorded) |
| E | Run AOF writes on the borrowed path (no owned `Command`, fewer stripes calls) | Could approach the 1,800 cycles of ordered-path, dispatch and `to_command` cost | High: the ordered, logged write path's structure | No: out of scope, recorded |

## The chosen implementation

```rust
pub(crate) fn resp_push(parts: &[&[u8]]) -> Vec<u8> {
    let mut out = Vec::with_capacity(resp_push_len(parts).unwrap_or(0));
    write_push_header(&mut out, parts.len());       // core_engine::resp: '>' + format_i64 + CRLF
    for part in parts {
        write_bulk(&mut out, Some(part));            // '$' + format_i64 + CRLF + bytes + CRLF
    }
    out
}

fn resp_push_len(parts: &[&[u8]]) -> Option<usize> {
    let digits = |n: usize| n.checked_ilog10().map_or(1, |d| d as usize + 1);
    parts.iter().try_fold(3 + digits(parts.len()), |total, part| {
        total.checked_add(5 + digits(part.len()))?.checked_add(part.len())
    })
}
```

| Concern | How it is handled |
|---|---|
| Capacity overflow | Checked arithmetic. A total past `usize::MAX` (impossible for slices in memory on 64-bit) gives capacity 0, and the `Vec` then grows exactly as before, so there is no new panic path |
| Length header for a huge part | `write_bulk` formats `len` through `i64::try_from(len).unwrap_or(i64::MAX)`. Slices are at most `isize::MAX` long, so the decimal is exact, identical to `format!("{}", len)` |
| Empty parts, binary, embedded CRLF | Copied verbatim; the length header decides framing, as before |
| `unsafe` | None |
| Allocation failure | As before: the global allocator's abort on OOM. One allocation of the final size instead of a growth sequence ending at about twice the size |

## Constraints held

- **No AOF format change and no wire-protocol change.** The canonical frame is byte-identical. That is checked in three independent ways: against the original encoder on generated inputs, against a fixture of every frame a 111-command script produces on `a697f54`, and against hand-written frames.
- DEDUP envelopes (`dedup_wrap`), marks, refusals and checkpoint frames are covered by the fixture, unchanged.
- One frame still feeds the AOF, the replica stream and the WebSocket push, so observers are unaffected. No effect is skipped when nobody listens: the early-outs in `apply_write_effects_identified` are unchanged.
- The gate, the stripes, `on_write_logged`, the AOF queue and fail-stop are untouched.
