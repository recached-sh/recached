# v0.6.0 Phase 6O-A: performance, before and after PR 2

**Answer:**
- PR 2 raises standalone AOF throughput **6% at P=1 for all three workloads**, and **17.5% for SET at P=16**.
- Every one of the 15 interleaved P=1 repetitions favoured it, by 1.4% to 9.2%.
- CPU per operation falls 6–8% at P=1 and **22% at P=16**. User instructions per operation fall 26–36%. p99 improves in every cell.
- Without the AOF the two builds are identical, as they should be.
- Against **standalone Redis 7.2.5**:

  | Workload | Before | After | Target |
  |---|---:|---:|---:|
  | SET P=1 | 0.81× | **0.86×** | 0.90× |
  | INCR P=1 | 0.73× | **0.77×** | 0.90× |
  | HSET P=1 | 0.80× | **0.85×** | 0.90× |
  | SET P=16 | 1.01× | **1.18×** | 0.90× |

  The P=1 cells are improved, but they **do not reach the 0.90× target**.

## Gate checks

| Gate | Requirement | Result |
|---|---|---|
| **A1** SET P=1 ≥ 0.90× standalone Redis | `everysec`, no replicas, same workload, machine, affinity and clients | **NOT MET: 0.862×** (median of 5; per repetition 0.836–0.862), up from 0.812× |
| **A2** CPU efficiency | A credible CPU reduction or throughput gain, with no correctness, RSS, p99 or physical-write regression | **PASS.** CPU/op −6.0% (SET), −6.7% (INCR), −8.1% (HSET), −22% (P=16). User instructions/op −26%, −29%, −31%, −36%. Throughput +6.0–6.2%, all 15 repetitions positive. p99 −4% to −20%. `write(2)` per command unchanged. RSS: see below |
| **A3** P=16 preserved | No material regression | **PASS, improved**: +17.5%, 1.18× Redis, p99 2.12 → 1.70 ms |
| **A4** INCR and HSET | Not worsened; measured against the corrected comparator | **Improved, not passed**: INCR 0.725 → **0.769×**, HSET 0.803 → **0.851×** |
| **A5** Durability, compatibility | Bytes compatible, crash and restart correct, no false acknowledgement, replication correct, CI | **PASS** ([correctness](V0.6O-A-CORRECTNESS-TESTS.md)); CI on the PR |

**RSS.** opt's RSS is 1.2–1.7 MiB higher in every cell, *including the no-AOF control* (26.0 → 27.3 MiB), where the changed code never runs. So it is a fixed per-process offset, not per-key or per-write growth.
- The binaries differ by 2 KiB (10,303,808 vs 10,301,728 bytes).
- The offset is about 5% of a 26 MiB process at this run's tiny dataset, and does not scale with load.
- Its exact source (allocator arena or page layout) is **NOT VERIFIED**.
- It is not a material increase. Memory per key, a separate gate, is measured by 6P.

## Measurement uncertainty

| Source | Size | Effect on the conclusions |
|---|---|---|
| Run-to-run throughput (same server, different runs) | ±4% (Redis SET P=1: 137.9k, 148.1k, 142.8k) | Absolute ratios to Redis carry about ±0.03. SET P=1 opt is 0.836–0.862 across repetitions here; none reaches 0.90 |
| Within-run spread | 1–7% (P=1), 3–11% (P=16) | opt/base per repetition stays between 1.014 and 1.092; the direction is never in doubt |
| Swap in use (stale) | 3.9–4.1 GiB flat, memory PSI ≈ 0 | The same for every interleaved cell |
| `/proc` user/system split | tick-sampled | Instructions and cycles from `uprof` are the precise figures |
| Kernel-internal attribution | — | NOT VERIFIED (`perf_event_paranoid=2`) |
