# v0.6.0 Phase 6O-A0: the standalone AOF baseline, against standalone Redis

**Answer:**
- With AOF `everysec`, standalone Recached is at **0.79× standalone Redis 7.2.5 for SET at P=1**: median of 6 interleaved repetitions in two runs, range 0.77–0.84.
- INCR is at **0.71×** and HSET at **0.78×**, against a 0.90 target.
- SET at P=16 is at **0.94×**, Valkey 9.1.0 at 0.99×.
- The "0.80× standalone vs Redis" quoted after 6N-C5 came out about right, but by accident. It divided standalone Recached by **Redis with a replica attached**: `run-c5.sh`'s `redis` cells start a replica, because its `replicated` flag defaults to 1. That topology is not equivalent.
- 6N-1's standalone-vs-standalone 0.67–0.78× was the right method, and this run agrees with it.
- **Even with no persistence at all, Recached SET at P=1 is 0.81× Redis.** Removing every AOF-specific cost relative to Redis therefore could not bring SET P=1 to 0.90×. Part of the gap belongs to the no-persistence command path (6O-B).

### Host state

The host was rebooted at 11:37 local time (03:37 UTC). Two things then loaded the HDD:
- GNOME's file indexer re-indexed it after the boot.
- plocate's daily `updatedb` ran from 12:09 to about 12:24 local.

The drivers waited for both to finish: no `updatedb` and no compiler running, 1-minute load < 1.0 and IO PSI some avg10 < 5%, then 120 s of settling.

The IO pressure at the Recached cells' start is the order effect 6N-C6 identified: a P=16 cell's AOF writeback lands on the next cell. In A0, SET P=1 repetition 1 started at 5% IO PSI and repetitions 2 and 3 at 24–30%. Their ratios to Redis were 0.817 and 0.797/0.841, so the effect on this cell is within the run's noise. The validation run adds an IO-settle wait before every cell regardless.

**Generator capacity.** `redis-benchmark` used 0.84–1.19 CPUs of the 2 threads × 3 CPUs it had, so it was not saturated. At P=1 the server is not CPU-saturated either: 116k ops/s × 6.4 µs is 0.74 of a core. 50 clients at P=1 are round-trip bound, and per-command server time sets the round trip.

## The AOF policy ablation (A1a, SET P=1, medians of 3)

These are diagnostic configurations for isolating cost. They are **not** interchangeable durability settings.

| Configuration | Recached ops/s | Redis ops/s | Ratio | Recached CPU µs/op (user / sys) | Redis CPU µs/op (user / sys) | Recached user instr/op | Redis user instr/op |
|---|---:|---:|---:|---|---|---:|---:|
| no AOF | 148,137 | 181,802 | **0.815** | 4.51 (1.05 / 3.44) | 3.69 (0.72 / 2.96) | 5,246 | 4,806 |
| AOF `no` | 114,273 | 148,082 | 0.772 | 6.38 (2.29 / 4.09) | 4.43 (1.09 / 3.36) | 13,903 | 8,184 |
| AOF `everysec` | 114,260 | 148,082 | **0.772** | 6.42 (2.27 / 4.14) | 4.36 (1.13 / 3.26) | 13,902 | 8,175 |
| AOF `always` (50k requests) | 330 | 434 | 0.76 | 23.8 (5.8 / 17.8) | 16.4 (2.6 / 13.8) | 15,826 | 9,142 |

What it shows:

1. **`everysec` costs the same as `no` for both servers.** The background `fdatasync` once a second is not what costs throughput. The AOF *write path* is.
2. **AOF adds +1.91 µs/op to Recached and +0.67 µs/op to Redis:**

   | Server | user | system | user instructions |
   |---|---:|---:|---:|
   | Recached | +1.22 µs | +0.70 µs | +8,656 |
   | Redis | +0.41 µs | +0.30 µs | +3,369 |

   The user-space part is [the CPU profile](V0.6O-A-CPU-PROFILE.md).

   The system-time part follows `write(2)`: 0.1 calls per command at 5.3–7.1 µs each is 0.53–0.71 µs per command, which is the whole +0.70. Redis's +0.30 is consistent with larger batches per write. It appends once per event-loop pass over every ready client. Its writes per command are **NOT MEASURED**: Redis has no counter for them, and `/proc` `syscw` mixes its socket and file writes.
3. **The no-persistence gap is already 0.815×.**
   - Recached keeps 77% of its no-AOF throughput with AOF on; Redis keeps 81%.
   - Even if Recached's AOF path cost exactly what Redis's does, SET P=1 would still be at the no-persistence ratio, about **0.81–0.82×**, not 0.90×.
   - AOF work alone can close at most the 0.77 → 0.815 part of the gap.
4. **`always` is a fail-stop durability mode, not a throughput mode.** At 330 ops/s against Redis's 434, both servers are bound by HDD `fdatasync` latency (p99 0.4–0.5 s). It confirms that `always` is still paid for by every acknowledged batch: 0.04 writes per command, 25 frames per fsync batch.

## Answers

**1. What was the actual standalone Redis baseline?**

| Workload | Ratio to standalone Redis |
|---|---:|
| SET P=1 | 0.79× (pooled; 0.84× in A0, 0.77× in A1a) |
| INCR P=1 | 0.71× |
| HSET P=1 | 0.78× |
| SET P=16 | 0.94× |

For Valkey: SET P=1 0.83×, INCR P=1 0.79×, HSET P=1 0.81×, SET P=16 0.99×.

**2. Was the previously reported gap accurate?**
- The 0.80× number was close, but its method was not valid: the denominator was replicated Redis.
- 6N-1's standalone method gave 0.78 (SET), 0.67 (INCR) and 0.71 (HSET) on `e6fcd5b`, consistent with these results.
- Between then and now, SET improved slightly and INCR/HSET by about 5%, which is about this host's run-to-run spread.
