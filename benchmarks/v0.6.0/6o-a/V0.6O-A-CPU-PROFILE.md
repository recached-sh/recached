# v0.6.0 Phase 6O-A1: where standalone AOF P=1 spends its CPU

**Answer:**
- Turning the AOF on adds **≈ 5,860 user cycles per SET**, about half of everything the command costs in user space.
- The largest single part is **frame construction** in `broadcast_for_at` → `resp_push`: **1,921 cycles/op (16% of all user cycles)** at P=1, and 1,646 cycles/op (29%) at P=16.
  - Half of it is the allocator: 8 allocator calls per `SET` frame, mostly `realloc` growth.
  - Most of the rest is `format!`.
- The same frame build is 2,184 cycles for INCR and 2,583 for HSET. It also holds **≈ 90% of the AOF path's allocator time**.
- The connection gate costs ≈ 850 cycles/op on top of the no-AOF path, plus ≈ 620 cycles of scheduler work, mostly the one yield per settle that produces the 10-frame batches.
- The write-order stripes cost ≈ 680 cycles/op.
- The AOF's **system-time** cost, +0.70 µs/op, is `write(2)` at 0.1 calls per command.

The frame build is the largest reducible cost with no ordering or durability role, so it was optimized in [PR 2](V0.6O-A-OPTIMIZATION-DESIGN.md). The gate was examined and not changed (below).

## The path a standalone SET with AOF takes, from the source (`a697f54`)

```text
connection task (handle_tcp, the only worker)
  RequestDecoder::decode_any                    borrowed CommandRef
  try_execute_borrowed → None                   needs_write_log(): an AOF write may not run borrowed
  CommandRef::to_command                        owned Command: key String + value Vec (2 allocations)
  special-command match, is_write_command
  execute_ordered_write
    persistence_is_healthy, DEDUP check
    try_execute_unordered → None                (same reason)
    ReplHub::lock_write                         write-order stripes: tokio Mutex per key stripe
    execute_locked_write_identified
      execute_and_record_ref                    Instant::now; store.execute_reporting_ref; record_metrics
      apply_write_effects_identified
        needs_write_log / would_route / watch   checks
        now_unix_ms()                           SystemTime::now (vDSO clock_gettime)
        broadcast_for_at → resp_push            THE FRAME: format! per header, Vec growth (8 allocations)
        ServerState::on_write_logged
          AofWriter::append_client_write        AOF_DEFERRED task-local + Arc clone
            queue_only: AofShared::lock, AofBatch::push_frame (copy into the batch's Vec; Instant::now
                        once per batch), AofDone Arc
            DeferredAof::push                   ticket (std Mutex), deduplicated per batch
    stripes released
  Value::serialize_into(resp_buf)               "+OK\r\n"
  BufWriter::write_all
read batch done → BufWriter::flush
  AofGatedWriter::poll_settled
    DeferredAof::pop; Coalescer::should_yield
    Box::pin(async { yield_now; observe; lead; gate_wait })   once per settle
      tokio::task::yield_now                    other ready connections queue their frames
      AofShared::lead → perform → write(2)      one batch, ≈ 10 frames at P=1
      AofDone::wait (Notify) when another task performed it
  WriteHalf::poll_write → send(2)
```

What each piece is for:

| Kind | Pieces |
|---|---|
| Required for the store mutation | Decode, store execute |
| Required for the canonical AOF frame | `broadcast_for_at` (choose the replayable form, rewrite relative TTLs) and the encoding itself (`resp_push`) |
| Ordering | The stripes: AOF order equals store commit order across connections and workers |
| Optional observers | `would_route` and the watch checks: cheap when nobody listens |
| Scheduling | The gate's yield and lead, and the task re-poll |
| Physical I/O | `write(2)` per batch; `fdatasync` once a second on the blocking pool |
| Reply | `serialize_into`, `BufWriter`, `send(2)` |

### Allocations (request_path, in-process, one pipelined connection, AOF `everysec`)

The real `handle_tcp` loop with the AOF on, as in the profile above. The counting allocator wraps the shipped jemalloc on the server's thread. Medians of 5 runs × 200,000 commands, release build, in the sandbox (allocation counts do not depend on the host). Raw: [`request-path-allocs.txt`](request-path-allocs.txt).

Pipelining amortizes the gate's per-settle allocation, so these are per-command costs. The frame build is per command at any depth.

| Workload | no AOF | AOF, baseline `a697f54` | AOF, after PR 2 | **removed by PR 2** |
|---|---:|---:|---:|---:|
| SET | 1.00 | **11.05** | 4.05 | **7.00** |
| INCR | 0.92 | **11.95** | 2.95 | **9.00** |
| HSET (1 field) | 0.00 | **20.05** | 6.05 | **14.00** |
| MSET ×4 | 11.00 | **41.15** | 15.15 | **26.00** |
| SET EX | 10.92 | **23.98** | 13.98 | **10.00** |

`resp_push` alone went from 8 allocations per frame to 1, measured directly on both builds by `frame_encoding_6oa::a_frame_is_one_allocation_of_its_exact_size`. The rest of each reduction is the HSET/MSET part copies and the counters' `to_string`.

A SET still allocates 3 more times per command with the AOF on than without it:
- the owned `Command`'s key and value, since a logged write cannot run borrowed;
- its one frame.

The gate's boxed settle future and the batch's buffer are amortized over the pipeline here.

## Ranked bottlenecks

| # | Area | Cost (SET P=1) | Confidence | Reducible without touching ordering or durability? | Decision |
|---|---|---:|---|---|---|
| 1 | **Frame construction**: `resp_push`'s `format!` per header and `Vec` growth, plus HSET/MSET copying their parts and counters' `to_string` | **1,921 cycles** (16%); 29% at P=16 | High: samples plus allocation counts | **Yes.** The bytes are fixed, only how they are produced changes | **Optimize ([PR 2](V0.6O-A-IMPLEMENTATION.md))** |
| 2 | `write(2)` per batch | +0.70 µs system | High (counters) | Only through bigger batches, which is the gate's heuristic | Not this phase (see #3) |
| 3 | Gate: `poll_settled`, boxed future, `yield_now`, lead, plus the scheduler's re-poll | ≈ 850 + ≈ 620 cycles | Medium (scheduler context is shared) | The yield *is* the coalescing (1 → 10 frames per write; 6N-1 measured 2× throughput from it). The only removable piece measured is its per-settle allocation, ≤ 110 cycles (allocator time outside the frame build) | **Not changed** (below) |
| 4 | Write-order stripes | 681 cycles | High | No. This is the ordering contract (AOF order = commit order) | No |
| 5 | Ordered path and `on_write_logged` dispatch, owned `Command` | 662 + 505 + 154 cycles | High | Only by running AOF writes borrowed, a redesign of the logged write path | Recorded as a follow-up, out of scope |
| 6 | Clock reads | +222 cycles | Medium | `now_unix_ms` per write is needed for any relative-TTL command, and computing it lazily touches every arm | No (small) |

## The deferred gate (6O-A3): investigated, not changed

The brief's questions, answered from the counters and samples:

| Question | Answer |
|---|---|
| Does the gate yield unnecessarily at P=1? | No. One yield per settle, and each write then carries 10.0 frames. Without it (6N-1, `RECACHED_AOF_COALESCE=off`) a write carries 1.0 frame and throughput halves. |
| Does it report false batching gains? | No, not here. `coalesce_gained` is 1.0 per command at P=1 and `coalesce_missed` ≤ 3·10⁻⁵, and the batches do hold 10 frames, so the gains are real. At P=16, 0.0625 gains per command (one per settle). 6N-C4's false-gain case was the *inline* fan-out path at P=16, which the standalone gate does not use. |
| Does it lead batches opened by other writers? | Yes, by design. The first connection to resume after its yield performs the open batch for everyone in it. The other ≈ 9 find it complete (`done.result` set) and do not park: 0.0006 context switches per op. |
| Yields per command | ≈ 1 per settle, so 1 per command at P=1 and 1 per 16 at P=16 |
| Frames per batch | 10.0 (P=1), 161 (P=16) |
| CPU of the gate | ≈ 850 user cycles/op beyond the no-AOF `poll_settled`, plus ≈ 620 scheduler cycles |
| Would avoiding redundant leads help? | There are none to avoid. Over each timed run, `lead_busy`, `lock_contended` and `gate_parked` were all **0**, at P=1 and at P=16 (A0 repetition 1). A lead finding the batch already written costs one uncontended lock. |
| Would a change hurt P=16? | Any change to when it yields changes the batch sizes that P=16's 0.94× depends on |

**Conclusion.**
- The gate's cost is mostly the mechanism that makes the AOF affordable at all.
- The one removable piece, the boxed future per settle, is ≤ 110 cycles/op, about 1%. That is not worth a change to a cancellation- and fail-stop-sensitive state machine.
- No gate PR was opened (PR 3 skipped, as the brief allows).
- Bigger batches, to bring `write(2)` closer to Redis's once-per-event-loop write, would be a scheduling design question for a later phase.
