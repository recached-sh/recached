## What the reviewer ran

1. **Rebuilt the fixture independently.** In a scratch tree at `513075c` with `propagation.rs` and `core-engine/src/resp.rs` reverted to `a697f54`, the regenerated `broadcast-6oa-baseline.bin` was byte-identical (`cmp`) to the committed one. The fixture is the base's output, not the new code's.
2. **Checked the tests can fail.** With the base encoder, `a_frame_is_one_allocation_of_its_exact_size` fails ("resp_push allocated 8 times") and `aof_logged_writes_stay_within_their_allocation_budget` fails ("SET … 11.06 allocations per command, budget 5"). Both pass on `513075c`.
3. **Ran three differential tests of their own**, all passing:
   - 3,000 random part lists against the old encoder, checking exact capacity too. Part counts 0..40 plus 9/10/11/99/100/101; lengths at 10^k − 1, 10^k and 10^k + 1 up to 10^6, plus 0..50.
   - About 40,000 `i64` values through INCR/DECR/INCRBY/DECRBY: every power-of-ten boundary, both signs, `i64::MIN`, `i64::MIN + 1`, `i64::MAX`, random values.
   - HSET and MSET with 0, 1, 4, 5, 49, 50, 499 and 500 pairs, against the old copy-then-encode path.

## Checked and found correct (the reviewer's list, condensed)

| Area | Finding |
|---|---|
| Length calculation | Header 3 + d, each part 5 + d + len. `checked_ilog10` gives `None` for 0, so 1 digit. Every sum is checked; `3 + d` and `5 + d` cannot overflow (d ≤ 20) |
| `len_i64` saturation vs `format!("{}", usize)` | They differ only above `i64::MAX`, which no slice length or part count reaches on any supported target |
| Huge frames | A total past `usize::MAX` falls back to growing. One between `isize::MAX` and `usize::MAX` panics in `with_capacity`, exactly as the old growth path would. A single large value now needs less peak memory: the old code over-allocated about 2× through growth |
| `format_i64` | `i64::MIN` is exactly 20 bytes; 0 gives `"0"`; it matches `to_string` for every `i64` |
| Ownership and borrowing | The counter's digit buffer outlives the `resp_push` call. The HSET/MSET capacities cannot overflow. Field order is unchanged |
| Other `resp_push` callers | `dedup_mark_frame`, `dedup_refusal_frame`, `checkpoint_frame`, `ephemeral_aof_seed`, and the replica DEDUP unwrap (`replication.rs`) all produce the same bytes. `dedup_wrap`'s header parse sees the same bytes. The fixture includes the envelope, mark, refusal and checkpoint |
| Exact capacity downstream | Nothing appends to a frame after building it. AOF copies from `&[u8]`; replicas `to_vec` then `Arc`; WebSocket holds the `Vec` in `SyncPush`; nothing accounts memory with `capacity()` |
| Untouched | No new await points. No change to `apply_write_effects_identified`'s ordering, early acknowledgements, DEDUP outcome logging, shutdown or cancellation, `SyncRouter` routing or `push_keys`. Tenant isolation, replication and WebSocket bytes are unchanged |
| Test soundness | The allocation counter is thread-local with const-initialised `Cell`s, and `allocations_in` saves and restores `TRACKING`, so it is sound under parallel test threads. `Vec::with_capacity(n)` giving exactly `n` is documented for non-zero-sized types, so the capacity assertion does not depend on platform or allocator |
| Performance | The extra pass over parts and `ilog10` are negligible. Thin LTO with one codegen unit lets the core-engine helpers inline across the crate boundary |
