# v0.6.0 Phase 6N-C5: independent review

**Reviewer:** an engineer-agent that did not write the changes. It reviewed statically, ran only the focused test module, and was asked to construct counterexamples rather than approve. Benchmarks and host commands were off-limits to it.

**Scope:** PR 2 (`perf/v0.6n-c5-repl-fanout`), the replica sender change, together with the PR 1 instrumentation it builds on. PR 3 (multi-worker coalescing) is reviewed in [its own section](#pr-3-multi-worker-coalescing).

## PR 2: replica sender batching. Three rounds, final verdict **APPROVE WITH NITS**

The design changed twice under review. The merged design is the third.

| Round | Design reviewed | Verdict |
|---|---|---|
| 1 | **Yield before draining.** The sender received a frame, then `yield_now` before draining and flushing. | REQUEST CHANGES (2 Medium) |
| 2 | Round 1, plus a threshold that skips the yield on small channels or with a quarter of the byte budget queued, and a `send_yields` counter | REQUEST CHANGES (1 **High**) |
| 3 | **Drain on every wake, hold only the flush.** `RoundEnd` completes when tokio's deferred wake fires. Channels under 2048 frames flush on every wake. | **APPROVE WITH NITS** |

### Round 1 findings

| ID | Severity | Finding | Resolution |
|---|---|---|---|
| F1 | Medium | The skip threshold was a fixed 512 frames. With `RECACHED_REPL_BUFFER=16`, one round of ready writers fills the channel during the yield and a healthy replica is disconnected. The byte budget had the same problem: 64 writers × 256 KiB. | Round 2 added a capacity and bytes guard. Superseded by round 3, where channels under 2048 frames flush on every wake (test `a_small_channel_is_drained_on_every_wake`, mutant `no-small-channel-guard`). |
| F2 | Medium | While the sender is deferred it is pinned to one worker. Behind a long synchronous poll, frames from other workers pile up in the channel. | Round 3 drains on every wake, on any worker. Only the send waits for that worker's round. The lag bound is documented (S3). |
| F3 | Low | The lag bound was unstated | Documented in the sender comment |
| F4 | Low, pre-existing | `rd.read_exact(&mut ack_buf)` inside `select!` is not cancel-safe. A partial ack read lost to a won `recv` branch misaligns later acks. This affects only the lag metric. | **Recorded as a follow-up**, not changed. It predates 6N-C5, and the change does not make it worse. |
| F5 | Low (test) | The cancellation test did not cancel the sender: `server.abort()` aborts only the accept loop. | The test keeps the per-connection `JoinHandle`s and aborts the sender while its flush is held (`aborting_the_sender_before_its_round_flush_strands_nothing`). |
| F6 | Low (test) | The skip branch was untested; an "always yield" mutant survived. | Superseded by the round 3 tests and mutants |
| F7 | Low (test) | TLS, full sync, acks, small capacities untested | Small capacity and acks are now tested. TLS and full sync use the same generic sender loop and are covered by the existing replication suites (`replication_dedup`, `repl_6l_cpu`, `integration_6nc`), which pass in both fan-out modes. |
| N1, N2 | Nit | Comment wording. `send_frames` excludes partial-resync frames. | Fixed |

### Round 2 findings

| ID | Severity | Finding | Resolution |
|---|---|---|---|
| **R1** | **High** | The round 2 guard is checked only before the yield. A round has a time bound, not a frame bound. Example: no AOF, default capacity 4096, 32 connections pipelining 128 SETs per poll on the sender's worker. Those queue about 4096 frames while the sender is deferred, and the healthy replica is disconnected. Before 6N-C5 the sender ran after each poll. | **Redesigned (round 3).** I tried the reviewer's suggestion, a high-water `Notify` plus an adaptive back-off, and it still overflowed. A trace showed why: once a round ends, the deferred wake queues the sender behind the tasks that round woke, and a `try_send` or `notify` cannot move a task that is already queued. Round 3 drains on every wake, so the queue stays at about one poll within a round (test `one_round_of_pipelines_is_drained_as_it_is_queued`, 40 × 128 frames against 4096; mutant `no-drain-while-held`). |
| R2 | Medium | F2 is documented but not mitigated | Moot in round 3: draining continues on any worker. |
| R3 | Low | The F5 test depends on tokio 1.54's defer and LIFO order | Comment added: a scheduler change makes it fail, not pass. |
| R4 | Low | The byte guard had no behavioural test | `large_frames_do_not_overflow_a_batching_sender`: 32 × 2 frames of 32 KiB against a 1 MiB budget |
| R5, R6 | Nit | Test name; mutation logs in `/tmp` | Renamed; logs go to a `mktemp -d` directory |

A bug in the test tooling surfaced during round 2. `run-mutants.sh` restored the source with `mv` of a copy taken *before* mutating, so the restored file's mtime was older than the last mutant's build. Cargo kept running the last mutant's binary, and one suite run tested a mutant. The script now `touch`es the restored file. Every result in this phase was re-run after the fix.

### Round 3 findings

| ID | Severity | Finding | Resolution |
|---|---|---|---|
| S1 | Medium (claim) | "The queue behaves as before" is not exact. When a round ends, tokio pops the defer list from the back and each wake pushes the LIFO occupant to the back of the run queue. The sender's single round-end entry was registered early, so it runs *behind* the writers that round deferred: coalesced-AOF writers, and pipelines that ran out of coop budget. Those writers can queue up to a round before it drains. | **Comment and commit message corrected.** I tried the suggested mitigation, re-arming the wait after every drain. It did not help: the reproduction still disconnected 10 of 10 runs. It remains as an equivalent mutant. |
| S2 | Low | `RoundEnd` kept the waker from the poll that armed it | Fixed: it stores the latest poll's waker and re-checks `fired` after swapping, so a wake that lands in between is not lost. |
| S3 | Low | A held flush of fewer than 512 frames waits for the arming worker's next park or maintenance tick. A long synchronous poll there is replica lag (no disconnect). | Documented in the sender comment |
| S4 | Nit | The single-round pipelined test did not cross a round boundary | Renamed `one_round_of_pipelines_is_drained_as_it_is_queued`. The round boundary is covered by the ignored reproduction below. |

### The recorded exposure (R1 residual)

When a scheduling round of deep pipelines produces more frames than the replica channel holds (default `RECACHED_REPL_BUFFER=4096`), a sender queued behind that round is overrun, and the replica is disconnected and resynchronized.

**This is pre-existing.** Before 6N-C5 the sender reached the same position whenever a replica acknowledgement woke it through the I/O driver, behind the connections that became ready in the same poll. The reproduction is `pipelined_rounds_at_default_capacity_with_acks`, which is `#[ignore]`d because it fails by design. It runs 40 writers × 128-frame polls resuming together each round, against a scripted replica that acknowledges every burst as `run_repl_client` does. Measured on the 6N-C5 host:

| Sender | Disconnected |
|---|---:|
| Before 6N-C5 (flush on every wake: the `flush-every-wake` mutant) | 8 of 10 runs |
| 6N-C5 (held flush) | 10 of 10 runs |

The reviewer's reading: the comparison is fair, but it cannot tell the designs apart. Each round makes 5120 frames against 4096 slots, so either design fails once the sender lands behind a round. The old sender gets there by chance (about 18% per round); the new one every round. In a sustained deep-pipeline workload, both disconnect within seconds.

The root cause is a channel sized in frames that is smaller than one round of deep pipelines. Changing it means changing a default (size the channel by bytes, or raise `RECACHED_REPL_BUFFER`). That is a maintainer decision and is listed as a follow-up in the [release gate](V0.6N-C5-RELEASE-GATE.md). The peak queue depth, old against new, is measured in [performance](V0.6N-C5-PERFORMANCE.md#replica-queue-peak).

### What the reviewer confirmed

| Guarantee | Finding |
|---|---|
| A. Replication ordering | Holds. Frames are drained FIFO, written in order and flushed once, and offsets are assigned under the stream lock exactly as before. `concurrent_writers_stream_exactly_the_backlog` compares the live stream with a backlog resync under 4 workers. |
| B. Full sync | Untouched. The cut is still made under `lock_all_writes`, with registration before the barrier drops. |
| C. Promotion | Untouched (replica side) |
| D. Durability | Holds. `on_write_logged` still awaits the AOF stage before `fan_out`. Only the socket send moves, and no client acknowledgement depends on it. |
| E. Backpressure | Holds within a round. Bounded channel, byte budget and bounded backlog are unchanged. Frames written into the 64 KiB `BufWriter` have released their byte charge, as before. Round boundaries: see above. |
| F. Cancellation | Holds. An aborted sender has drained its channel, so no byte charge stays accounted, nothing held reaches the replica, and the next write unregisters it. A closed channel flushes what is buffered. |
| `RoundEnd` | `Send + Sync`, `Unpin`. Off a worker it fires at once. The task → waker → `Arc<RoundWake>` reference is released when the task ends. A stale defer entry can only cause a spurious wake. Liveness: while a flush is held the future is polled, so it is armed, and it fires at the worker's next park or maintenance tick. |
