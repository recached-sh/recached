# v0.6.0 Phase 6N-C5B: replica sender flush batching

**Change:** PR 2 (`perf/v0.6n-c5-repl-fanout`), on top of the PR 1 instrumentation.

**Scope:**
- `handle_replica`'s streaming loop (the replica sender task), plus a small `RoundEnd` future.
- No change to `ReplHub::fan_out`, `write_order`, offset assignment, the backlog, the channel, the byte budget, the AOF path, the replica side, or any wire or persistence format.
- `RECACHED_AOF_FANOUT=inline` is still the default. Option A was not implemented.

**Why this optimization:** the [replication profile](V0.6N-C5-REPLICATION-PROFILE.md) found that a replica's cost per write is dominated by **flushes per write**, not by work per frame. Each flush is one socket `send` and, on the replica, one acknowledgement that the primary must receive. The old sender flushed after almost every writer:

| Workload | frames per flush |
|---|---:|
| P=1, `coalesced` | 3.6 |
| P=16, `coalesced` | 3.8 |
| P=16, replication without AOF | 28.8 |

The per-frame candidates the brief listed (frame copy, backlog, stream lock, channel enqueue) were measured, and together they come to a fraction of that. See [why the other candidates were not implemented](#candidates-not-implemented).

## Mechanism

### Before

```text
writer task (worker W)                 replica sender task
  fan_out(frame)
    try_send ───── wakes ──────────►  [LIFO slot of W: runs right after this poll]
  ... poll ends                         recv frame; drain what is queued (1–4 frames)
                                        flush  ──► send(2) ──► replica wakes, applies,
                                                               acks ──► recv on primary
next writer ...                         (repeat per writer)
```

Tokio puts a task woken from a worker into that worker's LIFO slot. So the first `try_send` after each drain made the sender the next task to run, and it flushed what one writer had queued.

### After

```text
writer task                             replica sender task
  fan_out(frame)
    try_send ───── wakes ──────────►  recv frame; drain all queued into the BufWriter
                                        flush held until the round ends: RoundEnd armed
next writer: fan_out ── wakes ────►   drain into the BufWriter (no syscall)
...                                     ...
worker parks / maintenance tick ───►  RoundEnd fires → one flush for the whole round
```

The sender **still drains its channel on every wake**, as it did before. Only the socket send is held, until one of three things happens:

| Condition | Code | Effect |
|---|---|---|
| The **scheduling round ends**: the worker has run its other ready tasks (it parks), or reaches its maintenance tick, every 61 polls | `RoundEnd` | One flush carries the round |
| `REPL_SEND_BATCH_FRAMES` (512) frames are buffered | unchanged constant | Flush now, so a busy primary still flushes regularly |
| The channel is smaller than `REPL_SEND_DEFER_MIN_CAPACITY` (2048 frames; default 4096) | new constant | Flush on every wake, exactly as before. See [review F1](V0.6N-C5-INDEPENDENT-REVIEW.md). |

`RoundEnd` exists because tokio's own `yield_now` future returns `Ready` on its second poll, whether or not the deferred wake has fired. Keeping it across the sender's wakes would end the "round" at the next writer's wake. In the first prototype that collapsed batching to about 2 frames per flush. `RoundEnd` polls `yield_now` once, through a wrapper waker that records when tokio's deferred wake really fires. It then completes only after that, however often it is polled, and wakes the waker of its latest poll (review S2).

### What changes and what does not

| Property | Before | After |
|---|---|---|
| Offsets, order of frames on the wire | assigned under the stream lock, sent FIFO | **unchanged** |
| Backlog contents and partial resync | — | **unchanged** |
| AOF stage before fan-out | `on_write_logged` awaits it, then `fan_out` | **unchanged** |
| What a client waits for | its AOF stage (if any); never the replica | **unchanged** |
| Channel and byte budget; disconnect when full | bounded; `try_send` never blocks | **unchanged**. Drained on every wake, as before. |
| When bytes reach the socket | after every wake | at the end of the scheduling round, or at 512 frames |
| Replica lag | — | up to one round longer. Sub-millisecond in the benchmarks, and as long as a long synchronous poll on the arming worker if one runs. See [performance](V0.6N-C5-PERFORMANCE.md). |
| Order of tasks at a round boundary | the sender ran next (LIFO) after each writer | once the round ends, the sender runs behind the tasks that round deferred (review S1). Before 6N-C5, an acknowledgement wake put it in the same position. See [the recorded exposure](V0.6N-C5-INDEPENDENT-REVIEW.md#the-recorded-exposure-r1-residual). |

### Memory ownership

- No buffer type changed: frames are still `Arc<Vec<u8>>`, shared by the backlog and each replica queue.
- Frames written into the sender's 64 KiB `BufWriter` have left the channel and released their byte charge. That was already true before, between the write and the flush; it now lasts until the end of the round. The `BufWriter` writes straight to the socket when it fills, so the bytes outside the charge are bounded by 64 KiB per replica.
- RSS, steady state: see [performance](V0.6N-C5-PERFORMANCE.md).

### Instrumentation (PR 1, no behaviour change)

`INFO replication` gains:

| Field | Meaning |
|---|---|
| `recached_replication_offset` | newest fanned-out offset, in frames |
| `recached_replication_send_flushes` / `_send_frames` | flushes and live frames written by replica senders. Frames per flush is the batching achieved. |
| `recached_replication_send_queue_peak` | deepest queue a sender found when it woke, against `RECACHED_REPL_BUFFER` |
| `recached_replication_send_deferred` (PR 2) | flushes held to the end of a round |

The cost is one relaxed add per flush and one `fetch_max` per wake.

## Candidates not implemented

The profile measured these directly (LBR call-stack samples, user cycles per operation; see [the profile](V0.6N-C5-REPLICATION-PROFILE.md)).

| Brief candidate | Measured | Decision |
|---|---|---|
| 1. Frame copy (`resp.to_vec()`) | **≤ 81 cycles/op**: all of `on_write_logged`'s own time with no AOF, which includes the copy, its allocation and the dispatch. That is ≤ 0.02 µs, or < 0.3% of CPU/op. It is paid with or without a replica attached. | **Not implemented.** It is below run-to-run noise, and it would need `on_write_logged` to take ownership of the frame, which the WebSocket push also consumes. |
| 2. Per-write backlog | `fan_out` (backlog push and trim, `Arc::new`, offset, lock) is 320–400 cycles/op in every replication-enabled configuration | **Not implemented.** It is small, it is paid with no replica attached too, and amortizing it means batching fan-out across writes, which the brief forbids ahead of the AOF stage. |
| 3. Sender wake-ups / buffered socket writes | sender task about 950 cycles/op user, plus about 0.9 µs/op kernel, all per flush | **Implemented** (this change) |
| 4. Stream mutex | no samples in the futex or lock-slow paths with one worker. The lock is held only inside `fan_out`. | **Not implemented.** No evidence of cost. |
| `gauge!` in `fan_out` | zero samples: the benchmark runs with metrics off (a no-op recorder) | **Not measured** with Prometheus on. Noted as a follow-up. |

## Rollback

The change is confined to the sender loop. Two ways back:
- Revert the PR 2 commit. The PR 1 instrumentation can stay, since it has no behaviour change.
- Operationally, with no code change: setting `RECACHED_REPL_BUFFER` below 2048 restores flush-on-every-wake. The cost is a shorter replica queue before a slow replica is disconnected, so treat it as an emergency switch, not a tuning knob.
