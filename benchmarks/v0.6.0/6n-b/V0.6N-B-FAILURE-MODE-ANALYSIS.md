# v0.6.0 Phase 6N-B: concurrency scenarios and failure modes

**Applies to:** the preferred design ([`V0.6N-B-WATERMARK-DESIGN.md`](V0.6N-B-WATERMARK-DESIGN.md)) in `RECACHED_AOF_FANOUT=watermark` mode.
**Source:** `dev` `a90e08d`.
**Invariant names:** [`V0.6N-B-ORDERING-INVARIANTS.md`](V0.6N-B-ORDERING-INVARIANTS.md).

For each scenario:
1. what happens;
2. which rule makes it correct;
3. what would break it (the counterexample the tests must catch).

## Part 1: the ten scenarios

### S1 — Same-key concurrent writes

```mermaid
sequenceDiagram
    participant A as conn A
    participant B as conn B
    participant K as stripe(k)
    participant Q as AOF queue
    participant P as performer
    participant O as observers
    A->>K: lock
    A->>A: X: k=1, capture (payload "1")
    A->>Q: stage → s=7
    A->>K: unlock
    B->>K: lock (after A's unlock)
    B->>B: X: k=2, capture (payload "2")
    B->>Q: stage → s=8
    B->>K: unlock
    P->>Q: take batch {7,8}
    P->>P: write(2)
    P->>O: release 7 then 8 (offsets n, n+1; keychange 1 then 2)
    P->>P: done.complete
    Note over A,B: both gates release; A's reply and B's reply
```

**Correct because:**
- the stripe hand-off orders `stage(7)` before `stage(8)` (N1);
- seqs order the file;
- the single performer releases in seq order (N2);
- every observer queue is FIFO;
- payloads were fixed at capture (N8), so the keychanges carry 1 then 2.

**Acknowledgments:** each reply follows `done.complete`, which follows release (N4). Replies on different connections have no order requirement, as today.

**Breaks if:**
- payloads are read at release time: both would carry "2", hiding the intermediate value and making a delta subscriber's `INCRBY` applications wrong;
- two performers could release concurrently: `busy` must stay held through release;
- staging happened after dropping the stripe.

### S2 — Independent writes

Keys `a` and `b` are on different stripes, so the writers run concurrently on different workers. Each takes the AOF queue lock once (already the case on the deferred path).

| What | Order | Rule |
|---|---|---|
| Staging | Whatever order they reach the queue lock | — |
| File, replication offsets, pushes | That staging order | N2 |

This is **stronger** than today, where an independent pair can reach the file and the replication stream in different orders (current architecture §6).

**What parallelism remains:**
- execution and capture fully parallel across stripes;
- the queue lock is a short critical section;
- the performer is serial, as today.

**What is lost:** nothing that exists today. The inline path already serializes on `write(2)` per write.

### S3 — WATCH racing EXEC

| Case | Who takes stripe(k) first | Outcome |
|---|---|---|
| (a) | A (the writer) | A sets `dirty[B]` under the stripe (N5) and stages. B's EXEC takes stripe(k) after A's unlock, reads `dirty = true` and aborts (nil). It does so **even though A's batch may not be written yet**. An abort on an unwritten conflicting write is safe: it only makes B retry |
| (b) | B (EXEC) | B commits with current reads. A executes after, and B's transaction has already finished; A's `dirty[B]` mark lands after `unregister_all_watches`, so it finds no subscriber and nothing carries over |

```text
(a)  A: lock(k) → X(A) → dirty[B]:=1 → stage → unlock(k)
     B:                                         lock(k ∪ Q) → dirty? 1 → abort
```

**Breaks if** dirtiness travels on the staged keychange (`watch_rx`): B reads an empty channel and commits on a stale read. This is model property P3, reproduced by the `naive` and `drain-only` variants.

**Second-order case: a staged keychange delivered after the abort.**
- **Today:** the WS `watch_rx` arm sets `watch_dirty = true` on every notification. Under staging it would wrongly dirty the *next* transaction.
- **The design:** the arm stops setting it (WATCH section of the design). A late keychange is only pushed.

**Information exposure:** an abort reveals that *some* watched key changed before its write is durable. This is the same class as a GET seeing it (O2). It is not an acknowledgment and makes no durability claim.

### S4 — Snapshot (`SAVE`) during pending writes

1. `save()` takes `save_lock`, then `lock_all_writes_drained`. Holding all stripes, it waits until `released ≥ issued` (N6). Every staged write is now written, under the required stage, with its effects released.
2. Marker `append` + `flush`: unchanged. The marker gets a seq after every staged write.
3. `persist_dedup`, `durable_snapshot`, `save_snapshot_entries`: the store holds exactly the released writes.
4. `truncate` (a zero-frame batch), seed `append`s, `flush`: no effect is pending across the truncate.

**Correct without the drain too**, because the marker's `flush` waits for every earlier batch. The drain is there so that "snapshot ⊆ released" holds and the truncate never runs with effects in flight.

**`always` failure inside the drain:** fail-stop. The `SAVE` client gets no reply, as today.

### S5 — Replica attaches mid-batch (the consistent cut)

```text
F: lock_all_writes → I := issued → wait(released ≥ I)
   → O := repl offset; snapshot (or backlog after the requested offset) + DEDUP table
   → register sender(sent = O) → unlock
```

**The cut:**
- **Before the cut:** writes with `s ≤ I`. They are in the snapshot, and their replication frames carry offsets `≤ O` (released before `O` was read).
- **After the cut:** writes with `s > I`. They execute after `unlock` and are streamed with offsets `> O`.

**Breaks if there is no drain:**
- a staged write is in the snapshot **and** later released with offset `O+1` into the new replica's channel: applied twice, so an `INCR` diverges (model P4);
- the snapshot is transmitted before that write's `write(2)` (model P2).

**Partial resync:** `resume_frames` reads only released frames (the backlog holds nothing else). Without the drain, staged frames would get offsets `> O` and reach the new channel, which is also correct. The drain is kept for uniformity.

### S6 — AOF partial-write failure

The performer's `write(2)` lands `n` bytes of batch `[s_a..s_b]` and then fails.

| Question | `everysec` / `no` | `always` |
|---|---|---|
| File afterwards | `cut_back` keeps the whole frames that landed and cuts the torn one; or it records `torn_at` and refuses later appends (unchanged, G9) | Same cut-back, then `fail_stop` |
| Frames considered complete | For durability claims: none of the batch (the outcome is per batch). The whole frames that stayed in the file do replay after a crash | — |
| Propagated? | **Yes, the whole batch** (G3, decision D2): memory has them, later writes get MISCONF | **No** (N9): the process exits before release |
| Acknowledged? | Yes, with a normal reply (unchanged contract); persistence latched | No reply; exit 74 |
| Pending notifications | Released with the batch | Never released; dropped with the process |
| Watermarks | `settled`/`released` advance; `gap_from := s_a`; `durable` frozen at `< s_a` until a checkpoint truncates the file | Frozen |
| Torn-write repair vs watermark | No interaction. The repair acts on the file before `settle`. Watermarks are seq-based and never refer to file offsets | — |

**Why not split the batch and release only the frames that landed whole?**
- It would give a failed `everysec` batch two different outcomes for its writers, but every writer of the batch already gets the same reply and MISCONF latch.
- Under `always` it would be wrong outright: frames that landed but were not fsynced are not durable (the PR #125 F3 page-cache caveat).

### S7 — `always` fail-stop

1. The performer (blocking pool) runs `perform`; write or fsync fails.
2. `settle`, then `fail_stop`: `stopped := true`, then `process::exit(74)` on this thread. The batch's `done` is never completed, `busy` is never cleared, and **`release` is never reached**.
3. Concurrent paths that could emit something:

| Path | Why nothing escapes |
|---|---|
| Another performer | Impossible: `busy` is held |
| An earlier batch's release, still running | Can only be for seqs `< s_a`, which were fsynced. Allowed |
| `+DUP` waiters / drained barriers | Wait on `released`, which never reaches `s_a` |
| `flush` failing outside `busy` | Already parks in `settle` and checks `stopped` (unchanged). `release` additionally checks `stopped` first (N9) |
| TCP gate | `poisoned` is sticky (unchanged) |
| Test `Latch` mode | `done` completes with `Err` and **without** release. `wait_released` returns `Err` when `stopped` |

**Mutation the tests must catch:** releasing before `settle`, or not checking `stopped` in release. Either lets a replica frame leave for a batch that is never acknowledged.

### S8 — Scope narrowing while notifications are staged

1. A WS connection holds scope `tenant:a:*` with a QSUB `tenant:a:*`.
2. A write to `tenant:a:x` stages a push and a keychange for it.
3. The client sends `SYNC TOKEN` with a narrower grant before release.

| Sub-case | Outcome |
|---|---|
| The new token covers every held subscription | Routes are updated (`set_routes`) and `sync_scopes` replaced before the reply. The staged push meets `forwards_push` at dequeue, under the **new** scopes (N11). **The staged keychange is re-authorized at dequeue as well** (design §11, review RV-2): current scopes, the held subscription and the subscription epoch. Without that check, a socket that QUNSUBs a pattern and then narrows away from it (not a "revoking" change, since the pattern is no longer held) received a late keychange for the old scope |
| The new token does not cover a held subscription, or the subject changed | The connection is answered and **closed** (`WS_CLOSE_SCOPE_CHANGED`). Staged items are released into closed channels: `try_send` fails, and the item is dropped and its budget charge released |
| Token expiry | The expiry arm closes the connection. Today the push arm also checks `token_lapsed` at dequeue, but the `q_rx`/`watch_rx` arms do not. The design adds the check to both arms (WATCH section of the design), so a staged keychange cannot be forwarded in the gap between the deadline and the expiry arm firing |

**Breaks if** authorization moved to capture time (a "pre-approved" push), or if narrowing kept a revoked QSUB alive instead of closing.

### S9 — Client disconnect with pending effects

| Who disconnects | What happens |
|---|---|
| The writer (TCP) | Its `AofGatedWriter` drops and **leads** its queued batches (unchanged). The batch and its effects belong to `AofShared`, not to the connection, so other observers still receive the write: it is applied in memory and will be in the AOF |
| The writer (WS) | The command future is dropped mid-await. The WS path calls `lead()` **before** its coalescing yield and before awaiting (design §6, review RV-3), so a dropped future has always already led. Nothing relies on the `everysec` ticker, which does not run under `always` or `no` |
| Ephemeral release after disconnect | `release_ephemeral_state` runs after the connection's gate is dropped and outside its deferral scope. Under the design's ticket rule it leads after dropping its guards (RV-3) |
| An observer | Its mailbox, `q_rx` or `watch_rx` receiver drops. At release, `try_send` fails and the item is dropped; budgets are released by `Drop` (`WatchNotif`, `QueuedReplFrame`, mailbox state). Registry entries are removed at teardown (`unregister_all_*`) as today |
| Memory | Reclaimed when the batch is released. No connection state is referenced by an effect, apart from channel senders, which tolerate a closed receiver |

### S10 — Replica promotion with outstanding effects

- **On the replica being promoted:** replicated writes stay on the inline path (O4; replica apply is unchanged). No staged effects exist from them.
- **Client writes:** refused (`READONLY`) until promotion, so none exist either.
- `promote_to_primary` takes the drained barrier anyway, so the code stays correct if a later PR stages replica-side writes.
- **6L R2** still holds: a replicated frame holds its stripes while it checks `still_following` and applies, so it is applied before the barrier or refused after it.
- **Demotion does not exist at runtime.** Only `REPLICAOF NO ONE` is a command. A node's replica role is set at startup (`main.rs:699`), so no staged primary write can meet a role change. (The reviewed draft discussed a `REPLICAOF host port` demotion; review RV-14 corrected it.)
- **Replica-side DEDUP records:** on a chained replica, mark-only and refusal records are applied today without stripes or `still_following` (`replication.rs:1623–1632`). They can miss a sub-replica's cut and land after promotion (review RV-7). This is pre-existing and fixed independently (PR 0d).

## Part 2: further failure modes

### Crash consistency (process crash at any point)

| Crash point | AOF | Replicas / WS | Client |
|---|---|---|---|
| After execute, before stage | Not in AOF | Not released | No reply |
| After stage, before `write(2)` | Not in AOF | **Not released** | No reply |
| After `write(2)`, before release (`everysec`) | In the page cache: survives a process crash | Not released. The replica resyncs on the new run id; WS clients reconnect | No reply (an unknown outcome; DEDUP resolves it) |
| After release, before reply | In AOF | Released | No reply (unknown outcome) |

**Invariant B holds at every point:**
- **today's inline path:** no observer ever holds a write the AOF lacks;
- **watermark mode:** the same, plus the reply never claims more than the AOF has.

### DEDUP

| Case | Outcome |
|---|---|
| Original on TCP (watermark or today's deferred path), retry on another socket before the original's release | `+DUP` waits on `wait_released(mark.seq)` (N7). If the batch then fails under `always`, the process exits before either reply |
| Retry after a crash | The mark is in the AOF inside the write's envelope; replay restores both or neither (G7, unchanged) |
| Refusal outcome | `log_dedup_outcome` stages a refusal frame. A replay answered from the remembered refusal waits for its seq the same way |
| `CLIENT DEDUPBARRIER` | Unchanged: a per-socket rule about deferring later writes, not about the AOF |

### Backpressure

| Situation | Behaviour |
|---|---|
| Slow replica | `fan_out_batch` drops it when its channel (4096) or byte budget (8 MiB) is full. It reconnects and resyncs. The primary never waits |
| Slow WS client | Mailbox gap: close with sync-gap; the client reconnects with a fresh `qstate` |
| Slow watcher | Notification budget or queue overflow: disconnect (unchanged) |
| AOF disk stall | The performer blocks in `write(2)` (inline on a worker under `everysec`, as today) or `fdatasync` (blocking pool). `pending` grows to the cap, after which writers wait inline under their stripes (N10). Bounded |
| Replication disconnect | Its sender's channel closes; `fan_out_batch` drops it (`Closed`). No effect on staging |
| AOF writer failure | §S6 / §S7 |
| Sustained writes faster than the disk | Degrades to inline throughput at the cap. Memory ≤ cap + one frame per in-flight writer |

**Deadlock argument (backpressure):**
- A writer waiting inline at the cap holds only its stripes.
- The performer needs none.
- Barriers that wait (drain) also hold only stripes, plus `save_lock` for `SAVE`.
- Nothing in release waits on anything a writer or barrier holds.

### Shutdown and cancellation

| Event | Behaviour |
|---|---|
| SIGTERM | The shutdown save runs `save()` → drained barrier → every staged effect released → snapshot → exit. Staged replica frames reach the sender channels; whether the sender flushes them before exit is best effort (as today for frames already queued) |
| Abrupt exit | Staged effects are lost with the process; equivalent to a crash at "after stage, before `write(2)`" or "after `write(2)`, before release" |
| Gate dropped mid-yield | `Drop` leads (unchanged). Release then runs on the dropping thread. It is synchronous and works without a runtime |
| `wait_released` cancelled | Its `Notify` registration is dropped; no state to clean up |
| Drain cancelled (a barrier holder's task dropped) | Its guards drop, and the batch still completes through other leaders. The barrier itself has no side effects before its cut |
