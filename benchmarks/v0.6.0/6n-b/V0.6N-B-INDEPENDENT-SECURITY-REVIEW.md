## Findings

### RV-1 — High — every reply path must wait for release (design)

**Counterexample:**
- The draft gated replies only through the TCP `AofGatedWriter` and "after a write command" on WS.
- A WS `EXEC` runs `execute_locked_write`, then `ws_send!(results)` (`connection.rs:1755–1806`). `EXEC` is not a write command, so its reply would leave before the staged batch's fdatasync.
- WS admin and out-of-scope DEDUP refusals (`connection.rs:1585–1596`, `1641–1646`) stage a refusal frame, then reply at once.
- The draft's `stage()` registered no ticket with the TCP gate. Today only `append_client_write` does.

**If the batch then fails under `always`:** the process exits 74 after a client was told its transaction applied.

| | |
|---|---|
| **Violated** | G1, N4, brief invariant C |
| **Mitigation (adopted)** | Ticket-registration rule (design §6). Every stage is registered with the reply owner: the TCP gate's tickets, or a WS task-local high-water seq awaited before **every** WS reply. Outside a connection, the caller leads after dropping its guards. New invariant **N13** |
| **Architecture change** | No |
| **Re-review** | Required (round 2) |
| **Confidence** | CONFIRMED |

### RV-2 — High — late keychange after unsubscribe and narrowing (design; window exists today)

**Counterexample:**
1. A strict socket holds `QSUB tenant:a:*` and `QSUB tenant:b:*`.
2. `SET tenant:a:x` stages a keychange for it.
3. The client sends `QUNSUB tenant:a:*`. This does not drain `q_rx` (`connection.rs:2050`).
4. The client sends `SYNC TOKEN` for `tenant:b:*` only, same subject. This is not "revoking", because no held pattern is lost.
5. Release puts the keychange into `q_rx`. The arm forwards it without any check (`connection.rs:2334`).

The same works with UNWATCH + WATCH. Today the window is enqueue-to-dequeue; staging stretches it to a batch plus an fsync.

| | |
|---|---|
| **Violated** | N11 (draft), brief invariant G, cross-scope isolation |
| **Mitigation (adopted)** | Keychanges are re-authorized at dequeue (design §11), on both arms and in every mode (PR 3). Four checks: token not lapsed; current scope allows reading the key (for a pattern sentinel, the pattern); subscription still held; subscription epoch unchanged. N11 revised |
| **Architecture change** | No |
| **Re-review** | Required (round 2) |
| **Confidence** | CONFIRMED for the design; PLAUSIBLE for today's window (needs a test) |

### RV-3 — Medium — liveness: staged batches with no leader (design)

**Counterexample:** under `always` and `no` there is no flush ticker (`main.rs:777` runs only for `everysec`). These stage sites had no leader:
- `release_ephemeral_state` after `drop(writer)` (`connection.rs:1069–1075`);
- the memory-eviction sweeper;
- a WS command future dropped during its pre-lead yield.

Their DELs, replica frames and pushes would wait for unrelated traffic. The draft also contradicted itself on whether stage leads.

| | |
|---|---|
| **Mitigation (adopted)** | A stage outside a connection leads after dropping its guards. The WS path leads **before** yielding. No reliance on the ticker (design §6, §12; failure analysis S9) |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-4 — Medium — the replica apply path is not "unchanged" if `on_write_logged` stages (design)

**Counterexample:** `apply_repl_frame` and `apply_dedup_envelope` call `on_write`/`on_write_logged`, then `notify_write` and `tx.send` directly (`replication.rs:1625–1665`, `1731–1734`). If `on_write_logged` staged, a replica's watchers and pushes would precede its own AOF write.

| | |
|---|---|
| **Mitigation (adopted)** | The replica path calls an explicit `on_write_logged_inline` in every mode (design §8; PR 4) |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-5 — Medium — a client can stall every writer through QSUB's drain (design)

**Counterexample:** the draft drained QSUB while holding all 256 stripes, which costs one fdatasync under `always`. A scoped browser looping QSUB/QUNSUB stalls all writers once per iteration. The pattern limit does not bound the loop.

| | |
|---|---|
| **Mitigation (adopted)** | QSUB takes its cut and registers under the barrier, records `I = issued`, **drops the stripes**, then waits for `released ≥ I` before sending `qstate` (design §9, N6). The full drain remains only for replica sync, promotion and SAVE |
| **Architecture change** | No |
| **Re-review** | Required (round 2) |
| **Confidence** | CONFIRMED |

### RV-6 — Medium — strict WS client can take the global write barrier (pre-existing)

**Counterexample:**
1. A strict WS client with any token sends `DEDUP c <n> FLUSHDB`.
2. The command is refused as Admin.
3. The refusal path takes `lock_commands([Dedup(FlushDb)])` (`connection.rs:1589`). `ordering_key_refs` of FLUSHDB is `None`, so this locks every stripe with the gate closed.
4. It then performs an inline AOF append, which is an fsync under `always`.

| | |
|---|---|
| **Violated** | G10 |
| **Mitigation** | PR 0b: no stripes; a lock shared with `save` for the checkpoint concern; rate-limit refusals |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-7 — Medium — replica-side DEDUP records bypass stripes and `still_following` (pre-existing)

**Counterexample:**
1. On a chained replica, mark-only and refusal records are applied with no stripes (`replication.rs:1623–1632`).
2. A sub-replica's `handle_replica` takes its barrier, reads its offset and captures the DEDUP table.
3. The record then commits and fans out at offset O+1, before the sub-replica's sender is registered.
4. The sub-replica has the mark in neither the table nor the stream.

These records are also applied after `REPLICAOF NO ONE`.

| | |
|---|---|
| **Violated** | G4 (6L R2), G5, G7 |
| **Mitigation** | PR 0d: `lock_commands(&[])` + `still_following` |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-8 — Low — QSUB `qstate` can expose a deferred write before its `write(2)` (pre-existing; documents corrected)

**Counterexample:**
1. A TCP `SET k` defers. It has no watcher and no WS route candidate, because the WS socket is not routed for `k`.
2. A QSUB on that WS socket takes `lock_all_writes`, which does not wait for deferred batches, and sends `qstate` with `k`.
3. Under `always`, a failure then exits 74 after the browser saw a never-durable value.

The current-architecture document had claimed deferred writes have no observer; it was corrected.

| | |
|---|---|
| **Mitigation** | PR 0c (all modes): QSUB waits for the AOF tail recorded at its cut before sending `qstate`, outside the stripes |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-9 — Low — refusal remembered before its frame; WS early replay bypasses `dedup_order` (design and current code)

**Counterexample:**
- `record_dedup_refusal` remembers the refusal before logging it (`propagation.rs:716–717`).
- The WS early-replay path (`connection.rs:1476`) takes no `dedup_order`, so it can answer a refusal, or a `+DUP` from a deferred TCP mark, before the frame exists.

| | |
|---|---|
| **Mitigation (adopted)** | Stage or log first, then remember with the seq. PR 0a's "DEDUP never defers" covers the `+DUP` case in `inline`; N7 seq gating covers `watermark` |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | CONFIRMED |

### RV-10 — Low — `+DUP` wait while holding `dedup_order` (design)

**Counterexample:** `execute_ordered_write` holds the global `dedup_order` through its replay answer (`propagation.rs:385`). A waiting `+DUP` would serialize every tenant's DEDUP writes behind an fsync.

| | |
|---|---|
| **Mitigation (adopted)** | Copy `(reply, seq)` under the lock, release it, then wait (design §11) |
| **Architecture change** | No |
| **Re-review** | No |

### RV-11 — Low — `flush` fsync outside `busy` vs a concurrent batch's release (design; same race today)

**Counterexample (under `always`):**
1. `flush`'s fsync runs outside `busy` (`persistence.rs:1412–1440`).
2. A concurrent batch's own fsync succeeds, ordered in the kernel after the flush's failed one.
3. That batch settles and is released before the flush thread latches `stopped`.

| | |
|---|---|
| **Violated** | G8/N9 |
| **Mitigation (adopted)** | `flush`'s fsync is performed as a zero-frame batch holding the writer role (design §10; PR 2, all modes) |
| **Architecture change** | No |
| **Re-review** | No |
| **Confidence** | PLAUSIBLE (timing) |

### RV-13 — Low — under-specified stalls (design)

### RV-15 — Low — routed push vs a concurrent read by a delta-applying client (pre-existing, widened)

## Guarantees the reviewer attacked and could not break

| Guarantee | Why it held |
|---|---|
| N1/G2, conflicting order | Seqs are assigned under the queue lock while the stripe is held, and the stripe hand-off orders stages |
| N2 | `busy` is exclusive, the blocking drain holds it throughout, and release runs before `busy` clears |
| N3/G3 (primary client path) | Release follows `settle` in the same performer; an `always` failure exits before release |
| N4/P1 | Gates and `AofDone::wait` key on completion, which follows release |
| N5/G6 | EXEC takes the stripe after the writer's capture, so it reads the dirty flag; spurious aborts only err safe |
| N6/G4/G5, full sync | Every primary replication-frame producer holds stripes, so `issued` is frozen under the barrier; offsets are assigned at release; snapshot, offset and DEDUP table are one cut. The exception was RV-7 |
| G4, partial resync and backlog | `resume_frames` sees only released frames; trimming is unchanged |
| N8 | Payloads are fixed under the stripe, as today |
| N9 in the normal case | `busy` is never released after `fail_stop`; `wait_released` never reaches the failed seq |
| G9 | Cut-back runs in `perform` before `settle`; seqs never refer to file offsets |
| N12 | FIFO queue with a single performer |
| Release deadlock | Release takes only the stream mutex, the route-table read lock and `try_send`; no leader holds them |
| Shutdown and cancellation | The gate's `Drop` leads; the drain runs without a runtime |
| G7 envelope atomicity | One frame in the AOF and in replication; replay unchanged |

## Round 2: re-review of the mitigations

The reviewer re-attacked the revised documents. Three questions were asked explicitly: the QSUB cut-then-wait argument, the keychange dequeue checks, and the WS reply gate.

### Status of the round-1 items

| Item | Round 2 | Notes |
|---|---|---|
| RV-1 | **RESOLVED** | No WS or TCP reply path bypasses the gate; no stage escapes registration. Condition adopted: the wait lives inside the WS reply macro (design §6) |
| RV-2 | PARTIALLY | The four checks close the counterexample and the UNWATCH/WATCH variant. FLUSHDB sentinels and TCP WATCH are covered. The epoch mechanism introduced NEW-1 |
| RV-3 | NOT RESOLVED | The stage-site rules are correct, but the RV-13 `lead()` bound reopened a liveness hole (NEW-2) |
| RV-4 | **RESOLVED** | Condition adopted: `log_dedup_outcome` pinned inline on the replica path too |
| RV-5 | **RESOLVED** | **Cut:** writes with `s ≤ I` were captured before registration, so nothing was prepared for the new subscriber; the snapshot carries them and their pushes are superseded. Writes with `s > I` are captured with the new subscriber. **Delivery:** `q_rx` is not polled until `qstate` is sent. **Residual found:** QSUB of an already-held pattern did not re-register, so a delta could apply twice (pre-existing, Low; fixed by the NEW-1 design) |
| RV-9, RV-10 | **RESOLVED** | — |
| RV-11 | PARTIALLY | Applying the in-role fsync in every mode would put `everysec`'s once-a-second `fdatasync` on the writer role. Restricted to `always`, and run on the blocking pool |
| RV-13 | PARTIALLY | The batch cap produced NEW-2 |

### New findings

| ID | Severity | Finding | Resolution |
|---|---|---|---|
| NEW-1 | **High** | A per-kind epoch bumped by `SYNC TOKEN`, `QUNSUB` and a partial `UNWATCH` silently dropped live keychanges, for example on a routine token renewal. The browser's copy stayed stale with no gap close | Replaced by per-registration ages: `registered_at` per key/pattern; the notification stamped at `prepare` under the registry lock; no bump on `SYNC TOKEN`; QSUB of a held pattern re-registers; no silent drops (design §11, check 4) |
| NEW-2 | Medium-High | A bounded `lead()` that set a "lead needed" flag could strand a gate already parked in `gate_wait`, which never re-leads (`persistence.rs:1212`). Under `no`, a reply waits forever | Every waiter re-leads in a loop on `advanced`; the bounded leader notifies (design §6) |
| NEW-3 | Medium | The round-1 suggestion for RV-7, `lock_commands(&[])`, takes no stripe. `UnorderedGate` closers do not exclude each other, so the race remained | Hold a real stripe: `lock_commands_and_keys(&[], once(client))` (design §8, PR 0d) |
| NEW-4 | Low | The design's RV-6 row said "`dedup_order` only"; `save` does not take it. A refusal could be erased by a concurrent checkpoint's truncate | A lock shared with `save` (design §9, PR 0b) |

**Round 2 verdict:** PASS WITH CONDITIONS. Option A unchanged. NEW-1 required another look.

## Round 3: NEW-1 and NEW-2

| Item | Result | Detail |
|---|---|---|
| NEW-1 | RESOLVED, with refinement R3-1 | **Holds:** stamp vs registration race (both under the same registry lock per kind; QSUB also under the barrier); no silent loss; cross-scope; TCP WATCH; token renewal. **Condition:** compare only registrations of the notification's own kind, because the counter is shared |
| **R3-1** (Low-Medium) | Fixed in design | With overlapping patterns, an older `P2 = tenant:*` still delivered a keychange staged before a new `QSUB tenant:a:*` whose `qstate` already held the write, so a delta applied twice. A stale FLUSHDB sentinel matched through `*` could delete keys of a fresh `qstate`. **Fix:** deliver only if a covering same-kind registration exists **and none** is newer than the stamp; match sentinels to their exact pattern only (design §11). The reviewer judged this checkable at PR 3's code review, not needing another design round |
| NEW-2 | NOT RESOLVED → R3-2 | Re-leading waiters fix parked gates. Stage sites outside a connection lead but never wait, so a bounded leader's notification can find nobody registered |
| **R3-2** (Medium) | Fixed in design | A bounded leader with batches left always spawns a continuation as well as notifying (design §6). `drain_blocking` (`always`) is unbounded and unaffected |
| NEW-3, RV-11, RV-4, NEW-4 | **RESOLVED** | NEW-4 implementation notes adopted: an `RwLock` (not `save_lock`'s mutex), and the lock order `dedup_order` → shared lock, `save_lock` → shared lock → stripes |

**Round 3 verdict:** PASS WITH CONDITIONS. Option A unchanged. The conditions were R3-1 and R3-2, both now in the design. R3-1 is to be re-checked at PR 3's code review, not by a further design round.
