# v0.6.0 Phase 6N-B: validation plan for the future implementation

**Status:** a plan. Nothing here was run in 6N-B. It applies to PRs 0–7 of the [implementation plan](V0.6N-B-IMPLEMENTATION-PLAN.md).

## 1. Correctness tests

### 1.1 Deterministic strategy

Probabilistic race tests are kept as smoke tests only. Every invariant has at least one **deterministic** test, built from four tools.

**1. Pause hooks (`cfg(test)`), in the style of `unordered_pause` and `AofFault`:**

| Hook | Holds |
|---|---|
| `PauseAfterStage(key)` | The writer, after `stage`, before it drops its stripes |
| `PauseAfterUnlock(key)` | The writer, after its stripes drop, before its reply gate |
| `PauseBeforePerform` | The performer, after taking a batch, before `write(2)` |
| `PauseBeforeRelease` | The performer, after `settle`, before `release` |
| `PauseBeforeComplete` | The performer, after `release`, before `done.complete` |

Each hook is a `(Notify, Notify)` pair: "reached" and "resume". A test orchestrates the exact interleaving.

**2. Fault injection:** the existing `AofFault` (fail, short, torn, unrepairable, fsync), plus `DelayWrite(ms)` for stall tests. The subprocess harness's content-keyed arming covers production exit paths.

**3. Probes:**
- A probe socket reads the AOF file on every byte it receives, as the existing #121 test does.
- An in-process replica (`attach_test_replica`) checks the file at every frame.
- A WS test client checks the file at every push and keychange.

**4. A schedule-exploration test of the performer state machine.** Port [`model/ordering_model.py`](model/ordering_model.py) to a Rust test using `loom` (std mutex and atomics) or `shuttle` (seeded random schedules over async tasks):
- states: stage → perform → settle → release → complete, with N4 and N9;
- check: release order, completion after release, nothing released after `stopped`.

## 3. Performance: primary workload

**Reuse the 6N-1 kit** (`benchmarks/v0.6.0/6n-1/run-targeted.sh`, Test B) with a `FANOUT` dimension. It needs a native Linux host with `perf` installed; 6N-1's host had none. Test B's harness also records counters, replica lag (`repl_check.py probe`) and convergence.

| | |
|---|---|
| Topology | 1 primary + 1 connected replica (full sync complete), separate cores |
| Primary | AOF `everysec`, 1 worker, CPU 0 |
| Load | `redis-benchmark` SET, 50 clients, P=1, 1M requests, CPUs 3–5, 3 interleaved reps |
| Recached modes | `inline` (baseline: 54k rps, 14.02 µs/op, 1.00 writes/cmd, p99 1.21 ms), `coalesced`, `watermark` |
| Redis | 7.2.5 primary with `appendonly yes`, `appendfsync everysec`, **plus one connected replica**, same pinning. Not compared against standalone Redis |

### Measurements (each cell)

- Throughput.
- µs CPU / op.
- **Instructions / op** (`perf stat`).
- Physical AOF writes per command, and average frames per batch (`INFO persistence` histogram).
- p50/p95/p99/max latency.
- Replica lag p50/p99/max.
- WS propagation latency p50/p99: writer-send to subscriber-receive, from `observers.mjs`.
- Queue depth: `recached_aof_pending_*`, replica queue, mailbox.
- RSS.
- Backpressure events: `backpressure_waits`, replica drops, gap closes, notification overflows.
- `drain_waits` / `drain_usec`.

## 5. Sustained validation

Only after §1–2 pass and §3 shows a benefit:
- **one 40-minute run** of the 6L soak harness (primary + replica, multitenant WS, QSUB/WATCH, DEDUP ledger, crash recovery) in `watermark` mode;
- the same 28 checks as 6N-1 Test D, plus the new counters.

The `inline` soak is **not** rerun: 6N-1 Test D covers it, unless the inline path's code changed. The 5-run soak matrix and the unaffected batteries (6L C, E; capped reservations) are not repeated.

## 6. Targets and decision rules

These are **targets, not predictions**. The [alternatives](V0.6N-B-ALTERNATIVES.md) estimates are hypotheses to be confirmed.

| Metric (primary workload) | Target for `watermark` |
|---|---|
| AOF writes / command | ≤ 0.2 (6N-1 standalone: 0.10) |
| Throughput | ≥ 1.5× `inline` (≥ about 80k rps). Report the ratio to Redis primary+replica against the v0.6.0 0.90× parity target |
| µs CPU / op | ≤ 9 |
| p99 | ≤ `inline` p99 (1.21 ms); no significant regression at P=16 or 4 workers |
| Replica lag p99 | ≤ `inline` + 10% |
| WS propagation p99 (subscription-heavy) | ≤ `inline` + 10% |
| Drain stall on replica attach | max writer latency during attach ≤ 2× the p99 |
| RSS | ≤ `inline` + pending cap |
| Correctness | zero violations in §1–2 and the soak |

**Decision rules:**

| Rule | Condition | Then |
|---|---|---|
| M1 (after PR 1) | `coalesced` reaches ≥ 0.85× standalone (≥ about 103k rps) **and** the P=16 replicated case is within 0.85× standalone P=16 | Option A is **not** needed for this bottleneck; the maintainer may stop at D |
| M2 (after PR 7) | `watermark` does not beat `coalesced` by ≥ 15% at P=1 **or** ≥ 30% at P=16 | Keep `coalesced` as the recommended mode, and reconsider whether A's complexity is justified |
| Default change | Requires §1–2, the soak and §6 all met, plus a separate maintainer decision | — |
