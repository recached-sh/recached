## The question

6O-B measured 590–780 inclusive user cycles per command in the TCP write-half path. The connection used `tokio::io::split`, whose two halves share the stream behind a lock taken on every read and write poll. The brief asked whether `TcpStream::into_split`'s owned halves, which poll the socket directly, remove a measurable part of that, without assuming the whole figure is removable.

## Prototype

The structure:
- `handle_tcp`'s body becomes `handle_tcp_halves<R, W>(reader, raw_writer, …)`;
- `handle_tcp<S>` (TLS, in-memory test sockets) keeps `tokio::io::split`;
- a new `handle_tcp_stream(TcpStream)` uses `into_split()`;
- the plain-TCP listener in `main.rs` calls `handle_tcp_stream`.

What the reviewers and the author checked against the tokio 1.54.1 source (`net/tcp/split_owned.rs`, `io/split.rs`):

| Aspect | Finding |
|---|---|
| Read-half and write-half ownership | `OwnedReadHalf`/`OwnedWriteHalf` share an `Arc<TcpStream>`; no lock is taken on poll |
| Shutdown on drop | **Differs.** A dropped `OwnedWriteHalf` calls `shutdown(Write)` (FIN) at once, unless `forget()`. `tokio::io::split`'s halves have no `Drop`: the socket closes when the last half drops |
| EOF and error propagation | Unchanged: the body is shared, and read and write results are the same `io::Result`s |
| Cancellation | No connection task is ever aborted. On runtime shutdown the future is dropped, as before |
| Socket options | `TCP_NODELAY` is set on the `TcpStream` before the split; it is a socket property and survives |
| Buffer lifetimes | Unchanged: the read buffer, `BufWriter` and `AofGatedWriter` are those of the body |
| `AofGatedWriter` | Wraps the write half as before. Its `Drop` leads queued AOF batches and touches no socket |
| Reply coalescing | Unaffected: it acts on the `BufWriter`, whatever the half |
| TLS, WebSocket, replication, metrics | Untouched (`replication.rs` keeps its own `tokio::io::split`) |

How to read it:
- Throughput rose in every P=1 cell at one worker, in every repetition (e.g. GET 188.7/185.2/186.9k → 192.3/188.7/194.2k). User instructions fell by ≈ 200 per command everywhere: the lock's acquire and release on each poll.
- The cycles saved (100–360) are a fraction of the 590–780 inclusive figure, as the brief cautioned. The rest is the write itself.
- At P=16 a poll is amortized over 16 commands and nothing is visible.
- The one-client cell at 3 workers moved within its noise in the other direction; user instructions fell there too.
- Allocations are unchanged: the split allocates one `Arc` per connection either way. RSS is unchanged (26–27 MiB).

## The defect the prototype had

The handler drops its writer *before* its cleanup: unsubscribing, unregistering watches, releasing ephemeral keys. With `tokio::io::split` that drop sends nothing; the socket closes when the read half drops at the end. With a bare `OwnedWriteHalf`, the drop sent FIN at once. A client could therefore see EOF while its watches and ephemeral keys still existed, and one that reconnects on EOF could observe them.

The new test `eof_reaches_the_client_only_after_the_connections_cleanup` (multi-threaded, 1,000 watches and 500 ephemeral keys per connection) failed **30 rounds of 30** with the bare half. The production `TcpWriteHalf` calls `OwnedWriteHalf::forget()` on drop, and the test passes 30/30, six runs out of six in the review.

One change in drop order remains, and it is harmless. The read half is now a parameter, so it drops after the function's locals, including the connection's registry guard. A client that sees EOF is therefore already out of `CLIENT LIST` and the active-connection count. Before, that was not always so.

## Not done

- **No end-to-end TLS test exists**, before or after. The generic path is still exercised over in-memory duplex sockets (`request_path`, `reply_coalesce_6ob`).
- **Pre-existing, unchanged behaviour:** a close with unread client input sends RST instead of FIN, as on every Linux socket. An example is QUIT with more commands pipelined behind it. The client can then lose the last reply.
