## 1. The current path: three lookups per key

The server runs an unlogged MSET (no AOF, no replica, no watcher) through `try_execute_unordered`, then `execute_and_record_ref`, then `KeyValueStore::execute_reporting_ref`. That calls `run_write(WriteScope::Keys(keys))` (`run_write_gated`, l. 4193). For an MSET of *n* pairs on an **uncapped** store:

| Step | Code | Per key | Notes |
|---|---|---|---|
| Scope | `mutation_scope` (l. 7015) | | `SmallVec<[&str; 4]>` of the keys: spills to the heap at n > 4 |
| Sort, dedup | `keys.sort_unstable(); keys.dedup()` (l. 4248) | ≈ log n string compares | Only for `before_states` below |
| Stripes | `order_keys` (l. 3006) | 1 hash (`write_order_stripe`) | Stripe indices sorted and deduped, locked in ascending order |
| Before | `entry_state` (l. 2958) | **lookup 1**: hash + probe | Size and TTL-ness; `SmallVec<[_; 4]>`, heap at n > 4 |
| Write | `mset` → `write_slot` (l. 5083, 1990) | **lookup 2**: hash + probe; a new key probes twice (`get_mut`, then `entry`) | Replace in place, or insert |
| After | `data.get` in the loop at l. 4330 | **lookup 3**: hash + probe | Size, TTL-ness, emptied check; `SmallVec<[_; 4]>`, heap at n > 4 |
| Index | `index_for(key).sync(..)` | Only if presence or TTL-ness changed | A created key, or a TTL that MSET cleared |
| Memory | `adjust_memory(before, after)` | Once | |

The capped path (`enforce`) takes the capacity gate exclusively. It reserves key slots (`reserve_key_slots`) and copies the touched entries for rollback when the write could cross the memory cap. It then evicts if needed, or rolls the whole command back (l. 4372). MSET names several keys, so it is never eligible for the single-key reservation fast path (`try_reserved_write`, l. 4498).

Measured (6O-B CPU profile, `V0.6O-B-CPU-PROFILE.md` l. 24 and l. 154): the store costs 16,400 user cycles per MSET ×10, of which `entry_state` is 8,614. That is mostly each random key's **first** DRAM miss in a 100,000-key working set larger than L3, so it moves to the next lookup rather than vanishing. The removable part is the second and third lookups per key and 3 × 10 SipHash computations (≈ 1,800), ≈ **2–3k cycles**. Decode is another 2,900: MSET is built owned, one `String` per key, one `Vec` per value and the pairs vector.

## 2. Proposed path: `mset`'s own loop with one probe per pair, under one multi-stripe hold

The single-key machinery already exists and is proven: `write_slot` records a key's before-state into a `KeyProbe` (l. 1995–2012). `SlotRef`/`SlotVacant` record the after-state on drop, while the shard guard is still held (l. 1931–1976). `run_probed_write_ordered` (l. 4450) does the whole accounting for one key from that probe, for a caller that holds the key's stripe. It covers the memory delta, the index sync only when presence or TTL-ness changed, and the emptied-collection removal (which never applies to a string).

The proposal applies whenever the write does **not** enforce caps (`!enforce`, decided once per write, l. 4210). That is an uncapped store, or a capped follower applying replication (`set_follower(true)`), whose generic path today also neither reserves nor rolls back:

```rust
// In run_write_gated, before the generic multi-key branch. Bare MSet only:
// Dedup(MSet) stays generic (the server strips DEDUP before the store anyway).
// `exec` is bypassed: for MSet it is `mset` in both execute_reporting and
// execute_reporting_ref. `within_capacity` brings a gate, so enforce is true
// there and this branch is not taken.
if !enforce && let Command::MSet(..) = cmd.borrow() { ... }

/// Owned pairs (execute_reporting: values move, as today) or borrowed ones
/// (execute_reporting_ref, a future CommandRef::MSet).
fn run_probed_mset<K, V>(&self, keys: &[&str], pairs: impl Iterator<Item = (K, V)>) -> Value
where K: AsRef<str> + Into<Key>, V: Into<StrValue>
{
    // Every stripe the command's keys map to, ascending, deduplicated: the
    // generic path's hold. `keys` is the scope the caller already built.
    let _order = self.order_keys(keys);
    let now = now_ms();                       // once per command, as mset does
    let (mut before, mut after) = (0usize, 0usize);
    for (key, val) in pairs {
        let probe = KeyProbe::default();      // fresh per pair: record_before keeps the FIRST state
        // mset's loop body, unchanged, with the probe passed to write_slot:
        // replace in place or insert; Str(val), Deadline::NONE, last_access = now.
        self.mset_pair(key.as_ref(), key, val, now, &probe);
        let (b, a) = self.account_probe_ordered(key, probe);   // run_probed_write_ordered's
        before += b;                                           // bookkeeping minus adjust_memory;
        after += a;                                            // (0, 0) if probe.before is None
    }
    self.adjust_memory(before, after);        // one atomic for the command, as today
    Value::SimpleString("OK".to_string())     // one reply
}
```

The pair is written by **`mset`'s own loop body** (l. 5089–5106) with a per-pair `KeyProbe` handed to `write_slot`, not by `set()`. `set()` would add, per pair, a `now_ms()` clock read and a `SimpleString("OK")` allocation and free, plus its option branches (≈ 0.7–1.5k cycles per MSET ×10, design review). `account_probe_ordered` is the bookkeeping half of `run_probed_write_ordered`:
- the index sync, only when presence or TTL-ness changed;
- the emptied removal, never reached for a string.

It returns the key's `(before, after)` sizes instead of applying them, so the memory counter is still touched once per command. Index syncs stay per key, after that key's shard guard is released, as now. Being generic over the pairs, the owned entry point (`execute_reporting`, used by AOF replay at `persistence.rs:2169` and library callers) keeps moving values in rather than copying them. A version taking `&[(String, Vec<u8>)]` would copy every value on replay.

Per key, the work becomes:
- one stripe hash;
- one write lookup (two for a key that did not exist: `write_slot`'s `get_mut` then `entry`, as today);
- an index sync only when it changed.

Removed per command: the key sort and dedup, three `SmallVec` heap spills, *n* `entry_state` lookups and *n* post-write lookups. Unchanged: the stripes held and their order, the index protocol, and when the shard guard is released.

The by-reference entry point (`execute_inner_ref`'s `MSet` arm, l. 4798) and AOF replay / replica apply (`execute_inner_probed`'s fall-through, l. 5257) both reach `run_write`. They take the same new branch, owned or borrowed.

## 3. Exact memory accounting

- **Per pair**, the probe's before-state is the key's state *at that pair's write*, and its after-state is the state that write committed. Both are recorded under the key's shard guard (`record_before` at the slot, `record_after` in `SlotRef::drop` before the guard is released, l. 1931–1939).
- **Duplicate keys** (`MSET k 1 k 2`): the pairs run in order, so the second pair's before-state is the first pair's after-state. The command's total is Σ (afterᵢ − beforeᵢ), which telescopes to *final − original* for that key: exactly what the generic path charges from one before and one after. No dedup is needed, and none is done.
- **Stripes**: the whole command holds every stripe of its keys (`order_keys`), so no other accounted writer, nor the expiry sweeper (which takes the same stripes), can change any of them between a pair's before and after. This is the invariant `run_probed_write` relies on for one key; here it holds for all *n* keys at once.
- **The counter**: `adjust_memory` is called once with the summed before and after, as now. One atomic per command, none when the sizes match.
- **Key count and index**: a key created by its first pair is synced (`index_changes(None, Some(false))`). A duplicate's later pairs see it present without a TTL and change nothing. A key whose TTL MSET clears (`Some(true)` → `Some(false)`), including an expired-but-unswept entry, is synced exactly as the generic path does (l. 4357–4368). Expired-but-unswept entries stay in the map and are overwritten in place, as `write_slot` does for SET.

The proof obligation reduces to **"today's `mset` loop, plus one probe per pair, under one stripe hold"**. The writes are the same code, so only the accounting is new, and it is the existing single-key probe invariant applied per pair. The differential test (§8) checks it against today's path exactly.

## 4. Reservation strategy

**None on the new path, by restriction.** The new path is taken only when `enforce` is false, decided once per write as now:
- **an uncapped store**: nothing can be refused, evicted or rolled back;
- **a capped follower applying replication**: today's generic follower path does not reserve or roll back either, so the behaviour is unchanged. A promotion that lands mid-write is decided once, as today.

A pre-existing gap stays as it is: `remove_victim` takes no stripe, so a promotion racing an evicting write is unprotected on both paths. The per-pair probes are, if anything, more robust there than the generic path's separate before and after reads. Capped stores keep today's gated path unchanged, with `reserve_key_slots`, rollback copies, eviction, and the `growth_bound` and `creating_keys` already covering MSET (l. 7072, 7103, 7178).

A capped variant was considered and is **not proposed**. A multi-key reservation would reserve `growth_bound(MSET)` plus one slot per *absent distinct* key under the shared gate, then run the pairs. Counting the absent keys needs a lookup per key before the write, which brings back the lookup this design removes. Alternatively it would reserve *n* slots pessimistically and release the unused ones afterwards. That would refuse an MSET of existing keys on a store at its key cap, which is a behaviour change. Neither pays for itself in this phase.

## 5. Lock-order guarantees

| Lock | Taken | Order |
|---|---|---|
| Capacity gate | Not taken (uncapped) | As now |
| Write-order stripes | All of the command's, before the first pair | Ascending stripe index, deduplicated (`order_keys`, unchanged) |
| Data shard guard | One at a time, per pair, released before the next pair | Never two at once: no deadlock with another multi-key writer, which also holds at most one |
| Index shard lock | After the pair's data guard is released, one at a time | `data` → `index` is the established order (`sync_key_metadata`); the index lock is never held across a data lookup |

These are exactly the generic path's locks, in its order, minus two lookups per key. No new lock is introduced, no lock is held longer, and none is taken in a new order.

## 6. Atomicity

- **Against other accounted writers** (SET, MSET, DEL, INCR, the expiry sweeper, every `run_write`): unchanged. They take the same stripes, so a concurrent writer to any of the MSET's keys runs entirely before or entirely after it.
- **Against plain readers: unchanged, and not atomic today.** `GET`/`MGET` (`read_str`, the borrowed path) and the general read path take no stripe, only a shard guard per key. The generic MSET path already writes key by key (`mset`, l. 5089), so a concurrent `MGET a b` can see the new `a` with the old `b`. Redis documents MSET as atomic. This is a **pre-existing** deviation that this design neither causes nor fixes. It is recorded in the release gate as an open item with its own decision, since it needs a read-side protocol (for example, multi-key readers taking the stripes shared).
- **Readers that do see MSET whole today keep doing so.** These are the `lock_all_writes` barriers: SAVE/snapshot, QSUB's initial state, the replica full-sync cut and the expiry tick, which also drain the unordered gate. An EXEC whose queue writes or WATCHes the MSET's keys (`lock_commands_and_keys`) is in the same position. An EXEC holding only MGET, with no WATCH, is not atomic against an ordered MSET, today or after.
- **Replication and AOF**: the frame is built from the command, not from the store's internal sequence. The store change is below the ordering layer: `execute_ordered_write` still holds the replication-order guards (`lock_commands_and_keys`) for a logged or replicated MSET across execution and frame emission. Replay and replica apply call the same store function and produce the same final state.
- **MULTI/EXEC**: a queued MSET runs through `execute_locked_write` under the transaction's guards. Same store function, same result.

## 7. Failure and rollback

The question the brief raises is what happens if a failure occurs after some per-key work has started. On the new path **no failure is possible after the first pair**, which is why it is restricted to uncapped stores:
- Key validity, the even arity and every argument check happen at decode (`build`, `from_value`). An invalid MSET never reaches the store.
- An uncapped store refuses nothing: no key cap, no memory cap, no `NoEviction` rollback.
- `SET` without options cannot fail on any existing type. It replaces the value (`set`, l. 4700ff).
- Allocation failure aborts the process (Rust's default), so no partially committed state is ever observed by a live server, as today.
- A panic inside a pair (none is reachable) would unwind with the stripes held. They are `lock_stripe` mutexes with poison recovery, as on every path. Pairs already written stay written, exactly as with today's `mset` loop. The generic path has the same property.

So there is no "allocate and mutate in the same loop, then fail" window: there is no late failure. A **bounded preflight stage** would be required for any variant that can refuse (a capped store). That is why the capped path keeps today's code, which reserves and decides under the exclusive gate *before* `exec` and rolls back from copies if the memory cap is crossed.

## 8. Correctness test plan

All deterministic, no timing:

1. **Differential, store level.** Generated MSETs run on three stores:
   - inputs: 1–12 pairs, duplicate keys, existing strings, keys of every other type, keys with TTLs, binary and empty values;
   - expired-but-unswept keys, built deterministically with a deadline in the past (`SET … PXAT <past>` or `PEXPIREAT`), not with `sleep`;
   - the stores: (a) the new path; (b) the same pairs as plain SETs in order; (c) the generic path (`WriteScope::Keys` with a capped-but-unlimited store, as `probed_writes_account_exactly_like_the_general_path` does).

   After every command, compare the replies, every key's value and TTL, the memory counter and the key count, and run `assert_accounting_exact`.
2. **Duplicates**: `MSET k 1 k 2 k 3` with *k* absent, present, present with a TTL, expired, and of another type. Final value, TTL and accounting.
3. **Concurrency** (`race`, 8 threads × 2,000 rounds): MSETs over overlapping key sets racing SET, DEL, INCR, EXPIRE and the expiry sweeper; `assert_accounting_exact` at the end. A lost-update check: MSETs of counters `(k_i, "t:r")` and, after the race, every key holds a value some writer wrote, with memory matching the recomputation.
4. **Lock order**: MSETs whose keys hash to overlapping stripe sets in opposite key orders, racing each other and multi-key DEL, to check for deadlock (bounded by a test timeout).
4a. **All-or-nothing against writers.** Per-pair accounting stays exact even if the stripes are taken per pair, so these tests kill that mutant:
   - concurrent MSETs over the same key set, in varied key orders, each writing one tag to all its keys; after quiescence every key holds the same tag (`T1 MSET a 1 b 1` and `T2 MSET b 2 a 2` must never end with a=2, b=1);
   - MSET racing a multi-key DEL of the same set: the keys end all present or all absent.
5. **Capped store unchanged**: the same scripts on capped stores (key cap, memory cap with `NoEviction` and with `AllKeysLru`), checked against the pre-change binary's behaviour (refusals, rollback, evictions). Also a **capped follower** applying MSETs (the new path) against the generic follower path, and a promotion landing mid-write.
6. **AOF and replication**: `aof_v06`, `restart` and replica tests with MSET in the stream, in both `RECACHED_AOF_FANOUT` modes. Replay of an AOF containing duplicate-key MSETs.
7. **Redis differential** (`redis_diff`): MSET with duplicates, then MGET/TTL/TYPE.
8. **Mutants**, each of which tests 1–5 must kill:
   - commit one key before a later failure (n/a, since there is none, so the mutant is a skipped pair);
   - skip a duplicate key;
   - skip the TTL clear;
   - accumulate before or after only for new keys;
   - take stripes per pair instead of up front (killed by 4a);
   - reuse one `KeyProbe` across pairs (its before-state would stick at the first pair);
   - drop the index sync for created keys;
   - call `adjust_memory` per pair with a wrong sign.

## 9. Expected CPU improvement

| Item | Cycles per MSET ×10 (estimate) | Basis |
|---|---:|---|
| Post-write lookup, 10× (cache-warm after the write) | 800–1,500 | Profile: the extra lookups and their hashes ≈ 2–3k in total. dashmap 6.1 hashes once per operation, so an existing key goes from 3 SipHashes to 1 (20 removed per ×10). The stripe hash is multiplicative and stays |
| `entry_state`, 10×: the DRAM miss moves to the write's lookup, the rest goes | 600–1,000 | The miss (≈ 8,000 of 8,614) is not removable |
| Key sort and dedup; two `SmallVec` heap spills and frees (`before_states`, `ttl_states`) | 250–500 | The scope's own `SmallVec<[_; 2]>` (built by the caller) and `order_keys`' stripe and guard vectors still spill on both paths. Raising `order_keys`' inline capacity is an optional extra |
| **Total** | **≈ 1.6–3.0k** | Against a ≈ 3,150-cycle gap at P=1. This assumes the pair is written by `mset`'s loop body (§2); per-pair `set()` would give back 0.7–1.5k |

This alone is **likely insufficient** to reach 0.90× by a margin. Its upper estimate only just covers the gap, and at P=1 the per-request network path is 55–65% of MSET's server CPU (profile, l. 189). A borrowed MSET (§11) removes a further ≈ 1.5–2.5k decode cycles at low risk. The two together have a credible chance of crossing 0.90×. Neither is measured: these are estimates to be confirmed by a prototype before any production PR.

## 10. Implementation complexity

Small in code, ≈ 60–90 lines in `store.rs`:
- one branch in `run_write_gated`;
- `run_probed_mset`;
- a variant of `run_probed_write_ordered` that returns the sizes instead of applying them.

Plus the tests above, ≈ 300 lines. The risk is not the size but the argument: §3 and §6 must hold exactly. Every capped path stays untouched by construction.

## 11. Comparison with smaller alternatives

**Recommendation (revised after the design review).** Approve (A), then (B), as two separate PRs:
- **(A) first.** Its generic `run_probed_mset` is the multi-key accounted entry (B) needs anyway. It comes with the full test plan of §8 and its own independent implementation review.
- **Then (B),** as a thin decode plus one `execute_ref_into` arm calling `run_probed_mset` with borrowed pairs, under the 6O-C2 test pattern.

Measure (A) alone, then (B) on top, against the pinned pre-change binary with ~30 s cells, and stop as soon as MSET crosses 0.90× with margin. (C) is dominated by (A) and is not recommended.

## 13. Independent design review

An independent reviewer read this design against the code at `be3c90e` (read-only). **Verdict: APPROVE WITH CHANGES.**

**Confirmed:**
- MSET-pair ≡ SET with default options: same `Str` value, `Deadline::NONE`, `last_access_ms = now`, the same `write_slot`, any type replaced, length-based `entry_size`.
- Per-pair telescoping with a fresh probe per pair. There is no stale `Arc` and no double index sync for duplicates. A TTL clear or an expired entry is synced once. One `adjust_memory` is equivalent.
- Lock order: stripes ascending before any shard guard; one shard guard at a time; index locks after the guard is released. A per-pair `run_probed_write` inside the hold would self-deadlock, so the `_ordered` variant is required.
- No late failure.
- AOF, replica, MULTI and WATCH are unaffected.
- (C) is dominated.

| Sev | Finding | Applied |
|---|---|---|
| High | Per-pair `set()` adds a clock read, a reply allocation and option branches per pair (≈ 0.7–1.5k cycles per ×10), not counted | §2: `mset`'s loop body with a per-pair probe, `now` once, one reply; §9 updated |
| Medium | A `&[(String, Vec<u8>)]` branch copies values on AOF replay and in library callers, which move them today | §2: generic over owned and borrowed pairs |
| Medium | (B) is not "no accounting change": a borrowed MSET needs a multi-key accounted entry without a `Command` | §11: risk restated; recommendation now (A), then (B) |
| Medium | The "stripes per pair" mutant survives the planned tests | §8 4a: all-or-nothing final-state tests |
| Low | The condition is `!enforce`, which also covers capped followers. Pre-existing: `remove_victim` takes no stripe | §4, §8.5 |

| Nit | Expired entries in tests built deterministically; bare `MSet` only; `exec` bypass stated; (0, 0) when the probe never took a slot | §2, §8 |
