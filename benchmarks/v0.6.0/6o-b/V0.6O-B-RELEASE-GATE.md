## The fourteen questions

| # | Question | Answer |
|---|---|---|
| 1 | Updated no-persistence baseline? | `dev` `51ae15c`, 1 worker, 50 clients, P=1, against Redis 7.2.5: **SET 0.84×, LPUSH 0.70×, SADD 0.64×, MSET 0.72×**; controls GET 0.88×, INCR 0.80×, ZADD 0.91×. One client: 0.98–1.06×. P=16: SET ≈ 1.0×, LPUSH ≈ 0.67×, SADD ≈ 0.57×, MSET ≈ 0.83× ([baseline](V0.6O-B-BASELINE.md)). Re-measured as `base` in V1: 0.827, 0.690, 0.659, 0.725 |
| 2 | Furthest from Redis? | Before: **SADD (0.64×)**, then LPUSH (0.70×) and MSET (0.72×); at P=16, SADD 0.57× and LPUSH 0.65×. After: **MSET (0.83–0.84×)**, then SADD (0.87×) |
| 3 | Why is one client strong and 50 clients weak? | With one client the server's CPU is ~40% idle (9.8 of 25.5 µs per op), waiting for the client's round trip; throughput is round-trip latency, and Recached's is slightly shorter than Redis's (1.00–1.08×). With 50 clients the server's CPU is saturated, so throughput is 1 / CPU time per op. Recached spent more of it per op, mostly because it flushed each reply the moment its command ran. That spread replies across the pass, and the generator's threads slept and woke per reply (0.31–0.55 sleeps/op against Redis's 0.05). Each wake-up is a remote `try_to_wake_up` the kernel runs in softirq **on the server's CPU**, invisible in the task's own times under `IRQ_TIME_ACCOUNTING`. Redis writes all replies in `beforeSleep`. On top of that, LPUSH, SADD and MSET spent more user cycles per command ([profile](V0.6O-B-CPU-PROFILE.md)) |
| 4 | Networking and system CPU? | **About 82–86% of the server CPU's per-op budget** (system time plus softirq) at 50 clients, P=1, for Recached and Redis alike. SET before: 6.26 µs/op = sys ≈ 3.1 + softirq 2.06 + user ≈ 1.0. Of the base SET's 1.08 µs/op gap to Redis, ≈ 0.61 µs was kernel (softirq +0.34, task kernel time ≈ +0.27) and ≈ 0.41 µs user space. After: the gap is 0.42 µs, ≈ 0.15 softirq (residual wake-ups) and ≈ 0.28 user. Syscall counts were always identical to Redis's (1.0 `recv` + 1.0 `send` per command) |
| 5 | Command execution? | In process, per command (B0, layered bench): SET 568 ns, LPUSH 723, SADD 851, MSET 5,213. That is ≈ 10% (SET) to ≈ 45% (MSET) of the per-op budget at 50 clients. Store execution in user cycles per op, before → after: SET 2,035 → 1,787, LPUSH 2,863 → 1,166, SADD 3,992 → 2,375, MSET 16,707 → 16,332 |
| 6 | Which allocations were removed? | For LPUSH, RPUSH and SADD: the general decoder's intermediate `Value` array and its per-argument buffers, and the store's clone of the owned `Command` with all its values. A SADD of an existing member now allocates nothing (insert by reference). Allocator user cycles per op: LPUSH 500 → 157, SADD 489 → 127, SET 92 → 25, MSET 834 → 712. Allocations were not counted one by one in this phase |
| 7 | Which optimizations were implemented? | PR 2 (shared path): (a) cross-connection reply coalescing, one `yield_now` before a flush with per-worker back-off and a kill switch; (b) the pubsub/WATCH overflow arm polled only once a sender exists; (c) a lock-free empty check in the AOF gate. PR 3 (commands): (a) LPUSH, RPUSH and SADD built straight from the read buffer; (b) run through the key's single write slot with probe accounting, by reference, and on the reservation fast path in capped stores ([implementation](V0.6O-B-IMPLEMENTATION.md)) |
| 8 | Throughput gain per command? | 50 clients, P=1, paired: **SET +11.9%, LPUSH +29.8% (V3 +26.5%), SADD +31.9%, MSET +14.3% (V3 +13.1%)**. P=16: +6%, +42%, +41%, +3%. One client: 0%, +5%, +5%, 0%. Controls: GET +11%, INCR +7%, ZADD +22% |
| 9 | Did SET, LPUSH, SADD and MSET reach 90%? | **Only SET (0.925×).** LPUSH 0.896–0.897× (at the line, not over it), SADD 0.870×, MSET 0.83–0.84×. Not a complete victory |
| 10 | Did P=16 remain healthy? | **Throughput yes**, every command up: SET 1.08× Redis, LPUSH 0.92×, SADD 0.80×, MSET 0.80×. **The tail widened** for MSET P=16 (+11% p99) and SET P=16 at 3 workers (+26%) |
| 11 | Did p99 improve or regress? | At P=1: improved for LPUSH, SADD and ZADD; +0.008 to +0.032 ms for SET, GET, INCR and MSET, at or below Redis's except MSET. p50 fell in every no-persistence 50-client cell (−7% to −36%). At P=16: LPUSH −19%, SADD −18%, SET +6%, **MSET +11%** |

## Recommended next milestone

1. **Phase 6O-C: close the no-persistence gate, narrowly.** In this order:
   1. Follow-up #1, the B3 condition: a small change to the yield's condition, re-measured at P=1, P=16 and 3 workers.
   2. Follow-up #3, the borrowed LPUSH/RPUSH/SADD path. Expected to take LPUSH over 0.90× and SADD part of the way.
   3. Follow-up #5, the split write half, as a measured prototype first.
   4. MSET's multi-key probe (#4) only with its own design review, because of its multi-key accounting risk.
   - SADD's remaining gap is the set layout and belongs with memory (6P), so 6O-C may end with SADD still short. That should be decided, not hidden.
2. **The WATCH overflow High (#2)** before any release candidate, in its own PR.
3. Separately, as decisions: **Phase 6P** (memory, including the list and set layouts seen here); the **AOF P=1 follow-up**; the **Option A decision**; then the **final release-candidate soak**.

**STOP.** Phase 6O-B ends here. Memory redesign (6P), Option A, the AOF follow-up and the release are not started.
