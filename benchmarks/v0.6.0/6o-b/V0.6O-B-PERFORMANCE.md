**Answer.**

- Against Valkey 9.1.0, the secondary comparator: SET 0.97×, LPUSH 0.94×, SADD 0.90×, MSET 0.89×.
- Every primary cell improved in every paired repetition. No cell regressed beyond its measurement step:
  - one client: SET and MSET unchanged, LPUSH and SADD +5%;
  - P=16: SET +6%, LPUSH +42%, SADD +41%, MSET +3%;
  - controls: GET +11%, INCR +7%, ZADD +22%.
- **CPU per operation fell** on the server's saturated CPU: SET 6.26 → 5.59 µs, LPUSH 7.26 → 5.59, SADD 7.59 → 5.76, MSET 11.14 → 9.76. That is task time plus inline softirq.
  - The mechanism is the one the profile predicted: the generator's wake-ups per reply fell from 0.31–0.55 to 0.11–0.17. Redis's figure is 0.05.
- **p99 at P=1** moved by +0.008 to +0.024 ms for SET, GET, INCR and MSET, and fell for LPUSH, SADD and ZADD. Every P=1 p99 except MSET's is now at or below Redis's.
  - **MSET at P=16 is the exception**: p99 4.21 → 4.66 ms (+11%, in every repetition), while p50 fell 7% and throughput rose 3%. It is recorded as a residual in [the release gate](V0.6O-B-RELEASE-GATE.md).
- **Standalone AOF `everysec` (B5)**: SET P=1 0.839 → 0.857×, INCR 0.742 → 0.767×, HSET 0.823 → 0.859×, SET P=16 1.10 → 1.14×. Paired gains are +2–4%, all repetitions positive at P=1.
  - Against 6O-A's figures (0.862, 0.769, 0.851, 1.184) the after-figures are equal within run-to-run noise.
  - The no-persistence gain carries into the AOF path only slightly, by design: with AOF tickets queued, the AOF gate's own coalescing applies, and the new yield stands aside.
- RSS: +0.3 to +1.3 MiB per process, flat across commands and workloads. Not data-dependent.
- **Multi-worker (3 workers, V2 and the V3 control)**: throughput is unchanged. The coalescing yield costs a lone connection +3% CPU per op (no throughput effect) and widens SET P=16's p99 by +26%, against the same binary with `RECACHED_REPLY_COALESCE=off`. Both are recorded as residuals.

**Host state (V1).**

**Measurement uncertainty.**
- **Quantization.** `redis-benchmark` stops on its 250 ms timer, so a cell's rate steps by 0.25 s / duration.
  - Most V1 cells ran 15–19 s, one step = **±1.4–1.7%**.
  - Short of the ≥ 20 s floor the baseline set: MSET (×0.3: 6–10 s, ±2.5–4%), ZADD (12–14 s, ±2%), and the c1 MSET cells (6 s).
  - V3 re-ran LPUSH and MSET at c50 P=1 with ~30 s cells: LPUSH's V1 ratio sat within one step of 0.90, and MSET's cells were short.
- **Repetition spread** ((max − min)/median) was ≤ 4% for every primary c50 P=1 cell, ≤ 9% elsewhere.
- **Exact measures** are unaffected by the timer: on-CPU µs/op (schedstat), softirq and idle on the server's CPU (`/proc/stat`), instructions and cycles per op (uprof).

What changed:
- **Softirq per op** fell by 0.19–0.43 µs in every command and is now within 0.15–0.19 µs of Redis's. Fewer client threads sleep between replies, so the server's `send` wakes fewer of them ([profile §3](V0.6O-B-CPU-PROFILE.md)).
- **Task time per op** fell by 0.4 µs for SET (cheaper kernel send path and the loop's fixed cost: the overflow arm, the AOF gate's lock), and by 1.3–1.4 µs for LPUSH and SADD (PR 3's direct decode and single-slot execution, on top).
- **User instructions per op** for SET rose by 7% (the yield and its bookkeeping) while user cycles per op fell by 9%: fewer wake-ups leave the caches warmer. For LPUSH and SADD both fell, by 23% (instructions) and 40% (cycles).
- MSET's user cycles fell by 8%, all from the shared path: its user instructions are unchanged (+1%), because PR 3 did not touch MSET.

The kernel's per-op cost is now Redis's within the 0.15–0.19 µs of softirq that the remaining wake-ups cost. **The remaining distance to 0.90× is user-space command work**; see [§ post-change profile](#post-change-user-space-profile-v3-samples).

Read with the throughput: in a closed loop of 50 clients the mean latency is 50 × P / throughput, so it fell in every cell. The coalescing yield changes the distribution's shape, toward Redis's:
- A reply now leaves after the other ready connections' commands ran, not straight after its own.
- **p50 fell in every no-persistence 50-client cell** (−7% to −36%). The tail widened a little where the median fell most.
- p99 at P=1: SET +0.024 ms, GET +0.032, INCR +0.024, MSET +0.008, below Redis's p99 for all but MSET. LPUSH, SADD and ZADD p99 fell.
- **MSET at P=16 is the one cell where p99 rose materially**: +0.46 ms (+11%), consistent in all three repetitions (4.62, 4.66, 4.93 against 4.18–4.48), with p50 −7% and throughput +2.6%.
  - Cause: a ready connection's reply now waits for the other ready connections' batches. At P=16 an MSET batch is 160 key writes, so that wait is longest here. Redis has the same shape (its `beforeSleep` writes after every ready client ran), and its p99/p50 is 1.21. Recached's is now 1.28 (before 1.08).
  - Bounded: one yield per flush, at most one pass over the worker's ready connections.
  - Recorded in [the release gate](V0.6O-B-RELEASE-GATE.md) with the candidate mitigation (do not yield after a long batch, where the flush is already amortized) and the operational switch `RECACHED_REPLY_COALESCE=off`.

**Pre-existing, unchanged: LPUSH max latency.** In the LPUSH P=16 cells the *maximum* latency is 270–290 ms for both `base` and `new`, about 65 ms at one client, against 1–3 ms for Redis. `LPUSH mylist` grows one list to 20 million elements, and Recached's list is one `VecDeque`: each doubling copies the whole ring at once. Redis's quicklist grows in fixed nodes. The same structure gives the 1.96× RSS (1,328 against 678 MiB). This is memory layout, Phase 6P; not touched here.

## Multiple workers (V2 and the V3 control)

The brief's matrix is one worker. As a sanity check, the same cells ran with `RECACHED_WORKER_THREADS=3` on CPUs 0–2 (`redis-benchmark` with 3 threads on CPUs 3–5).
- V2: 2 repetitions, the V1 request counts.
- Then a control with longer cells (c1 1.2M, c50 P=1 9M, c50 P=16 60M requests; 20–34 s), 3 repetitions. `off` is the **same `new` binary** with `RECACHED_REPLY_COALESCE=off`; its server log confirms the switch.

|---|---:|---:|---|

- **Throughput: no regression.** With three workers the 50-client cells are limited by the generator (1.7–1.95 of its 3 CPUs busy, server CPUs partly idle), not by the server, so these runs cannot show the one-worker gain either. The c50 P=1 control has 6–13% spread.
- **One client: +3% CPU, no throughput effect.**
  - On-CPU per op is 13.18 µs with coalescing on against 12.77 off, in every repetition (13.18, 12.94, 13.25 against 12.77, 12.58, 12.86).
  - At one worker the same cell is unchanged (V1: 12.51 → 12.30).
  - Throughput is equal within one step (35,786 against 35,785). At one client CPU 0 is ~70% idle, waiting for the client's round trip.
  - Likely cause, consistent with the code but not traced: `reply_coalesce::end` scores a yield that resumes on *another* worker as neither gain nor miss. A lone connection whose yields migrate then never accumulates misses and never backs off. Each flush costs a scheduler round trip, and possibly a remote wake-up of an idle worker.
- **SET P=16: p99 +26%** against `off` (1.18 against 0.94 ms; every repetition: 1.29, 1.18, 1.11 against 0.98, 0.94, 0.88), with p50 −22% and equal throughput. At one worker the same cell moved 0.80 → 0.85 ms (+6%, still below Redis's 0.89). This is the same tail-widening as MSET P=16 at one worker: a pipelined batch's flush is already amortized, so the yield only redistributes the wait.
- Both are recorded in [the release gate](V0.6O-B-RELEASE-GATE.md) with a candidate fix that touches only the yield's condition. Neither affects correctness, and `RECACHED_REPLY_COALESCE=off` restores the old flush behaviour exactly.
