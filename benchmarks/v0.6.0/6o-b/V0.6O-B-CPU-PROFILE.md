# v0.6.0 Phase 6O-B1: where a no-persistence command's time goes

**Answer.**

1. **At 50 clients and P=1 the server's CPU is saturated, and the throughput ratio equals the ratio of that CPU's time per command.** For SET, Recached spends **6.4–6.6 µs of CPU 0 per command and Redis 5.3–5.5 µs**: 0.84× against a measured throughput ratio of 0.84×. That time is the server task plus **softirq run inline in its own `send(2)`**.

   The kernel is built with `IRQ_TIME_ACCOUNTING`, which charges that softirq to the CPU and not to the task. It is invisible in `/proc/<pid>/stat` and in schedstat, which is why 6O-A's "CPU µs/op" (4.39 against 3.69 µs) understated both servers by about a third.

2. **Recached makes exactly the system calls Redis makes:** 1.00 `recv` and 1.00 `send` per command, against Redis's `read` and `write`, plus 0.034–0.040 `epoll_wait`. There are no EAGAIN reads and no extra wake-ups of the server. The syscall *kind* is not a cost: on one loopback pair `send` is 60 ns cheaper than `write`, and `recv` 120 ns cheaper than `read`.

3. **But Recached's `send` costs 4.1–4.8 µs against Redis's 3.6 µs, because of when replies leave.** Recached flushes each connection's reply the moment its command ran. The benchmark's two client threads (25 connections each) then sleep and are woken for almost every reply: **0.30–0.48 client sleeps per command against Redis's 0.05.**

   Each wake-up is a remote `try_to_wake_up`, which the kernel runs in softirq on the server's CPU while delivering the reply. Redis writes every reply of an event-loop pass at once, so a woken client thread finds a burst waiting.

   This is **+0.35–0.68 µs of softirq per command** and the largest single difference at c50 P=1. A prototype that defers the flush by one scheduler yield removed most of it: client sleeps 0.30 → 0.11, softirq 2.08 → 1.85 µs/op, SET +8%, LPUSH +18%.

4. **User space adds the rest**, measured per command in user cycles with LBR samples:

   | | Recached | Redis | Gap | Main items |
   |---|---:|---:|---:|---|
   | SET | 5,717–6,199 | 4,019 | ~1,900 | a fixed per-command loop cost of ~1,300 cycles |
   | LPUSH | 8,601 | 3,239 | 5,400 | generic decode 1,217; store's generic multi-key path ~1,000 |
   | SADD | 9,935 | 3,492 | 6,400 | generic decode 1,459; store's generic multi-key path ~1,000 |
   | MSET ×10 | 23,946 | 16,367 | 7,600 | store 16,400 of which `entry_state` 8,614; decode 2,900 |

   The fixed loop cost is the `select!` overflow arm at ~440, the gate and flush at ~650–930 (DeferredAof's lock ~150 of it), and clock and metrics at ~500. For MSET, most of `entry_state` is the first touch of 10 random keys in a 100,000-key set, which is DRAM latency.

5. **One client vs 50.**
   - With one client every reply wakes the client in both servers (1.00 sleeps per command each).
   - The round trip, about 27 µs, is dominated by latency, not by server CPU.
   - Recached's cheaper wake-up (`recv` 0.75 vs `read` 0.94 µs, `send` 5.8 vs `write` 6.6 µs, and 13,373 vs 16,597 user cycles per SET including the scheduler round trip) puts it at 1.00–1.06× Redis.
   - With 50 clients, Redis's per-pass batching starts to pay and Recached's per-command user cost starts to count.

- **At c50 the server thread almost never sleeps:** 45–160 voluntary context switches over 300,000–1,000,000 commands. CPU 0 is 92–96% busy with task plus softirq. Throughput is therefore set by CPU 0's time per command.
- The packet counts are identical: one request segment and one reply segment, ACKs piggybacked, one NET_RX per command. So the extra softirq is not extra packets.
- At c1 the CPU is idle 40% of the time. The round trip, not the server, sets the rate.

Recached's 0.017 zero-timeout `epoll_wait` per command is Tokio's maintenance poll, every 61 tasks. Its blocking `epoll_wait`s rarely sleep. Neither costs more than Redis's.

**Why the send costs more: the client's wake-ups.**
- `send(2)` on loopback delivers the segment to the receiving socket inline, in softirq on the sending CPU. If the receiver is asleep, it wakes it, which is a remote `try_to_wake_up` with an IPI.
- Recached's `send` costs +410 (SET) to +1,210 ns (MSET) more than Redis's `write` of the same 5 bytes. The extra tracks the generator's sleeps per command (0.30–0.48 against 0.05).
- The `tcpcost` control rules out the syscall itself: on one pair with no wake-up, `send` costs **2,759–2,774 ns against `write` 2,830–2,844 ns**, and `recv` 2,662–2,699 against `read` 2,781–2,823. (These absolute figures include the pure ACK a same-thread `read` provokes; only the differences matter.)
- The [prototype](V0.6O-B-OPTIMIZATION-DESIGN.md#candidate-1-in-detail) is the causal test. Deferring each connection's flush by one scheduler yield, so the replies of a pass leave together, cut client sleeps from 0.29 to 0.11 per command and softirq from 2.06 to 1.85 µs/op, and raised SET by 6–8% and LPUSH by 18%.

**Why clients sleep with Recached.**
- A Tokio worker runs one connection task at a time: read, execute, flush. So replies leave spread across the pass, one every 4–9 µs.
- A client thread answering one reply needs less time than that, so it parks in `epoll_wait` before the next arrives.
- Redis reads and executes every ready client, then writes all replies in `beforeSleep`. Its client threads wake to a burst.

What it says:

- **A fixed cost of ≈ 1,300–1,500 cycles per loop pass that Redis has no equivalent for:**
  - the `select!` overflow arm, polled on every pass (~440);
  - `DeferredAof::pop`'s two lock round trips with nothing queued (~150);
  - the gate and flush indirection.

  These scale with loop passes, not commands: at P=16 they nearly vanish (22 and 11 cycles).
- **LPUSH, SADD and ZADD take the generic decode path.** A `Value` is built per argument, then `from_value` makes a second copy of each, plus an upper-cased name: 1,217, 1,459 and 2,146 cycles.
- **LPUSH and SADD then take the store's multi-key write path:**
  - the command is cloned to run by reference (314–348);
  - the scope is sorted and deduplicated;
  - the key is looked up twice more for size and TTL accounting: `entry_state` before (314–346) and the state after.

  SET, INCR and HSET avoid all of this through the probe accounting of their one write slot.
- **MSET's store cost is 16,400 cycles for 10 keys.** `entry_state`, the first lookup of each key, takes 8,614. With 100,000 keys of about 200 B each, the working set exceeds L3, so this is where each key's DRAM miss lands; it would move to the next lookup rather than vanish. The second and third lookups per key (write, then after-state) and 3 × 10 SipHash computations (1,800) are the removable part, ≈ 2–3k cycles.
- Redis does less per SET in user space (4,019 against 6,199 cycles) and *more* per wake-up at c1 (16,597 against 13,978). Recached's per-wake-up path (Tokio park, epoll, re-poll) is cheaper; its per-command path is costlier.

## 3. In-process layers vs the network

`layered_cost_bench` (release build, sandbox, pinned to one CPU) gives ns and allocations per command at four layers:
- the **store** alone, on pre-decoded commands;
- **decode** alone;
- **dispatch**, the connection loop's per-frame work without the loop;
- **`handle_tcp`**, the real loop over an in-memory pipe with every command pipelined.

The network layers are the kit's cells.

The store layer runs the owned commands through `execute_reporting_ref`, which is what the owned path's unordered write runs. SET, GET and INCR really run borrowed (`execute_ref_into`), and their dispatch column is the real path. INCR's store figure includes creating its counter keys: the in-process keys are `ctr:<n>`, which are not prefilled.

**Answers to the brief's question: is LPUSH or SADD slow because of the container mutation, or because of request processing and network scheduling?**

- **The container mutation is not the problem.** The store executes an LPUSH in 285 ns and a SADD in 384 ns, no more than a SET (340 ns).
- **The request processing around it is:**
  - Decode costs 3× SET's (198–212 against 66 ns), with 6–7 allocations against 0. That is the general `Value` path.
  - Dispatch costs 629–760 ns against SET's 487, with 9–10 allocations against 1. That adds the command clone and the generic multi-key accounting.
- **At P=1 over TCP, both are small next to the per-command network and scheduling cost.** With pipelining amortizing wake-ups, the server spends 0.72–1.19 µs per command over TCP at P=16. At P=1 it spends 4.1–5.5 µs per command of task time, plus about 2.1–2.4 µs of softirq. So **≈ 85–90% of a P=1 command's server-CPU budget is the per-request network path:** the wake-up, the syscalls with their inline softirq, the scheduler's task poll and the reply's flush. Command execution is the remaining 10–15% (35–45% for MSET).
- That is why the largest single lever at c50 P=1 was *when* replies leave (§1). It is also why, at P=16, where the network cost is amortized, LPUSH and SADD fell furthest behind Redis: their extra per-command user work was then the difference.

An in-process microbenchmark is not a production throughput claim. These layers only locate the cost; the throughput claims are the TCP cells.

## 4. Ranked bottlenecks

| # | Bottleneck | Cost | Commands | Confidence |
|---|---|---|---|---|
| 1 | Replies trickle out per connection, so clients wake per reply | +0.35–0.68 µs/op of softirq on the server CPU and 0.30–0.48 client sleeps per command, at c50 P=1 | all | High: counters plus the causal prototype |
| 2 | Generic decode for LPUSH, SADD (and ZADD) | 1,217–2,146 cycles | LPUSH, SADD, ZADD | High |
| 3 | Generic multi-key store path for single-key LPUSH and SADD | clone 314–348, `entry_state` 314–346, after-lookup, sort | LPUSH, SADD | High |
| 4 | `select!` overflow arm polled every pass | 390–480 cycles | all at P=1 | High |
| 5 | MSET: three lookups and hashes per key | ≈ 2–3k of 16.4k store cycles (the DRAM miss itself is not removable here) | MSET | Medium |
| 6 | Gate lock with nothing queued | 140–280 cycles | all at P=1 | High |
| 7 | Clock reads and metrics per command | ≈ 500 cycles | all | High, but kept: metrics are a feature, and Redis 7.2 also times every command |
| 8 | Tokio scheduler per task poll | ≈ 1,000 cycles | all at P=1 | High, but architectural (task per connection) |

None of 1–6 needs an architectural change. Items 7 and 8 are the floor this design keeps: about 1,500 cycles per pass, roughly 0.37 µs at 4 GHz, of a 5.3–5.5 µs Redis budget.
