# v0.6.0 Phase 6O-B0: the no-persistence baseline

**Answer.**
- With no persistence, one worker, 50 clients and no pipelining, `dev` `51ae15c` reaches these fractions of standalone Redis 7.2.5's throughput:

  | Command | Ratio to Redis |
  |---|---:|
  | SET | **0.84×** |
  | LPUSH | **0.70×** |
  | SADD | **0.64×** |
  | MSET (10 keys) | **0.72×** |

- The three controls: GET 0.88×, INCR 0.80×, ZADD 0.91×.
- These are the 6L figures within noise: 6L had 0.83, 0.71, 0.70, 0.76, 0.86, 0.84 and 0.86.
- **With one client, Recached matches or beats Redis on every command:** SET 1.06×, LPUSH 1.00×, SADD 0.98×, MSET 1.03×.
- At pipeline 16 SET is at parity, but the collection commands fall further behind: LPUSH about 0.67× and SADD about 0.57×. Pipelining removes the per-reply network cost, which leaves user-space CPU as the whole cost. These are the commands whose per-command work is the heaviest; see the [CPU profile](V0.6O-B-CPU-PROFILE.md).

**Host state.**
- Swap held 3.38 GiB, stale and never active: it was constant to within 8 MiB, and memory PSI was ≤ 0.18% in every cell.
- IO PSI had a median of 1.9%, and a few cells started at the 90 s settle cap with up to 43%. That matters little with persistence off: the server does no disk I/O.
- The 1-minute load was ≤ 3.9 including the benchmark itself.
- GNOME localsearch, Firefox and VS Code were running on unpinned CPUs.

**Quantization (measurement uncertainty).** redis-benchmark detects completion on its 250 ms timer, so both its reported rps and the wall time step in 0.25 s. For example, SET c50 P=16 took 4.53, 4.78 or 5.03 s.
- A 13–25 s cell (c50 P=1, c1 P=1) carries **±1–2%** of quantization.
- The **4–6 s cells (P=16) carry ±5%**. Their ratios are reported here but are not decision-grade.
- The [validation run](V0.6O-B-PERFORMANCE.md) sizes every cell to ≥ 20 s.
- The exact per-operation measures are unaffected: on-CPU µs/op from schedstat, and instructions/op and cycles/op from uprof.

**Generator capacity.** `redis-benchmark` used 0.17–1.27 CPUs of its two threads on three CPUs, so it was never saturated. At c50 P=1 the **server's CPU is the bottleneck**: the server thread almost never sleeps, and the CPU's remaining time goes to inline softirq. See the [profile](V0.6O-B-CPU-PROFILE.md#1-the-server-cpus-budget).

**What the shape says** (explained in the [profile](V0.6O-B-CPU-PROFILE.md)):

- **SET** costs Recached *less* CPU than Redis everywhere except c50 P=1. There it costs 4.10 against 3.46 µs/op of task time, plus more softirq. Its 50-client deficit is not command execution.
- **LPUSH and SADD** cost more CPU at every pipeline depth once there are many requests to amortize the wake-ups over: +45–80% at P=16. That is per-command user work, the general decode path and the generic multi-key store path. At 50 clients the per-reply network effect is added on top.
- **MSET** costs 15–37% more CPU at every concurrency except c1 P=1. Most of it is in the store: three lookups per key, the first of which takes the DRAM miss of a random key.
- With one client and no pipelining, every command waits for a full network round trip of about 27 µs, of which server CPU is 12.7–18.5 µs. Recached's lower scheduler and syscall cost per wake-up, measured in the profile, puts it ahead of or level with Redis there.

## Answers

**1. Updated no-persistence baseline.** In the 50-client P=1 gate cells: SET 0.840, LPUSH 0.695, SADD 0.641, MSET 0.723 of Redis 7.2.5. Against Valkey 9.1.0: 0.880, 0.729, 0.672, 0.734.

**2. Furthest from Redis.** SADD (0.64×), then LPUSH (0.70×) and MSET (0.72×). At P=16, SADD is at 0.57× and LPUSH at 0.67×.

**3. Stability.** The repetition ranges are within ±3% of the median at c50 P=1, apart from SADD's first repetition at 0.695. Valkey sits 2–5% below Redis throughout, as in 6O-A.
