## Answers to the three questions

**1. Did Phase 6M materially improve real AOF performance?**

Unknown. The only proof so far is the batching counters (1.0 → 9.5 commands per write on macOS). There is no Linux throughput, CPU or p99 measurement of the RC.

**2. Is the corrected production build reliable under sustained load?**

Unknown.
- Fault-level correctness is well covered by tests.
- No sustained, integrated soak has ever completed on any v0.6 commit.

**3. What still prevents v0.6.0 from being released?**

| Kind | Items |
|---|---|
| **Known failing** | memory per key (1.89× vs 1.5×); non-persistence throughput on several commands (0.70–0.86× vs 0.90×) |
| **Unmeasured** | AOF throughput vs Redis after 6M; replication-path AOF overhead; one 40-minute production soak |

## Recommendation

The final path (A, B, C or D in the brief) cannot be chosen until Tests A, B and D run. All three are prepared in `run-targeted.sh` and take about 1 h 20 min on an idle host.

Whatever A shows, **path C (a focused CPU and memory milestone) is already required**, because the memory and no-persistence throughput targets fail on evidence that is still valid. Path D (release packaging) is ruled out.

| If Test A shows | Then |
|---|---|
| AOF < 90% of Redis | Add path A's profiling to it |
| Test B shows a ≥ 20% penalty with about 1 write per command | Also open 6N-B (design only) |
