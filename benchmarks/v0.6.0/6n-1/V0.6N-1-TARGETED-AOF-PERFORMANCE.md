# v0.6.0 Phase 6N-1: targeted AOF performance (Test A)

**Status: NOT VERIFIED. No measurement taken.**

On 2026-11-18 the only dedicated Linux host available, an i5-9400F with 6 cores, was fully occupied by another project's 6-hour soak (load average 25–28). Measuring under that load would give contended numbers that the brief forbids substituting. `run-targeted.sh` refuses to start above a 1-minute load average of 1.0, and refuses to run inside a Flatpak sandbox.

## What is known without a new run

- **Pre-6M baseline (6L final, `159d7e9`, same host, inside Flatpak):** SET, everysec, 1 worker, P=1, 50 clients.
  - Throughput: 6l 62,480 rps vs Redis 148,115 (**0.42×**) and Valkey 142,827.
  - CPU: 12.6 vs 4.3 µs per request.
  - Source: `../6l/fedora-i5-9400f-20261117-final/D-battery-aof/summary.md`.
- **6M macOS counters:** commands per `write(2)`, 1 worker, P=1, 50 clients, went from 1.0 to 9.5. This is exact, but it is a count, not throughput.
- **Unknown:** throughput, CPU per op and p99 with coalescing on dedicated Linux. That is this test.

## Matrix (`run-targeted.sh`, `RUN=A`)

**Servers:**
- `base`: the RC binary with `RECACHED_AOF_COALESCE=off`
- `recached`: the RC binary with coalescing on, the default
- Redis 7.2.5 and Valkey 9.1.0, the 6L builds

**Common settings:** everysec; 1M requests per run; 3 reps interleaved, rep outermost; server on CPUs 0–2, `redis-benchmark` on 3–5.

| Folder | Workload | Workers | Clients | P | Servers |
|---|---|---:|---:|---:|---|
| `A1-w1-set-c50` | SET | 1 | 50 | 1, 16 | off / on / Redis / Valkey |
| `A2-w1-set-c100` | SET | 1 | 100 | 1 | off / on / Redis / Valkey |
| `A3-w4-set-c50` | SET | 4 | 50 | 1, 16 | off / on / Valkey (`--io-threads 4`). Redis is single-threaded: its A1 rows are the reference |
| `A4-w1-incr-hset-c50` | INCR, HSET | 1 | 50 | 1 | off / on / Redis / Valkey |

That is 26 cells × 3 reps = 78 runs, about 30 minutes.

**What each row records** (`aof-profile.sh`):
- rps; p50, p95 and p99; server CPU-seconds, giving µs per request;
- RSS;
- the AOF counter deltas: batches, frames, `write(2)` calls, fsyncs, queue wait and waiters.

**Derived from the counters:**
- writes per million commands = `write_calls / requests × 10⁶`
- commands per batch = `frames / batches`
- mean queue wait = `queue_wait_usec / batches`
- errors come from `redis-benchmark`'s CSV and the server logs

**Instructions per op:** the native host has no `perf` installed. `A-perf.txt` records that, and this column stays NOT MEASURED unless `perf` is installed on the host first (`dnf install perf`; needs the owner).

## Commands

On the host, natively (outside the VS Code Flatpak: a host terminal, or `flatpak-spawn --host`). Only once the host is idle.

```sh
# 1. Build the RC in its own target dir. The native host has no C toolchain,
#    so build inside the dev sandbox and run the binary natively.
git -C ~/Documents/OpenSource/recached worktree add --detach ~/recached-6n1-bench/src-rc e6fcd5bcac3fc15a171ee7800340d77501c4bfc8
cd ~/recached-6n1-bench/src-rc && test -z "$(git status --porcelain)"
CARGO_TARGET_DIR=$HOME/recached-6n1-bench/target-rc cargo build --release --locked -p recached --bin recached-server
RC_BIN=$HOME/recached-6n1-bench/target-rc/release/recached-server
RC_SHA256=$(sha256sum "$RC_BIN" | cut -d' ' -f1)

# 2. Tests A and B (about 35 minutes), from the kit checkout at d462dc3 + this folder.
RC_SHA=e6fcd5bcac3fc15a171ee7800340d77501c4bfc8 RC_BIN=$RC_BIN RC_SHA256=$RC_SHA256 \
  bash benchmarks/v0.6.0/6n-1/run-targeted.sh
```

Copy the results into `benchmarks/v0.6.0/6n-1/<host>-<utc>/`, keeping `conditions.txt`, every `results.csv` and `summary.md`, and the server logs. Leave out the data directories.

## Stop rule

If A1 shows `on` within 5% of `off` (no real gain), or a p99 regression larger than 20%, stop after A1. Capture the counter deltas and the server logs before running A2–A4. Do not tune.
