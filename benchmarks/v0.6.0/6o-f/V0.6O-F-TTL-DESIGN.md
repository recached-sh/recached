# v0.6.0 Phase 6O-F1: expiring keys through replay, design

| | |
|---|---|
| Root cause | `V0.6O-F-ROOT-CAUSE.md` §1 and §4 |
| Status | **Design only. Implementation awaits maintainer approval** (2026-11-24 decision: "design first, no ship") |
| Shipped in 6O-F instead | The deadline-overflow restart blockers (`V0.6O-F-TTL-FIX.md`), plus reproductions and regression guards for this design |
| Recommended | **Option E: logged expirations, timeless application.** This is Redis's model: the primary logs a `DEL` for every expiry it acts on, and the AOF replay and replicas never evaluate expiry themselves |
| Rejected | **Option 1: absolute deadline in the counter frame** (`SET k n PXAT T`). Implemented, reviewed, and rejected by the 6O-F review (§2) |
| Needs approval for | An AOF marker record, and a replication capability (§5) |

## 1. What must hold

The AOF replay and a replica must reach the state the primary had **on the original timeline**: every frame applied to the state its command saw.

Today two things break this:
1. **Expiry is evaluated at the applier's clock.** The AOF replay runs after the restart, and a replica can apply a frame after a delay or with a skewed clock. A frame whose command found its key live can find it expired.
2. **Expirations are not logged.** The sweeper removes keys silently, and a write that finds a key expired resets it silently (`typed_entry!`, `SET … NX`). A frame whose command found its key absent or expired can find it live, or expired with stale content.

Each gives wrong states:

| Command on the primary | Frame | Applied later | Result |
|---|---|---|---|
| `INCR` of a live key with deadline `T` | `SET k n KEEPTTL` | after `T` | **permanent** key (resurrection) |
| `APPEND`/`HSET`/`RPUSH` to a live volatile key | the delta | after `T` | **permanent** key holding the last part only |
| `LSET`, `RENAME` on a live volatile key | verbatim | after `T` | `no such key`: **AOF replay refused, no restart** |
| `PEXPIREAT k T2` extending a live key | `PEXPIREAT k T2` | after the old deadline | no-op: **key lost** |

## 2. Option 1, rejected: the absolute deadline in the counter frame

Option 1 changed the counter and `SET … KEEPTTL` frames to `SET k n PXAT <deadline after the write>`. That is self-contained for the counter itself: one frame, no new command. It was built, tested, matched Redis on the plain fixed-window case, and then failed independent review (`V0.6O-F-INDEPENDENT-REVIEW.md` R1).

| Original timeline (replay at the instant shown) | Today (`KEEPTTL`) | Option 1 (`PXAT`) |
|---|---|---|
| `SET k 1 PXAT T1`, `INCR`, replay after `T1` | permanent `2` ✗ | absent ✓ |
| `INCR`, `EXPIRE` on every hit (sliding window), replay between `T1` and `T2` | `2` until `T2` ✓ | **absent** ✗ |
| `SET k 1 PXAT T1`, `INCR`, `PERSIST`, replay after `T1` (AOF or replica) | permanent `2` ✓ | **absent** ✗ |
| `SET k 1 PXAT T1`, `INCR`, `RENAME k k2`, replay after `T1` | replays (`k2` permanent) | **replay refused: no restart** ✗ |

The counter frame was never the problem: it describes the counter correctly once the key is live where it is applied. The later frames (`PEXPIREAT`, `PERSIST`, `RENAME`) only work because `KEEPTTL` resurrected the key first. No frame format fixes both rows: as long as the applier evaluates expiry on its own clock, a later frame that refers to the key's existing state can find it gone. The regression cases are now permanent guards (`guard_*` in `server-native/src/tests/expiry_replay_6of.rs`). The rejected code is kept on the local branch `experiment/v0.6o-f-counter-pxat-rejected` (`e55f7d5`).

## 3. Option E, recommended: logged expirations, timeless application

This is what Redis does:
- `propagateDeletion` logs a `DEL` for every key it expires: active expiry and lazy expiry.
- `keyIsExpired` answers "not expired" while loading the AOF, and to the master link on a replica.

| Part | Change |
|---|---|
| **E1. Writes log what they found expired** | A write command that finds an expired entry for any key it touches emits `DEL <key>` before its own frame, under the same ordering guards, through the same `on_write` path. This covers: `typed_entry!` resets; `SET` with `NX`/`XX`/`GET`/`KEEPTTL` on an expired entry; `*STORE`/`COPY`/`RENAME` sources; `LSET`/`LINSERT`/`HINCRBY`, and so on. The store reports the keys it observed expired during the call, in a thread-local list collected like 6O-E's `at_instant`, so no command implementation changes its reply |
| **E2. The sweeper logs what it removes** | `sweep_expired_tick` already runs under the all-write barrier. It emits `DEL` for each key it removes, batched per chunk (`DEL k1 k2 …`) |
| **E3. Timeless application** | The AOF replay and a replica apply frames with **no expiry evaluated**: an entry is live until a `DEL` removes it. Implementation: run the store call inside `at_instant(0)`. Frames carry only absolute deadlines, so a clock of 0 sees no entry as expired. Afterwards the real clock applies as usual, and the sweeper removes what has expired by then |
| **E4. Replicas stop expiring on their own** | A follower does not run active expiry. It applies the primary's `DEL`s and masks expired keys on reads by its own clock, as a Redis replica does. Promotion turns its sweeper back on |

**Why it is right.** With E1 and E2, every transition on the primary from "has key `k`" to "has no key `k`" is in the log. Explicit deletions already were, expirations now are. With E3, the applier never makes such a transition itself. So the applier's state before each frame is the primary's state before that frame's command, and a frame applied to the state its command saw reproduces the command's result. That holds because every frame is deterministic given the prior state: the 6B design rule, and why the STORE family replays verbatim. The table in §1 then resolves:

| Case | With E |
|---|---|
| `INCR` of a live key, applied after `T` | `KEEPTTL` keeps `T` on the entry (live, timeless). Afterwards the real clock says expired, and the key is gone ✓ |
| A counter on an expired key | E1 logs `DEL k` first. `SET k 1 KEEPTTL` on an absent key gives a permanent `1` ✓ |
| A delta, then `EXPIRE` extending | the delta lands on the live entry, and the `PEXPIREAT` extends it ✓ |
| `RENAME`/`LSET` after the deadline | the entry is live to the frame, so the replay succeeds and gives the right state ✓ |
| Counter frames | **unchanged** (`KEEPTTL`) |

## 4. Costs and risks

| | Effect |
|---|---|
| AOF and replication volume | One `DEL` per expired key the primary acts on: every swept key, and each write that finds an expired entry. A `SET … EX 1` workload doubles its records, as in Redis. Batching per sweeper chunk bounds the frame count |
| Sweeper | Its removals become effects: an AOF append and a replication send per chunk, under the barrier it already holds. An expiry-heavy workload with `appendfsync always` pays an fsync per chunk |
| Replica memory | Expired keys stay on a replica until the primary's `DEL` arrives: the replication delay plus the primary's sweep latency. Reads mask them meanwhile |
| Write path | One thread-local check per store call for observed expirations; a `DEL` frame only when one was observed |
| Lazy expiry on reads | Not logged, unlike Redis. A read that masks an expired key changes nothing; the next write or the sweeper logs it. This is what E1 relies on, and it keeps reads write-free (6O-C/6O-D) |
| Clock skew | It no longer matters for replicas: only the primary decides expiry |
| DEDUP | A write's `DEL`s go before its `DEDUP` envelope, outside it. They are ordinary writes, and the envelope stays one frame |
| Transactions (6O-E) | A queued write's observed-expired `DEL`s are emitted with the frames of that queued command, at the transaction's instant |

## 5. Compatibility: why approval is needed

| Peer | Problem | Proposal |
|---|---|---|
| **Old AOF files** | Their records assume time-evaluated replay. Under E3, a delta that recreated an expired key on the old primary would merge onto stale content (no `DEL` before it) | Timeless replay starts after an **AOF marker record** written at the head of every new file (creation, and after each checkpoint truncate). Records before the marker, or in a file with none, replay as today |
| **Downgrading to a binary before E** | An old binary refuses an unknown record (`invalid AOF command`): a new marker would stop the restart | Use a marker the old replay already ignores: a `RECACHED-CHECKPOINT` record with a reserved id, or `DEL` of a reserved key. The old binary then replays the file time-evaluated, today's behaviour; the extra `DEL`s are harmless. **Decision needed** between the two |
| **New replica of an old primary** | No `DEL`s are logged, so timeless application would merge onto stale content | A replication capability, `caps=expirylog`, beside today's `caps=dedup` (same negotiation, carried in the run-id strings). Without it, the replica applies as today and keeps its own sweeper |
| **Old replica of a new primary** | It receives extra `DEL`s (harmless) and keeps sweeping (today's behaviour) | Nothing |
| **Browser and mobile sync** | Pushes gain `DEL`s for expired keys. Clients already apply `DEL` and expire locally | Nothing. Arguably better: a browser learns of an expiry without its own clock |

Both the marker and the capability are additive. Neither changes an existing record or frame. But they change what the AOF and the replication stream carry, which the brief reserves for explicit approval.

## 6. Tests the implementation must pass

- **Already in place** (`expiry_replay_6of.rs`): every `reproduce_*` case passes with `RECACHED_REPRODUCE_6OF_COUNTER=1` (the gate is then removed), and every `guard_*` and control still passes.
- **Replica:** a replica applying after the deadline, with a skewed clock, after a backlog replay and after promotion. A replica's memory under an expiry-heavy load (bounded by the primary's sweep).
- **Old files:**
  - every legacy record shape replays as today;
  - a mixed legacy-then-marker file;
  - a downgrade: a new file replayed by the `410235b` binary.
- **Process level and Redis:** `counter_restart_diff.py` extended with the sliding window, PERSIST, RENAME, LSET and the partial updates, against Redis 7.2.5. Redis's own model gives the expected state.
- **Mutants:**
  - an observed expiry not logged;
  - a `DEL` placed after the frame;
  - the sweeper not logging;
  - the replay still time-evaluated after the marker;
  - the replica still sweeping with the capability;
  - timeless application before the marker.
- **Both AOF fan-out modes, and all three fsync policies.**

## 7. Milestones (for the implementation phase)

1. **The store reports observed expirations** (thread-local, per call), with property tests over every write command.
2. **E1**: `DEL` emission in `apply_write_effects`, including transactions and DEDUP.
3. **E2**: the sweeper logs its removals.
4. **E3** for the AOF: the marker record and timeless replay.
5. **E3/E4** for replication: the capability, timeless application, and a follower without active expiry.
6. Compatibility matrix, performance (expiry-heavy SET, INCR with AOF, replica memory), independent review.

## 8. What 6O-F ships instead

- **Deadline overflow** (`V0.6O-F-TTL-FIX.md`): commands refuse a deadline past `i64::MAX` as Redis does, so no frame carries one, and records from older servers are clamped on replay. It closes two restart blockers that do not depend on this design.
- **Reproductions and guards** for this design, which fix the target and protect the cases Option 1 broke.
- **Counter propagation is unchanged.** Resurrection stays open: a v0.6.0 release blocker, Medium, pre-existing.
