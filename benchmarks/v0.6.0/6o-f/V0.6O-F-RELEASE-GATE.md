## 2. The nineteen questions

| # | Question | Answer |
|---|---|---|
| 1 | Was the expiring-counter bug reproduced deterministically? | **Yes.** 10 of 15 tests failed on `410235b` in 5 runs out of 5, using the store's clock override (no sleeps), for AOF no/everysec/always, a real replica, and transactions. End to end with SIGKILL: Redis 7.2.5 has no key, Recached brings it back permanent |
| 2 | What caused the expiration metadata to disappear? | Counters propagate as `SET k n KEEPTTL`. Applied after the original deadline, the entry is expired to the applier, `KEEPTTL` keeps nothing, and the key is recreated without a deadline. **More generally:** the AOF replay and replicas evaluate expiry on their own clock, and expirations are not logged. The same thing resurrects partial updates (`APPEND`, `HINCRBY`, `RPUSH`) and makes replay refuse `LSET`/`RENAME` of expired keys |
| 3 | How does the new representation preserve the original deadline? | **It does not ship.** The `SET n PXAT <deadline>` representation was built and rejected: it fixes the counter alone but breaks later frames that extend, persist or rename the key. The recommended design (logged expirations, timeless application) leaves counter frames unchanged and makes every frame apply on the original timeline |
| 4 | Does AOF replay after the deadline remain correct? | Unchanged from `410235b`: correct for every case except the resurrection class, which stays open (gated reproductions). The deadline-overflow restart blocker is fixed |
| 5 | Do lagging replicas remain correct? | Same as 4. Replicas also now accept legacy over-range deadlines (bare or in DEDUP) instead of breaking the link |
| 6 | Are existing AOF files still readable? | **Yes**, and more of them: files holding a deadline past `i64::MAX` (which no version could replay) now replay. One exception: a pre-0.3 relative `PX` record whose `now+ms` overflows (a TTL beyond 292 million years) now fails, naming the offset |
| 7 | Are there unavoidable limitations for historical records? | Yes, for the future expiry design: a legacy `KEEPTTL` record replayed after its deadline cannot recover a deadline it never stored, and old files cannot be replayed timelessly. They lack the logged expirations, so the design applies timeless replay only after a marker record (`V0.6O-F-TTL-DESIGN.md` §5). A key already resurrected by an older replay carries no trace of its deadline |
| 8 | Did INCR CPU, p99 or throughput regress? | Instructions per op: no change (5,435 → 5,440). Throughput at P=1: −2.2% in all 5 repetitions (cycles +3.7%, same instructions: layout or run conditions, since INCR's code is untouched). P=16: +1.1%. p99: +1 histogram step. Counter frames are unchanged |
| 9 | Was the external transaction partial-visibility issue reproduced? | **Yes**: `[new, old]` in 10 runs out of 10 on `410235b` |
| 10 | Which transaction visibility design is recommended? | **Option E: two-phase EXEC.** A core-engine `apply_transaction` runs every queued store command synchronously, holding and marking (6O-D `seq`/`multi`) the store stripes its writes take from the first write to the last. In-scope reads bypass the stripes. The effects run afterwards in command order, with notifications coalesced per key by effective write |
| 11 | Can the design safely span asynchronous persistence work? | **It does not span it.** Every store mutation completes in a synchronous section before any await, so no `std` guard crosses an await and no reader waits on I/O |
| 12 | Can readers remain correct during a slow fsync? | Yes, and unblocked: no store stripe is held or marked during the effects phase. Writers of the transaction's keys wait for the server stripes, as today |
| 13 | What happens on cancellation and crashes? | Phase 1 cannot be cancelled. A panic is contained per command inside the held scope, with a convergence procedure (MISCONF until SAVE, run-id rotation forcing a full replica resync, metadata rebuild). Phase 2 has today's exposure. **Crash atomicity and replica-side atomicity are not given** without AOF and replication framing (separate approval) |
| 14 | What are the expected memory and latency costs? | Memory: the frames held until phase 2 (command-sized) and one index per written key; no value copies. Latency: readers of a written stripe wait for the synchronous write span (microseconds typically). **Worst case**: a capped or `FLUSHDB` transaction marks every stripe, so every reader and writer waits for its write span (up to 10,000 commands). To be measured in 6O-G |
| 15 | How much did each stripe count reduce unrelated-key contention? | Contended acquisitions halved per doubling (28,238 → 13,372 → 6,557 per 30 s), and waits fell from 684 to 147 to 59 ms per cell. For **2-key transactions** that is 0.04% of connection time at 256, and throughput did not improve (512: 1.000; 1,024: 0.976 against `x256`; the same with AOF everysec). **Wide transactions do collide at 256:**
- read-only `MGET×10`: 31% of connection time waiting, which shows in p99 (−35% at 512);
- **write transactions of 20 keys: +37% throughput at 512 and +55% at 1,024**, with p99 cut up to 5×. Net work rises (about 1.64 M → 2.45 M key operations per second at 1,024, as idle capacity is put to work). Concurrent 2-key writers get a smaller share at saturation (−30%, −83%) |
| 16 | How did larger stripe counts affect snapshots and other all-stripe barriers? | Linearly, plus waiting: idle SAVE barrier 14 → 23 → 42 → 76 µs; the sweeper chunk 183 → 270 → 419 → 657 µs. **Capped stores**: evicting writes 0.75 / 0.51 / 0.31 and capped EXECs 0.66 / 0.41 / 0.24 at 512 / 1,024 / 2,048. A whole-keyspace read inside EXEC: 0.65 / 0.39 |
| 17 | Should the next implementation use 256, 512, 1,024 or another approach? | **256 for the server layer, for now.** Wide write transactions would gain from 512 or more, but the all-stripe barrier's cost grows with N, and capped stores take it on every evicting write and every EXEC (0.66 / 0.41 at 512 / 1,024). **Reconsider 512 after a cheaper all-stripe barrier.** For the store layer, 256 is provisional until 6O-G measures phase 1's store-stripe contention. Cheaper follow-ups than more stripes: a set-word scan in `transaction_stripes` (~12% of a 2-key transaction); a shared read mode for read keys; a cheaper all-stripe barrier for capped stores |
| 18 | Are all existing 6O-D and 6O-E guarantees preserved? | **Yes.** No change to transactions, WATCH, MSET atomicity, the clock or the stripes. The 6O-D/6O-E suites pass in both fan-out modes. The F2 design was reviewed against them |
| 19 | What remains before v0.6.0 can be released? | §4 |

## 3. Decisions requested from the maintainer

1. **Expiry design (F1):** approve `V0.6O-F-TTL-DESIGN.md` Option E for implementation, including:
   - the AOF marker record (and which encoding: a reserved checkpoint id or a reserved-key `DEL`, for downgrade safety);
   - the replication capability `caps=expirylog`.

   Or accept expiring-counter resurrection as a documented v0.6.0 deviation.
2. **Transaction atomicity (F2):** authorize Phase 6O-G1 (Option E, runtime atomicity). Separately, decide on 6O-G2 (AOF and replication transaction framing, for crash and replica atomicity).
3. **Capped-store transactions (new, pre-existing):** every EXEC on a capped store takes all 256 stripes, so capped transactions are globally serialized. In the measured mix that is 1.9× fewer total operations than uncapped. Every multitenant deployment is capped. Accept, or schedule a cheaper capped barrier.
4. **Stripe count:** no change (256).
