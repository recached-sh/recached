## 1. The deadline bound (production change)

**Defect (pre-existing, High: availability).** Every expiry form accepted any value and saturated the deadline in `u64`. `SET … EXAT` and `EXPIREAT` propagated it as `PXAT`/`PEXPIREAT` past `i64::MAX`, which no parser accepts:
- the AOF replay refused the file, so the server could not restart;
- a replica treated the frame as a broken stream.

A single client command could do this.

**Fix.**
- `core_engine::store::deadline_after(base, amount, unit)` gives `base + amount × unit` only if it fits a signed 64-bit count of milliseconds. Every expiry form uses it: `SET` EX/PX/EXAT/PXAT, `SETEX`, `PSETEX`, `EXPIRE`, `PEXPIRE`, `EXPIREAT`, `PEXPIREAT` and `GETEX`.
- Overflow answers `ERR invalid expire time in '<command>' command`, as Redis 7.2.5 does.
- The order follows Redis:
  - `SET` (including `NX`/`XX`/`GET`) and `EXPIRE` check before looking at the key;
  - `GETEX` looks the key up first (an absent key is nil), then checks the type (WRONGTYPE), then the deadline.

**Records already written** are clamped. `persistence::clamp_overflowing_deadline` rewrites `SET k v PXAT n` and `PEXPIREAT k n`, bare or after a `DEDUP <client> <id>` prefix, with an all-digit `n` past `i64::MAX`, to `i64::MAX`. That is what `PEXPIRETIME` reported for the key, so the meaning is unchanged. It runs:
- in AOF replay, with one summary warning per replay;
- on a replica, before the DEDUP dispatch.

The bytes a replica forwards downstream stay the primary's, which keeps offsets correct, and every applier clamps.

## 4. Limitations

- **AOF files from before 0.3** stored relative `SET k v PX <ms>` records. One whose `now + ms` passes `i64::MAX` used to saturate on replay; it now fails, and the error names the offset. Such a TTL is beyond 292 million years (review round 1, F3).
- **Not clamped** (pre-existing, recorded):
  - a snapshot holding a legacy deadline past `i64::MAX` (its `PTTL` wraps negative);
  - wasm-edge WAL replay of such a record (the record is dropped).
- **Pre-existing parser differences from Redis**, unchanged: `GETEX` on an absent key with a value the parser refuses; `EXPIRE k -1`; parser errors inside MULTI.
