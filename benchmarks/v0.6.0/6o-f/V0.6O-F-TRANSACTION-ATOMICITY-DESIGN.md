# v0.6.0 Phase 6O-F2: transaction atomicity to outside readers, design

| | |
|---|---|
| Defect | 6O-E F1 (High, pre-existing): readers outside `MULTI`/`EXEC` see a transaction's writes part-way |
| Reproduction | `an_outside_reader_never_sees_a_transaction_part_way` (`RECACHED_PROBE_6OE_F1=1`): `[new, old]`, 10 runs out of 10 on `410235b` (`raw/f0-reproduction/f1-probe-on-410235b.log`) |

| Recommended | **Option E (revision 2): two-phase EXEC.** A core-engine `apply_transaction` runs every queued store command synchronously, holding and marking (6O-D `seq`/`multi`) the store stripes its writes take from the first write to the last; in-scope reads bypass the stripes. | Not recommended | A (long-lived marks across awaits), B (private staging), C (versioned publication), D (global async barrier) |
| Needs separate approval | Crash atomicity and replica-side atomicity, which need transaction framing in the AOF and the replication stream (§6) |

## 1. Root cause

Two layers order writes, and only one of them is visible to readers:

| Layer | EXEC holds | An ordinary reader consults |
|---|---|---|
| **Server**: 256 replication-order stripes (`tokio::sync::Mutex`) and the unordered gate | Gate closed, and the stripes of every read, written and watched key, from before the first queued command until after the last (6O-E) | nothing |
| **Store**: 256 write-order stripes (`std::sync::Mutex` + `seq` + `multi`, 6O-D) | each queued command's stripes, **separately**, inside that command's synchronous store call | `read_one_at` (waits on `multi`) and `read_many` (validates `seq`, then falls back to the locks) |

`run_transaction_queue` runs queued command *i*'s store call, then **awaits** its effects (`apply_write_effects`: AOF append, under `always` with observers its `fdatasync`, replication fan-out, WATCH notification, WebSocket pushes), then runs command *i+1*. Through that await no store stripe is held or marked. The store makes each command atomic, and the server excludes writers, so a reader sees *i* and not *i+1*.

## 2. Requirements

1. An outside reader observes a transaction's writes **all or none**. This covers single-key and multi-key reads, the borrowed path, and WebSocket reads, and holds across several sequential reads by one client.
2. Never hold a `std::sync::MutexGuard` across an `.await`; never block a Tokio worker for an I/O wait.
3. Keep every 6O-D and 6O-E guarantee: MSET reader atomicity, EXEC read isolation, one transaction clock, writer exclusion, guards released before the reply, no early acknowledgement.
4. Ordinary `GET`/`MGET` keep their cost when no transaction is applying.
5. Bounded memory and bounded waits.

## 3. Options

### Option A: long-lived transaction visibility marks

Mark the store stripes of the transaction's write keys before its first mutation and clear them after its last, **across** the awaits.

- **The reader cannot wait synchronously.** The mark can last through an `fdatasync` (milliseconds on SSD, seconds on a stalled disk). `wait_for_multi` spins and then blocks the thread on the stripe lock. On a 1-worker runtime that **deadlocks**: the reader blocks the only worker, and the transaction needs it to finish its await. On N workers, up to N−1 workers sit blocked behind a disk.
- **So a reader seeing the mark would need an asynchronous fallback.** One candidate: await the server replication-order stripes of its keys, which EXEC holds to its end, then re-read with the mark ignored for keys it now holds. That is sound: ascending order, it holds nothing else, and a held server stripe proves no transaction writes that key. But it turns every borrowed read into a possible `.await`: a second read path, a "may suspend" result from the store, and a change to the 6O-C/6O-D hot path.
- **The marks need a different discipline.** They would need read-modify-write words, because 6O-D's words have a single writer (the holder), while nested commands also mark.
- **Readers wait for persistence.** Under `appendfsync always` with a replica, a reader waits for every queued write's fsync.

Rejected. It is correct only with an asynchronous reader fallback, and it makes readers wait for the disk.

### Option B: a private staged write set

Execute the queue against a private copy of the affected entries, then publish the copies in one synchronous step.

- It reuses the command engine on a scratch `KeyValueStore` holding the scope's keys at the instant.
- **The cost is the copy.** A queued `LPUSH` onto a 1-million-element list copies the list, and a `SUNIONSTORE` copies every source. The worst case is unbounded by the queue length.
- **Accounting is duplicated.** Capacity, eviction and the TTL index run on two stores.
- **Whole-keyspace commands** (`FLUSHDB`, `KEYS`) cannot be staged, so a second mechanism is needed anyway.

Rejected: Option E gives the same reader behaviour with no copy.

### Option C: versioned publication (epochs)

Keep committed and pending versions per key, and have readers pick the committed one. This is MVCC: two versions per entry, garbage collection, and every read path made version-aware. The memory cost conflicts with Phase 6P's per-key target (1.88–1.98× Redis now, ≤1.5× wanted). Simpler variants (an epoch per stripe) only tell a reader to retry, and that is Option A without its fallback.

Rejected.

### Option D: a coarse barrier (reference)

An async `RwLock`: every read takes it shared, and a writing EXEC takes it exclusive. It is trivially correct, but every `GET` gains an atomic read-modify-write on one shared line. From 6O-C/6O-D's profiles that costs a 3-worker `GET P=16` tens of percent, and it serialises every writing transaction against every reader of every key.

Kept only as the reference upper bound of contention.

### Option E: two-phase EXEC (recommended, revision 5)

Revisions 2–5 follow four rounds of independent design review (`V0.6O-F-INDEPENDENT-REVIEW.md` §3). Revision 1 deadlocked on its own reads (R1) and corrupted delta clients (R2), among other defects. Rounds 2–4 approved with changes (N1–N6, P1–P3, Q1–Q2). Changes are marked **[R*n*]**, **[N*n*]**, **[P*n*]** and **[Q*n*]**.

**Observation.** Nothing a queued *store* mutation needs is asynchronous. The awaits in the EXEC loop all belong to the **effects** of a write:
- AOF append and wait;
- replication fan-out;
- WATCH and QSUB notification;
- WebSocket pushes;
- the I/O of eviction effects.

`PUBLISH` awaits too, but it is not a store mutation. WATCH, SUBSCRIBE and QSUB are refused at queue time (`connection.rs`), and no blocking or scripting command exists. Everything else in a queued command is synchronous: the store call, the frame (with its deadline read-back), the claimable-members check, ephemeral reconciliation, and eviction's forgetting of claims.

| Phase | What runs | Held |
|---|---|---|
| **0. Lock** (unchanged) | Close and drain the gate; take the server stripes of every read, written and watched key in ascending order (6O-E `lock_transaction`); read the instant `t`; WATCH check | gate, server stripes |
| **1. Apply** (new, synchronous) | `KeyValueStore::apply_transaction(queue, t, per_command)`. Before the **first queued write**, it takes the capped store's capacity gate if any **[R5]**, then the store stripes the queue's writes will take, in ascending order, and marks them `SEQ_ACTIVE \| SEQ_MULTI`. It runs every queued command in order inside `at_instant(t)`. For each one it records the reply, its frame (`broadcast_for_at`, deadline read-back included), its evicted keys, every synchronous `ServerState` change in command order (claims, reconciliation, eviction's `forget_ephemeral_keys`) **[R6]**, and for each key the position of its **last** queued write **[N1]**. It releases the stripes (and the gate) **after the last queued write** **[R7]** | gate, server stripes, and store stripes from the first write to the last |
| **2. Effects** (asynchronous) | Only I/O and notifications, in command order: AOF append (one batch for the transaction), replication, WATCH/QSUB notifications coalesced per key (below) and read lazily as today, WebSocket pushes, each command's eviction `DEL`s placed between its frame and the next, `PUBLISH` delivery **[R6]** | gate, server stripes |
| **3. Release** (unchanged) | Unregister the watches, drop the guards, write the reply (still gated on durability) | — |

#### The transaction scope (core-engine)

`apply_transaction` sets a thread-local **transaction scope** for its duration. It is synchronous and per thread, like 6O-E's `at_instant`, so it cannot cross an await or reach another task.

- **The stripe set is computed inside core-engine [R3].** It is the union of what `run_write` would take for each queued command: `mutation_scope`, or every stripe for a `WriteScope::All` command or a capped store. So it is complete **by construction**, not by an oracle test over a second classification. The server no longer computes store stripes.
- **Writes [R1].** `order_keys` and `order_all` take nothing inside the scope: the transaction holds and marks every stripe its writes need, and nested calls do not mark (the single-writer rule of 6O-D's words is kept).
- **The capacity gate [R5, N3].** A std `RwLock` is not re-entrant, so every acquisition reachable from phase 1 must use the scope's gate. There are three:
  - `run_write_gated`'s write lock;
  - `try_reserved_write`'s read lock (the reserved-write path, off by default);
  - the capped sweep and eviction entry points.

  Inside the scope, `run_write_gated` skips `try_reserved_write` (the gate is already held exclusively) and reuses the held gate. The capped-store tests run with reserved writes both on and off.
- **Reads [R1, N6].** Inside the scope, `read_one_at` and `read_many` never wait on `multi` and never lock a stripe. The scope is checked only on the slow path, right before a wait or a lock: an in-scope read that sees no mark and validates is already correct. So an ordinary `GET` keeps its exact cost. This covers queued reads, the deadline read-back and the claimable-members check (`SISMEMBER`). It is safe because phase 0's server stripes and the closed gate exclude every writer of every key the transaction reads or writes. The only other mutations in flight are outside writers of *unrelated* keys, and the transaction reads none of their keys. Locking an unheld stripe from inside phase 1 is never done: it would be an out-of-order acquisition.
- **A panic inside phase 1 is contained per command [R3, N2, P2, P3].**
  - **All** of a queued command's phase-1 work runs under `catch_unwind` **inside** the held scope, so nothing is released while unwinding. That is its store call, frame, claimable check, reconciliation and eviction bookkeeping. A panic after a complete mutation but before its frame would otherwise leave a write that is never logged.
  - The closure is wrapped in `AssertUnwindSafe`. That is justified because, after a panic, the store's state is never used as if consistent: it is repaired or flagged as below.
  - The `ServerState` ephemeral maps recover poisoned mutexes (`into_inner`), as the store already does. Today they silently stop tracking.
  - On a panic, phase 1 stops applying: the commands already applied stay, and the rest are answered with an error. Only then are the stripes and the gate released. Phase 2 logs, replicates and notifies the applied prefix, as for any EXEC.
  - This is exactly today's exposure. A panic in queued command *k* already leaves 1..*k*−1 applied and logged, and kills only that connection's task.
  - It does not widen the blast radius: release builds keep `overflow-checks = true` for client-supplied numbers, so a client-reachable panic must not become a process exit.
  - **What readers can then see [P2].** The old state, the applied prefix, or **the prefix plus a half-applied command *k***. `catch_unwind` cannot undo a mutation interrupted part-way (a RENAME between removing the source and writing the destination, an MSET after some pairs). This is the same as today: the stripe hold publishes on unwind.
  - **Convergence after a contained panic [P2].**
    - Command *k* has no frame, so its partial effect would never reach the AOF or replicas. The server rebuilds the metadata of *k*'s touched keys (size, key count, TTL and eviction indexes skipped by `run_write_gated`).
    - It marks persistence unhealthy, so writes get `MISCONF` until a `SAVE` writes a snapshot of the actual state and truncates the AOF.
    - It **rotates the primary's replication run id** (or clears its backlog) and then closes the replica links [Q2]. Closing alone is not enough: a replica would reconnect with the same run id and an in-backlog offset and resume **partially**, and *k* has no frame. Rotating the run id forces every replica into a full resynchronisation from a snapshot.
    - A replica that takes a full resynchronisation must force its own sub-replicas to do the same, by rotating its own run id or clearing its backlog. This is to be verified, and tested, as part of the implementation: no such reset was found on that path at `410235b`.
    - WebSocket sync clients are closed with the sync-gap code (`invalidate_all`, as a replica's full resync does), and *k*'s touched keys are notified as full values [Q2].
    - For a *k* that is `FLUSHDB`, the metadata rebuild is the whole keyspace's (`rebuild_metadata`).
    - Optionally the server starts a checkpoint itself, instead of leaving writes on `MISCONF` until an operator runs `SAVE`. This is an implementation choice to be reviewed.
    - The event is logged with its own message (not the AOF fail-stop's) and counted in a metric.
  - So a transaction is not atomic only when the store has a bug that panics, and even then every copy converges on the primary's actual state.
- **No scope miss is possible by construction** (the stripe set comes from `mutation_scope`). A `debug_assert!` in `order_keys`/`order_all` guards it in tests.

**Notifications, coalesced per key [R2, N1, N4, N5].** A WATCH, QSUB or `CLIENT DELTA` notification reads the key's value lazily (`KeyChange::current`, `stored_nothing`), and must describe the store right after the write that caused it. In phase 2, later queued writes have already applied. Revision 2 copied each value in phase 1; round 2 showed that unbounded (10,000 `APPEND`s to an 8 MiB string). Revision 3 copies nothing:

- **Counted by effective writes [P1, Q1].** "Written", "written more than once" and "last write" count only **effective** writes. Effective means exactly today's notification condition: the command produced a frame (`broadcast_for_at` returned `Some`). A failed `SET k b NX`, a refused `RENAME` and a WRONGTYPE error are not counted. Otherwise `SET k a; SET k b NX` would place the key's only notification on a write that sends none.
  - A `*STORE` always produces a frame, and an empty one onto an **existing** destination deletes it: a real change, counted.
  - **Removal kinds.** Each effective write's removal kind is recorded in phase 1. `DEL`/`UNLINK`, `FLUSHDB` and eviction are known from the command itself. A `*STORE` is classified by checking, with an in-scope read, whether its destination exists after the command.
- **A key with one effective write** is notified exactly as today, from that write, read lazily in phase 2. No later queued write touches it, and no outside writer can touch it under the server stripes, so the value read is the one right after its write.
- **A key with several effective writes** is notified **once**, at its last effective write, as a **full value** (`keychange`), never as a delta. A delta of the last write alone would land on a client copy that never saw the earlier writes: `SET k a; APPEND k b` sent as `keydelta(append b)` gives `old+b`. The full value read in phase 2 is the value after the last write, for the same reason as above.
- **WATCH invalidation is the OR of the key's writes [P1].** Whether a notification invalidates a WATCH depends on its kind (`live_at_watch || !is_removal()`). So the coalesced notification carries `invalidates` = the OR over **all** the key's effective writes. A watcher of an absent key is invalidated by `SET k a; DEL k`, as in Redis, even though the final notification is a removal. The same holds when the last write is `FLUSHDB`, an eviction, or a `*STORE` that emptied the key.
- **"Last write"** counts every key a command changes:
  - each key of a multi-key command (MSET, RENAME's two keys, `*STORE`'s destination);
  - every key for `FLUSHDB`, which sends its pattern sentinel as today, after which nothing earlier is notified;
  - eviction victims, whose removal is notified at the evicting command.
- **TCP WATCH** needs only the signal, which the OR above preserves.
- **Registration while EXEC runs [N4].** Another connection can register a watcher while EXEC runs (the gate is a shared counter). Reading in phase 2 at worst over-notifies, which is a spurious `EXEC` abort and therefore safe. 6O-E's `watched_after_write` fence stays where it is, after each write.
- **WebSocket pushes** carry each command's own frame, not a store read, so they stay per command and in order.
- **The clock [N5]:** values are read in phase 2 on the wall clock, exactly as today, so no remaining-TTL arithmetic is computed at one instant and sent at another.

**Read-only transactions** run no phase 1: no store stripe, no scope, as today.

## 4. Proof obligations (brief §4.5)

| # | Obligation | Option E, revision 2 |
|---|---|---|
| 1 | When the transaction becomes visible | When its store stripes are released, right after its last queued write. From before its first write until then, every stripe its writes touch is marked |
| 2 | Whether all writes become visible together | Yes, by 6O-D's argument for MSET. A single-key reader of a marked stripe waits (`read_one_at`). A multi-key reader validates `seq` across all its stripes and retries or falls back to the locks. One client's sequence of reads cannot see new then old: once any written key's new value is visible, every written stripe is released (new) or still marked (the reader waits) |
| 3 | Before publication | The old state, if the read finished before the marks; otherwise it waits for phase 1's write span. That span is synchronous CPU work: no I/O, no await |
| 4 | After publication | The new state |
| 5 | Concurrent writers | Writers of the transaction's keys are excluded by the server stripes and the closed gate (6O-E, unchanged). **Writers of unrelated keys still run [R4].** Server and store stripes hash differently, so such a writer can need a store stripe phase 1 holds. It then waits, spinning and then blocking its worker thread, for phase 1's write span: the store-layer false sharing of §5 |
| 6 | WATCH | Checked in phase 0 at `t` (unchanged). Notifications are sent in phase 2, in command order, with the values captured in phase 1 |
| 7 | Cancellation | Phase 1 cannot be cancelled (no await). A panic in it is contained per command inside the held scope: the applied prefix is kept, then released and logged, today's exposure [N2]. Phase 2 has today's exposure: a task abort, which happens only at shutdown, leaves writes applied and some effects unlogged. A client disconnect does not cancel EXEC |
| 8 | Connection termination | As 7 |
| 9 | AOF failure | Phase 2's append fails as today. `always` is fail-stop: the process exits before the reply. `everysec`/`no`: persistence turns unhealthy, and the applied state stays in memory, as for any write today |
| 10 | A stalled `fdatasync` | **Readers are unaffected**: no store stripe is held or marked in phase 2. Writers of the transaction's keys and the all-write barriers wait for the server stripes, as today |
| 11 | A crash between queued commands | Memory is gone. The AOF holds what was appended (§6) |
| 12 | Replication | Frames are sent in command order under the server stripes. A replica applies them one at a time (§6) |
| 13 | Full and partial resynchronisation | The replica cut takes the all-write barrier, which waits for the transaction's server stripes |
| 14 | Snapshots | `ServerState::save` takes the all-write barrier: the same |
| 15 | Bounded resources | The queue is capped at 10,000 commands. Phase 1 buffers the queue's frames (command-sized) and one index per written key; no value is copied [N1]. Store stripes held: at most 256 (16 KiB of stripe lines) |
| 16 | Deadlock freedom | Order: gate → server stripes (ascending) → **capacity gate** (capped only) → store stripes (ascending, all taken before the first write) → shard guards → index. This matches the store's documented order (gate, then stripes) **[R5]**. Inside the scope nothing waits on or takes a store stripe **[R1]**. Outside parties: an outside reader in `read_one_at` waits only for the stripe it reads and holds nothing; `read_many`'s fallback takes its stripes in ascending order and holds no server lock; an outside writer **[R4]** holds at most its own server stripes (never ones phase 1 needs, since those belong to the transaction's keys and are held by it) and takes its store stripes in ascending order. Phase 1 holds its whole set from the start and acquires nothing more, so no cycle can form. On a capped store the server's all-write barrier (`lock_all_writes`) excludes every capped writer, the sweeper and the eviction tick, so the gate is uncontended |
| 17 | Ordinary GET performance | Unchanged on the fast path: the scope is checked only before a wait or a lock [N6]. Waits happen only on a stripe a transaction is applying |
| 18 | 6O-D `seq`/`multi` | The transaction is one more multi-step holder: one mark, one release. Nested calls neither mark nor wait |

**Other cases.**
- **Overlapping transactions** are serialised in phase 0.
- **Duplicate keys** are deduplicated.
- **`FLUSHDB` in a transaction** holds every stripe for its write span, so it is no longer visible part-way to readers.
- **Expiry** runs at `t`.
- **Eviction** (capped): every stripe is held, and victims are forgotten in phase 1 and logged in phase 2.
- **Tenants**: unchanged.
- **DEDUP envelopes** queue, and the store refuses them at EXEC (`store.rs`), so they are harmless and covered by the stripe set **[R9]**.
- **Exclusion [R8].** `KEYS`, `SCAN` and `DBSIZE` outside a transaction take no stripe and can still see any multi-key write part-done (pre-existing, Low, 6O-D). This design does not change that.

## 5. Costs

| | Estimate |
|---|---|
| Read-only transactions | none |
| Writing transactions, uncontended | one take, mark and release per distinct written store stripe; the nested calls no longer take their own. Frames are held to phase 2 (built today too). No value is copied: notifications are coalesced per key [N1] |
| AOF | one batch per transaction: fewer `write(2)` calls, and fewer `fdatasync`s under `always` with observers |
| Outside readers and **writers** of a written stripe [R4] | they wait for phase 1's **write span** (from the first queued write to the last), spinning and then blocking their worker thread. Typical transactions: microseconds |
| **Worst case [R7]** | a capped store or a `FLUSHDB` transaction marks **every** stripe, and its write span contains whatever queued commands lie between its first and last write: up to 10,000 commands, including any `SUNIONSTORE` or big `SMEMBERS` among them. **Every reader and writer on every worker blocks for that span.** That is the behaviour Redis has for every EXEC, but it is a new stall class for Recached. Its bound is the CPU time of the transaction's write span. It must be measured (§8, milestone 5) and could be capped later, for example by refusing all-stripe transactions above a size |
| Unrelated keys | ≈ written stripes ÷ 256 of them share a store stripe per transaction (from the hash; **not measured**). A collision blocks an OS worker thread (`std::sync::Mutex`), not an async task, so the server layer's measured 0.04% (`V0.6O-F-STRIPE-SCALING.md` §2.1) does not carry over; 6O-G must measure it |

No prototype was built in 6O-F. These are estimates from 6O-D's MSET measurements: MSET×10 is the same mechanism over 10 keys and cost −1% to −3% under mixed contention.

## 6. Durable and replica atomicity: what Option E does not give

| Property | Today | Option E | To give it |
|---|---|---|---|
| Runtime atomic visibility on the primary | ✗ | ✓ (except `KEYS`/`SCAN`/`DBSIZE`, §4) | — |
| Crash atomicity (AOF) | ✗ | ✗, narrower: see below | **Transaction framing in the AOF** (`MULTI` … `EXEC` records, or one composite record), with a replay that discards an incomplete block at the tail |
| Replica readers | ✗ | ✗ | **Framing in the replication stream**, and the replica applying a group through the same `apply_transaction`, behind a capability (`caps=txn`) |
| Visibility before durability | yes, per write | yes, for the whole transaction | It is the same as today and as Redis: readers on the primary can see a transaction before any of it is durable **[R10]** |

**How narrow the crash window is [R10].** Option E appends the transaction's frames as one batch. That only helps if:
- the batch is never split across two AOF batches (the coalescer must append it as one unit);
- the crash is a process crash: on a power loss under `everysec`/`no`, the page cache can persist a non-prefix of the file.

**What replication framing must also handle [R10]:**
- a partial resynchronisation that resumes inside a group;
- backlog trimming that cuts a group;
- a sub-replica forwarding a group.

Both framings change what the AOF and the replication stream carry: **separate approval** (proposed 6O-G2, after the runtime fix 6O-G1).

## 7. Testing strategy (for the implementation)

- **The F1 probe** becomes permanent, plus MGET, sequential GETs, `EXISTS`, the borrowed path and WebSocket readers.
- **In-scope reads [R1]:**
  - `MULTI; SET k v; GET k; EXEC`;
  - `SET k v EX n` with an AOF, a replica and a watcher (the deadline read-back);
  - `EADD`;
  - a queued read of a key that shares a written key's store stripe;
  - all of these on 1 and 4 workers.
- **A phase-1 hook [R11]:** a synchronous `write_pause`-style stop inside `apply_transaction`, on a multi-thread runtime: `exec_pause` is asynchronous and cannot stop inside phase 1. Readers arriving before, during and after; an outside writer on a shared stripe.
- **WATCH under coalescing [P1, Q1]**, for a watcher of an absent key. Each of these must abort the watcher's EXEC, as Redis does:
  - `SET k a; DEL k`;
  - `SET k a; FLUSHDB`;
  - `SET k a`, then an eviction of `k`;
  - `SET k a; SUNIONSTORE k <empty>`;
  - `SET k a; SET k b NX`.

  Negative case: `SUNIONSTORE k <empty>` alone, on an absent `k`, must **commit** the watcher's EXEC (Redis signals nothing). For a watcher holding `k` live: `SUNIONSTORE k <empty>` aborts it.
- **Delta clients [R2, N1]:** `SET k a; APPEND k b`, `RENAME s l; LPUSH l x`, `SET k 1; INCR k` and `MSET a 1 b 2; DEL a` to a `CLIENT DELTA ON` WebSocket client and to a QSUB client, whose local copy must equal the server's. Also, the number of notifications per key (one per key written several times), and a WATCH invalidated by a key written twice.
- **Memory [N1]:** 10,000 `APPEND`s to an 8 MiB string with a watcher present; RSS must stay bounded by the value itself.
- **Ephemeral state [R6]:** command *i* evicts `k`, command *i+1* runs `ESET k`; disconnect; `k` must be removed.
- **Panic [R3, N2, P2, P3]:** a test-only panic injected in queued command *k*, **before** and **during** its mutation, and after it but before its frame.
  - Commands 1..*k*−1 are applied, logged and replicated, and the rest are answered with an error.
  - No stripe or gate is left held.
  - *k*'s keys have their metadata rebuilt, and persistence reports `MISCONF` until `SAVE`.
  - Replicas, and their sub-replicas, resynchronise **in full**: a partial resynchronisation is refused after the run id rotates.
  - WebSocket clients are closed with the sync-gap code.
  - The server keeps running, and the ephemeral maps keep tracking.
- **Capped store [R5, R7, N3]**, with reserved writes on and off:
  - a 10,000-command transaction against concurrent readers, with the stall measured;
  - the sweeper and the eviction tick running concurrently.
- **Slow fsync:** a stalled AOF writer under `always`; readers of the transaction's keys answer within a bound.
- **The 6O-E history checker** with outside readers.
- **Mutants:**
  - an in-scope read that locks (deadlock, caught by the timeout);
  - notifications reading the store in phase 2 (delta test);
  - eviction's forget moved to phase 2 (ephemeral test);
  - marks set after the first write;
  - release before the last write;
  - the store stripes held into phase 2 (slow-fsync test);
  - a panic that unwinds out of the held scope (stripes released mid-transaction);
  - an in-scope `try_reserved_write` taking the gate (deadlock, caught by the timeout).
- **Both AOF fan-out modes, all fsync policies, replication.** The existing 6O-D and 6O-E suites must pass; some need the new hook in place of `exec_pause` where they stop between queued writes **[R11]**.

## 8. Implementation milestones (6O-G, after approval)

1. **`KeyValueStore::apply_transaction`**:

## 9. Stripe count

Phase 1 holds **store** stripes, for its write span only. Its false sharing belongs to the store layer, and it now includes unrelated **writers** [R4]. The 6O-E contention numbers belong to the **server** layer, held for the whole transaction. `V0.6O-F-STRIPE-SCALING.md` measures the **server** layer. There, more stripes do not help 2-key transactions, but they do help wide write transactions (+37% at 512, +55% at 1,024), and they slow every all-stripe barrier, which is decisive on capped stores. Wide transactions are also where phase 1's store-stripe holds will matter most. It measures the store layer only as a 1,024-stripe variant under today's code, not under phase 1. Keeping 256 for the store layer is therefore **provisional**, and phase 1's store-stripe contention is part of milestone 5's measurements.
