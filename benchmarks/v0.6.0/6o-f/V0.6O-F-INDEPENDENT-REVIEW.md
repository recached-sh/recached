## 1. The counter-frame fix (R-TTL), rejected

The reviewer's probes (`raw/review/review_6of_probes.rs`) were run on the fix (`e55f7d5`) and on `410235b` to tell new failures from old ones:

| Probe | `410235b` | `e55f7d5` | Class |
|---|---|---|---|
| `INCR` then `EXPIRE` (extend), replay between the deadlines | correct | **key lost** | **new regression** |
| `INCR` then `PERSIST`, replay after the old deadline (AOF, and replica) | correct | **key lost** | **new regression** ×2 |
| Sliding-window rate limiter (`INCR` + `EXPIRE` on every hit) | correct | **key lost** | **new regression** |
| `INCR` then `RENAME`, replay after the deadline | replays | **replay refused: no restart** | **new regression (High)** |
| `LSET` on a volatile list, replay after the deadline | refused | refused | pre-existing restart blocker |
| `SET … EXAT` / `EXPIREAT` with `i64::MAX` | refused | refused | pre-existing restart blocker |

**Root cause.** The AOF replay and replicas evaluate expiry when the frame is applied, and expirations are not logged. No counter-frame format can be right in every case (`V0.6O-F-TTL-DESIGN.md` §2).

**Maintainer decision (2026-11-24).**
- The counter fix is a design first, with nothing shipped: `V0.6O-F-TTL-DESIGN.md`, Option E, which needs approval for an AOF marker and a replication capability.
- Fix the `i64::MAX` restart blockers now.

The rejected code is kept on the local branch `experiment/v0.6o-f-counter-pxat-rejected`. Its regression cases are now permanent guards.

## 3. F2 transaction atomicity design (R-F2)

| Round | Verdict | Findings | Resolution |
|---|---|---|---|
| 1 (rev 1) | **DESIGN NOT APPROVED** | **R1 Critical**: phase 1 deadlocks on its own reads (`MULTI SET k v GET k EXEC`: `read_one_at` locks a stripe the thread holds). **R2 High**: notifications read final values, which corrupts delta clients (`SET k a; APPEND k b` gives `"abb"`). **R3 High**: a panic in phase 1 publishes a part-applied transaction with no effects logged. R4–R7 Medium (outside writers in the deadlock proof; capacity-gate order; ephemeral state split across the phases; the worst-case all-stripe stall). R8–R11 Low | Revision 2: core-engine `apply_transaction` with its stripe set taken from `mutation_scope`; in-scope reads bypass the stripes; the gate is taken before the stripes; every `ServerState` change in phase 1; marks only over the write span; worst case stated |
| 2 (rev 2) | APPROVED WITH CHANGES | **N1 High**: capturing values is unbounded (10,000 `APPEND`s to an 8 MiB string). N2 Medium: abort-on-panic ordering, and its blast radius with `overflow-checks`. N3 Medium: the reserved-write path self-deadlocks on the gate. N4/N5 Low, N6 Nit | Revision 3: notifications coalesced per key (one full value for a key written several times); panics contained per command inside the held scope; reserved path bypassed; scope checked on the slow path only |
| 3 (rev 3) | APPROVED WITH CHANGES | **P1 High**: coalescing broke WATCH when the last write is a removal or a no-op. P2 Medium: containment cannot undo a half-applied command, and copies diverge. P3 Low: unwind safety | Revision 4: effective writes; `invalidates` is the OR over the key's writes; convergence after a contained panic (metadata rebuild, MISCONF until SAVE, replica resync); the whole per-command apply wrapped |
| 4 (rev 4) | APPROVED WITH CHANGES; **no remaining objections once folded in** | Q1 Medium: "effective" must mean "produced a frame" (an empty `*STORE` onto an existing key is a deletion); two test expectations were not Redis's. Q2 Medium: closing replica links lets them resume partially | Revision 5: effective = the frame condition, with the `*STORE` removal kind by an in-scope read; the run id is rotated to force a full resync, sub-replicas likewise, WebSocket clients closed with the sync-gap code |

**Confirmed across the rounds.**
- The root cause.
- The visibility argument for marked stripes.
- That no queued store mutation needs an async effect.
- The soundness of the in-scope read bypass.
- That the stripe set from `mutation_scope` is complete.
- That the deadlock proof holds, outside writers and the capacity gate included.
- That OR-ing `invalidates` never invalidates where Redis would commit.
- That the rejected options A–D are rejected for valid reasons, and that no simpler correct design was found.

**Design approval is not implementation approval.** The High finding 6O-E F1 stays open until 6O-G is authorised, implemented and reviewed.

## 4. F3 stripe study (R-F3)

**Verdict: ACCEPT WITH CHANGES.** The evidence supports keeping 256 at the current code. No workload gains throughput reproducibly at 512 or 1,024, and every all-stripe path gets slower with N; the reviewer confirmed this cleanly in the per-repetition data for workload E and both capped paths. Several explanations claimed more than the data shows. All findings were accepted, and `V0.6O-F-STRIPE-SCALING.md` was revised:

|---|---|---|---|

The gate cannot explain 6O-E's −34%, since it already closed per EXEC before 6O-E. Capped-store writers, always ordered, ran at 89k/s | Restated as a hypothesis. Stated that 6O-E's false-sharing mechanism is **refuted** at `410235b` and that its cause is **unknown**. The gate follow-up is conditional on an ablation |
