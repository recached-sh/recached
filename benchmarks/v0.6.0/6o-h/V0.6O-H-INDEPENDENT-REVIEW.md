# v0.6.0 Phase 6O-H: independent review

## How the reviews were run

- **Reviewers.** Each was an agent that wrote none of the code or design under review.
  - Code reviewers worked on their own detached worktrees, with their own Cargo target directories, and removed them afterwards.
  - Design reviewers read the code at the base commit and ran the real older binaries.
- **What they got.** The design or the diff, the brief's requirements and its attack list, the old binaries (v0.4.0, v0.5.1, v0.5.2, `410235b`, `f9a364d`) and Redis 7.2.5. They did not get the author's correctness argument.
- **Follow-ups.** Every follow-up went back to the same reviewer, which checked its own probes and mutants against the fix.

## 6. Review E, performance and resources

### Round 1, `dev` `c093795` + #190 `9a47d1e`: APPROVE WITH CHANGES

**Scope.** The reviewer worked read-only:
- the code of the write path, sweeper, replay and replica;
- the raw results under `raw/perf/`, re-deriving several medians (they match);
- no builds, because the host was measuring.

**Verdict.** "The everysec request-path numbers are sound and reproducible. F1 and F2 should block the release until fixed or measured."

| # | Severity | Finding | Resolution |
|---|---|---|---|
| F1 | **High** | The sweeper waits for its `DEL`s' AOF write, and under `always` their `fdatasync`, while holding the all-write barrier. Every writer stops for a disk flush per chunk, and the 25 ms budget ends a tick after one chunk. Evidence: `always` expiring counters RSS +80% (33.6–36.1 MB against 18.5–19.3 MB), records/op 1.583, on-CPU +15%, none of it in §3 | **Fixed in #191 and #192** (performance §7.1).
- **#191** (`QueuedFrames`): the frames are queued under the barrier, which fixes their place in the file, and replicated there. The write is waited for after the barrier is released. p95 217 → 175 ms.
- **Round 2 found it partial:** the tick still waited per chunk. **#192** starts each chunk's write and waits once per tick. RSS 33.2 → 16.4 MiB (base 16.5), frames per command 1.71 → 1.00.
- **Tests:** `the_sweeper_writes_its_dels_after_releasing_the_barrier` and `a_slow_disk_does_not_slow_the_sweep_to_a_chunk_per_tick`; both mutants killed |
| F2 | **High** | #190 was validated only with the replica's files on tmpfs, where the unfixed build did not loop either | **Confirmed, and #190 was insufficient.** On the HDD, `final` resynchronized 3–4 times and #190's first design 2–3 times. The queue overflowed 0.6 s after each full sync completed, while the replica applied its backlog without reading its link. **Fixed in #190 (`7b4ae13`):** the link is read concurrently with applying, into a bounded 64 MiB queue of chunks. Test extended, previous design killed as a mutant. HDD rerun in performance §5.5 |
| F3 | Medium | The read-ahead buffer lives as long as the connection; up to 128 MiB; it compounds with other buffers | **Fixed** in #190 `7b4ae13`: each chunk, the read-ahead included, is freed once consumed. | F4 | Medium | The 274 ms GET max is plausibly the sweeper's `write(2)` (inline, one worker, an HDD) | F1's fix takes the wait out of the barrier, and the `write(2)` is led after the barrier is released. Not re-measured with 5 repetitions under a write load: follow-up |
