## 1. The mechanism

`observing_expirations(f)` runs `f`, one write's store call, and returns the keys that write found expired and removed. Inside the scope, **before a write runs**, the store removes every expired entry among the keys the write names (`mutation_scope`: what it writes and what it reads), under the stripes it already holds and, on a capped store, the capacity gate, and reports each key. The command then runs exactly as before.

That is a deliberate change from the 6O-F proposal, which would have each command's own expiry handling report what it reset. A per-command hook needs every path audited and kept audited: `typed_entry!`, `SET` with `NX`/`XX`/`GET`/`KEEPTTL`, the `RENAME` and `RENAMENX` source checks, `LSET`, `COPY`, the `*STORE` sources, `GETDEL`, `GETEX`, `PERSIST`, the `EXPIRE` family, the probed and borrowed paths, and any future command. The purge makes the audit a property of one function instead: after it, **no expired entry exists among the command's keys**, so no command can remove or reset one unreported, whatever its code does. What has to hold instead is that `mutation_scope` lists every key a write reads or writes. 6O-D/6O-G already rely on that for atomicity; review A re-checked it (every write in the read-scope list has a `mutation_scope` entry).

| Requirement (brief §2.3) | How |
|---|---|
| The exact key | the map key removed, reported as is (tenant prefixes included) |
| Command order | the scope is one store call: the caller logs its keys before that call's own effects |
| No duplicate records for one transition | a removed key is no longer expired: reported once even if named twice. `DEL`/`UNLINK` are reported too, and the server leaves them out once their own frame names the keys (§3) |
| Scoped to the operation | per thread, per call; a nested scope collects its own; the outer one is restored on return and on unwind |
| Multi-key operations | every named key (`MSET`, `RENAME`, `SMOVE`, `COPY`, `*STORE` destination and sources) |
| Nested transaction execution | inside `apply_transaction`'s scope the purge takes no stripe (`order_keys` asserts membership in the held set) |
| The frozen `EXEC` clock | the scope fixes the clock for the write (`at_instant(now)`), or keeps a transaction's instant |
| No allocation when nothing expires | `Vec::new()`; the purge is one lookup per named key |
| Errors and panics | a write that fails still reports what it removed; a panic drops the collected keys (the caller then treats its log as diverged, as a panicking transaction does) |

## 2. Where it runs

| Path | Behaviour inside a scope |
|---|---|
| `run_write_gated`, general path | after `order_keys` and the capacity gate, before admission (`reserve_key_slots`), the `NoEviction` rollback snapshot and the accounting |
| Single-key probed fast path | `run_probed_command`: the same, under the key's stripe |
| Reserved capped fast path | declines an expired key (the gated path removes it under the exclusive gate, as the sweeper does) |
| Borrowed `execute_ref_into` | declines writes (the owned path runs them) |
| `WriteScope::All` (`FLUSHDB`) | nothing: its frame removes every key |
| A `DEDUP` envelope reaching the store | nothing: the store refuses it without running |
| Reads | never remove (masking only) |
| Outside any scope | nothing changes: embedders, AOF replay and replicas behave as before |

## 3. Coverage

Every write the store implements was run, on every store kind (uncapped; capped with LRU or `noeviction`; with and without the reserved fast path), on an expired key of the type it acts on. In each case the key is reported once and gone, the metadata equals a rebuild, and **the reply equals that of the same write on a key that never existed** (Redis's model: an expired key does not exist).

| Family | Writes |
|---|---|
| Strings, counters | `SET` (plain, `NX`, `XX`, `KEEPTTL`, `GET`), `SETNX`, `SETEX`, `PSETEX`, `GETSET`, `APPEND`, `GETDEL`, `GETEX PERSIST`, `INCR`, `DECR`, `INCRBY`, `DECRBY` |
| Expiry | `EXPIRE`, `PEXPIRE`, `EXPIREAT`, `PEXPIREAT`, `PERSIST` (all answer 0 on an expired key, and remove it) |
| Hashes | `HSET`, `HSETNX`, `HINCRBY`, `HINCRBYFLOAT`, `HDEL` |
| Lists | `LPUSH`, `RPUSH`, `LPUSHX`, `RPUSHX`, `LPOP`, `RPOP`, `LSET` (`no such key`), `LREM`, `LTRIM` |
| Sets, sorted sets | `SADD`, `SREM`, `SPOP`, `ZADD`, `ZINCRBY`, `ZREM`, `ZPOPMIN`, `ZPOPMAX` |
| Other | `JSET`, `JMERGE`, `RLSET`, `RLCHECK`, `ESET`, `EADD`; a `WRONGTYPE` that becomes a create |
| Multi-key | `MSET` with a repeated key, `RENAME` (expired source: `no such key`; expired destination), `RENAMENX`, `COPY`, `SMOVE`, `SINTERSTORE`/`SUNIONSTORE`/`SDIFFSTORE` with an expired source |
| `DEL`/`UNLINK` | report the expired keys they remove; a `DEL` refused on a store over its key cap still reports them |

Not implemented by Recached, so not applicable: `SETRANGE`, `LINSERT`, `ZUNIONSTORE`, `LMOVE`/`RPOPLPUSH`.

## 4. Tests

`observed_expiry_tests.rs`, 22 tests:
- the single-key table above;
- live, absent and read keys report nothing and allocate nothing;
- multi-key writes;
- `DEL`/`UNLINK`, and a refused `DEL`;
- tenant-prefixed keys;
- one instant shared by the removal and the write (at the deadline, one millisecond before, after);
- the capped key cap (no eviction for a purged slot);
- the reserved and within-capacity paths;
- transactions at their instant, per queued command;
- nesting and panics, a panic after the purge inside a transaction, eight concurrent writers;
- `FLUSHDB`;
- the scope fixes the clock;
- review A's probes as regressions: the purge before admission, the rollback snapshot after the purge, a rolled-back write keeps its reclaimed victim, the DEDUP envelope, the borrowed path.

**Mutants.** Mine: 9 of 9 killed. Review A's: 17, with one surviving. They cover:
- the purge removed, or moved after admission;
- the report dropped;
- each path's purge removed;
- the reserved decline, the frozen clock, the memory and index accounting, `evicted.clear()` restored, the `DEDUP` early return, the borrowed-path decline;
- `DEL` not reporting.

The survivor, M11 (`holds_expired` on the system clock), is close to equivalent: it differs only when a caller uses `at_instant` with a future instant outside a transaction.
