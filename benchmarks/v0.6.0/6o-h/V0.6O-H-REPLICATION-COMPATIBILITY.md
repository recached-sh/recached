## 1. Negotiation

The capability is carried in the run-id strings, the same way as `dedup1`:
- The primary advertises `<run-id>;caps=dedup1,expirylog1`, or `;caps=expirylog1` when DEDUP replication is off.
- A replica that is offered it answers `<run-id>;accept=dedup1,expirylog1`.
- It is never inferred from a version.

A replica advertises it to its own replicas iff its keyspace was built from a primary that did (`writes_expiry_log`). This stays as it is while the link is down.

| Primary → replica | Behaviour | Evidence |
|---|---|---|
| new → new | negotiated; timeless application; no replica sweeper | `a_new_replica_negotiates_the_expiry_log_with_a_new_primary` |
| old → new | not offered; legacy application and sweeper, as today | `a_primary_without_the_capability_gets_todays_replica`; compat matrix "old primary → new replica" |
| new → old 0.6 (6O-F/6O-G) | finds `dedup1` and ignores `expirylog1` (it splits values on `,`); applies the extra `DEL`s harmlessly and sweeps as before | review C round 1, a fake primary against real `f9a364d` and `410235b` replicas |
| new → 0.5 | unchanged: refused while `RECACHED_REPL_DEDUP=on`; with it off, the replica echoes the string and applies as before | `a_dedup_primary_refuses_a_replica_that_cannot_read_dedup_frames`; review C round 1 |
| old → old | unchanged | — |
| chain new → new → new | relayed: the middle node advertises it once its keyspace came from a capable primary | `a_replica_relays_the_capability_down_its_chain` |

The run-id string is limited to 128 bytes by every release. The capability list uses 23 of the 82 bytes left after a 40-character run id.

## 2. A capable replica

| Rule | How |
|---|---|
| Frames apply without evaluating expiry | `apply_replicated` runs the store call inside `without_expiry` (DEDUP envelopes included) |
| The full-sync snapshot is installed whole | `replace` inside `without_expiry`. The primary sends every entry still in its map (R2-2) |
| No local active expiry | `sweep_expired_tick` returns at once on a replica with `upstream_expirylog` |
| Reads mask, never mutate | unchanged: reads evaluate expiry by the replica's clock and never remove (6O-C/6O-D; review A) |
| Promotion | `writes_expiry_log` becomes true; the sweeper runs and logs; writes log what they find expired; the node advertises `expirylog1` (`promotion_gives_expiry_back_to_the_promoted_node`) |
| The wire carries pushes only | a frame received as an array is normalized before it is logged, forwarded or backlogged (`the_wire_carries_pushes_only`; R2-1) |
| Tenant-scoped sync sockets | a replicated multi-key `DEL` is pushed one key at a time (`a_replicas_tenant_sockets_get_the_primarys_swept_dels`; review B, B-5) |

## 4. The full-sync checkpoint

A pre-existing defect (review C, H1, reproduced on `f9a364d`): a replica's AOF never recorded its full syncs. A restart replayed the old keyspace plus the new frames. On a node restarted as a primary, that state was served.

Now, with an AOF configured:
1. Under `save_lock` and the all-write barrier of the keyspace replacement, and before any further frame is applied or acknowledged, the replica checkpoints its files.
2. The snapshot is the received payload, spliced into the snapshot envelope: no filter and no second serialization. Then the DEDUP table and the truncation.
3. The new AOF begins with `FORMAT` iff the stream is `expirylog`.
4. The resume point is set once this is durable, so a later disconnect resumes partially.

| Case | Test |
|---|---|
| A capable primary: the replica's AOF is `FORMAT`, then the frames as arrays | `a_full_sync_checkpoints_the_replicas_own_files` |
| An old primary: no `FORMAT`, frames as pushes | same |
| Restarted from its own files alone, the replica serves the primary's keyspace, not the stale one | same |
| The checkpoint fails: writes answer `MISCONF` until a `SAVE` succeeds, also after a promotion; the resume point is cleared | `a_failed_full_sync_checkpoint_fails_closed` |
| A replica restarted on a file in the format leaves the format at once (review C, R3-1) | `a_replica_restarted_on_a_format_file_leaves_the_format_at_once` (#188) |

Without an AOF there is no checkpoint: the replica's snapshot autosave covers it, as before.

**The link meanwhile (#190).** The primary streams frames right after the snapshot, without waiting for the boundary. Two phases used to stop the replica reading them:
- its checkpoint, which fsyncs the snapshot and truncates the AOF;
- the catch-up afterwards, at about 185k frames/s on a stream with one `DEL` per expired `SET`.

During both, the backlog went into the primary's 8 MiB queue to that replica. On an HDD it overflowed, causing another full sync, in a loop: 4 resyncs after one 10 s stall, against base's 1.

The replica now reads its link in both phases:
- **During the install:** a read-ahead of up to 64 MiB.
- **While streaming:** a reader that runs concurrently with applying, into a bounded queue of 64 MiB.

Each chunk is freed once applied. The result on the HDD is 1, 1 and 2 resyncs (`V0.6O-H-PERFORMANCE.md` §5.5). Test: `a_replica_reads_ahead_while_its_full_sync_checkpoint_runs`.

## 5. Timing

Covered by the 6O-F replica tests, which use a fixed store clock rather than sleeps:

| Case | Test |
|---|---|
| Before the deadline | `a_replica_applying_a_counter_before_its_deadline_keeps_that_deadline` |
| After the deadline (late link, backlog, clock ahead) | `reproduce_a_replica_applying_a_counter_after_its_deadline`, which **now passes** |
| `INCR` then `PERSIST`, applied after the old deadline | `guard_a_replica_applying_incr_then_persist_after_the_old_deadline` |
| A full resync after the deadline | `a_full_resync_after_the_deadline_does_not_keep_the_counter` |

The process-level runs (`V0.6O-H-CORRECTNESS-TESTS.md` §3) use real binaries. A replica is paused past the deadlines, resumed, promoted, and restarted from its own files, and the result is compared with Redis 7.2.5.

## 6. Memory under lag

A capable replica keeps expired entries until the primary's `DEL` arrives: the replication delay plus the primary's sweep latency. On a live link this is not measurable at a few milliseconds of delay. While the link is down, it keeps every key it held, expired or not: bounded in size by that keyspace, not in time. See `V0.6O-H-PERFORMANCE.md` §5.3–§5.5. Adding local deletion to hide this would bring the defect back.
