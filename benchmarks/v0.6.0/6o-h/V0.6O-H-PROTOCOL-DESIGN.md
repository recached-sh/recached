## 1. What the protocol has to carry

Option E makes the primary the only node that decides expiry:
- **E1/E2.** The primary logs a `DEL` for every expired entry it removes, both those a write acts on and those the active sweeper removes.
- **E3/E4.** The AOF replay and a replica apply frames **without evaluating expiry**. An entry stays until a logged `DEL` removes it.

E3 is only sound for records written under E1/E2. A record written before them assumes its applier expires keys by its own clock. Applied timelessly, it can merge onto stale content: an `APPEND` that recreated an expired key on the old primary would land on the old value. So the AOF has to say which of its records were written under E1/E2 (§2–§7), and a replica has to know that its primary's stream carries them (§8).

**The normative rule (E1).** Every expired entry a write removes is logged as a `DEL` before anything the write itself logs. That includes a write that fails or changes nothing (`EXPIRE` or `LSET` of an expired key), and a write inside `EXEC`. A `DEL`/`UNLINK` whose own frame names the key counts as that log record. See `V0.6O-H-EXPIRATION-CAPTURE.md` and `V0.6O-H-EXPIRATION-PROPAGATION.md`.

## 2. Encoding

### 2.1 `FORMAT`: a control record

```
RECACHED-CHECKPOINT <id>         two bulk strings, as today's checkpoint marker
id = 0xEC00 << 48 | kind << 40 | layout << 32 | payload        (decimal u64)
```

| Field | Bits | Values |
|---|---|---|
| tag | 63–48 | `0xEC00`. An id with this tag is a control record, never a checkpoint |
| kind | 47–40 | 1 = `FORMAT`. Kinds `0x80`–`0xFF` are reserved as *ignorable* (a reader that does not know one skips it). Any other unknown kind ends the timeless part (§3.2) |
| layout | 39–32 | 1. An unknown layout ends the timeless part |
| payload | 31–0 | `FORMAT`: feature bits. Bit 0 is `expirylog`. Bits 0–15 are ignorable; 16–31 are must-understand (§9) |

`FORMAT` v1 with `expirylog` is id `17005593296757587969` (`0xec00010100000001`). The record is 57 bytes.

### 2.2 Authorship: arrays, not pushes

Every release since 0.4 writes its AOF records as RESP3 pushes (`>N`), because `broadcast_for_at` builds them that way. Every release also *replays* RESP2 arrays (`*N`): replay normalises a push to an array before parsing it.

A server that writes the format writes each record into the AOF as an array. It re-encodes only the first byte, while copying the frame into the AOF batch, which costs nothing. The replication wire and WebSocket pushes keep `>`.

So within a format file:
- an array record was written by a server that logs its expirations;
- a push record was written by something else: an older server after a downgrade, or a server that does not log expirations.

That holds after any crash, since no shutdown step is involved. A replica that follows a primary without `expirylog` never writes the format (§4.1), so its records are pushes as well.

**Normative rules (review C round 2):**
1. **The replication wire carries only pushes.** Every node sends `>` frames. A replica normalizes a received frame's first byte to `>` before it puts the frame in its backlog, forwards it, or logs it (R2-1). Old replicas copy their primary's bytes into their own AOF unchanged (reproduced), so one `*` on the wire would make an old replica's records look like the format's.
2. **Re-encode in exactly one place:** `AofBatch::push_frame`, one RESP value per call (a debug assertion). `dedup_wrap` and everything before it see pushes only (R2-5).
3. **A writer writes arrays only into a file it found timeless to its end** (pass 1), or one it began itself with `FORMAT`. Anything else gets pushes (R2-6).
4. **On a checkpoint, `FORMAT` is queued in the same batch as the truncation**, under one queue-lock hold, so no record can come before it (R2-7b).

### 2.3 Why an old binary ignores both

**The control record.** Every supported release parses the checkpoint marker the same way (`checkpoint_marker`, identical in v0.4.0, v0.5.x and `dev`). A two-element record whose first element is `RECACHED-CHECKPOINT` and whose second parses as `u64` is a checkpoint marker. The first pass moves the replay start past such a marker only if its id equals the snapshot's checkpoint id. The second pass skips every marker. A control record is therefore a no-op to an old binary if:
- its id is a `u64` (true by construction), and
- its id never equals a snapshot's checkpoint id.

Checkpoint ids count saves upward from the loaded snapshot's id, so reaching `0xEC00 << 48` would take about 1.7 × 10¹⁹ saves. The new binary also refuses to *load* a snapshot whose checkpoint id is in the reserved range (only a corrupt file could hold one), and recognises control records by value.

**The array encoding.** Replay normalises `>` to `*` before parsing (`Value::Push(inner) => Value::Array(Some(inner))`), so arrays are what it parses in the end. v0.4.0 refuses an AOF holding DEDUP records whatever their encoding ("ERR DEDUP is only available on the WebSocket port"). That limit is documented and unchanged.

### 2.5 Rejected alternatives

| Alternative | Why not |
|---|---|
| **B: `DEL <reserved key>`** | B1: an old binary deletes a user key of that name. Any byte string is a valid key |
| A new record name | Every old binary refuses the file (A5) |
| A sidecar file | Not atomic with the AOF, and it cannot say where in the file the format begins |
| A snapshot format bump | Old binaries refuse it, and it cannot describe the AOF after it |
| Appending `FORMAT` to a legacy file | The legacy prefix replays by the replaying node's clock, so its state at the marker depends on when the replay runs (§4.2) |
| Rewriting a legacy file at startup | Forbidden by the brief; a checkpoint already does this safely |
| **Revision 1: `SEAL` at clean shutdown, `RESUME` at start, `LEGACY` at a replica's handshake** | `SEAL` misses a crash before a downgrade (review C, H2). Writes after the shutdown save landed after `SEAL` (M1, reproduced). A lost `LEGACY` (a checkpoint racing the handshake, a failed append) was unsafe (M5). Authorship (§2.2) covers all of it without a shutdown step |

## 3. Replay

### 3.1 Two modes

| Mode | Applies to | Expiry |
|---|---|---|
| **legacy** | files without `FORMAT` at the head; in a format file, every record from the first push on | evaluated by the replaying node's clock, as today |
| **timeless** | array records after `FORMAT`, up to the first push or unknown non-ignorable control record | **not evaluated**: an entry is live until a logged `DEL` removes it |

### 3.2 Pass 1

Pass 1 already reads the whole file for the checkpoint and the DEDUP marks. It now also finds `timeless_end`, the offset of the first record to replay legacy:

```
timeless = the first record is FORMAT with the expirylog bit, and no must-understand bit unknown here
for each record at offset o:
    FORMAT at o > 0                       -> ignored
    control record, ignorable kind        -> ignored
    control record, other unknown kind or layout -> timeless_end = min(timeless_end, o)
    checkpoint marker                     -> as today (the snapshot's moves the replay start)
    a push (>N)                           -> timeless_end = min(timeless_end, o)
    an array (*N)                         -> nothing
```

Checkpoint markers and control records are recognised by value, whatever their encoding: an old binary's marker is a push, and the head `FORMAT` counts in either encoding (R2-7a). An *ignorable* kind or feature is one a **writer may omit**: records written without it must stay valid under it (R2-6).

In pass 2, a record at offset `o ≥ replay start` is applied timelessly iff `timeless` and `o < timeless_end`. A push that ends the timeless part is logged with a warning ("records an older server appended").

### 3.3 The timeless apply

`core_engine::store::without_expiry(f)` is an explicit thread-local mode. Inside it, `Entry::is_expired` answers `false` and snapshot restore keeps entries whose deadline has passed. **The clock does not change.** `at_instant(0)` (proposed in 6O-F) would answer the same, because `Deadline` is a `NonZeroU64`. But it also sets every replayed entry's `last_access_ms` to 0, so `OBJECT IDLETIME` would report 56 years and LRU would treat everything as idle. It would also count any relative deadline from the epoch.

The audit (`store.rs` at `f9a364d`):
- `Entry::is_expired` has 87 call sites, and the mode covers them all.
- `restore_ordered`'s filter is covered.
- `exp - now` in `get_current_with_ttl` and `scan_current` becomes `saturating_sub`.
- The TTL replies already saturate.

The replay's helper reads also run inside the mode: `ReplayEphemeral::claimable_members` (`SISMEMBER`) and `discard_abandoned` (`SCARD`, `SREM`, `DEL`). The sweeper and eviction run on their own tasks, outside it.

Every frame E1/E2 writes carries absolute deadlines only. A frame with a deadline already past (`SET k v PXAT <past>`, `PEXPIREAT k <past>`) leaves an expired entry on the primary, and the timeless apply reproduces it. A `GETEX` with a past deadline deletes the key on the primary and is propagated as `DEL`.

During the timeless part the store is a **follower** (`set_follower(true)`), as on a replica:
- the file holds the primary's eviction `DEL`s, so the replay must not choose victims of its own;
- a frame the primary accepted must not be refused for capacity.

The replay's state never holds more than the primary's did at the same record. It holds the same physical entries, minus those expired entries the snapshot left out.

### 3.4 The snapshot that precedes the records

The snapshot is loaded keeping every entry. Its expired entries are then dropped (silently, as a load) unless the records it precedes replay timelessly:

| Situation | Snapshot |
|---|---|
| The AOF is timeless at the replay start | kept whole |
| The AOF is empty, and the node starts as a primary (it writes `FORMAT` next, §4.1) | kept whole |
| The AOF is empty on a replica (its first full sync replaces the keyspace and checkpoints, §4.1) | expired entries dropped |
| Legacy AOF, or no AOF configured | expired entries dropped, as today |

A snapshot leaves out entries that had expired when it was saved. That is safe because the primary treats such an entry as absent: a later write to the key logs a `DEL` first (E1), which is a no-op on replay. It assumes the primary's clock does not step back below that deadline afterwards (§10).

## 4. File boundaries

### 4.1 When `FORMAT` is written

`FORMAT` is only ever the first record of a file, and only a node that logs every expiration it acts on writes it:
- a primary always does;
- a replica does only while its keyspace was built from a primary that negotiated `expirylog` (§8).

| Event | Primary | Replica |
|---|---|---|
| Startup, AOF empty or new | `FORMAT` before any record | nothing (its first full sync checkpoints) |
| Startup, AOF in the format | continues it: array records | continues it until its first full sync |
| Startup, legacy AOF | **stays legacy until its next checkpoint**: push records | the same |
| Checkpoint (`SAVE`, autosave, shutdown save) | `FORMAT` in the truncation's batch, before the ephemeral seed | `FORMAT` iff its keyspace was built from an `expirylog` stream (R2-7c) |
| **Full synchronization (new, review C H1)** | — | With an AOF configured: **a checkpoint under `save_lock` and the barrier of the keyspace replacement**, before any further frame is applied or acknowledged. It writes the snapshot **from the payload received** (spliced into the snapshot envelope: no filter, no second serialization, R2-2/R2-4), then the DEDUP table and the truncation, then `FORMAT` iff the new stream is `expirylog`. The resume point is set once the checkpoint is durable, so a later disconnect resumes partially (R2-4). **On failure**: persistence is latched unhealthy (writes answer `MISCONF` until a `SAVE` succeeds, also after a promotion), the resume point is cleared, and the link ends; under `always`, an fsync failure is a fail-stop as for any save (R2-3). Without an AOF, no checkpoint: the snapshot autosave covers it (R2-7e) |
| Partial resynchronization | — | only in the mode the replica applied that run id in (§8), so the file's mode cannot change underneath it |

A file never becomes timeless part-way. An upgraded server keeps its legacy file legacy, and keeps writing pushes to it. Its extra `DEL`s are harmless under legacy replay. A `DEL` is logged only for an entry the primary removed after its deadline, so replaying it can only make the replica agree with the primary.

The format then begins at the first checkpoint: autosave, which runs every 900 s by default, or `SAVE`. No file is rewritten.

The full-sync checkpoint fixes a pre-existing defect (review C, H1, reproduced on `f9a364d`). A replica's AOF never recorded its full syncs, so a restart of the replica, or of the same node as a primary, replayed the old keyspace plus newer frames. Redis 7.2.5 rewrites a replica's AOF base after a full sync in the same way.

### 4.2 Why a mid-file boundary is not used

A legacy prefix replayed at time *t* yields a state that depends on *t*. For example, `SET c 5 PXAT T` followed by `INCR c` (frame `SET c 6 KEEPTTL`):
- replayed before `T`, it gives `c=6` with deadline `T`;
- replayed after `T`, it gives a permanent `c=6`.

A timeless `APPEND c x` placed after a mid-file marker would extend whichever of the two the replay happened to build. A snapshot records absolute deadlines, so its state does not depend on when it is loaded.

### 4.3 Checkpoint and crash windows

`checkpoint` holds `save_lock` and every write stripe throughout. It runs these steps in order:
1. `RECACHED-CHECKPOINT n`, then flush. The checkpoint id becomes `n` here, so a later failure cannot make the next save reuse `n` (review C, L2: pre-existing; reuse lost writes).
2. DEDUP sidecar.
3. Snapshot `n`.
4. Truncate.
5. `FORMAT` (if the node writes the format).
6. Ephemeral seed.
7. Flush.

| Crash after | Files | Replay |
|---|---|---|
| marker `n` | snapshot `n−1` and the AOF holding `n` | from offset 0, mode from the head, as before the save ✓ |
| snapshot `n` renamed | snapshot `n` and the AOF holding `n` | from after `n`; nothing follows, since writes are blocked ✓ |
| truncation | snapshot `n` and an empty AOF | a primary writes `FORMAT` at startup and keeps the snapshot whole (§3.4) ✓ |
| `FORMAT`, whole or torn | `FORMAT`, or nothing (a torn tail is cut) | timeless, or empty ✓ |
| seed | the normal state ✓ | |

After a checkpoint the file starts with `FORMAT` again, so replay after any number of checkpoints is timeless.

### 4.4 Startup removals and the seed (review C, M2/M3; pre-existing)

- **Abandoned ephemeral keys.** At startup, replay discards ephemeral keys whose owner did not survive the restart. That discard was never logged, so the next session's records were written against a state the next replay does not rebuild. Reproduced on `f9a364d`: an acknowledged `APPEND` was lost. The discards are now appended to the AOF (`DEL`, `SREM`) before the server accepts connections: to the AOF only, since no replica or client is connected yet (R2-7d).
- **Snapshots on a node that writes the format keep every entry still in the map**, expired or not (R2-2). The primary decides expiry and logs a `DEL` when it removes one. A snapshot that dropped entries by the snapshotting node's clock was the one place that clock still decided: on a replica whose clock runs ahead, a key the primary still held went missing from the snapshot, and a later `APPEND` recreated it without a deadline. Older binaries drop such entries when loading, as they always did.
- **The ephemeral seed** after a truncation rewrote `ESET k v` without the key's deadline. `EXPIRE` does not end ephemeral status, so a volatile ephemeral key came back permanent: a resurrection, reproduced on `f9a364d`. The seed now writes `PEXPIREAT k T` after the `ESET`/`EADD` of a key that has a deadline.

## 5. Downgrade and re-upgrade

**Downgrade.** An older binary ignores the `FORMAT` record (A1–A4), replays the array records (A6), and appends pushes. Expiry is evaluated by its own clock, which is today's behaviour. The documented procedure is unchanged:
1. `SAVE`.
2. Stop.
3. Start the older binary.

Without the `SAVE`, a file holding `COPY` (or, for 0.4, DEDUP records) still stops an older binary, as before. A successful downgrade does not give the older binary the new replay guarantees.

**Re-upgrade.** The older binary's pushes end the timeless part of the file (§3.2). They replay with expiry evaluated, which is the older binary's own semantics, and the file stays legacy until its next checkpoint. This holds whether or not either server shut down cleanly. **No re-upgrade procedure is needed.**

## 6. Durability ordering

| Rule | How |
|---|---|
| An observed-expiry `DEL` precedes the frame of the command that observed it | One AOF batch, `[DEL][frame]` (and `[DEL][DEDUP envelope]`), queued in one step. On replication, two frames, `DEL` first |
| A write with no frame of its own | Its `DEL` alone, then (for DEDUP) its mark or refusal record |
| No acknowledgment before both are written | The frame's own batch wait. Under `always`, one `fdatasync` for both, and fail-stop on failure, as today |
| A prefix only (`DEL` without its frame) | Possible after a crash or a torn tail. Harmless: the entry had already expired on the primary, and the command was not acknowledged |
| Inside `EXEC` | Per queued command: its observed `DEL`, its frame, its eviction `DEL`s, all in the transaction's one batch (6O-G). No crash atomicity is claimed; that is 6O-I |
| Sweeper | `DEL k1 k2 …` per chunk, at most 64 KiB of keys per frame, under the all-write barrier the sweeper already holds. Under `always`, one `fdatasync` per frame |

## 7. Security

| Threat | Why it cannot happen |
|---|---|
| A client forges a control record | `RECACHED-CHECKPOINT` is not a command (`unknown command`, also inside `DEDUP` and `MULTI`). Every frame comes from `broadcast_for_at`, which starts with a command name. A key or value holding those bytes is a bulk string inside another record |
| A client turns on timeless replay | Only a `FORMAT` at offset 0 does that, and only the server writes it. The array encoding is the server's choice of first byte, never a client's |
| A replica is fed a control record | Control records go only to the AOF (`AofWriter`), never to the replication stream. A primary sending `RECACHED-CHECKPOINT` breaks the link, as today |
| A collision with user data | None: a control record is not a key operation (contrast B1) |
| A corrupt record | A non-`u64` id is refused as corruption. Another valid `u64` is either an unknown control record (which ends the timeless part) or a checkpoint id, the same exposure as today. A byte flipped from `*` to `>` ends the timeless part, which is the safe direction |
| Unbounded input | Pass 1 keeps one offset and a flag |

## 8. Replication: `caps=expirylog1`

Negotiated like `dedup1`, inside the run-id strings:
- the primary advertises `<run-id>;caps=dedup1,expirylog1`;
- the replica answers `<run-id>;accept=dedup1,expirylog1`.

`HandshakeId::has` has split values on `,` since 6B, so the 6O-F and 6O-G replicas still find `dedup1`. Review C verified this with a fake primary against the real binaries. A 0.5 replica echoes the string back without `accept`.

Every release refuses a run-id string over 128 bytes. With a 40-character run id, 82 bytes remain for parameters; 23 are used. Capability tokens must stay short.

| | Rule |
|---|---|
| A node advertises `expirylog1` | iff its stream carries every expiry transition. Always on a primary. On a replica, iff the keyspace it serves was built from a primary that negotiated it (it forwards that primary's `DEL`s and runs no sweeper). Unchanged while the link is down |
| A replica accepts it | whenever offered. Never inferred from a version |
| With it, a replica | applies every frame, and a full-sync snapshot, without evaluating expiry. Runs no active expiry; it removes keys only on the primary's `DEL`. Its reads still mask expired keys by its own clock, without changing the store. Its own AOF is in the format (§4.1) |
| Without it | as today: expiry evaluated on apply, its own silent sweeper, a legacy AOF |
| Mode change on the same run id | The replica remembers the mode it applied a run id's frames in, and asks for a **full** sync if offered another mode for it. A node's own stream changes mode only through a full sync (which resets its stream: new run id, sub-replicas resynchronize in full, 6O-G) or through promotion (to `expirylog`; its existing sub-replicas stay legacy, which is safe, until they reconnect) |
| Promotion | Active expiry starts again, now logged, and writes log what they find expired. The node advertises `expirylog1`. Its AOF keeps its mode until the next checkpoint |
| A follower's own writes | none: a replica refuses client writes. Its legacy-mode sweeper is silent, as today, and its expiry-log mode has none |

| Primary → replica | Behaviour |
|---|---|
| new → new | `expirylog` negotiated; timeless application; no replica sweeper |
| old → new | not offered; legacy application and sweeper, as today |
| new → old 0.6 (6O-F/6O-G) | the old replica finds `dedup1` and ignores `expirylog1`; the extra `DEL`s are harmless; it sweeps as today |
| new → 0.5 | unchanged: refused while `RECACHED_REPL_DEDUP=on`; with it off, the replica echoes the string and applies as today |
| old → old | unchanged |

A capable replica keeps expired entries until the primary's `DEL` arrives: the replication delay plus the primary's sweep latency. That is the cost of correctness. Deleting locally to hide it would bring the defect back. PR 6 measures it.

## 9. Extensibility and 6O-I transaction framing

There is one marker family for both milestones:
- **`FORMAT` feature bits.**
  - **0–15, ignorable.** A reader that does not know a feature replays as if it were absent, so such a feature must be defined so that ignoring it is no worse than legacy replay. `expirylog` is bit 0: a reader that ignores it replays legacy, as every older binary does.
  - **16–31, must-understand.** A reader that sees one it does not know replays the file legacy and warns. It then appends to the file as pushes (§2.2), so a later reader that knows the feature sees where its records end.
- **Control kinds `0x80`–`0xFF` are ignorable** by any reader. Every other unknown kind, or an unknown layout, ends the timeless part. A future `TXN-BEGIN`/`TXN-COMMIT` (6O-I) can therefore be either:
  - ignorable, if replaying the grouped records one by one is acceptable to older readers (it is today's behaviour); or
  - a must-understand `FORMAT` feature, if not.

The per-command order 6O-H produces inside `EXEC` (observed `DEL`, frame, eviction `DEL`s) is what such a group would wrap, unchanged. No `caps=txn` is implemented here.
