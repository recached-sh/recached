## 1. Write-observed expirations (E1)

The store half (`V0.6O-H-EXPIRATION-CAPTURE.md`) reports the expired entries each write removed. The server logs them as one `DEL` **before anything the write itself logs**.

**When.** When anything observes writes: the AOF, replication, a WebSocket client routed pushes, or a WATCH or live query (`observes_writes`, the predicate 6O-G uses to build frames). With nothing observing, no scope is entered and the store removes nothing early, so the plain-cache path is unchanged (test `a_plain_cache_removes_nothing_early`).

**Paths.** Every logged write goes through one of these:
- `execute_locked_write_identified`: the ordered path, which also serves `ESET`/`EADD`, capped stores under every stripe, and the ephemeral release on disconnect;
- `execute_locked_write_within_capacity`: capped writes under their own stripes;
- `apply_queued_write`: `EXEC`, see `V0.6O-H-TRANSACTION-INTEGRATION.md`.

The unordered and borrowed paths run only when nothing observes. A replica's frame application never removes early, by design.

| Stream | Order and grouping |
|---|---|
| AOF | `[DEL][frame]`, or `[DEL][DEDUP envelope]`, queued in **one batch**, in one step under the queue lock. That is one `write(2)`, and under `always` one `fdatasync` before either is acknowledged, in both fan-out modes. With deferral (`append_client_writes`) the connection's reply waits for that batch |
| Replication | the `DEL` frame, then the write's frame |
| Sync clients | the `DEL` push first, then the write's push. Origin 0 (the server's deletion, as for an eviction), so the writer's own browser is told as well |
| WATCH/QSUB | `notify_removed` for the keys, then the write's own notification |
| Ephemeral claims | forgotten for the removed keys, before the write's own reconciliation, as the sweeper does |

| Case | What is logged |
|---|---|
| The write produced a frame | `DEL k…`, then the frame |
| The write failed or changed nothing (`RENAME`/`LSET`/`EXPIRE`/`PERSIST`/`HDEL`/`SET XX` of an expired key) | `DEL k…` alone |
| A `DEL`/`UNLINK` that ran | its own frame only: it names every key, the expired ones too |
| A `DEL` refused (a store over its key cap) | `DEL k…` for what it removed |
| Capacity reclaim of an expired key the write did not name (`reserve_key_slots`) | unchanged: an eviction `DEL` after the command. Its removal does not affect the command's result |

## 2. The sweeper (E2)

`sweep_expired_tick` on a primary logs each chunk it removes:
- **Frames.** `DEL` frames of at most 64 KiB of keys each (`EXPIRY_DEL_FRAME_KEY_BYTES`), at least one key each. They are appended and replicated with `on_write`, under the all-write barrier the sweeper already holds. So no write to these keys can be logged between the removal and its `DEL`, and none can be reordered around a transaction, which holds its keys' stripes.
- **Locks.** No store lock is held across the await: the removal is a synchronous store call before it.
- **Sync clients.** Pushed one key at a time. A frame naming several keys reaches only a socket allowed to read them all, which a tenant-scoped socket is not when a chunk spans tenants (test `the_sweepers_pushes_respect_tenant_scopes`).
- **Watchers.** Notified as before.
- **A replica's sweeper** stays silent: its primary's stream is what its AOF and sub-replicas follow. PR 5 turns it off on an `expirylog` replica.
- **Eviction** keeps its own `DEL` path. Reclaimed expired keys are reported as evictions, after the command (test `eviction_keeps_its_own_dels_and_nothing_is_logged_twice`).

## 3. DEDUP

| Case | Records |
|---|---|
| Applied | `DEL k`, then `DEDUP c n <frame>`. The `DEL` is outside the envelope: it is not part of the write a retry would repeat, only the state the write found |
| Applied, changed nothing (`HDEL` of a missing field) | `DEL k`, then `RECACHED-DEDUP c n` |
| Refused for good | `DEL k`, then `RECACHED-DEDUP-REFUSED c n …` |
| A duplicate (retry of an applied id) | nothing: it is answered from the mark before any store call |

A prefix alone (the `DEL` without what follows) can survive a crash. It is harmless: the primary had already treated the entry as gone, the write was not acknowledged, and its retry runs again, finding nothing expired. The `DEDUP` acknowledgment contract (a mark committed only after its frame's AOF stage) is unchanged. A `DEDUP` write never defers its AOF wait (6N-C O1), so its `DEL` is in the same waited batch.

## 4. Tests

`expiry_log_6oh.rs`, 13 tests:
- the observed `DEL` before the write, in all four modes (`always`/`no` × inline/coalesced), with the batch count and the replication stream;
- failed and no-op writes;
- DEDUP applied, no-op, refused and duplicate;
- `EXEC`, byte-identical to per-command execution in all four modes;
- the sweeper's bounded batches, and the frame splitter;
- a replica's silent sweep;
- the eviction distinction;
- sync pushes, plain and in `EXEC`;
- the sweeper's tenant scoping;
- WATCH on a removed key (live at WATCH: aborts; already expired: commits);
- the refused `DEL`;
- a plain cache.

`transaction_streams_6og.rs`: a delta client converges when a write finds its key expired.

**Mutants: 15 of 15 killed.** They cover:
- the `DEL` skipped;
- placed after the frame, in the AOF or on replication;
- the sweeper silent;
- the `EXEC` order;
- a refused `DEL` dropped, and a `DEL` logged twice;
- watchers not told;
- the `DEL` inside the DEDUP envelope;
- a chunk pushed to tenant sockets;
- no observing scope, on the ordered path or in `EXEC`;
- the WS push dropped;
- a failed write's `DEL` dropped;
- a replica's sweep logged.

Raw: `raw/mutation/pr3.txt`.

## 5. Cost

One `DEL` record per expired key the primary removes, plus one lookup per named key per observed write. Measured in `V0.6O-H-PERFORMANCE.md`.
