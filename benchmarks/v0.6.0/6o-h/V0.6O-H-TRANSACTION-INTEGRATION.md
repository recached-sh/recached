## 1. Where it fits

6O-G split `EXEC` into a synchronous apply (phase 1, every queued write under the transaction's store hold, at the transaction's instant) and asynchronous effects (phase 2). 6O-H adds one thing to each:

| Phase | 6O-H |
|---|---|
| 1. Apply | Each queued write's store call runs inside `observing_expirations` when something observes writes, at the transaction's frozen instant (it nests in `apply_transaction`'s `at_instant`). The expired entries it removes are recorded on that write (`AppliedWrite::expired`); claims on them are forgotten, before the write's own ephemeral reconciliation. No effect is emitted here |
| 2. Effects | Per queued command, in queue order: its expiry `DEL`, its frame, its eviction `DEL`s. The AOF batch, the replication frames and the sync pushes follow that order. Notifications go through the plan (below) |

Nothing else in 6O-G changes:
- the stripe set (from `mutation_scope`, which already lists every key the purge visits);
- the capacity-gate order;
- the in-scope read bypass;
- panic containment and the metadata repair;
- `MISCONF` recovery;
- the AOF acknowledgment gate;
- the phase-2 skip when nothing observes (a write records nothing to remove then);
- no synchronous store guard across an `.await`: the purge is part of phase 1's synchronous store call.

## 2. Ordering

`MULTI; INCR c; EXPIREAT c 4000000000; APPEND s tail; SUNIONSTORE out src; RENAME gone to; INCR c; EXEC`, with `c`, `s`, `src` and `gone` expired at the transaction's instant, produces one AOF batch:

```
DEL c · SET c 1 KEEPTTL · PEXPIREAT c 4000000000000 · DEL s · APPEND s tail ·
DEL src · SUNIONSTORE out src · DEL gone · SET c 2 KEEPTTL
```

- The replication stream carries the same records in the same order.
- Running the commands one by one gives byte-identical records, in all four combinations of `always`/`no` × inline/coalesced.
- `RENAME gone to` fails (`no such key`) and has no frame. Its removal is still logged.
- This is the order brief §6.4 sets out for a future transaction group (observed `DEL`, frame, eviction `DEL`s, per command). A 6O-I `BEGIN`/`COMMIT` can wrap it unchanged.

No crash atomicity is claimed: one batch makes a torn transaction less likely, not impossible (6O-G).

## 3. Notifications

The 6O-G plan announces each key once, at its last effective change in the transaction. 6O-H adds one kind of change, an **expiry removal**, at the queued write that removed the entry and before that write's own change:
- The key's write count includes it. A key removed and then written by the same command (`APPEND` on an expired string) has two changes, so it is announced as its **full value**, never as a delta that a client holding the stale value would apply to it. This is the coalescing rule review R2 required for any key written more than once (6O-F design).
- If nothing later in the transaction changes the key, the expiry removal is its last change. It is announced as a removal, or as `removed_after_set` if an earlier write in the transaction set it, which invalidates a `WATCH` as the set did.
- A sync client gets the `DEL` push before the command's own push, with origin 0 (the server's deletion, as an eviction).

Test `delta_clients_converge_when_a_write_finds_its_key_expired`: a `CLIENT DELTA ON` live query holding `"old"` for a key that expired on its own ends with `"tail"`, the server's value, both one by one and inside `EXEC`. Without the removal (mutant M7) it ends with `"oldtail"`.

## 4. WATCH, delta and QSUB clients

| Check | Result |
|---|---|
| A watcher of a key live at `WATCH`, removed by another connection's write (which fails) | `EXEC` aborts (as for the sweeper's removal) |
| A watcher of a key already expired at `WATCH`, then removed | `EXEC` commits |
| The 6O-E/6O-G `WATCH`, QSUB, delta and convergence suites | unchanged, both fan-out modes (`V0.6O-H-CORRECTNESS-TESTS.md`) |

## 5. DEDUP

A `DEDUP` envelope queued in `MULTI` is refused at `EXEC` (6O-G), so no transaction carries one. Outside transactions, see `V0.6O-H-EXPIRATION-PROPAGATION.md` §3.
