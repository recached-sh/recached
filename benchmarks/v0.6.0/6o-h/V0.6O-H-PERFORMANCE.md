## 2. Writes with the AOF (`everysec`)

Here every write enters an observing scope: a thread-local swap, a clock read, and one `remove_if` per named key (review B, B-6).

The extra cost comes in two parts.

**The observing scope.** On writes that never meet an expired key (`SET`, `INCR`, `HSET`), the server pays +1.6–3.7% CPU per write and −1% to −3% ops/s. The batching is unchanged: `write(2)` per command stays at 0.100, and records per op stay at 1.000. This is the computational overhead of the mechanism, and it is accepted. Two cheaper options were not taken:
- skipping the scope when the keyspace holds no volatile key (review B's suggestion) costs an index walk per write;
- folding the lookup into each command's own slot access is the per-command audit the design avoids (`V0.6O-H-EXPIRATION-CAPTURE.md` §1).

**The expiry log itself.** Where keys really expire, the records and bytes grow by what the design requires: one `DEL` per expired key the primary removes, whether a write found it or the sweeper did. `SET PX 100` re-writes keys that expired 100 ms earlier: 0.83 `DEL` records per `SET`, +30% bytes, +30% CPU per write, −19% ops/s.

Redis pays the same kind of cost (§4).

## 3. `appendfsync always`

| Cell | base ops/s | h ops/s | records/op | fsyncs per run (base → h) | p99 ms base → h |
|---|---:|---:|---|---|---|
| `SET` | 365 | 368 | 1.000 → 1.000 | 2000 → 1998 | 267 → 233 |
| `INCR` on expiring counters | 363 | 358 | 1.000 → 1.583 | 1999 → 2008 | 242 → 317 |

On this disk, throughput under `always` is bound by `fdatasync`, and unchanged. **The fsyncs per run are unchanged where a `DEL` is added:** a write's `DEL` travels in the write's own batch (`[DEL][frame]`, one `write(2)`, one `fdatasync`). The `INCR` p99 rises from 242 to 317 ms (medians). That is not within noise: the per-repetition p99 ranges are 208–292 ms on base and 242–382 ms on h (review E, F8). The 7–10% spread is the ops/s spread.

**Not visible in the ops/s column: the sweeper under `always`** (review E, F1). The sweeper waited for each chunk's `DEL` `fdatasync` (about 65 ms here) inside its tick, the first time under the all-write barrier. Two consequences:
- **Writers:** every writer stopped for a disk flush per chunk.
- **The sweep:** its 25 ms budget ran out after one 256-key chunk per tick.

This cell's population is written with `PX 1000` and has expired before the timed run starts. So an `INCR` logs a `DEL` only when it meets a counter the sweeper has not reached yet. At about 360 commands/s that is most of them:
- **Records:** 1.583 per op here, against 1.017 under `everysec`, where the sweeper clears the expired population within seconds.
- **RSS:** 33.6–36.1 MB on h against 18.5–19.3 MB on base, in all 5 repetitions. h keeps the ~95k expired counters it has not swept; base ends near the keys the run touched.

The RSS is capped by the 100k-key keyspace, so it does not grow with the run's length. #191 took the wait out of the barrier; #192 waits once per tick instead of once per chunk (§7.1).

Redis logs a `DEL` for every expiry it acts on (`propagateDeletion`). Its throughput on these workloads falls to 0.78–0.82 of its `SET`; 6O-H's falls to 0.74–0.82, and base's to 0.90–0.91. The baseline fell less because it logged nothing, which was the defect.

What this run does not show (review E, F7):
- **Redis's own share.** The run does not separate the cost of Redis's `DEL`s from the rest of its `PX` cost. That would need a Redis cell with deadlines that never pass during the run.
- **A like-for-like comparison.** The Redis cells ran in their own stage, 3 repetitions, not interleaved with the Recached cells.

So "the same kind of cost" is supported; "the same amount" is not claimed.

The absolute gap between Recached and Redis under `everysec` (`SET` 129k against 158k) predates this phase (6O-A/6O-B). The thresholds that track it are unchanged.

## 5. Replication, replay, the sweeper, replica memory

`h-repl.py` (in `raw/perf/kit/`), 3 interleaved repetitions of `base` and `h`, with medians and the individual runs in `raw/perf/results-repl/results.json`. Where each part runs:
- **Replay and sweep:** a single server with AOF `everysec`.
- **Replication:** the primary runs without an AOF, on CPU 0. The replica runs on CPU 1 with an AOF (`appendfsync no`), whose growth measures the stream.

Each server uses one worker thread.

### 5.1 Replay

| Experiment | base | h |
|---|---|---|
| Restart after 1,000,000 `SET`s (45 MB AOF, about 632k keys) | 1.44 s (1.48, 1.40) | 1.43 s (1.43, 1.41, 1.49) |
| The same legacy file, copied, replayed by each binary (5 alternating runs, `raw/perf/results-native3/legacy-replay.jsonl`) | 3.27 s | 3.15 s (`final`) |

Timeless replay costs nothing measurable. An earlier cell had `h` replaying base's file in 1.76–2.51 s. The A/B above shows that the extra time comes from the method, not from the binary: a freshly copied file replays slower for both binaries.

### 5.2 The sweeper

About 632k keys are written with `PX 1000`, then left to expire under a GET load (c50).

| | base | h |
|---|---:|---:|
| Time until the keyspace is empty | 35.8 s (36.3, 35.6, 35.8) | 42.6 s (42.3, 46.8, 42.6) |
| AOF bytes the sweep added | 0 | 14.4 MB, **23.1 B per swept key** |
| GET ops/s meanwhile | 184,604 | 181,818 |
| GET p99 | 0.519 ms | 0.415 ms |
| GET max | 6.1–8.6 ms | 6.0, 10.2, **273.9** ms |

The sweep is 19% slower: it now builds and logs a `DEL` frame per chunk under the all-write barrier it already held. That is the price of propagating sweeps, and it is bounded per chunk (64 KiB of keys per frame).

GET throughput and p99 are not hurt. One of the three `h` runs had a single GET at 274 ms; the other two runs, and all of base's, stay at 6–10 ms.

Review E (F4) gives a plausible mechanism. Only the sweeper writes to the AOF in this experiment. Under `everysec` its batch's `write(2)` runs inline on the server's single worker, and on an HDD a `write(2)` can block behind writeback.

Two limits of this run:
- **No write load.** The run measures GETs only, not how long writers wait behind the sweeper's barrier.
- **Measured before #191/#192.** Since then the sweep's write is started and waited for outside the barrier.

A rerun with a write load and 5 repetitions is a follow-up.

### 5.3 Replication, `SET PX 100` at c50 for 30 s

| | base | h |
|---|---:|---:|
| Primary ops/s | 128,084 | 101,559 (0.79×) |
| Replication stream bytes per op | 93.2 | 135.1 (+45%) |
| Peak primary keys / replica keys | 92,893 / 91,064 | 89,948 / 89,940 |
| Largest gap, primary keys − replica keys, sampled every second | 63k–80k | **21–34** |
| Peak RSS, primary / replica | 64.3 / 65.3 MB | 66.7 / 64.4 MB |
| Replica reaches the primary's key count after the load | 3.41 s | 3.61 s |

- **Throughput and bandwidth.** These fall by about what the AOF cells (§2) showed for this workload: 0.83 `DEL`s per `SET`, now also on the wire.
- **How the bytes are counted.** Stream bytes are measured as the replica's AOF growth. That leaves out each frame's 12 bytes of offset and length, so the extra frames are under-counted: about 147 bytes per `SET` on the wire, against 135 here (review E, F6).
- **Key counts.** A base replica held tens of thousands fewer keys than its primary because it expired them by its own clock. That early removal is the silent, unlogged deletion this phase removes. A capable replica tracks its primary key for key.
- **Replica memory.** It is unchanged at this delay. The replica keeps an expired entry only until the primary's `DEL` arrives: the replication delay plus the primary's sweep latency.

### 5.4 A stalled replica (SIGSTOP for 10 s at t = 10 s)

| | base | h (`3d9ba3c`) |
|---|---:|---:|
| Peak replica RSS | 68.2 MB (65.4–68.5) | 85.8 MB (85.6–86.1) |
| Peak primary RSS | 62.7 MB | 84.7 MB |
| Peak replica keys / primary keys | 79,406 / 84,850 | 90,636 / 90,274 |
| Full resynchronizations after the stall | 1 | **4** (in one run with logs, `raw/perf/results-lag-logs/`) |

- **Replica memory.** The capable replica's extra ~18 MB is expected. While stopped it receives nothing, and once resumed it holds the primary's keyspace, expired entries included, until their `DEL`s arrive.
- **Primary memory: not attributed.** The primary's RSS is also higher during the stall: +8–22 MB. This holds even with a single resync (§5.5), so the repeated full syncs do not explain it. Without a replica stall the primaries differ by +2.4 MB (§5.3). The buffers that grow during a stall are byte-bounded: the per-replica queue (8 MiB) and the backlog (16 MiB). A 45% larger stream fills them with more, smaller frames, and each frame carries its own allocation. That is a candidate cause, not a measured one.
- **The full-sync loop.** The replica checkpointed its files under the barrier, fsyncing a snapshot and truncating its AOF. During that checkpoint it did not read its link. The primary streams right after the snapshot, so the stream backed up into its queue to that replica. The primary logged `Replica byte queue full — disconnecting so it can resync` about 0.6 s after each reconnect. Base performs no checkpoint and resynchronized once. Design §10 had listed this window as a known limit (R2-4); #190 closes it (§5.5).
- **Stream bytes per op.** The `stream bytes per op` the script reports for `lag` (base 60, h 0.3) is **not valid**. It is measured from the replica's AOF, and the full-sync checkpoint truncates that file.
- **What this experiment measures (review E, F6).** In every run, base's included, the 10 s stall overflowed the primary's 8 MiB queue within a second. So this experiment measures a stall followed by a full resync, not a replica waiting on late `DEL`s over a live link.
- **How long a replica keeps expired keys.** That is bounded in size, not in time: while the link is down, a capable replica keeps every key it held when the link stopped, expired or not, and takes no writes. Its reads mask the expired ones. When it reconnects, the resync replaces the keyspace (or, on a partial resync, the primary's `DEL`s remove them). §5.3 is the live-link case: no retention measurable at a delay of a few milliseconds.

### 5.5 The full-sync loop and #190

**The loop needs a disk.** In the first reruns (`raw/perf/results-lag-fixe/`), the script put the data directories on `/tmp`, which is tmpfs on this host. There, `base`, `final` and #190's first build each resynchronized once. Review E (F2) pointed this out. The runs below keep the replica's files on the HDD (`TMPDIR_BENCH`).

| Build | Full resynchronizations after the 10 s stall, 3 runs | Primary `queue full` events | Peak replica RSS | Primary ops/s |
|---|---|---|---|---|
| `final` (`c093795`, no fix) | **4, 4, 4** (`results-lag-hdd/`, a 1st set: 3, 4, 4) | 4, 4, 4 | 74–82 MB | 106–110k |
| #190, 1st design: read-ahead during the checkpoint only (`5268c81`/`9a47d1e`) | 2, 3, 3 (`results-lag-hdd/`) | 3, 3, 3 | 92–126 MB | 103–105k |
| #190, 2nd design: the link also read while applying (`7b4ae13`) | **1, 1, 2** (`results-lag-hdd2/`) | 1, 1, 2 | 94–95 MB | 104–107k |
| `base` (`f9a364d`), for reference | 1 (`results-lag-logs/`) | 1 | 61–68 MB | 130–134k |

**What the logs show.** In the `final` runs and the first-design runs, the primary's queue overflowed about 0.6 s after each full sync *completed*, not during its checkpoint. The replica then applied its backlog without reading its link. At about 185k frames per second (one `DEL` per expired `SET`), its catch-up margin is thin, and the backlog went back into the primary's 8 MiB queue.

**The second design.** It reads the link concurrently with applying, into a bounded queue of 64 MiB on the replica's side (plus at most 64 MiB of read-ahead during the checkpoint). It removed the loop: one full sync, as on base, in 2 runs of 3.

**The third run is not attributed.** It needed a second full sync, after a checkpoint that took 1.07 s, and then converged.

**Memory.** The replica's peak RSS is about 13 MB higher with the second design. That is the backlog now held on the replica instead of the primary, bounded at 128 MiB per link.

**In-process.** The test sets a 1 MiB primary queue, a 5 s checkpoint, 1 ms per applied frame, 24 MiB during the checkpoint and 16 MiB during the catch-up. It passes. The first design fails it with a queue disconnect, so the mutant is killed.


## 6. Interpretation

| Question | Answer |
|---|---|
| Is the change free? | No (review E, F5). The measured costs:<br>• **The scope:** +1.6–3.7% CPU on every logged write.<br>• **Expiring workloads:** one `DEL` record per expired key, +11% to +30% AOF bytes at the `PX` rates measured.<br>• **Replication of `SET PX 100` without an AOF:** −21% primary ops/s and +45% stream bytes per op.<br>• **The sweeper:** drains 19% slower.<br>• **A stalled replica:** both nodes' peak RSS is higher during the stall and resync (§5.4).<br>• **`always`, before #191 and #192:** the sweeper's `fdatasync` stalled writers, and the sweep fell behind (RSS +17 MiB on expiring counters). ## 7. Review E's fixes, measured

### 7.1 The sweeper's disk wait (#191, #192)

`appendfsync always`, `INCR` on expiring counters (the population has expired before the run starts), 30,000 requests, 3 interleaved repetitions per run:
- **Run A** (`raw/perf/results-always2/`): base, `final`, and `comb` (#191).
- **Run B** (`raw/perf/results-always3/`): base, `comb`, and `comb2` (#191 + #192, `53a2f1e`).

| | base | final `c093795` | comb: wait outside the barrier, per chunk (#191) | comb2: once per tick (#192) |
|---|---:|---:|---:|---:|
| ops/s, run A / B | 373 / 353 | 343 / — | 364 / 352 | — / 357 |
| on-CPU µs/op, run A / B | 20.69 / 21.14 | 23.95 / — | 23.54 / 24.20 | — / **21.74** |
| p95 ms, run A / B | 183 / 175 | 217 / — | 175 / 175 | — / 175 |

| RSS MiB | 15.4 / 16.5 | 34.1 | 33.7 / 33.2 | **16.4** (16.3–17.2) |

**#191: writers no longer stall.** The writers stopped behind the sweeper's barrier for a disk flush per chunk. With the frames queued under the barrier and written after it, p95 and p99 fall to base's level.

**#191 alone: the sweep still fell behind (review E, round 2).** The tick still waited for each chunk's `fdatasync` against its 25 ms budget, so it swept one 256-key chunk per tick. The writes kept meeting expired counters the sweeper had not reached, and logging their `DEL`s: 0.7 extra frames per command. The ~95k expired counters stayed in memory: +17 MiB.

**#192: the sweep keeps pace.** The tick starts each chunk's write as the barrier is released and waits for all of them once, at its end. Against base:
- frames per command, RSS and on-CPU time return to base's;
- throughput is within the cell's 5–8% spread;
- p99 varies between 258 and 333 ms across these HDD runs for every build, so it is not separated by 3 repetitions.
